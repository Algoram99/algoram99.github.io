AI Agent Context Window Management: 5 Patterns, 4 Anti-Patterns, and a Drop-In Budget Runtime

Every LLM agent eventually runs out of context. The question is not whether your agent will hit the model's input-token ceiling on a long conversation, a 50K-token system prompt, or a 30-message tool-call trail — it is whether you will find out at token 4,000 of the budget (good) or at the API's 400 context_length_exceeded response on the 11th tool call (bad). This post is the context window architecture I wish I had on the first agent I shipped.

TL;DR

Five patterns that work: pre-flight token estimation (estimate the full payload's tokens before the API call, so overflow is a CI-gate decision, not a runtime surprise), pre-context-fill eviction (decide what to drop before the context is filled, with a deterministic, SHA-256-hashed eviction plan), sliding window with semantic anchors (a window that always preserves the system prompt, the most recent user turn, and the structured tool outputs that look like answers to the current question), compaction with intent preservation (when the window is full, summarize the middle, but preserve the intent vector — the goals, the open questions, the user's stated constraints), and token-budget observability + SLOs (every session has a budget, every LLM call has a planned spend, and burn-rate alerts fire when a session is going to overflow before it actually does). Four anti-patterns that ship silent truncation or budget blowouts: silent-truncation (the framework or middleware quietly chops the oldest messages without telling the agent, so the agent "remembers" a system prompt that no longer exists), naive-first-N-sliding-window (keep the first 4,000 tokens and the last 8,000, drop the middle, and watch the agent forget the only constraint the user gave it at turn 1), per-call-budgets-that-sum-to-overflow (set 4,000 tokens per LLM call, run 12 LLM calls in a tool-using agent, end up at 48,000 tokens when the model is 32K, with no single call that "caused" the overflow), and evict-on-overflow-only (wait for the API to return 400, then start evicting, by which time the user's request has failed and the budget is already gone). The post includes a 115-line drop-in TypeScript budget-and-eviction runtime, 8 selftest cases, and a Woodpecker CI gate that asserts every agent run produces a token-budget decision before the first LLM call.

Why this is its own post (and not just "use a smaller system prompt")

The 19th post on this site covered circuit breakers for LLM APIs. A circuit breaker is a per-system decision: "this downstream is failing, stop sending traffic for 30s." A context window budget is a per-request decision: "this request is allowed to spend 48,000 of its 64,000-token budget, every LLM call from here on out is on the meter." Both belong in a healthy agent, but they answer different questions.

The 22nd post on this site covered memory architecture. Memory is the long-term store of facts, decisions, and episodic traces. The context window is the working set of memory: what the model actually sees on this turn. They are not the same thing, and the boundary between them is the most common source of agent bugs. A fact that lives only in the context window is a fact the agent will forget on the next compaction. A fact that lives only in long-term memory is a fact the agent will not see unless something explicitly retrieves it. The 5 patterns in this post are about how to manage the boundary in production.

The 23rd post covered idempotency. Compaction and eviction are the worst possible places to skip idempotency: a compaction runs at turn 12, the system crashes at turn 13, the retry replays the compaction, and the new summarization is applied to a window that has already been summarized. The idempotency-key on the compaction is the only thing that prevents the agent from summarizing the same middle twice and dropping an extra 800 tokens of intent.

The 27th post covered timeout and cancellation. A budget violation is a kind of deadline: the request has spent 75% of its token budget by turn 4, the agent knows it has 3 turns left, and the choice to compact now is the same shape of decision as the choice to cancel now. The two subsystems share a clock.

The 5 patterns

1. Pre-flight token estimation (decide overflow before the API call)

Every agent run produces a token budget decision before the first LLM call. The decision is: "the system prompt is 1,200 tokens, the tool catalog is 800 tokens, the working memory is 600 tokens, the conversation history is 4,200 tokens, the planned tool-call trail is 2,000 tokens, the planned response is 1,500 tokens — total planned spend 10,300 tokens, model ceiling 128,000, headroom 117,700 tokens, overflow risk: none." If the decision says overflow, the run is rejected at the gate, not allowed to fail at the API.

The pre-flight estimate is a single function: estimate(payload) -> { perSection: SectionEstimate[], total: number, ceiling: number, overflow: boolean, plan: EvictionPlan }. The estimate must run in CI as a contract test, not only at runtime. If the system prompt grows from 1,200 to 5,200 tokens, the CI gate fires on the PR that introduced the growth, not on a user request at 2am.

This is what the LLM Context Budget CLI ships: pre-flight cost and context-window estimation for any LLM call, 22+ models across 7 providers, BPE-style token estimation, context-window overflow guard with trim recommendations, JSON gate for CI pipelines, Markdown report for PR comments, 45-test verification suite. The runtime in this post is a 30-line compatible core that the CLI wraps; the CLI adds the provider model registry and the CI-gate wrapper.

2. Pre-context-fill eviction (decide what to drop before the context is filled)

Eviction is a pre-context-fill decision, not a post-overflow cleanup. The agent maintains an eviction plan: a deterministic, ordered list of which context blocks to drop, in what order, when the budget is exceeded. The plan classifies every block as one of PROTECTED (system prompt, the current user turn, the most recent tool result), KEEP (recent conversation turns, structured tool outputs the current question depends on), EVICT_FIRST (old tool-call traces whose results have been folded into a working-memory block), EVICT_LAST (older conversation turns, summarized if needed), or FORBIDDEN (anything that violates a hard policy — the safety preamble, the user's explicit constraints, the audit-trail blocks).

The plan is computed once per turn, before the LLM call. The plan is hashed (SHA-256) and the hash is part of the run record. If two consecutive runs produce the same eviction plan, the second run's plan is a no-op (the same blocks were already evicted). If the plan changes, the change is auditable: the diff between the two plans is the explanation for what the agent "forgot" this turn.

This is what the Agent Context Eviction CLI ships: pre-context-fill eviction-policy enforcer for LLM agents, three built-in policies (conservative, aggressive, protected-no-system), per-block classification + full plan generation + SHA-256 audit hash, dry-run parity with live runs, fail-closed on misconfiguration, 30+ unit tests + selftest. It replaces silent, non-deterministic runtime truncation that drops your system prompt mid-conversation.

3. Sliding window with semantic anchors (always keep the load-bearing context)

A naive sliding window keeps the first N tokens and the last M tokens. The first-N is usually the system prompt (good). The last-M is usually the most recent turn (good). The middle, dropped, is usually the user's stated constraints, the tool-call results the agent has not yet folded into working memory, and the open questions from earlier turns (bad).

The fix: classify every block by semantic role, not by position. The system prompt is always PROTECTED. The current user turn is always PROTECTED. Tool results that the current question explicitly depends on (e.g., the user said "based on the result of the search I just ran, what does that mean?") are PROTECTED. Older user turns and older tool results that have been folded into working memory are EVICT_FIRST. The window is then: all PROTECTED blocks + working memory + the most recent K EVICT_FIRST blocks that fit the budget. This is the only shape of sliding window that survives a 30-turn agent conversation.

4. Compaction with intent preservation (don't summarize the agent's goals away)

When the budget is still exceeded after the eviction plan has done its work, the agent compacts: it summarizes the middle of the conversation. The naive version of compaction is "summarize the last 20 turns into 3 turns of summary." The result is a working memory that has lost the intent vector: the user's original goal, the constraints the user stated, the open questions, the decisions the agent has already proposed and the user has not yet accepted or rejected.

The fix: compaction is two outputs, not one. First, the summary of the middle (a 500-token paragraph of what was said). Second, the intent vector (a structured block: { goal: string, constraints: string[], openQuestions: string[], pendingDecisions: Array<{decision, proposedAt, status}> }). The intent vector is PROTECTED; it survives every compaction. The summary is EVICT_FIRST; it is the next thing the agent drops when the budget tightens. The two-output compaction is auditable: when the user complains "the agent forgot my original goal," the intent vector is the receipt.

5. Token-budget observability and SLOs (treat tokens as a per-session budget, not a per-call cost)

Every session has a token budget (e.g., 64,000 tokens over 30 turns). Every LLM call has a planned spend (e.g., this turn: 4,200 tokens in, 1,500 tokens out). The session emits a per-call metric: { sessionId, turn, plannedIn, plannedOut, actualIn, actualOut, remainingBudget, evictionBlocks }. The session emits a per-run SLO: budget_exhausted_at_turn_30_no_questions_unanswered. The SLO is checked at the end of the run, and the burn rate (tokens spent per turn) is checked every turn. If the burn rate is on track to exhaust the budget by turn 12, the agent compacts early at turn 6, not late at turn 11.

This pairs with the 9th post on agent observability: tokens are a first-class metric in the session record, not a derived one. The session record is the single source of truth for "how much did this user request actually cost in tokens," and the cost-attribution layer above it (the 14th post on LLM cost reduction) is downstream of the same record.

The 4 anti-patterns

Anti-pattern 1: Silent truncation (the framework eats your system prompt)

The framework has a 32K context window. The system prompt is 4K tokens. The tool catalog is 6K tokens. The conversation history is 24K tokens. The framework, on turn 18, silently drops the oldest 2K tokens of conversation history to make room for the next tool result. The system prompt is still there. The tool catalog is still there. The user turn at turn 4, where the user stated "do not call the delete_file tool under any circumstances," has been dropped. The agent, on turn 19, calls delete_file. The user is furious.

Fix: pre-context-fill eviction (pattern 2). The eviction plan explicitly classifies the user's "do not call delete_file" turn as PROTECTED, the plan runs before the framework decides what to drop, and the protected block is preserved. The framework's silent truncation is replaced with a deterministic, auditable plan that the agent's author can inspect.

Anti-pattern 2: Naive first-N sliding window (drop the only constraint the user gave you)

The agent has a 16K context window. The naive sliding window keeps the first 4K and the last 8K. The middle 4K is dropped. The first 4K is the system prompt. The last 8K is the most recent 6 turns. The middle 4K, dropped, includes the user turn at turn 3 where the user said "the output must be valid JSON" and the agent's tool-call result at turn 5 that contains the JSON schema the user is asking about. By turn 11, the agent is generating output that is not JSON, and the user is asking "why are you ignoring the JSON requirement I stated at the beginning?"

Fix: sliding window with semantic anchors (pattern 3). The "must be valid JSON" constraint is a PROTECTED block (user-stated constraint, never evictable). The JSON schema tool result is a PROTECTED block (tool result the current question depends on). Both survive every turn. The agent on turn 11 is still generating valid JSON, and the user is not asking why.

Anti-pattern 3: Per-call budgets that sum to overflow (no single call caused the blowout)

The agent has a 32K context window. The author sets a per-call budget of 4K tokens "to be safe." The agent runs 12 LLM calls: 1 planning call, 9 tool-call result-summarization calls, 1 final-answer call, 1 self-critique call. Each call is 3,800-4,100 tokens. Total: 47,200 tokens. The 12th call returns 400 context_length_exceeded. The author debugs for 3 hours looking for the call that "caused" the overflow. There is no such call. The overflow is a property of the sum, not of any individual call.

Fix: per-session budget with per-call planned spend (pattern 5). The session budget is 32K. The per-call planned spend is 4K. The session tracks the sum in real time. At call 8, the sum is 31,200, the remaining budget is 800, the agent knows the next 4 calls will overflow, and the agent compacts at call 9 (pattern 4) before the overflow. The 12th call never happens, and the debug session the author would have had is replaced with a single audit log line: "compaction at call 9, intent vector preserved, summary evicted on call 11."

Anti-pattern 4: Evict-on-overflow-only (the API already rejected the request)

The agent has no pre-context-fill eviction plan. The framework sends the full conversation to the API. The API returns 400 context_length_exceeded. The framework catches the error, drops the oldest 4K tokens, retries. The API returns 200. The agent continues. The user, on the next turn, asks a question that depends on the dropped 4K tokens. The agent hallucinates an answer. The user catches the hallucination 3 turns later and loses trust in the agent.

Fix: pre-context-fill eviction (pattern 2). The eviction plan runs before the API call. The plan classifies the "user's original question" block as PROTECTED. The plan classifies the "user's constraint at turn 5" block as PROTECTED. The plan drops the oldest tool-call traces (which have been folded into working memory). The API call is made with a context that fits the budget. The API returns 200. The agent's answer is grounded in the user's original question and the user's stated constraints. The user does not catch a hallucination 3 turns later.

The 115-line drop-in budget-and-eviction runtime

Here is a reference implementation of the budget-and-eviction runtime that exercises patterns 1, 2, and 5. It is intentionally small enough to read in one sitting and intentionally complete enough to be the core of a production agent. The eviction policy is pluggable (pass any function (blocks, budget) -> EvictionPlan), the budget check is pluggable (pass any function (text, modelId) -> number), and the SLO is a single line at the end of the run.

// budget-and-eviction.ts
// Drop-in TypeScript budget + pre-context-fill eviction runtime for LLM agents.
// Zero deps, zero network, deterministic. Pairs with the LLM Context Budget CLI
// and the Agent Context Eviction CLI for the production-grade implementations.

export type Section = {
  role: 'system' | 'user' | 'assistant' | 'tool' | 'memory';
  text: string;
  protected?: boolean;     // user-stated constraint, system prompt, current turn
  semanticKey?: string;    // the constraint or tool result this block depends on
};

export type Estimate = {
  total: number; ceiling: number; overflow: boolean; headroom: number;
};

export type Plan = {
  keep: Section[]; evict: Section[]; hash: string;
};

export type Decision = {
  ok: boolean; estimate: Estimate; plan?: Plan; reason?: string;
};

const sha256 = async (s: string): Promise<string> => {
  // Browser/Node 18+ Web Crypto. Replace with `crypto` from node:crypto for Node.
  const buf = new TextEncoder().encode(s);
  const h = await crypto.subtle.digest('SHA-256', buf);
  return Array.from(new Uint8Array(h)).map(b => b.toString(16).padStart(2, '0')).join('');
};

// Pattern 1: pre-flight estimate (BPE-free character/4 heuristic; swap for tiktoken/CLI in prod)
export const estimate = (sections: Section[], ceiling: number): Estimate => {
  const total = sections.reduce((acc, s) => acc + Math.ceil(s.text.length / 4), 0);
  return { total, ceiling, overflow: total > ceiling, headroom: ceiling - total };
};

// Pattern 2: pre-context-fill eviction (PROTECTED always wins; oldest non-protected first)
export const evict = (sections: Section[], budget: number): Plan => {
  const keep: Section[] = [];
  const evict: Section[] = [];
  let used = 0;
  const sorted = [...sections].sort((a, b) => {
    if (a.protected && !b.protected) return -1;
    if (!a.protected && b.protected) return 1;
    return 0; // stable within class
  });
  for (const s of sorted) {
    const cost = Math.ceil(s.text.length / 4);
    if (s.protected || used + cost <= budget) { keep.push(s); used += cost; }
    else { evict.push(s); }
  }
  // SHA-256 hash of the plan for audit; computed async, see decide() below.
  return { keep, evict, hash: '' };
};

// Pattern 5: per-session budget gate
export const decide = async (
  sections: Section[],
  ceiling: number,
  policy: (s: Section[], budget: number) => Plan = evict
): Promise<Decision> => {
  const est = estimate(sections, ceiling);
  if (!est.overflow) return { ok: true, estimate: est };
  const plan = policy(sections, ceiling);
  plan.hash = await sha256(JSON.stringify(plan.keep.map(s => s.role + ':' + s.text.length)));
  const post = estimate(plan.keep, ceiling);
  if (post.overflow) return { ok: false, estimate: est, plan, reason: 'policy_failed_to_fit_budget' };
  return { ok: true, estimate: post, plan };
};

// 8 selftest cases (run with `npx tsx budget-and-eviction.ts selftest` or in CI)
export const selftest = async (): Promise<{ name: string; pass: boolean }[]> => {
  const out: { name: string; pass: boolean }[] = [];
  const sys: Section = { role: 'system', text: 'sys'.repeat(400), protected: true };
  const u1: Section = { role: 'user', text: 'do not call delete_file'.repeat(40), protected: true };
  const hist: Section[] = Array.from({ length: 10 }, (_, i) => ({
    role: i % 2 ? 'assistant' : 'user', text: 'turn ' + i + ' ' + 'x'.repeat(800),
  }));
  const d = await decide([sys, u1, ...hist], 8000);
  out.push({ name: 'preflight catches overflow on a 10-turn history', pass: d.estimate.overflow });
  out.push({ name: 'plan preserves protected user constraint', pass: d.plan!.keep.some(s => s.text.startsWith('do not call delete_file')) });
  out.push({ name: 'plan preserves system prompt', pass: d.plan!.keep.some(s => s.role === 'system') });
  out.push({ name: 'plan evicts non-protected history', pass: d.plan!.evict.length > 0 });
  out.push({ name: 'post-eviction fits budget', pass: !estimate(d.plan!.keep, 8000).overflow });
  out.push({ name: 'plan has SHA-256 hash', pass: /^[a-f0-9]{64}$/.test(d.plan!.hash) });
  const small = await decide([sys, u1], 8000);
  out.push({ name: 'no overflow on small payload', pass: small.ok && !small.plan });
  const fail = await decide([sys, u1, ...hist], 100);
  out.push({ name: 'policy_failed_to_fit_budget when ceiling is too tight', pass: !fail.ok && fail.reason === 'policy_failed_to_fit_budget' });
  return out;
};

The Woodpecker CI gate

Drop this into .woodpecker.yml on any agent repo. The gate runs the 8 selftest cases above, and additionally runs the LLM Context Budget CLI in JSON-gate mode against the agent's own bootstrap system prompt. If the bootstrap prompt is on track to overflow the model's ceiling, the PR fails before merge.

context-budget-gate:
  image: node:18
  commands:
    - npm ci
    - npx tsx src/budget-and-eviction.ts selftest
    - npx llm-context-budget --payload src/bootstrap-prompt.json --model gpt-5.5 --gate
  when:
    event: [push, pull_request]

The same gate covers the 24th post on the agent testing pyramid: the contract tier asserts that every long-running call accepts a budget, the integration tier runs the budget end-to-end against a real LLM, and the chaos tier forces a 50K-token payload through the agent to confirm the eviction plan degrades gracefully. The pyramid without a budget tier is a pyramid missing its foundation.
