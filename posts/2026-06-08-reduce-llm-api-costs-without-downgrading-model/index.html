How to reduce LLM API costs without downgrading the model.

A 9-step, field-tested playbook for cutting LLM API spend by 40-80% on OpenAI, Anthropic, and Gemini while keeping the same model. No quality compromise, no vendor lock-in pivot, no “switch to a smaller checkpoint” cop-out.

TL;DR. The cheapest token is the one you never send. Most teams pay 2-3x more than they need to because they never measure per-request cost, they paste the same system prompt on every call, they never cache, and they never reject oversized requests at the edge. The 9 steps below are ordered by leverage: measure first, then prompt compression, then prompt caching, then streaming cancellation, then batch API, then semantic cache, then difficulty-based model routing, then per-request budget enforcement, then a feedback loop that compounds the savings. Apply them in order. Most teams recover 40-60% in the first week and 70-80% by month two. The whole post ships with copy-paste TypeScript snippets and cross-links to three Algoram99 tools that make the durable version of this loop trivial: LLM Context Budget CLI, Agent Cost Ledger, and Claude Code Hook Pack.

Why this post exists.

Every team that ships a production LLM feature eventually hits the same wall: the bill grows faster than the usage. The reflex is to switch to a smaller model. That is almost always the wrong move. The smaller model degrades quality in places that are not obvious until a customer complains. A 1% quality regression on a high-traffic product is a much bigger cost than the API bill.

The good news: in nearly every codebase we have audited, 50-80% of the spend is recoverable without touching the model. The waste is structural: unmeasured requests, un-cached prefixes, batched-when-it-should-be-streamed calls, streamed-when-it-should-be-batched calls, and a small set of runaway loops that no one noticed. This post walks through the 9 fixes that recover the largest share of that waste, in the order they pay off.

Step 1 — measure before you optimize.

The first mistake teams make is guessing. They assume the bulk of the cost is in the system prompt. They assume most of the calls go to the largest model. They assume streaming is saving them money. Almost every assumption is wrong, and the gap between perceived and actual cost is usually a factor of 2-3.

Stand up a per-request cost ledger before you change anything. The shape of the ledger matters more than the storage engine. A flat log file with one JSON line per request is enough. The fields you need are: timestamp, model, route, prompt_tokens, completion_tokens, cached_tokens, latency_ms, request_id, and user_hash (or session id, not raw user id). The first three queries you will run on this ledger are:

  • Which model is the dominant cost? (Not always the one you think.)
  • Which route is the dominant cost? (Often a single chat endpoint, not the long tail.)
  • What is the average completion-to-prompt token ratio? (If completion is >50% of cost, your problem is verbosity, not context size.)

A minimal TypeScript cost-ledger snippet you can drop into any Node.js runtime:

// cost-ledger.ts
import { appendFile } from "node:fs/promises";

type Usage = { prompt_tokens: number; completion_tokens: number; cached_tokens?: number };
type LedgerRow = {
  ts: string; model: string; route: string; request_id: string;
  prompt_tokens: number; completion_tokens: number; cached_tokens: number;
  estimated_usd: number; latency_ms: number;
};

// Pricing in USD per 1M tokens. Update per your negotiated rates.
const PRICE: Record = {
  "claude-sonnet-4-5": { in: 3, out: 15, cache_read: 0.30 },
  "gpt-4o":            { in: 2.5, out: 10, cache_read: 1.25 },
  "gemini-2.5-pro":    { in: 1.25, out: 10, cache_read: 0.31 },
};

export async function record(model: string, route: string, rid: string, u: Usage, latency: number) {
  const p = PRICE[model] ?? { in: 3, out: 15, cache_read: 0.30 };
  const cacheReads = u.cached_tokens ?? 0;
  const freshIn = Math.max(0, u.prompt_tokens - cacheReads);
  const usd = (freshIn * p.in + u.completion_tokens * p.out + cacheReads * p.cache_read) / 1e6;
  const row: LedgerRow = {
    ts: new Date().toISOString(),
    model, route, request_id: rid,
    prompt_tokens: u.prompt_tokens,
    completion_tokens: u.completion_tokens,
    cached_tokens: cacheReads,
    estimated_usd: Number(usd.toFixed(6)),
    latency_ms: latency,
  };
  await appendFile("./cost-ledger.jsonl", JSON.stringify(row) + "\n");
}

Run it for a week before you change a single line of prompt. You will discover that the “expensive” route is the wrong one, and the cheap one is the real budget sink. Step 2 — compress prompts with structural pruning.

Aggressive prompt truncation breaks quality. Structural pruning preserves it. The difference is intent: truncation is “delete characters until the response fits in the window”; pruning is “delete the structure that was never earning its keep.”

  • Strip repeated system context. If your system prompt is 4,000 tokens and only 800 of them are referenced in any single request, you are paying for the other 3,200 on every call. Move the long tail to retrieved chunks.
  • Dedupe tool descriptions. MCP servers and tool-use prompts often ship the same tool description three times (system, manifest, examples). Each copy is a token the model reads on every call. Dedupe to one canonical copy and reference it.
  • Move long reference material to RAG. A 30,000-token knowledge base is not a system prompt. It is a query. Send only the top 3-5 chunks that match the user input, not the whole corpus.
  • Compress few-shot examples. If you ship 10 few-shot examples, the model probably uses 2-3 of them. Run an ablation: remove pairs and measure quality. The ones the model does not lean on are dead weight.

The LLM Context Budget CLI runs a per-prompt budget check before the request leaves the runtime. It catches oversized system prompts, repeated tool descriptions, and unfocused retrieval pulls in CI, so the budget breach fails the build instead of the production bill.

Step 3 — turn on prompt caching for the long tail.

Both Anthropic and OpenAI offer prompt caching. Anthropic bills cached reads at 10% of base input price; OpenAI automatic caching drops effective input cost on the cached portion by ~50%. Gemini cached content is free to read on stable system instructions. The pattern in all three is the same: if your system prompt, tool list, or retrieved context is reused across requests, the cache hits compound.

The cache eligibility rules matter more than the headline discount:

  • Anthropic requires the cached prefix to be at least 1,024 tokens, with explicit cache_control: { type: "ephemeral" } breakpoints. 5-minute TTL by default, extendable to 1 hour.
  • OpenAI automatic caching is enabled by default for gpt-4o and o-series; the discount applies when the prompt is >1,024 tokens and the prefix matches an earlier request.
  • Gemini explicit caching lets you upload a context blob once and reference it across thousands of calls. Free reads, billed only on cache writes.

A common anti-pattern: teams re-build the system prompt on every call by concatenating strings in their wrapper. The concatenation breaks prefix matching, so the cache never hits. Use the SDK’s structured messages array, and let the cache layer see stable prefixes.

Step 4 — stream completions and stop on natural boundaries.

Streaming does not cut input cost, but it cuts wasted output cost. When the model goes off-track, the wasted tokens are the ones it produced before you noticed. Pair streaming with a stop sequence or a max-tokens cap to bound the damage.

// streaming-with-cap.ts (Anthropic SDK shape)
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();
const stream = client.messages.stream({
  model: "claude-sonnet-4-5",
  max_tokens: 1024,
  stop_sequences: ["\n\nQuestion:", "\n\nUser:"], // natural boundaries
  messages: [{ role: "user", content: prompt }],
});

let totalOutput = 0;
for await (const event of stream) {
  if (event.type === "content_block_delta" && event.delta.type === "text_delta") {
    process.stdout.write(event.delta.text);
    totalOutput += event.delta.text.length / 4; // ~4 chars/token heuristic
    if (totalOutput > 800) {             // hard cap, 80% of max_tokens
      await stream.close();
      break;
    }
  }
}

The cap of 80% of max_tokens matters because most production runs overshoot the natural endpoint by 10-20%. Capping at 80% saves that 10-20% on every long response without breaking the user experience.

Step 5 — use the batch API for any non-interactive workload.

Both OpenAI and Anthropic offer 50% discounts for batch processing with 24-hour SLA. Gemini offers a similar path through Vertex AI. The savings are not subtle. The cost is the SLA. The right workloads are: nightly summary jobs, evaluation runs, embeddings regeneration, log re-classification, and any background pipeline that does not need a sub-second response.

  • OpenAI batch: /v1/chat/completions with batch endpoint, 50% discount, 24h SLA.
  • Anthropic message batches: client.messages.batches.create(...), 50% discount, up to 1M requests per batch.
  • Vertex AI batch predictions: 50% discount on Gemini, 24h SLA, async upload via JSONL.

The anti-pattern: teams default to interactive calls for everything because “the latency budget allows it.” If the work is not user-facing, batch it. The latency you save by interactive calling on a nightly job is the latency you pay for in cost. Every. Single. Time.

Step 6 — add a semantic cache in front of read-heavy endpoints.

A 2-3% similarity threshold on a vector cache catches 20-40% of repeat queries. The implementation is small: a Redis instance plus a small embedding model (or a hosted endpoint like Voyage or OpenAI text-embedding-3-small). The cache shape is: key = hash of the request metadata, value = cached response, lookup = cosine similarity on the embedded prompt.

// semantic-cache.ts
import { createHash } from "node:crypto";
import type { Redis } from "ioredis";

type Cached = { embedding: number[]; response: unknown; ts: number };
const TTL_MS = 1000 * 60 * 60 * 6; // 6 hours

function cosine(a: number[], b: number[]): number {
  let dot = 0, na = 0, nb = 0;
  for (let i = 0; i < a.length; i++) {
    dot += a[i] * b[i]; na += a[i] * a[i]; nb += b[i] * b[i];
  }
  return dot / (Math.sqrt(na) * Math.sqrt(nb));
}

export async function cachedOrFetch(
  redis: Redis, prompt: string, embed: (s: string) => Promise,
  fetch: () => Promise, threshold = 0.97,
): Promise<{ value: unknown; hit: boolean }> {
  const key = "sc:" + createHash("sha1").update(prompt).digest("hex").slice(0, 16);
  const exact = await redis.get(key);
  if (exact) return { value: JSON.parse(exact), hit: true };

  const v = (await embed(prompt));
  // scan recent keys for nearest neighbor (small cache, simple linear scan)
  const candidates = await redis.keys("sc:*");
  for (const c of candidates) {
    const raw = await redis.get(c);
    if (!raw) continue;
    const e: Cached = JSON.parse(raw);
    if (Date.now() - e.ts > TTL_MS) continue;
    if (cosine(v, e.embedding) >= threshold) return { value: e.response, hit: true };
  }

  const response = await fetch();
  const entry: Cached = { embedding: v, response, ts: Date.now() };
  await redis.set(key, JSON.stringify(entry), "PX", TTL_MS);
  return { value: response, hit: false };
}

The threshold is a knob, not a constant. Start at 0.97 (very strict) and lower it until the cache hit rate plateaus. The wrong direction — starting too loose — returns stale answers that customers notice. The right direction starts strict and only loosens after measuring quality drift.

Step 7 — route by query difficulty.

Most production traffic is not frontier-tier. Classification, extraction, summarization, and short-form generation do not need a $15/M-token model. A 70/30 split with a small model handling the easy 70% and the frontier model handling the hard 30% typically cuts total cost 40-60% with a quality drop under 1% on user-visible outputs.

The hard part is the router. A small classifier model (or even a regex + length heuristic) decides which route. The wrong classifier sends hard questions to the cheap model and tanks quality. The right classifier is a function of (a) input length, (b) domain signals (code, math, creative), and (c) historical user feedback on the same prompt shape.

The first time a team runs this, they almost always discover that the hard route is the one that actually earns its cost, and the “easy” route has quietly become the dominant spend.

Step 8 — enforce per-request token budgets at the edge.

Unbounded requests are how a $5k/month bill becomes a $50k/month bill. The fix is to reject the request at the edge before it reaches the API. The cost of a refused request is zero. The cost of an unbounded one is whatever the runtime billed.

// budget-gate.ts
type Budget = { maxPromptTokens: number; maxCostUsd: number };

export function withinBudget(prompt: string, estCostUsd: number, b: Budget): { ok: true } | { ok: false; reason: string } {
  const estTokens = Math.ceil(prompt.length / 4); // rough heuristic
  if (estTokens > b.maxPromptTokens) return { ok: false, reason: "prompt_too_large" };
  if (estCostUsd > b.maxCostUsd)     return { ok: false, reason: "cost_cap_exceeded" };
  return { ok: true };
}

// Usage:
const gate = withinBudget(req.body.prompt, estimatedCost, { maxPromptTokens: 32_000, maxCostUsd: 0.50 });
if (!gate.ok) return res.status(429).json({ error: "budget_exceeded", reason: gate.reason });

Step 9 — close the feedback loop.

The first 8 steps recover the bulk of the waste. Step 9 is what makes it durable. Every cost observation should be queryable. If a route is bleeding, route more conservatively. If a prompt is expensive, compress it. If a model is underperforming, escalate it. The compounding effect is what makes 40-80% reductions permanent rather than one-off.

Three practices that make the loop actually work:

  • Weekly cost review. A 30-minute meeting with the ledger open. Look for the route with the highest cost-per-useful-output (not the highest absolute cost). The ratio is what tells you where the next dollar of optimization pays off.
  • Cost regressions in CI. Pin a per-prompt budget. If a prompt change pushes its estimated cost over the budget, fail the build. The LLM Context Budget CLI is the only tool that does this as a first-class CI check.
  • Routing feedback from user signals. Thumbs-up, thumbs-down, retry-on-error, and abandon-mid-response are all signals. Feed them back into the router. The router that improves from production data beats the router that improves from offline evals.

The 7 anti-patterns that silently double cost.

These are the failure modes we see in 80% of the codebases we audit. Each one is a small mistake with a 2-3x compounding effect on the bill.

  1. Re-concatenating the system prompt on every call. Breaks prefix caching. Fix: use the SDK’s structured messages array.
  2. Sending the full conversation history on every turn. The history grows linearly; cost grows super-linearly. Fix: summarize older turns into a compact recap.
  3. Streaming when batch would do. Streaming is for user-facing UI; batch is for everything else. The latency budget for a nightly job is the cost you pay every time.
  4. No cost ledger. If you can’t query last week’s per-route cost, you can’t prioritize the next optimization. The ledger is not optional.
  5. Unbounded retries. A flaky tool call that retries 5 times at 4,000 tokens each is 20,000 tokens of cost. Fix: exponential backoff with a hard ceiling.
  6. Routing everything to the frontier model. The 70% of traffic that doesn’t need it is a 5-10x overspend. Fix: difficulty-based routing with a quality gate on the cheap route.
  7. Prompting with raw document dumps. 30,000-token knowledge bases should be RAG, not system prompts. Sending the whole corpus is the most expensive typo in the codebase.
