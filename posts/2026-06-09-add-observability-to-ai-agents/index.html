1. The three observability gaps that break production agents

You shipped the agent. It works on the dev box. Then it goes to production and three things happen at once:

  1. Token costs drift up 30% in a week with no code change. You have no per-call cost attribution, so you cannot tell whether it is a model price change, a prompt regression, a new tool call, or one user who pasted a 200k-token document.
  2. A user reports the agent “hallucinated a refund”. The dev console shows the prompt and the response, but not which tool call returned what, in what order, with what schema, with what upstream latency. You cannot reproduce.
  3. Latency p99 spikes from 4s to 22s. The LLM provider status page is green. The retriever is fine. The vector DB is fine. The actual cause is a single tool that started returning 4x larger payloads after a vendor upgrade — but you have no span attributes for response size, so it is invisible.

All three are observability problems, not model problems. The fix is the same for all three: emit the right OpenTelemetry spans, attach the right attributes, ship them somewhere queryable, and gate CI on them.

2. The four spans every agent must emit

OpenTelemetry GenAI semantic conventions are still moving (the spec is in semantic-conventions GenAI 1.30+ as of mid-2026), but the four-span pattern below is stable across all major agent frameworks. Each span has a clear parent-child relationship:

// Span tree for one agent turn:
//   agent.turn
//   ├─ llm.plan
//   ├─ tool.call (repeated)
//   │  └─ tool.upstream
//   └─ llm.synthesize
// Each span carries the attributes below. Missing any of these
// is what produces the three gaps in section 1.
SpanRequired attributesWhy it matters
agent.turnagent.user_id, agent.session_id, agent.turn_indexGroups everything for one user turn. Required to attribute cost and detect per-user abuse.
llm.plangen_ai.request.model, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens, gen_ai.response.finish_reasonThe decision step. Catches token drift and finish-reason regressions (truncation, length-cap, content-filter).
tool.calltool.name, tool.input_schema_hash, tool.output_schema_hash, tool.upstream.statusCatches schema drift and upstream latency cliffs. The schema hashes are the secret sauce — see section 3.
llm.synthesizesame as llm.plan + agent.tool_calls_planned vs agent.tool_calls_executedThe final response step. Catches the silent-failure mode where the model plans 3 tool calls but the runtime executes 2.

If your trace has all four spans per turn with all the listed attributes, you can answer 90% of production “what happened?” questions in under 5 minutes. If you are missing any one of them, you are flying blind on the corresponding failure mode.

3. Anti-pattern #1 — stringifying prompts into span attributes

Anti-pattern. Copying the full prompt and full response into gen_ai.prompt / gen_ai.completion attributes. This does three things badly:
  1. Blows up span size past OTLP’s 16MB hard limit once a user pastes a 100k-token document.
  2. PII / secrets / API keys from prompts get indexed by every observability backend that has span search enabled. You will leak customer data into Datadog / Honeycomb / Tempo / your own S3.
  3. Span serialization dominates your actual LLM latency. A 50k-token prompt takes 80ms to serialize through protobuf; 80ms per turn x 100 turns/min x 5 spans = real money.

Fix. Store the prompt and response as a span event on a separate, write-only, encrypted store keyed by trace_id, and put a hash + length + first-100-chars preview into the span attributes. For bullet 2 (PII / secrets in span attributes), drop the Agent Secrets Redactor CLI Buy $29 into the span-emit path as a pre-serialize step. 12 deterministic patterns (AWS, GitHub PATs, OpenAI/Anthropic/Stripe, PEM, 64-char hex wallet seeds, JWTs, Slack, GCP, email, phone) with redact / hash / drop actions, sub-millisecond per KB — the same redactor that should run in your log pipeline runs in your OTel exporter. For context-window-blow-up (bullet 1), the Agent Context Eviction CLI Buy $29 emits the deterministic eviction plan as a span event so you can see what was thrown away. The OTel SDK makes this two lines:

import { trace, context, SpanStatusCode } from '@opentelemetry/api';
import { createHash } from 'node:crypto';

const tracer = trace.getTracer('agent-core');

export async function tracedLLMCall(model: string, prompt: string, call: () => Promise<string>) {
  const span = tracer.startSpan('llm.plan', {
    attributes: {
      'gen_ai.request.model': model,
      'gen_ai.prompt.length': prompt.length,
      'gen_ai.prompt.sha256': createHash('sha256').update(prompt).digest('hex').slice(0, 16),
      'gen_ai.prompt.preview': prompt.slice(0, 100),
    },
  });
  try {
    const response = await context.with(trace.setSpan(context.active(), span), call);
    span.setAttribute('gen_ai.completion.length', response.length);
    span.setAttribute('gen_ai.completion.sha256', createHash('sha256').update(response).digest('hex').slice(0, 16));
    span.setStatus({ code: SpanStatusCode.OK });
    span.addEvent('llm.response.body', { /* encrypted external store */ });
    return response;
  } catch (err: any) {
    span.recordException(err);
    span.setStatus({ code: SpanStatusCode.ERROR, message: err.message });
    throw err;
  } finally {
    span.end();
  }
}

4. Anti-pattern #2 — silent schema drift

Anti-pattern. Emitting a tool.call span with tool.name and a JSON-stringified tool.input, but no schema hash. Then a vendor updates their API and returns a slightly different shape — same field names, but a nested amount that used to be a string is now a number. Your agent’s downstream parser crashes 12 hours later in a way that the test suite (which mocks the tool) cannot reproduce.

Fix. Emit tool.input_schema_hash and tool.output_schema_hash on every tool span. Compute the hash from the JSON schema of the input/output, not the values:

function schemaHash(value: unknown): string {
  // Strip all values, keep only the shape: keys, types, nesting, array-ness.
  const shape = JSON.stringify(value, (_, v) => {
    if (v && typeof v === 'object' && !Array.isArray(v)) {
      return Object.fromEntries(
        Object.keys(v).sort().map(k => [k, typeof (v as any)[k]])
      );
    }
    if (Array.isArray(v)) return `array<${v.length}>`;
    return typeof v;
  });
  return createHash('sha256').update(shape).digest('hex').slice(0, 16);
}

// On every tool call:
span.setAttribute('tool.input_schema_hash', schemaHash(toolInput));
span.setAttribute('tool.output_schema_hash', schemaHash(toolOutput));

Then in your trace query, alert on SELECT tool.name, count(distinct tool.output_schema_hash) FROM tool_call_spans WHERE timestamp > now() - 1h GROUP BY tool.name HAVING count(distinct tool.output_schema_hash) > 1. A new hash appearing for a known tool name is a vendor-API drift signal, not a customer issue.

5. Anti-pattern #3 — span flood from retriever calls

Anti-pattern. Emitting a tool.call span for every single chunk retrieved, every re-rank, every embedding call. A single RAG turn produces 50+ spans. Your trace backend costs 10x what it should, and the flame graph becomes unreadable.

Fix. Collapse retriever sub-operations into a single parent span with summary attributes:

export async function tracedRetrieve(query: string, retrieve: () => Promise<Chunk[]>) {
  const span = tracer.startSpan('rag.retrieve', { attributes: { 'rag.query.length': query.length } });
  const start = Date.now();
  try {
    const chunks = await context.with(trace.setSpan(context.active(), span), retrieve);
    span.setAttributes({
      'rag.chunks_returned': chunks.length,
      'rag.top_score': chunks[0]?.score ?? 0,
      'rag.embedding_calls': chunks.length,  // summarized, not per-chunk
      'rag.rerank_calls': 1,
      'rag.duration_ms': Date.now() - start,
    });
    span.setStatus({ code: SpanStatusCode.OK });
    return chunks;
  } finally {
    span.end();
  }
}

Rule of thumb: one span per logical “thing the agent did” (retrieve, plan, call tool, synthesize), not one span per LLM token or per vector lookup. If your trace tree has more than ~12 spans per turn, you are over-instrumenting.

6. Anti-pattern #4 — missing trace context across the async boundary

Anti-pattern. Your agent makes an async call to a downstream service (a webhook, a queue, a sub-agent) and the trace breaks at the boundary. Now you have two disconnected traces and no way to follow the request flow. The OTel context is lost the moment you cross a process boundary without propagation.

Fix. Use the W3C Trace Context propagator and pass the headers explicitly. This is the single most-skipped OTel feature, and it is the difference between a trace you can follow and a trace you cannot:

import { propagation, context, trace, ROOT_CONTEXT } from '@opentelemetry/api';
import { W3CTraceContextPropagator } from '@opentelemetry/core';
propagation.setGlobalPropagator(new W3CTraceContextPropagator());

// Outbound: inject the current trace context into headers
export function outboundHeaders(): Record<string, string> {
  const headers: Record<string, string> = {};
  propagation.inject(context.active(), headers);
  return headers;  // e.g. { traceparent: '00-...-...-01' }
// Inbound: extract from inbound headers, then run the handler inside that context
export async function handleInbound(headers: Record<string, string>, handler: () => Promise<void>) {
  const parentCtx = propagation.extract(ROOT_CONTEXT, headers);
  await context.with(parentCtx, handler);
}

For queue-based async (SQS, Redis Streams, Kafka), inject the headers into the message envelope, not the message body. For webhook callbacks, the upstream service needs to accept and forward the traceparent header. Verify this in the Woodpecker CI gate below — it is the #1 thing teams miss.

7. The Woodpecker CI gate

You cannot trust that future PRs will keep emitting the right spans. So you write a test that fails CI when a span is missing. This is a 30-line .woodpecker.yml stage + a 20-line test:

# .woodpecker.yml — observability gate stage
observability:
  image: node:22
  commands:
    - npm ci
    - npx tsx tests/observability/span-shape.test.ts
  when:
    event: [push, pull_request]

// tests/observability/span-shape.test.ts
import { trace, context } from '@opentelemetry/api';
import { InMemorySpanExporter, SimpleSpanProcessor } from '@opentelemetry/sdk-trace-base';
import { runAgentTurn } from '../../src/agent/turn.js';

const exporter = new InMemorySpanExporter();
trace.getTracerProvider().addSpanProcessor(new SimpleSpanProcessor(exporter));

await runAgentTurn({ userId: 'test', prompt: 'refund my last order' });

const spans = exporter.getFinishedSpans();
const names = new Set(spans.map(s => s.name));

// Hard requirements — failure blocks merge
const required = ['agent.turn', 'llm.plan', 'llm.synthesize'];
for (const name of required) {
  if (!names.has(name)) throw new Error(`missing required span: ${name}`);
}

// Tool calls: at least one tool call span (we know this prompt hits refund)
const toolSpans = spans.filter(s => s.name === 'tool.call');
if (toolSpans.length === 0) throw new Error('expected at least one tool.call span');

// Per-span attribute presence
for (const s of spans) {
  const a = s.attributes;
  if (!a['gen_ai.usage.input_tokens']) throw new Error(`span ${s.name} missing input_tokens`);
  if (!a['gen_ai.request.model']) throw new Error(`span ${s.name} missing model`);
}

console.log(`OK: ${spans.length} spans, ${toolSpans.length} tool calls, all required attributes present`);

The gate is cheap (no LLM call — you stub the model) and catches the four anti-patterns above. A PR that introduces a new code path that bypasses the traced wrapper will fail the test, the PR cannot merge, and the trace tree stays intact.

8. The runbook — catching silent drift

Once the spans are flowing, you need a runbook for the three failure modes that “the agent feels slow today” actually masks. The queries below run against any OTLP-compatible backend (Honeycomb, Tempo, Datadog APM, SigNoz, self-hosted OTel Collector + ClickHouse).

8.1 Token drift

SELECT
  date_trunc('hour', timestamp),
  model,
  avg(gen_ai.usage.input_tokens) AS avg_in,
  avg(gen_ai.usage.output_tokens) AS avg_out,
  percentile_cont(0.99) WITHIN GROUP (ORDER BY gen_ai.usage.input_tokens) AS p99_in
FROM llm_plan_spans
WHERE timestamp > now() - INTERVAL '7 days'
GROUP BY 1, 2
ORDER BY 1 DESC, 2;

Alert when p99_in for a stable model moves more than 30% week-over-week. This catches prompt regressions that are too subtle for a unit test but too expensive to ignore.

8.2 Schema drift

SELECT
  tool.name,
  count(distinct tool.output_schema_hash) AS distinct_schemas,
  array_agg(distinct tool.output_schema_hash) AS hashes
FROM tool_call_spans
WHERE timestamp > now() - INTERVAL '1 hour'
GROUP BY tool.name
HAVING count(distinct tool.output_schema_hash) > 1;

Zero rows = healthy. Any row = a vendor changed their response shape in the last hour.

8.3 Latency cliffs that are not the LLM

SELECT
  tool.name,
  percentile_cont(0.50) WITHIN GROUP (ORDER BY duration_ms) AS p50,
  percentile_cont(0.99) WITHIN GROUP (ORDER BY duration_ms) AS p99,
  avg(tool.response_size_bytes) AS avg_bytes
FROM tool_call_spans
WHERE timestamp > now() - INTERVAL '24 hours'
GROUP BY tool.name
ORDER BY p99 DESC
LIMIT 10;

When avg_bytes and p99 both move up for the same tool, it is almost always a payload-size regression on the upstream side, not a model issue.
