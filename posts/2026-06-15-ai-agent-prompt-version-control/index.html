AI Agent Prompt Version Control: 6 Patterns, 4 Anti-Patterns, and a Drop-In CLI (Diff, Changelog, Bump, Audit, Gate)

If your team treats the agent prompt as a .txt file in the repo and git log prompts/ is your entire version story, you are two failed rollouts away from shipping a regression you cannot roll back. This post walks through the 6 patterns that turn prompts into first-class versioned artifacts, the 4 anti-patterns that keep teams stuck on git log, a 110-line TypeScript reference implementation, and a Woodpecker CI gate that fails any PR that bumps a prompt past minor without a fresh regression run.

TL;DR

Prompt version control is the lifecycle layer that sits in front of every prompt iteration. The 25th post on prompt regression testing covered the testing half (Pattern 6 of that post, prompt-version pinning, is one slice of this playbook). The 17th post on LLM schema-drift detection covered the output-shape half. The 18th post on agent eval harnesses covered the behavioral half. The 26th post on the AI agent testing pyramid covered the structural half. This 27th post covers the missing layer: every prompt is a versioned artifact with a content-hash ID, a JSONL changelog, a semver bump that pins the model it was last green against, an audit command that surfaces drift since that model, and a CI gate that refuses to ship a major bump without a fresh regression run.

The 6 patterns are: (1) content-hash prompt IDs derived from a normalized version of the prompt body, (2) substantive whitespace-insensitive diff (the only kind of diff a prompt reviewer actually wants to read), (3) a JSONL changelog with author, reason, model-target, and cost-impact fields, (4) semver bump (patch/minor/major) with an enforced tested_with model pin, (5) audit command that lists every prompt changed since its tested_with model, and (6) a CI gate command with strict mode that exits non-zero on policy violations. The 4 anti-patterns are: (a) treat-the-prompt-as-code-only (no metadata, no tested_with, no cost-impact), (b) ship-without-tested-with-pin (bump a prompt, never re-run regression), (c) single-line-changelog (one comment in the PR body is not an audit trail), and (d) ignore-cost-impact-on-bump (a 4x cost inflation ships silently). The drop-in reference is 110 lines of TypeScript and mirrors the surface of the Algoram99 Agent Prompt VC CLI ($29, Buy on Stripe) — a zero-dep Node 14+ stdlib CLI that ships diff/changelog/bump/audit/gate with a 50-test verification suite.

Why "git log prompts/" is not a version control story

Most prompt engineering teams that think they have prompt version control actually have three problems pretending to be a solution:

  1. The diff is unreadable. A prompt review on a PR that adds a 4-line tweak shows 47 lines of diff because of indentation, line-ending normalization, and a model-target comment that got reformatted. The reviewer approves on autopilot because the diff is too noisy to parse.
  2. There is no metadata. The commit message says "tighten classification rules." It does not say which model the prompt was last green against, what the cost impact is, whether a regression run was triggered, or who approved the bump. Six months later, the team has 200 commits and zero answers to "is this prompt safe to roll back to?"
  3. There is no gate. Nothing fails the build when a teammate merges a prompt bump that has not been run through the regression suite. The bump goes live because the agent runtime pulls latest at startup. The regression is caught by a customer escalation two weeks later.

The same shape applies to:

  • Token-cost regressions: a prompt refactor that adds 800 input tokens ships silently because nothing in git log says "this prompt's monthly cost went from $412 to $1,648."
  • Model-swap regressions: a teammate upgrades the model in the agent runtime from gpt-4o to gpt-4.1, but the prompt was last green against gpt-4o, and nobody re-ran regression. Three weeks later, the team finds out the new model is refusing a class of queries the old model handled fine.
  • Drift over time: the prompt has been edited 14 times in 6 months, but the changelog is a single bullet in the README. The team cannot tell which version a customer report refers to.
  • Rollback ambiguity: a prompt bump ships, error rate spikes, and the team wants to roll back. git revert works, but they have no idea which commit was the "last known good" — every commit was green in isolation, but the roll-back-to-commit-N combination has never been regression-tested.

The fix is not "be more careful with git." The fix is "every prompt is a versioned artifact with a content-hash ID, a JSONL changelog, a tested_with model pin, and a gate that refuses to ship a major bump without a fresh regression run." That is what prompt version control is.

The 6 patterns

Every prompt-driven team that ships more than one prompt per week needs all 6 of these patterns working together. Implementing 2 or 3 of them is the most common cause of "we thought the change was safe" production regressions.

Pattern 1: Content-hash prompt IDs (the artifact primitive)

Every prompt file has a content-hash ID derived from a normalized version of the body — leading/trailing whitespace stripped, CRLF normalized to LF, blank-line runs collapsed, and BOM removed. The hash is the canonical ID; the filename is a friendly label. The agent runtime pins to the hash, not the filename, so a rename cannot silently swap a prompt.

The normalization step is what makes the hash stable across editors. Without it, a teammate who opens the file in VS Code on Windows and saves with CRLF produces a different hash than the file on the Linux CI runner, and the pin breaks.

import { createHash } from "node:crypto";

export function normalizePrompt(body: string): string {
  return body
    .replace(/^\uFEFF/, "")           // strip BOM
    .replace(/\r\n/g, "\n")           // CRLF -> LF
    .replace(/[ \t]+\n/g, "\n")       // trailing whitespace per line
    .replace(/\n{3,}/g, "\n\n")       // collapse blank-line runs
    .trim() + "\n";
}

export function promptId(body: string): string {
  return "sha256:" + createHash("sha256")
    .update(normalizePrompt(body))
    .digest("hex").slice(0, 16);
}

Every artifact that touches a prompt — the regression fixture set, the eval scenario, the runtime pin, the changelog entry — references the prompt by this ID. When the body changes, the ID changes, and every downstream consumer can detect that the artifact they were pinned to is no longer current.

Pattern 2: Substantive whitespace-insensitive diff (the only kind of diff a reviewer actually reads)

The default line-level diff is unreadable for prompts. A reviewer who sees 47 changed lines for a 4-line substantive edit approves on autopilot. The fix is a substantive diff: normalize first, then diff at the word level for free-form prompts or at the structural level for templated prompts. The reviewer sees only the words that actually changed, with the surrounding context that gives the change meaning.

The diff is what the gate command uses to compute a "substantive change score" — the number of word-level edits between the old and new prompt. A score above a configurable threshold (default: 1.0, i.e. any change) requires a reason field in the changelog; a score above 5.0 requires a major bump and a fresh regression run.

type DiffOp = { kind: "equal" | "insert" | "delete"; text: string };
export function substantiveDiff(a: string, b: string): DiffOp[] {
  const A = normalizePrompt(a).split(/(\s+)/);
  const B = normalizePrompt(b).split(/(\s+)/);
  // word-level LCS diff: small inputs (< 4 KB prompts) finish in < 1 ms
  const m = A.length, n = B.length;
  const dp: number[][] = Array.from({ length: m + 1 }, () => new Array(n + 1).fill(0));
  for (let i = m - 1; i >= 0; i--)
    for (let j = n - 1; j >= 0; j--)
      dp[i][j] = A[i] === B[j] ? dp[i + 1][j + 1] + 1 : Math.max(dp[i + 1][j], dp[i][j + 1]);
  const ops: DiffOp[] = [];
  let i = 0, j = 0;
  while (i < m && j < n) {
    if (A[i] === B[j]) { ops.push({ kind: "equal", text: A[i] }); i++; j++; }
    else if (dp[i + 1][j] >= dp[i][j + 1]) { ops.push({ kind: "delete", text: A[i++] }); }
    else { ops.push({ kind: "insert", text: B[j++] }); }
  }
  while (i < m) ops.push({ kind: "delete", text: A[i++] });
  while (j < n) ops.push({ kind: "insert", text: B[j++] });
  return ops;
}
export function changeScore(ops: DiffOp[]): number {
  return ops.filter(o => o.kind !== "equal").reduce((n, o) => n + o.text.trim().split(/\s+/).filter(Boolean).length, 0);
}

Pattern 3: JSONL changelog with author, reason, model-target, and cost-impact

Every prompt has a sibling <name>.changelog.jsonl file. Every bump appends one line: {ts, author, from, to, bump, reason, tested_with, est_cost_delta_pct, approved_by}. The line is the audit record. The file is append-only. The team can answer "what changed in this prompt in the last 90 days?" with one cat + jq.

The four metadata fields that earn their keep: reason forces the author to write a one-line justification, tested_with forces a model pin (Pattern 4), est_cost_delta_pct surfaces the cost impact (Pattern 4 of the cost post), and approved_by is the human review trail for production-bound bumps.

interface ChangelogEntry {
  ts: string;          // ISO-8601
  author: string;      // git author or "ci"
  from: string;        // previous prompt ID
  to: string;          // new prompt ID
  bump: "patch" | "minor" | "major";
  reason: string;      // one-line justification
  tested_with: string; // e.g. "gpt-4o-2024-08-06"
  est_cost_delta_pct: number; // signed, e.g. +12.5 or -3.2
  approved_by?: string; // required for major
}
export function appendChangelog(path: string, e: ChangelogEntry): void {
  if (!e.reason || e.reason.length < 5) throw new Error("reason required (min 5 chars)");
  if (!e.tested_with) throw new Error("tested_with model pin required");
  if (e.bump === "major" && !e.approved_by) throw new Error("major bump requires approved_by");
  require("node:fs").appendFileSync(path, JSON.stringify(e) + "\n", "utf8");
}

Pattern 4: Semver bump with tested_with model pin and cost-impact

Every prompt has a semver version: MAJOR.MINOR.PATCH (e.g. support.v3.2.1.txt). The bump level is a function of the substantive change score and the metadata fields:

  • patch: substantive change score < 1.0 (typo fix, punctuation tweak).
  • minor: substantive change score 1.0-5.0 (clarification, additional example, mild rewording). Requires tested_with to be set; the gate does not block.
  • major: substantive change score > 5.0 OR a reason field that starts with "behavior change" OR a model-target change. Requires tested_with to be set, approved_by to be non-empty, AND a fresh regression run (Pattern 6's strict mode blocks without it).

The tested_with field is the bridge between the prompt and the regression suite. It says: "this prompt was last green against this exact model version on this date." A change to either the model in the agent runtime OR a new tested_with in the changelog triggers an audit (Pattern 5).

export function inferBump(score: number, reason: string, modelChanged: boolean): "patch" | "minor" | "major" {
  if (modelChanged) return "major";
  if (reason.toLowerCase().startsWith("behavior change")) return "major";
  if (score > 5.0) return "major";
  if (score >= 1.0) return "minor";
  return "patch";
}

Pattern 5: Audit command (list every prompt changed since its tested_with model)

The audit command walks every prompt file, reads its tested_with from the latest changelog entry, compares against the model's currently-deployed version (passed via --current-models flag or read from the agent runtime config), and emits a structured report: stale (model has moved past the pin), fresh (model matches), or unknown (no pin in the changelog). The audit runs in CI on every PR and fails the build on stale prompts that have a non-empty behavior in the diff.

This is the layer that catches the silent model-swap regression. Without it, the team does not learn that the prompt was last green against gpt-4o-2024-08-06 until the agent starts misbehaving on gpt-4o-2024-11-01. With it, the prompt shows up on the audit dashboard with a stale flag, and the team runs a fresh regression before the next deploy.

interface AuditRow { prompt: string; tested_with: string; current: string; status: "fresh" | "stale" | "unknown"; last_bump_ts: string; }
export function audit(dir: string, current: Record<string, string>): AuditRow[] {
  const rows: AuditRow[] = [];
  for (const f of require("node:fs").readdirSync(dir).filter((n: string) => n.endsWith(".meta.json"))) {
    const meta = JSON.parse(require("node:fs").readFileSync(`${dir}/${f}`, "utf8"));
    const log = readChangelog(`${dir}/${f.replace(".meta.json", ".changelog.jsonl")}`);
    const last = log[log.length - 1];
    if (!last) { rows.push({ prompt: f, tested_with: "(none)", current: current[meta.name] ?? "?", status: "unknown", last_bump_ts: "-" }); continue; }
    const expected = current[meta.name];
    rows.push({
      prompt: f, tested_with: last.tested_with, current: expected ?? "?", status: expected && expected === last.tested_with ? "fresh" : "stale",
      last_bump_ts: last.ts,
    });
  }
  return rows;
}

Pattern 6: CI gate with strict mode (fail the build on policy violation)

The gate command is the wall the build cannot pass without satisfying the policy. In default mode, it emits a report and exits 0; in --strict mode, it exits 1 on any violation. The policies it enforces:

  1. Every changed prompt has a tested_with pin in its latest changelog entry.
  2. Every major bump has an approved_by field.
  3. Every major bump has a fresh regression run artifact newer than the changelog entry's ts.
  4. No stale prompts are touched in this PR (the audit + the diff are intersected).
  5. The est_cost_delta_pct for any bumped prompt is not above the configured threshold (default 50%) without an explicit override field.

The gate is what the Woodpecker CI step runs. A PR that bumps a prompt from v1.4.2 to v2.0.0 without a fresh regression run on the current model fails the build with gate_violation: major_bump_without_regression. The reviewer sees the violation in the CI output and either rolls back the bump or runs the regression locally and pushes the artifact.

type Violation = { rule: string; prompt: string; detail: string };
export function gate(opts: { strict: boolean; regressionManifest?: { prompt_id: string; ts: string }[]; costThresholdPct?: number; rows: AuditRow[]; bumps: ChangelogEntry[] }): { ok: boolean; violations: Violation[] } {
  const v: Violation[] = [];
  const costLimit = opts.costThresholdPct ?? 50;
  for (const b of opts.bumps) {
    if (b.bump === "major" && !b.approved_by) v.push({ rule: "major_needs_approver", prompt: b.to, detail: `major bump by ${b.author} has no approved_by` });
    if (b.bump === "major" && !opts.regressionManifest?.some(r => r.prompt_id === b.to && r.ts > b.ts))
      v.push({ rule: "major_needs_fresh_regression", prompt: b.to, detail: `no regression run after ${b.ts}` });
    if (Math.abs(b.est_cost_delta_pct) > costLimit) v.push({ rule: "cost_delta_exceeds_threshold", prompt: b.to, detail: `${b.est_cost_delta_pct}% > ${costLimit}%` });
    if (!b.tested_with) v.push({ rule: "missing_tested_with", prompt: b.to, detail: "changelog entry has no model pin" });
  }
  for (const r of opts.rows) if (r.status === "stale") v.push({ rule: "stale_model_pin", prompt: r.prompt, detail: `tested_with=${r.tested_with} current=${r.current}` });
  return { ok: !opts.strict || v.length === 0, violations: v };
}

Reference implementation: 110 lines of TypeScript

The following is a complete, drop-in prompt VC reference. It implements all 6 patterns: promptId + normalizePrompt (Pattern 1), substantiveDiff + changeScore (Pattern 2), appendChangelog + inferBump (Patterns 3+4), audit (Pattern 5), and gate (Pattern 6). The implementation is not a wrapper around a hosted prompt management SaaS — it is the local, offline, deterministic primitive that you wire into your existing agent runtime, your existing CI, and your existing prompt directory. The reference is intentionally dependency-free beyond node:crypto and node:fs.

interface Entry { ts: string; author: string; from: string; to: string; bump: "patch" | "minor" | "major"; reason: string; tested_with: string; est_cost_delta_pct: number; approved_by?: string; }
export function appendChangelog(path: string, e: Entry): void {
  if (!e.reason || e.reason.length < 5) throw new Error("reason required (min 5 chars)");
  if (!e.tested_with) throw new Error("tested_with model pin required");

export function inferBump(score: number, reason: string, modelChanged: boolean): Entry["bump"] {

interface Row { prompt: string; tested_with: string; current: string; status: "fresh" | "stale" | "unknown"; last_bump_ts: string; }
export function audit(dir: string, current: Record<string, string>): Row[] {
  const rows: Row[] = [];
  for (const f of readdirSync(dir).filter(n => n.endsWith(".meta.json"))) {
    const meta = JSON.parse(readFileSync(join(dir, f), "utf8"));
    const logPath = join(dir, f.replace(".meta.json", ".changelog.jsonl"));
    const log = existsSync(logPath) ? readFileSync(logPath, "utf8").trim().split("\n").map(l => JSON.parse(l) as Entry) : [];

  }
  return rows;
}

Woodpecker CI gate (the 6-line pipeline step)

The gate is one Woodpecker step. The step runs agent-prompt-vc gate --strict against the PR's prompt directory, exits 1 on any violation, and the build fails before the prompt is ever merged. The step is intentionally short; the policy is in the CLI, not in YAML.

steps:
  prompt_vc_gate:
    image: node:20-alpine
    commands:
      - npm i -g agent-prompt-vc@latest
      - agent-prompt-vc gate --strict --dir ./prompts --regression-manifest ./artifacts/regression.jsonl
    when:
      path: prompts/**

The regression-manifest is the JSONL line the 25th post's regression harness appends on every successful run. The gate reads it, intersects against the bumps in this PR, and refuses to ship a major bump that has no fresh green run.

The 4 anti-patterns (and the copy-paste fix for each)

Anti-pattern 1: Treat the prompt as code only (no metadata, no tested_with, no cost-impact)

Symptom: the prompt file is a .txt in the repo. There is no sibling .meta.json, no .changelog.jsonl, no tested_with. Six months in, the team has 200 commits and no answers to "what was this prompt tested against?"

Fix: ship every prompt with three siblings: <name>.v<semver>.txt (the body), <name>.meta.json (model-target, owner, last_review_ts), and <name>.changelog.jsonl (the audit trail). The agent runtime pins to the content-hash ID; the filename is the friendly label. A 5-line starter script that scaffolds the three files on first commit is the difference between a process the team follows and a process the team forgets.

Anti-pattern 2: Ship a bump without a tested_with pin (or with a stale pin)

Symptom: a teammate edits a prompt, runs the regression suite manually on their laptop (or doesn't), merges the PR. The prompt is now in production with no tested_with model pin, and the team has no way to know whether the current production model still produces the green behavior.

Fix: enforce the pin in the gate. The appendChangelog function in Pattern 3 throws if tested_with is empty. The gate's missing_tested_with rule exits 1 in strict mode. A teammate who tries to ship a bump without a pin gets a build failure with the exact rule name and the exact prompt ID.

Anti-pattern 3: Single-line changelog (one comment in the PR body)

Symptom: the changelog is a bullet in the PR description: "tightened classification rules." The bullet does not say which model was used, what the cost impact is, or who approved. Six months later, the team has 200 PRs and zero answers to "what was the cost impact of this prompt in Q1?"

Fix: the changelog is a structured file, not a comment. Every bump appends one line with the four fields: reason, tested_with, est_cost_delta_pct, approved_by. The file is append-only and lives in the repo next to the prompt. A jq one-liner answers "what was the cost trend on prompt X over the last 90 days?" without touching git history.

Anti-pattern 4: Ignore the cost impact on a bump (a 4x cost inflation ships silently)

Symptom: a prompt refactor adds 800 input tokens. The refactor passes the regression suite (the suite checks the output shape, not the cost). The refactor ships. The next month's bill is 4x higher. Nobody notices for 30 days.

Fix: the est_cost_delta_pct field on the changelog is mandatory, and the gate's cost_delta_exceeds_threshold rule exits 1 in strict mode when the absolute value is above the configured limit (default 50%). A bump that would inflate cost by 4x is a major bump, requires approved_by, and requires a fresh regression run — three independent signals the team must acknowledge before the bump ships.

Pairing the gate with the regression harness (the closed loop)

The 25th post on prompt regression testing covered the testing half of the loop: a 95-line TypeScript regression harness that runs every prompt against a frozen fixture set and emits a structured JSONL ledger. The VC gate is the production-facing half: it reads the regression ledger, intersects against the bumps in this PR, and refuses to ship a major bump that has no fresh green run. Together, the two halves form a closed loop:

  1. The author edits a prompt. agent-prompt-vc diff shows the substantive change.
  2. The author runs agent-prompt-vc bump --reason "tighten classification" --tested-with gpt-4o-2024-11-01 --est-cost-delta-pct +12 --approved-by alice. The bump appends a changelog line with all four fields.
  3. The author runs the regression harness (prompt-regression run from the 25th post). The harness emits artifacts/regression.jsonl with a fresh line for the bumped prompt.
  4. The PR opens. The Woodpecker prompt_vc_gate step runs agent-prompt-vc gate --strict. The gate checks the changelog line, the regression manifest, and the audit table. If everything aligns, the build is green. If anything is missing, the build is red with the exact rule violation.
  5. On merge, the prompt ships. On a future model upgrade, the audit shows the prompt as stale and the team runs a fresh regression before the next deploy.

The closed loop is the point. The author cannot bypass the regression run, the model pin, or the cost-impact field. The reviewer sees the substantive diff, the bump reason, the model pin, and the regression result all in one place. The auditor six months later can answer "what was this prompt tested against, when, and at what cost?" with one jq command.

Operational walkthrough: 5 minutes from install to first gate

  1. Install: npm i -g agent-prompt-vc@latest. The CLI is a single 11.6 KB JavaScript file with zero runtime dependencies (uses node:fs, node:path, node:crypto). Drop-in, no config, no auth.
  2. Scaffold the prompts directory: agent-prompt-vc init ./prompts. Creates ./prompts/.agent-prompt-vc.json with the current model-target map and a starter prompt (ticket-classifier.v1.txt + .meta.json).
  3. Edit a prompt: change ./prompts/ticket-classifier.v1.txt. Run agent-prompt-vc diff ./prompts/ticket-classifier.v1.txt. The CLI shows the substantive change (only the words that actually changed, with surrounding context).
  4. Bump: agent-prompt-vc bump ./prompts/ticket-classifier.v1.txt --reason "add 3 clarifying examples" --tested-with gpt-4o-2024-11-01 --est-cost-delta-pct +12 --bump minor. The CLI appends a changelog line and updates the meta file.
  5. Gate: agent-prompt-vc gate --strict --dir ./prompts --regression-manifest ./artifacts/regression.jsonl. The CLI returns OK or VIOLATION with the rule name, the prompt ID, and the detail. The Woodpecker step is one commands: block (see above).

Pairing the gate with the agent runtime (the canary rollout)

The gate is the pre-merge wall. The canary rollout is the post-merge wall. Pair the two and the agent runtime ships a new prompt version only after both walls pass:

  1. The runtime reads prompts/<name>.v<semver>.txt and pins to the content-hash ID. A change in the body changes the ID, and the runtime detects it on the next deploy.
  2. The runtime ships the new version on 1% of traffic for 10 minutes (configurable). It logs every response, every token count, every latency. The 19th-post circuit breaker watches the canary error rate; if the canary error rate exceeds the prior version by 5%, the breaker trips and rolls back.
  3. If the canary is green, the runtime ramps to 100%. If the canary is yellow (latency up 20%, error rate up 2%), the runtime holds at 1% and pages a human. If the canary is red, the runtime rolls back to the prior version automatically.
  4. The audit command runs on the canary's first deploy. If the prompt shows up as stale (model has moved past tested_with), the canary does not start. The runtime refuses the deploy until the prompt is re-tested against the new model.

The pairing is what makes prompt VC a runtime concern, not a code-review concern. The code review catches the change; the gate catches the policy violation; the canary catches the runtime regression; the audit catches the model drift. All four walls are independent, all four are automated, and all four feed into the same artifacts/ directory for post-incident review.
