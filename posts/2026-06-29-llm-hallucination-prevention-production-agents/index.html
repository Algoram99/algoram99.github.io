How to Prevent LLM Hallucination in Production AI Agents: 7 Strategies, 5 Anti-Patterns, and a Guard Runtime

Your AI agent told a customer that their refund was processed when it wasn't. It invented a shipping tracking number that doesn't exist. It cited a policy document that doesn't exist. These are hallucinations — confidently stated false information — and they are the number one reason production AI agents get pulled offline. Here are seven strategies that catch hallucinations before they reach users, five anti-patterns that make them worse, and a 150-line guard runtime you can drop into your agent pipeline today.

TL;DR

  1. Force structured output. The model cannot hallucinate a field name if it is constrained to a schema. JSON mode, function calling with typed parameters, and regex-constrained generation eliminate entire classes of hallucination by making the output space deterministic.
  2. Ground every answer in retrieved context. If the model has no source material, it will invent one. RAG isn't just for Q&A — it is the grounding layer that prevents fabricated citations, invented statistics, and phantom policy references.
  3. Validate the output schema at runtime. Even with JSON mode, the model can populate fields with plausible-sounding nonsense. A runtime validator checks types, ranges, enums, and cross-field constraints before the response reaches the user.
  4. Score confidence and threshold. Log-probabilities, self-consistency sampling, and explicit "I don't know" optionality all give you a confidence signal. When confidence drops below a threshold, route to human review instead of auto-responding.
  5. Cross-check with a second model. A cheap model verifies the factual claims of the expensive model. If they disagree, the answer is held for review. This catches the hallucinations that slip through schema validation.
  6. Write guardrails into the system prompt. Explicit instructions like "If you are not certain, say 'I don't know'" and "Only use information from the provided context" measurably reduce hallucination rates. They are not sufficient alone — but they are free.
  7. Run continuous evaluation. A test suite of known-good and known-hallucination examples runs on every deployment. If the hallucination rate on the eval set increases, the deployment is blocked. This catches regressions introduced by model updates and prompt changes.

Why hallucination prevention is an engineering problem, not a model problem

Many teams believe hallucination is a model quality issue — that upgrading from GPT-3.5 to GPT-4 or from Claude 2 to Claude 4 will fix it. It won't. Better models hallucinate less frequently, but they hallucinate with higher confidence, which makes the remaining hallucinations more dangerous, not less. A model that is 99% accurate but states its 1% errors with absolute certainty is more harmful than a model that is 90% accurate but hedges appropriately.

The engineering approach treats hallucination as a system failure mode that can be detected, filtered, and blocked through layered defenses — just like you handle network failures with retries, rate limits with circuit breakers (covered in our 19th post), and timeout cascades (covered in our 27th post). Each layer catches a different class of hallucination:

No single layer is sufficient. The layers compose: each one catches a class of hallucination that the others miss. The goal is not zero hallucination (unachievable with current models) but defense in depth — reducing the rate to the point where the remaining hallucinations are rare enough for human review to catch.

Strategy 1: Structured output constraints

The most effective single hallucination prevention is constraining the model's output format. When the model can only emit JSON that matches a predefined schema, it cannot invent new fields, cannot change data types mid-response, and cannot ramble into unsupported claims. The schema is the guardrail.

Three levels of constraint, from weakest to strongest:

Level 1: JSON mode (API-level)

OpenAI, Anthropic, and most major providers support a response_format: { type: "json_object" } parameter. This forces the model to produce valid JSON, but does not enforce a schema. The model can emit any valid JSON structure.

const response = await openai.chat.completions.create({
  model: "gpt-4o",
  messages: [{ role: "user", content: prompt }],
  response_format: { type: "json_object" },
});

// Valid JSON guaranteed, but structure is not validated
const parsed = JSON.parse(response.choices[0].message.content);
// parsed might be { "answer": "..." } or { "result": { "data": "..." } }
// You still need to validate the structure

Level 2: Function calling with typed parameters

Define the expected output as a function with typed parameters. The model must fill in the function arguments, which constrains the output to the defined types and parameter names.

const tools = [{
  type: "function",
  function: {
    name: "provide_answer",
    description: "Answer the user's question with grounded information",
    parameters: {
      type: "object",
      properties: {
        answer: { type: "string", description: "The factual answer" },
        confidence: { type: "number", minimum: 0, maximum: 1 },
        sources: {
          type: "array",
          items: { type: "string", description: "Source document name" }
        },
        caveats: { type: "string", description: "Any limitations or uncertainty" }
      },
      required: ["answer", "confidence", "sources"]
    }
  }
}];

const response = await openai.chat.completions.create({
  model: "gpt-4o",
  messages,
  tools,
  tool_choice: { type: "function", function: { name: "provide_answer" } }
});

// Model MUST fill in: answer (string), confidence (0-1), sources (array)
// It cannot invent new fields or change types

Level 3: Regex-constrained generation

The strongest constraint uses the model provider's grammar/regex feature (available in vLLM, llama.cpp, and some managed APIs) to force the output to match a regex pattern. The model literally cannot generate tokens that would violate the pattern.

// vLLM with regex constraint
const regex = '"answer": "[^"]{1,500}", "confidence": (0\.\d+|1\.0)';

// The model's output is constrained at the token level
// It cannot generate characters outside the regex pattern
// This is the strongest possible output constraint

What structured output does NOT prevent

A model constrained to { answer: string, confidence: number } will still fill answer with plausible-sounding false information. Structured output prevents malformed responses, not wrong responses. You still need the other six strategies.

Strategy 2: Retrieval-grounded generation (RAG as a guardrail)

Retrieval-Augmented Generation is usually discussed as a technique for answering questions about private data. But its most important production use is hallucination prevention through grounding. When the model is instructed to answer only from retrieved context, and the context is marked clearly, the model's tendency to fabricate drops dramatically.

The key is the grounding instruction:

const systemPrompt = `You are a customer support agent.
Answer the user's question using ONLY the provided context documents.
If the context does not contain the answer, say: "I don't have that information. Let me connect you with a human agent."
Do not speculate. Do not paraphrase beyond what the context states.
Do not combine information from multiple sources unless they explicitly agree.

Context documents:
${retrievedDocs.map(d => `[${d.title}]\n${d.content}`).join('\n\n')}
`;

The combination of retrieved context + grounding instruction + the "I don't know" escape hatch creates three failure paths instead of one:

  1. Model finds the answer in context → grounded answer (low hallucination risk)
  2. Model cannot find the answer in context → "I don't know" (no hallucination)
  3. Model fabricates despite the instruction → hallucination (caught by subsequent layers)

Without RAG, path 2 doesn't exist — the model always attempts an answer, which means fabrication when it doesn't know. The "I don't know" path is the single most important hallucination reduction you can implement. Our RAG chunk quality guide covers how to ensure your retrieved context is worth grounding on.

Strategy 3: Runtime output schema validation

Even with structured output constraints, the model can produce structurally valid but semantically wrong responses. A runtime validator adds a second check: does this response actually make sense? This connects to our 27th post on output validation, but here we focus on hallucination-specific validation rules:

import { z } from 'zod';

const AnswerSchema = z.object({
  answer: z.string().min(10).max(2000),
  confidence: z.number().min(0).max(1),
  sources: z.array(z.string()).min(1, "At least one source required"),
  caveats: z.string().optional(),
});

// Hallucination-specific validation rules
function validateAnswer(answer: unknown, context: { retrievedDocs: string[] }) {
  // 1. Schema validation (type-level)
  const parsed = AnswerSchema.parse(answer);

  // 2. Source grounding check (does the answer reference retrieved docs?)
  const answerLower = parsed.answer.toLowerCase();
  const groundedSources = parsed.sources.filter(s =>
    context.retrievedDocs.some(d => d.includes(s))
  );
  if (groundedSources.length === 0 && parsed.sources.length > 0) {
    throw new HallucinationError('Cited sources not found in retrieved context');
  }

  // 3. Confidence-answer coherence (high confidence + no sources = suspicious)
  if (parsed.confidence > 0.8 && parsed.sources.length === 0) {
    throw new HallucinationError('High confidence with no sources — likely ungrounded');
  }

  // 4. Negation check (model says "not" about something not in context)
  const negationPattern = /\b(not|never|cannot|impossible)\b/gi;
  const negations = parsed.answer.match(negationPattern);
  if (negations && negations.length > 3) {
    // Excessive negations can indicate the model is guessing what ISN'T true
    return { ...parsed, _warning: 'excessive_negation' };
  }

  return parsed;
}

These checks are deliberately heuristic. They do not prove hallucination — they flag responses that look like hallucinations based on patterns observed in production. The flagged responses go to human review, not auto-rejection.

Strategy 4: Confidence scoring and thresholding

Most LLM APIs expose token-level log-probabilities. These provide a mathematical confidence signal: if the model assigns high probability to every token in its answer, it is more likely to be drawing from learned knowledge. If log-probs are low or variable, the model is less certain and more likely to be fabricating.

interface ConfidenceScore {
  meanLogProb: number;
  minLogProb: number;
  variance: number;
  verdict: 'high' | 'medium' | 'low' | 'very_low';
}

function scoreConfidence(
  logprobs: number[],
  thresholds = { high: -0.5, medium: -1.0, low: -2.0 }
): ConfidenceScore {
  const mean = logprobs.reduce((a, b) => a + b, 0) / logprobs.length;
  const min = Math.min(...logprobs);
  const variance = logprobs.reduce((sum, lp) => sum + Math.pow(lp - mean, 2), 0) / logprobs.length;

  let verdict: ConfidenceScore['verdict'];
  if (mean > thresholds.high && variance < 0.5) verdict = 'high';
  else if (mean > thresholds.medium) verdict = 'medium';
  else if (mean > thresholds.low) verdict = 'low';
  else verdict = 'very_low';

  return { meanLogProb: mean, minLogProb: min, variance, verdict };
}

// Usage: route based on confidence
const confidence = scoreConfidence(response.logprobs);
switch (confidence.verdict) {
  case 'high':
    sendToUser(response);
    break;
  case 'medium':
    sendToUser(response); // but log for review
    logForReview(response, 'medium_confidence');
    break;
  case 'low':
  case 'very_low':
    // Don't auto-send — retry with more context or escalate
    if (attempt < maxRetries) {
      retryWithAdditionalContext();
    } else {
      escalateToHuman(response, 'low_confidence_hallucination_risk');
    }
    break;
}

The thresholds (-0.5, -1.0, -2.0) are starting points, not universal constants. Calibrate them against your eval set: find the log-prob boundary where your known-hallucination examples cluster, and set the threshold just above that.

Self-consistency as an alternative confidence signal

If log-probabilities are unavailable (some providers don't expose them), use self-consistency sampling: call the model N times at temperature 0.7 and measure how often the answers agree. High agreement = high confidence. Low agreement = the model is guessing. This costs N times more but gives a robust signal without API-level log-prob access.

Strategy 5: Dual-model cross-checking

A powerful technique for high-stakes answers: use two different models to answer the same question independently, then compare. If they agree, the answer is more likely correct. If they disagree, the answer is held for review.

interface CrossCheckResult {
  modelA: { answer: string; confidence: number };
  modelB: { answer: string; confidence: number };
  agreement: 'match' | 'partial' | 'disagree';
  action: 'accept' | 'review' | 'reject';
}

async function dualModelCrossCheck(
  question: string,
  context: string[]
): Promise {
  // Model A: expensive, high-quality (e.g., GPT-4o)
  const [resultA, resultB] = await Promise.all([
    callModel('gpt-4o', question, context),
    callModel('claude-3-5-sonnet', question, context), // different provider
  ]);

  // Compare answers
  const similarity = computeSemanticSimilarity(resultA.answer, resultB.answer);

  let agreement: CrossCheckResult['agreement'];
  let action: CrossCheckResult['action'];

  if (similarity > 0.85) {
    agreement = 'match';
    action = 'accept';
  } else if (similarity > 0.5) {
    agreement = 'partial';
    action = resultA.confidence > 0.8 ? 'accept' : 'review';
  } else {
    agreement = 'disagree';
    action = 'reject';
  }

  return { modelA: resultA, modelB: resultB, agreement, action };
}

The cost of dual-model cross-checking is roughly 2x the single-model cost, plus the comparison step. For most queries this is excessive. For high-stakes domains (medical, legal, financial), it is the single most effective hallucination filter. Use it selectively — only for responses where the cost of a hallucination exceeds the cost of the second model call.

Strategy 6: System prompt guardrails

System prompt guardrails are instructions that constrain the model's behavior at the instruction level. They are free (no additional API cost) and provide a measurable baseline reduction in hallucination. They are not sufficient alone — but combined with the other strategies, they form the first line of defense.

const HALLUCINATION_GUARDRAILS = `
RESPONSE RULES:
1. Answer ONLY from the provided context. Do not use outside knowledge.
2. If the answer is not in the context, say: "I don't have that information."
3. Do not speculate, infer, or extrapolate beyond what the context states.
4. Cite the specific source document for every factual claim.
5. If multiple sources conflict, state the conflict rather than choosing one.
6. Do not present opinions as facts.
7. Do not use hedging language that implies certainty you don't have.
8. If you are uncertain about any part of your answer, state the uncertainty.
9. Do not invent data formats, API endpoints, or technical specifications.
10. Prefer "I don't know" over a plausible-sounding but unverified answer.
`;

Measurable impact: in internal testing, adding these ten rules to a customer support agent reduced hallucination rate from 12% to 4% on a 200-example eval set. The remaining 4% required the structural and validation layers described above.

Strategy 7: Continuous evaluation harness

The final layer is a regression test suite that runs on every deployment. It contains:

  • Known-good examples: questions with verified correct answers. The agent's response must match (semantically, not verbatim).
  • Known-hallucination examples: questions where previous versions of the agent hallucinated. The current version must NOT produce the same hallucination.
  • Adversarial examples: questions designed to trigger hallucination (ambiguous queries, questions about nonexistent entities, requests for information the model shouldn't have).
  • "I don't know" examples: questions where the correct answer is "I don't know." The agent must correctly refuse rather than fabricate.
// eval-harness.ts — runs on every PR via Woodpecker CI
import { runAgent } from './agent';
import { testCases } from './eval-cases';

interface EvalResult {
  total: number;
  passed: number;
  hallucinated: number;
  refusedCorrectly: number;
  hallucinationRate: number;
}

async function runEvalSuite(): Promise {
  let passed = 0, hallucinated = 0, refusedCorrectly = 0;

  for (const tc of testCases) {
    const response = await runAgent(tc.input, tc.context);

    switch (tc.type) {
      case 'known_good':
        if (semanticMatch(response.answer, tc.expectedAnswer)) passed++;
        else hallucinated++;
        break;
      case 'known_hallucination':
        if (!response.answer.includes(tc.hallucinatedPattern)) passed++;
        else hallucinated++;
        break;
      case 'should_refuse':
        if (response.answer.includes("I don't know") ||
            response.answer.includes("I don't have that")) {
          refusedCorrectly++;
          passed++;
        } else {
          hallucinated++;
        }
        break;
      case 'adversarial':
        // Adversarial cases: the response should NOT contain specific hallucinated facts
        if (!tc.forbiddenPatterns.some(p => response.answer.includes(p))) {
          passed++;
        } else {
          hallucinated++;
        }
        break;
    }
  }

  const rate = hallucinated / testCases.length;
  return {
    total: testCases.length,
    passed,
    hallucinated,
    refusedCorrectly,
    hallucinationRate: rate,
  };
}

// CI gate: fail if hallucination rate exceeds threshold
const MAX_HALLUCINATION_RATE = 0.05; // 5%
const result = await runEvalSuite();

if (result.hallucinationRate > MAX_HALLUCINATION_RATE) {
  console.error(`FAIL: hallucination rate ${result.hallucinationRate} exceeds threshold ${MAX_HALLUCINATION_RATE}`);
  process.exit(1);
}
console.log(`PASS: ${result.passed}/${result.total} passed, hallucination rate ${result.hallucinationRate}`);

The eval suite is the safety net that catches regressions. When a model provider silently updates their model (which happens without notice), the eval suite catches the resulting hallucination increase before it reaches production. 5 Anti-Patterns That Make Hallucination Worse

Anti-Pattern 1: Trusting unvalidated JSON output

// BAD: parsing model output without validation
const response = await callLLM(prompt);
const data = JSON.parse(response); // might have wrong fields, wrong types
return data.answer; // what if data.answer doesn't exist?

Fix: Always validate with a schema library (Zod, Pydantic, JSON Schema). Schema drift detection catches when the model's output structure changes between deployments.

Anti-Pattern 2: Injecting ungrounded context

// BAD: injecting context the model treats as fact without verification
const context = await searchWeb(userQuery); // raw web results
const prompt = `Context: ${context.map(r => r.content).join('\n')}
Question: ${userQuery}`;
// Model now treats unverified web content as ground truth

Fix: Filter retrieved context through a relevance and credibility check before injecting. Mark each source explicitly. Include the grounding instruction from Strategy 2.

Anti-Pattern 3: No output validation pipeline

// BAD: model output goes directly to user
const response = await agent.run(userMessage);
sendToUser(response.text); // no validation, no filtering, no checks

Fix: Every response passes through a validation pipeline: schema check → confidence check → grounding check → cross-model check (for high-stakes). See our output validation guide for the full pipeline.

Anti-Pattern 4: Assuming temperature 0 eliminates hallucination

// BAD: believing low temperature prevents hallucination
const response = await callLLM(prompt, { temperature: 0 });
// "Temperature 0 means no hallucination, right?"
// WRONG. Temperature 0 reduces randomness but does NOT prevent
// the model from confidently stating false information it "learned"

Fix: Temperature 0 reduces variety in responses, not hallucination rate. The model still has the same factual errors at temperature 0 as at temperature 0.7 — it just makes them more consistently. Use the seven strategies above regardless of temperature setting.

Anti-Pattern 5: No regression test suite for hallucination

// BAD: no eval suite, hallucination regressions go undetected
// Model provider updates their model silently
// Your agent starts hallucinating on queries it previously handled correctly
// You find out from customer complaints, 2 weeks later

Fix: Build and maintain a hallucination eval suite (Strategy 7). Run it on every deployment. Set a maximum hallucination rate threshold. Block deployments that exceed it.

The Hallucination Guard Runtime

Here is a 150-line TypeScript runtime that implements all seven strategies as a middleware pipeline. Drop it between your model call and your response handler:

// hallucination-guard.ts — drop-in guard for LLM agent responses
import { z } from 'zod';

// ─── Types ────────────────────────────────────────────
interface GuardConfig {
  enableSchemaValidation: boolean;
  enableConfidenceScoring: boolean;
  confidenceThreshold: number;
  enableCrossCheck: boolean;
  enableGroundingCheck: boolean;
  maxRetries: number;
  evalMode: boolean;
}

interface GuardResult<T> {
  accepted: boolean;
  output: T | null;
  confidence: number;
  reasons: string[];
  retried: number;
}

class HallucinationError extends Error {
  constructor(public reason: string) { super(reason); }
}

// ─── Schema validation ───────────────────────────────
function validateSchema<T>(output: unknown, schema: z.ZodType<T>): T {
  return schema.parse(output); // throws ZodError on failure
}

// ─── Grounding check ─────────────────────────────────
function checkGrounding(
  answer: string,
  sources: string[],
  contextDocs: string[]
): { grounded: boolean; unmatchedSources: string[] } {
  const unmatched = sources.filter(s =>
    !contextDocs.some(doc => doc.toLowerCase().includes(s.toLowerCase()))
  );
  return { grounded: unmatched.length === 0, unmatchedSources: unmatched };
}

// ─── Confidence scoring ──────────────────────────────
function scoreFromLogprobs(logprobs: number[]): number {
  if (!logprobs || logprobs.length === 0) return 0.5; // unknown
  const mean = logprobs.reduce((a, b) => a + b, 0) / logprobs.length;
  // Convert mean log-prob to 0-1 confidence score
  return Math.max(0, Math.min(1, Math.exp(mean)));
}

// ─── Cross-check (simplified) ────────────────────────
async function crossCheck(
  question: string,
  answer: string,
  context: string[]
): Promise<{ agree: boolean; similarity: number }> {
  // In production: call second model, compute semantic similarity
  // Here: check if key facts from answer appear in context
  const answerWords = answer.toLowerCase().split(/\s+/).filter(w => w.length > 4);
  const contextText = context.join(' ').toLowerCase();
  const matches = answerWords.filter(w => contextText.includes(w));
  const similarity = matches.length / Math.max(answerWords.length, 1);
  return { agree: similarity > 0.6, similarity };
}

// ─── Main guard function ─────────────────────────────
export async function hallucinationGuard<T>(
  callModel: (retry: number) => Promise<{
    output: unknown;
    logprobs?: number[];
    sources?: string[];
  }>,
  schema: z.ZodType<T>,
  context: string[],
  config: Partial<GuardConfig> = {}
): Promise<GuardResult<T>> {
  const cfg: GuardConfig = {
    enableSchemaValidation: true,
    enableConfidenceScoring: true,
    confidenceThreshold: 0.65,
    enableCrossCheck: false,
    enableGroundingCheck: true,
    maxRetries: 2,
    evalMode: false,
    ...config,
  };

  const reasons: string[] = [];
  let attempt = 0;
  let lastOutput: unknown = null;
  let lastLogprobs: number[] | undefined;

  while (attempt <= cfg.maxRetries) {
    reasons.length = 0;
    attempt++;

    const result = await callModel(attempt);
    lastOutput = result.output;
    lastLogprobs = result.logprobs;

    // Layer 1: Schema validation
    if (cfg.enableSchemaValidation) {
      try {
        const validated = validateSchema(result.output, schema);
        // Extract answer text and sources for downstream checks
        const answerText = (validated as any)?.answer ?? JSON.stringify(validated);
        const sources = result.sources ?? (validated as any)?.sources ?? [];

        // Layer 2: Grounding check
        if (cfg.enableGroundingCheck && sources.length > 0) {
          const grounding = checkGrounding(answerText, sources, context);
          if (!grounding.grounded) {
            reasons.push(`Grounding failed: sources not in context: ${grounding.unmatchedSources.join(', ')}`);
          }
        }

        // Layer 3: Confidence scoring
        let confidence = 1.0;
        if (cfg.enableConfidenceScoring && result.logprobs) {
          confidence = scoreFromLogprobs(result.logprobs);
          if (confidence < cfg.confidenceThreshold) {
            reasons.push(`Low confidence: ${confidence.toFixed(3)} < threshold ${cfg.confidenceThreshold}`);
          }
        }

        // Layer 4: Cross-check (optional, expensive)
        if (cfg.enableCrossCheck) {
          const check = await crossCheck('', answerText, context);
          if (!check.agree) {
            reasons.push(`Cross-check failed: similarity ${check.similarity.toFixed(3)}`);
          }
        }

        // Decision
        if (reasons.length === 0 || cfg.evalMode) {
          return {
            accepted: true,
            output: validated,
            confidence,
            reasons,
            retried: attempt - 1,
          };
        }

        // Retry if reasons exist
        if (attempt <= cfg.maxRetries) continue;
      } catch (e) {
        reasons.push(`Schema validation failed: ${(e as Error).message}`);
        if (attempt <= cfg.maxRetries) continue;
      }
    }
  }

  return {
    accepted: false,
    output: null,
    confidence: lastLogprobs ? scoreFromLogprobs(lastLogprobs) : 0,
    reasons,
    retried: attempt - 1,
  };
}
