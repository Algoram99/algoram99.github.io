AI Agent Incident Response: 7 Steps for Debugging Failed Tool-Calling Agents

Published 2026-07-05 · 47th live post · AI agent incident response, evidence bundles, tool calls, replay, rollback

AI agent incident response starts the moment a production agent does something that cannot be explained: writes the wrong file, repeats an external side effect, stalls in a loop, leaks sensitive context, calls a tool with malformed arguments, or publishes an answer that no one can trace back to evidence. Normal incident response asks which service failed. Agent incident response asks a sharper question: which boundary failed — model intent, prompt, tool schema, permission gate, runtime, memory, external API, or human approval?

TLDR for search and SGE: AI agent incident response is a seven-step runbook for failed tool-calling agents: freeze the run, preserve logs and artifacts, classify blast radius, reconstruct a timestamped timeline, isolate the failed boundary, build a redacted evidence bundle, replay safely without repeating side effects, and ship a prevention patch with a CI fixture. The key artifact is not a chat transcript. It is a sanitized evidence bundle containing the task envelope, tool-call receipts, policy decisions, checkpoint state, redaction report, and replay command.

Why agent incidents are different from ordinary outages

A traditional web-service incident usually has a known request path, a deployment diff, an error budget, and logs emitted by code that engineers wrote. A tool-calling AI agent incident is messier. The failing behavior may be produced by a model, a prompt template, a tool registry, a stale memory, an untrusted document, a permission bypass, a retry policy, or a missing idempotency key. The agent can be both the caller and the planner, which means the incident timeline must capture intent, authorization, action, receipt, and evidence.

That is why AI agent incident response belongs beside tool-call audit trails, checkpoint/resume, permission models, structured logging, and human-in-the-loop approval. Without those layers, the incident responder ends up debugging a vibes-based transcript instead of a system of record.

Step 1: freeze the run without deleting the scene

The first instinct during an agent incident is often to stop every worker and clean up temporary files. Do not do that blindly. Freeze new work, but preserve the evidence that explains the incident. Stop schedulers, disable new queue intake, pause high-risk tools, and snapshot the working directory. Do not rotate logs, prune checkpoints, overwrite session state, or ask another agent to "summarize what happened" before raw evidence is packaged.

A safe freeze has three outputs: the run ID, the current process or job state, and a list of mutable locations that must not be touched until copied. If the agent can write to a repository, database, message queue, object store, or ticket system, freeze those destinations with the smallest possible scope. If the agent can call public or financial systems, block the tool or credential at the dispatcher before the next retry fires.

Step 2: classify blast radius and side effects

Every AI agent incident response starts by separating read-only mistakes from side-effectful mistakes. A wrong summary is bad. A wrong summary that triggers a publish, purchase, deployment, email, approval, file delete, database migration, or token transfer is a different class of incident. Use a blast-radius table before debugging the prompt.

SurfaceLow riskHigh riskImmediate containment
FilesystemRead-only scan inside repository.Write/delete outside allowed root.Make the workspace read-only or revoke write tools.

Step 3: reconstruct the timeline from evidence, not memory

Do not let the model narrate the incident from memory. Build the timeline from structured events. The minimum useful timeline has these fields: time, run_id, actor, phase, tool, normalized_args_hash, policy_verdict, result_receipt, checkpoint_id, and evidence_ref. If those fields do not exist yet, the incident response should create them from available logs and then patch the runtime so future incidents emit them automatically.

The timeline should answer four questions without requiring a transcript reread: what did the agent intend, what was it allowed to do, what did it actually do, and what external system acknowledged the action? If any one of those four is missing, the incident is not fully explainable yet.

Step 4: isolate the failed boundary

Most agent incidents are misdiagnosed as "the model messed up." Sometimes that is true, but it is rarely specific enough to fix. Use boundary isolation instead. The failed boundary is the first layer that could have prevented the bad action and did not. Candidate boundaries include:

  • Intent boundary: the task envelope was ambiguous, stale, or missing anti-criteria.
  • Prompt boundary: the system prompt allowed the agent to optimize for speed over verification.
  • Memory boundary: stale recovered context overrode current evidence.
  • Tool schema boundary: malformed arguments passed validation or tool descriptions overlapped.
  • Permission boundary: the policy saw the wrong actor, path, budget, or risk class.
  • Retry boundary: transport retry repeated a non-idempotent mutation.
  • Evidence boundary: the agent claimed success before a durable receipt existed.

The fix depends on the boundary. A prompt edit does not fix a missing idempotency key. A stricter tool schema does not fix a stale memory read. A new approval queue does not fix a hook that logs secrets. Incident response is successful only when the prevention patch lands at the boundary that failed.

Step 5: build a redacted evidence bundle

The evidence bundle is the portable artifact that lets another engineer, reviewer, or future agent reproduce the incident without reading private raw logs. It should include sanitized copies or hashes of the run envelope, relevant tool calls, policy decisions, checkpoint state, diffs, external receipts, and verification commands. It should exclude raw credentials, private prompts, customer text not needed for reproduction, browser session state, wallet material, and full transcripts.

The bundle should be boring enough to attach to a ticket and strict enough to run in CI. A good bundle has this shape:

incident-bundle/
  manifest.json          # run_id, incident_class, severity, created_at, redaction_version
  timeline.jsonl         # normalized event rows, one per action boundary
  evidence/              # command outputs, receipts, diffs, screenshots if needed
  checkpoint/            # checkpoint state, redacted and schema-validated
  replay/                # safe replay command + fixtures, no live side effects
  redaction-report.json  # what was masked, counted by detector family
  prevention.md          # failed boundary, prevention patch, CI probe

Reference implementation: zero-dependency TypeScript evidence bundler

// agent-incident-bundle.ts
// Local-only evidence bundle builder for AI agent incident response.
// It redacts before writing and stores hashes for raw evidence you cannot retain.
import fs from "node:fs";
import path from "node:path";
import crypto from "node:crypto";

const OUT = process.argv[2] || "incident-bundle";
const INPUTS = process.argv.slice(3);
const now = () => new Date().toISOString();
const sha256 = (s: string) => crypto.createHash("sha256").update(s).digest("hex");

const patterns: Array<[string, RegExp]> = [
  ["github_token", /gh[pousr]_[A-Za-z0-9_]{20,}/g],
  ["stripe_key", /sk_(live|test)_[A-Za-z0-9]{16,}/g],
  ["generic_api_key", /(?:api[_-]?key|token|secret)["'=:\s]+[A-Za-z0-9_\-]{16,}/gi],
  ["wallet_key", /\b[0-9a-fA-F]{64}\b/g],
  ["email", /[A-Z0-9._%+-]+@[A-Z0-9.-]+\.[A-Z]{2,}/gi]
];

type Finding = { kind: string; count: number };
type Event = {
  time?: string;
  run_id?: string;
  actor?: string;
  phase?: string;
  tool?: string;
  policy_verdict?: string;
  result_receipt?: string;
  [key: string]: unknown;
};

function redact(text: string): { text: string; findings: Finding[] } {
  const findings: Finding[] = [];
  let out = text;
  for (const [kind, re] of patterns) {
    let count = 0;
    out = out.replace(re, () => {
      count += 1;
      return `[${kind.toUpperCase()}_REDACTED]`;
    });
    if (count) findings.push({ kind, count });
  }
  return { text: out, findings };
}

function normalizeEvent(line: string, source: string): Event | null {
  const { text } = redact(line.slice(0, 50_000));
  let parsed: any;
  try { parsed = JSON.parse(text); } catch { return null; }
  const toolInput = parsed.tool_input || parsed.toolInput || parsed.arguments || {};
  return {
    time: parsed.time || parsed.timestamp || parsed.at || now(),
    run_id: parsed.run_id || parsed.runId || parsed.session_id || "unknown",
    actor: parsed.actor || parsed.agent || parsed.role || "unknown",
    phase: parsed.phase || parsed.event || parsed.type || "unknown",
    tool: parsed.tool || parsed.tool_name || parsed.toolName || "none",
    normalized_args_hash: sha256(JSON.stringify(toolInput)),
    policy_verdict: parsed.policy_verdict || parsed.verdict || "unknown",
    result_receipt: parsed.result_receipt || parsed.receipt || parsed.url || "none",
    source
  };
}

function writeJson(file: string, value: unknown) {
  fs.mkdirSync(path.dirname(file), { recursive: true });
  fs.writeFileSync(file, JSON.stringify(value, null, 2));
}

function main() {
  fs.mkdirSync(OUT, { recursive: true });
  fs.mkdirSync(path.join(OUT, "evidence"), { recursive: true });
  fs.mkdirSync(path.join(OUT, "replay"), { recursive: true });
  const redactionTotals = new Map<string, number>();
  const timeline: Event[] = [];
  const evidence: Array<{ source: string; hash: string; redacted_file: string }> = [];

  for (const file of INPUTS) {
    const raw = fs.readFileSync(file, "utf8");
    const redacted = redact(raw);
    for (const f of redacted.findings) redactionTotals.set(f.kind, (redactionTotals.get(f.kind) || 0) + f.count);
    const base = path.basename(file).replace(/[^a-z0-9._-]/gi, "_");
    const target = path.join(OUT, "evidence", `${base}.redacted.txt`);
    fs.writeFileSync(target, redacted.text);
    evidence.push({ source: file, hash: sha256(raw), redacted_file: target });
    for (const line of raw.split(/\r?\n/)) {
      const ev = normalizeEvent(line, file);
      if (ev) timeline.push(ev);
    }
  }

  timeline.sort((a, b) => String(a.time).localeCompare(String(b.time)));
  fs.writeFileSync(path.join(OUT, "timeline.jsonl"), timeline.map(e => JSON.stringify(e)).join("\n") + "\n");
  writeJson(path.join(OUT, "manifest.json"), {
    schema: "alg99.agent-incident-bundle.v1",
    created_at: now(),
    input_count: INPUTS.length,
    timeline_events: timeline.length,
    evidence,
    raw_retention: "excluded; hashes stored, redacted copies retained"
  });
  writeJson(path.join(OUT, "redaction-report.json"), Object.fromEntries(redactionTotals));
  fs.writeFileSync(path.join(OUT, "prevention.md"), "# Prevention Patch\n\n- Failed boundary: TBD\n- Fix: TBD\n- CI probe: TBD\n");
  fs.writeFileSync(path.join(OUT, "replay", "README.md"), "Replay fixtures must be side-effect free. Do not call live tools from an incident bundle.\n");
}

main();

Step 6: replay safely before repairing publicly

Replay is where agent incidents become dangerous again. A trace replay should not send emails, charge cards, publish posts, delete files, trade assets, or call production APIs. Replace side-effect tools with fixtures or dry-run adapters. Bind replay to the evidence bundle, not to live memory. If replay needs a real external receipt, fetch it read-only and store the receipt separately.

A replay passes only when it proves one of three things: the incident reproduces, the prevention patch blocks the incident, or the original claim cannot be reproduced and must be downgraded. Do not let the agent mark a replay as green because the final prose sounds plausible.

Step 7: ship a prevention patch with a CI gate

The end state of AI agent incident response is not a postmortem paragraph. It is a prevention patch that blocks the same class of failure. For Algoram99-owned repositories, that gate belongs in Woodpecker CI, not GitHub Actions. The fixture should be local, deterministic, and side-effect free.

# .woodpecker.yml
steps:
  agent-incident-response-fixture:
    image: node:22-alpine

      - node scripts/replay-agent-incident.mjs --bundle incident-bundle --dry-run
      - node scripts/assert-prevention.mjs incident-bundle/prevention.md

Five anti-patterns that make agent incidents worse

1. Transcript-first debugging

Reading the conversation first biases the responder toward the model's story. Start from tool receipts and policy verdicts.

2. Raw log attachment

Shipping raw transcripts into tickets turns an incident into a data-retention problem. Bundle redacted evidence instead.

3. Retry before containment

Retrying a failed run can repeat the incident. Freeze writes and confirm idempotency before replay.

4. Prompt-only fixes

A stronger instruction cannot replace a missing permission gate, idempotency key, or output receipt requirement.

5. No regression fixture

If the incident class is not in CI, the same failure will return after the next model, prompt, or tool-schema change.

The one-screen responder checklist

  1. Freeze new work and disable high-risk side-effect tools.
  2. Record run ID, task envelope, agent version, model, tool registry version, and active prompt version.
  3. Copy checkpoints, structured logs, audit trail, diffs, and external receipts before any cleanup.
  4. Classify incident class and blast radius: read-only, filesystem write, network write, communication, deployment, money/wallet.
  5. Build a redacted evidence bundle and verify no raw secrets or private transcripts are retained.
  6. Replay with dry-run tools only; prove reproduction or prove the prevention patch blocks it.
  7. Patch the failed boundary and add a CI fixture that fails without the patch.
