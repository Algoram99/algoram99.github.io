How to Build an MCP Server From Scratch (TypeScript, Tested, Production-Ready)

TL;DR. An MCP server is a JSON-RPC program that exposes three things to an AI host: tools (actions the model can call), resources (read-only data the host injects into context), and prompts (templated instructions the user can trigger). This post walks you from npm init to a tested, security-reviewed install in nine steps: pin the SDK, pick a transport, define all three shapes, validate every input with Zod, build the error envelope, apply the security boundary, write a 30-test parity gate, add a CI gate, and ship install recipes for Claude Desktop, Cursor, and Continue. The reference server is 220 lines; the inspector smoke harness is 30 lines; the test gate is 30 tests covering every tool, resource, prompt, and error path. The four MCP-related products at the bottom of the post (Starter Kit, Tester, Poison Scanner, Supply Chain Audit) cover the rest of the lifecycle.

Why MCP, and why now

The Model Context Protocol is the JSON-RPC contract that lets an AI host (Claude Desktop, Cursor, Continue, Zed, custom agents) talk to a server you control. It is the difference between an agent that can call your tools and an agent that can only talk about them. A working MCP server means the model can read your files, query your database, hit your API, and call your scripts in a way the host can audit, log, and revoke.

The protocol is stable, the SDK is mature, and the host list is growing. The bar for shipping a "good" MCP server in 2026 is not "does it work" — it is "does it pass security review, does it have 30+ tests, and does it install in three hosts with a one-paragraph recipe." This post gets you there.

Step 1: Initialize the project and pin the SDK

Start with a clean TypeScript project. The SDK is the contract with the host; do not let a transitive bump drift it.

mkdir my-mcp-server && cd my-mcp-server
npm init -y
npm install @modelcontextprotocol/sdk zod
npm install -D typescript @types/node vitest
npx tsc --init --target ES2022 --module nodenext --moduleResolution nodenext --strict

Pin the SDK in package.json to the exact minor version you tested against ("@modelcontextprotocol/sdk": "1.0.4", no ^). Anything you drift from the protocol layer is what breaks host integration first, and the failure mode is "the host silently refuses to call your tool."

Step 2: Pick a transport: stdio for local, Streamable HTTP for remote

MCP supports two transports. Pick the right one before you write a line of tool code, because the runtime shape is different.

TransportWhen to useHost config example
StdioServerTransportLocal install (Claude Desktop, Cursor, Continue, Zed) — the server runs as a child process of the host"command": "node", "args": ["dist/index.js"]
StreamableHTTPServerTransportRemote install (hosted server, shared team install) — the server runs on its own host with auth"url": "https://mcp.example.com/mcp" + bearer token
Pitfall: Mixing transports is the single most common deployment failure. A server written for stdio that is then exposed over HTTP loses process isolation, which means a hostile prompt injection can hit your host filesystem. If you need both, run two server entrypoints that share a core library — do not flip a transport flag in one process.

Step 3: Define the three tool shapes: resources, prompts, tools

MCP has exactly three primitives the host can use. Ship at least one of each so the host learns your patterns.

  • Resources — read-only data the host can inject into context. Examples: a project file, a config block, a database row. Identified by URI.
  • Prompts — templated instructions the user can trigger. Examples: "review this PR," "summarize this log." Accept arguments.
  • Tools — actions the model can call. Examples: create_issue, run_query, deploy_preview. Accept arguments, return content.

The reference server below ships one of each against a tiny in-memory todo store. Replace the store with your real backend and you have a working server.

import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer(
  { name: "todo-mcp", version: "1.0.0" },
  { capabilities: { resources: {}, prompts: {}, tools: {} } }
);

const todos: Record<string, { id: string; text: string; done: boolean }> = {};

// Resource: list of all todos
server.resource(
  "todos",
  "todos://list",
  async (uri) => ({
    contents: [{
      uri: uri.href,
      text: JSON.stringify(Object.values(todos), null, 2)
    }]
  })
);

// Prompt: review pending todos
server.prompt(
  "review-todos",
  { filter: z.enum(["all", "pending", "done"]).default("pending") },
  ({ filter }) => ({
    messages: [{
      role: "user",
      content: {
        type: "text",
        text: `Review my ${filter} todos and suggest the next 3 to work on.`
      }
    }]
  })
);

// Tool: add a todo
server.tool(
  "add_todo",
  { text: z.string().min(1).max(500) },
  async ({ text }) => {
    const id = `t_${Date.now().toString(36)}`;
    todos[id] = { id, text, done: false };
    return {
      content: [{ type: "text", text: `Created todo ${id}: ${text}` }]
    };
  }
);

// Tool: mark a todo done
server.tool(
  "complete_todo",
  { id: z.string().regex(/^t_[a-z0-9]+$/) },
  async ({ id }) => {
    if (!todos[id]) {
      return {
        content: [{ type: "text", text: `No todo with id ${id}` }],
        isError: true
      };
    }
    todos[id].done = true;
    return {
      content: [{ type: "text", text: `Marked ${id} done` }]
    };
  }
);

const transport = new StdioServerTransport();
await server.connect(transport);
console.error("todo-mcp running on stdio");

Step 4: Validate every input with Zod before the tool runs

MCP tools receive untrusted JSON from the model. The model will pass null for a required string, it will pass a 10MB string for a 500-char field, and it will pass a date as a string when your schema wants a number. Validate at the boundary with Zod, return structured errors, and never let an exception escape the tool handler.

Notice in the reference above: z.string().min(1).max(500) on the add tool, z.string().regex(/^t_[a-z0-9]+$/) on the complete tool. Those constraints are not documentation — they are the contract. The Zod schema in the tool definition is what the host's UI shows the model; the Zod parse inside the handler is what enforces it.

Pitfall: Defining the tool with a loose schema (z.any() or z.string() with no bounds) and validating inside the handler is the most common source of host-side "tool crashed" errors. The host shows the user whatever the Zod schema says; if it says any, the model passes garbage and your handler throws.

Step 5: Build the error envelope the host actually surfaces

The MCP content envelope is the contract for tool output. Two shapes, both with a content array of typed parts:

// Success
return { content: [{ type: "text", text: "Created todo t_abc: buy milk" }] };

// Error (handled, not thrown)
return {
  content: [{ type: "text", text: "No todo with id t_xyz" }],
  isError: true
};

The host renders content[].text in the conversation. The isError: true flag tells the host to surface the text as a tool error rather than treating it as a successful model-visible result. A thrown exception inside the tool handler shows up as a generic "Tool failed" with no diagnostic — the user cannot tell whether it was a bug, a network error, or a bad argument. Wrap every known failure mode in a return { content, isError: true }.

Step 6: Apply the security boundary checklist

This is the step that turns a working server into one that passes security review. Run through the checklist before you ship:

CheckWhyWhat fails if you skip it
No child_process.exec / no shell-outPrompt injection turns shell-out into RCEServer executes attacker-controlled commands as your user
No reading env vars the host did not declareEnv vars leak across server boundaries and through process listingsServer reads secrets it was never authorized to see
No writing outside an allowlisted directoryPath traversal via filenames is trivialServer overwrites ~/.ssh/authorized_keys via ../../../
No following symlinksSymlink following defeats any allowlistAllowlisted /data/ follows a symlink to /etc/
No network access by defaultEvery network call is an exfiltration channelServer POSTs ~/.aws/credentials to attacker host
Validate every path with path.resolve + prefix checkPath traversal via .. segments is the defaultServer reads /etc/passwd via ../../etc/passwd
Use Zod.string().max(N) on every free-form inputUnbounded inputs are DoS vectorsServer OOMs on a 500MB string from the model

The MCP Poison Scanner checks #1, #2, #5, and #7 automatically across your source tree. The MCP Supply Chain Audit checks #3, #4, and #6 against your config. Both are run in the CI gate in Step 8.

Step 7: Write a 30-test parity gate

Test every tool, every resource, every prompt, every error path. Use the real in-memory MCP client from the SDK test utils — do not mock the protocol layer. A test that mocks JSON-RPC is a test that does not catch protocol drift when the SDK ships a new minor version.

import { describe, it, expect, beforeEach } from "vitest";
import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { InMemoryTransport } from "@modelcontextprotocol/sdk/inMemory.js";
import { createServer } from "../src/server.js";

let client: Client;
let server: ReturnType<typeof createServer>;

beforeEach(async () => {
  server = createServer();
  client = new Client({ name: "test", version: "0.0.1" });
  const [a, b] = InMemoryTransport.createLinkedPair();
  await Promise.all([server.connect(a), client.connect(b)]);
});

describe("tools", () => {
  it("add_todo creates a todo", async () => {
    const r = await client.callTool({ name: "add_todo", arguments: { text: "buy milk" } });
    expect(r.content[0].text).toMatch(/Created todo t_/);
  });
  it("add_todo rejects empty text", async () => {
    await expect(
      client.callTool({ name: "add_todo", arguments: { text: "" } })
    ).rejects.toThrow();
  });
  it("add_todo rejects 501-char text", async () => {
    await expect(
      client.callTool({ name: "add_todo", arguments: { text: "x".repeat(501) } })
    ).rejects.toThrow();
  });
  it("complete_todo marks done", async () => {
    const c = await client.callTool({ name: "add_todo", arguments: { text: "x" } });
    const id = c.content[0].text.match(/t_[a-z0-9]+/)![0];
    const r = await client.callTool({ name: "complete_todo", arguments: { id } });
    expect(r.content[0].text).toBe(`Marked ${id} done`);
  });
  it("complete_todo on unknown id returns isError", async () => {
    const r = await client.callTool({ name: "complete_todo", arguments: { id: "t_zzz" } });
    expect(r.isError).toBe(true);
  });
  it("complete_todo rejects malformed id", async () => {
    await expect(
      client.callTool({ name: "complete_todo", arguments: { id: "../etc" } })
    ).rejects.toThrow();
  });
});

describe("resources", () => {
  it("todos://list returns the todo array", async () => {
    await client.callTool({ name: "add_todo", arguments: { text: "a" } });
    const r = await client.readResource({ uri: "todos://list" });
    const list = JSON.parse(r.contents[0].text as string);
    expect(list).toHaveLength(1);
  });
  it("todos://list is empty before any add", async () => {
    const r = await client.readResource({ uri: "todos://list" });
    expect(JSON.parse(r.contents[0].text as string)).toEqual([]);
  });
});

describe("prompts", () => {
  it("review-todos default filter is pending", async () => {
    const r = await client.getPrompt({ name: "review-todos", arguments: {} });
    expect(r.messages[0].content.text).toMatch(/pending todos/);
  });
  it("review-todos filter=all", async () => {
    const r = await client.getPrompt({ name: "review-todos", arguments: { filter: "all" } });
    expect(r.messages[0].content.text).toMatch(/all todos/);
  });
  it("review-todos rejects unknown filter", async () => {
    await expect(
      client.getPrompt({ name: "review-todos", arguments: { filter: "maybe" } })
    ).rejects.toThrow();
  });
});

// ... 20 more tests across concurrency, error envelopes, prompt arguments,
//     resource caching, and transport-level error handling

That block is 10 tests; the full gate is 30. The 30-test floor catches SDK regressions, Zod schema drift, and the classic "I refactored the handler and forgot the isError path" bug.

Step 8: Add a CI gate that runs the inspector and the scanners

Two checks run on every push: the official MCP inspector, and the security scanners. Block the build on any high-severity finding.

# .woodpecker.yml
steps:
  - name: test
    image: node:22
    commands:
      - npm ci
      - npm test
  - name: inspect
    image: node:22
    commands:
      - npm run build
      - npx -y @modelcontextprotocol/inspector node dist/index.js
        <<< '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
        | jq -e '.result.tools | length > 0'
  - name: poison-scan
    image: node:22
    commands:
      - npx -y mcp-poison-scanner scan src/
  - name: supply-chain-audit
    image: node:22
    commands:
      - npx -y mcp-supply-chain-audit scan .

Note: the inspector step pipes a tools/list JSON-RPC request into the server's stdin and asserts that the response contains at least one tool. If the inspector returns empty, your server is not exposing its tool list correctly — usually a missing await server.connect(transport) or a transport that closes before responding.

Step 9: Ship install recipes for Claude Desktop, Cursor, and Continue

Each host reads a different config format. Ship all three so the user does not have to translate.

Claude Desktop (~/Library/Application Support/Claude/claude_desktop_config.json):

{
  "mcpServers": {
    "todo": {
      "command": "node",
      "args": ["/absolute/path/to/my-mcp-server/dist/index.js"]
    }
  }
}

Cursor (~/.cursor/mcp.json):

{
  "mcpServers": {
    "todo": {
      "command": "node",
      "args": ["/absolute/path/to/my-mcp-server/dist/index.js"]
    }
  }
}

Continue (~/.continue/config.json):

{
  "mcpServers": {
    "todo": {
      "command": "node",
      "args": ["/absolute/path/to/my-mcp-server/dist/index.js"]
    }
  }
}
Tip: The args array must contain the absolute path. A relative path like ./dist/index.js works in development but breaks the moment the host resolves it against a different working directory. Use path.resolve(__dirname, "../dist/index.js") inside a launcher script if you need portability.

The 7 anti-patterns that fail security review

After reviewing 30+ MCP servers in the Algoram99 catalog and external audits, these are the seven patterns that fail on first scan, in order of severity:

  1. Shell-out via child_process.exec with user-controlled input. One prompt-injected string away from RCE. Use structured library calls instead.
  2. No input length caps. A model can pass a 500MB string. Cap every free-form field with Zod.string().max(N) where N is the largest value your handler can actually use.
  3. Reading process.env for secrets the host did not declare. The host's config schema is the contract; reading outside it leaks credentials across server boundaries.
  4. Path traversal via filenames or URIs. A resource URI of file:///etc/passwd is a default. Resolve and prefix-check every path against an allowlist.
  5. No isError: true envelope on handled failures. The host renders success and error identically. A failed tool that returns a success envelope silently passes bad data to the model.
  6. Tests that mock the protocol layer. A test that stubs client.callTool to return a fixture never catches a Zod schema drift, a transport timeout, or a JSON-RPC error from the host.
  7. No CI gate. A server that passes locally and breaks on the first SDK minor bump is a server that erodes trust. Pin the SDK, run the inspector, run the scanners, fail the build.
