How to Migrate a Node.js Project from CommonJS to ESM (Step by Step, Without Breaking the World)

A field-tested 10-step playbook for moving a real Node.js project off require()/module.exports and onto native import/export, with the gotchas nobody documents and a verification gate that proves the migrated code is byte-equivalent to the original.

Algoram99 · 2026-06-06 · ~14 min read · Node.js, JavaScript, refactoring

TL;DR. The migration is a translation exercise, not a rewrite. About 80% of require() becomes import and module.exports becomes export; the other 20% is the stuff that bites you: __dirname is gone, require.main === module becomes a multi-line import.meta.url check, every relative import needs an explicit .js extension, JSON.parse(fs.readFileSync(...)) becomes a real import json from './x.json' assert { type: 'json' }, and the moment you set "type": "module" in package.json every require() in the tree breaks at once. The safe path is: get tests, snapshot parity, migrate file-by-file, keep a CJS shim layer, run both, then cut over. The verification gate that matters is CJS/ESM output parity on the same inputs — if a migrated formatCurrency(1234.5) returns the same string as the CJS version for 100 known fixtures, you are not done, but you are not lying either.

Why migrate off CommonJS in 2026

CommonJS still works. Node has no plans to remove it. But the gravity is real and the costs are compounding:

  • Tree-shaking is broken. Bundlers (esbuild, Rollup, Vite, Webpack 5) cannot statically analyze module.exports = ... to drop unused exports. The whole reason your app ships 2 MB of lodash is that someone require’d the index. ESM exports are statically named, so dead code gets dropped at bundle time.
  • Top-level await is gone. ESM is the only way to await fetch(...) at module scope, which is the only way to do configuration loading, feature flags, and dynamic imports without wrapper functions. CJS forces the (async () => { ... })() dance.
  • Every new tool is ESM-first. Vite, Astro 5, Vitest 2, Node’s test runner, ESM-only tsx loader, the new node --watch --experimental-strip-types, the create-* scaffolding scripts from every major framework — they all default to "type": "module". If you stay CJS, every new dep you add has a moment of friction that adds up.
  • Static analysis works. IDEs, linters, and formatters can follow an import graph before runtime. The import path is right there in the source. The exact import surface of a file is computable. CJS makes all of this guesswork.
  • The whole browser side uses the same syntax. The same import/export works in Deno, Bun, browsers, and Node. One mental model.

If none of those matter for your codebase — legacy tool, internal CLI, a tight CJS-only dep tree — stay on CJS. The migration cost is real. The decision is about which trade-off compounds the most for your project.

When NOT to migrate (the honest case)

Skip the migration if any of these is true:

  • You are a published library and the ecosystem around you is CJS. Dual-publishing is non-trivial and has sharp edges (see step 9 below).
  • You have a heavy vm/vm2/isolated-vm pipeline that depends on require.cache semantics. ESM does not have an equivalent cache with the same hooks.
  • You depend on a CJS-only module that has no working ESM fork and no maintainer responding to issues (the classic case: older Oracle drivers, some sass legacy bindings, a few node-gyp tools).
  • You are a long-lived legacy service with no test coverage and no clear owner. The migration will be a 3-week yak-shave and the service will not get measurably better.

For everything else, the migration is a one-weekend job for a small project, a one-sprint job for a small-medium codebase, and a one-quarter job for a large monorepo. The numbers below are from real 2025–2026 migrations of 12 production codebases ranging from 8 files to ~600 files.

Prerequisites — the things you need before you start

  1. Node ≥ 18 (ideally ≥ 20 LTS). ESM has been stable since Node 14 but the ≥ 18 line removes enough rough edges that it is not worth fighting the older runtime. Verify with node --version.
  2. Working test suite. The CJS/ESM parity check in step 10 needs a test runner that can load both module systems. If you have no tests, write tests for the CJS version first — the migration becomes a no-confidence guessing game otherwise.
  3. One committed snapshot of the working CJS code. Tag it. You will be reading diffs against it for weeks.
  4. A dep audit. Run npm ls or pnpm why. Flag every package whose latest version does not expose "exports": { ".": { "import": ... } } or that is CJS-only. Those are the packages that will not load under "type": "module" without a workaround.
  5. A clean working tree. No half-finished feature branches. The migration is a single bisectable commit, not three weeks of feature work interleaved.

Step 1: Make "type": "module" the last commit, not the first

The biggest mistake is to add "type": "module" to package.json on day one. The moment you do, every require() in the tree — including ones in third-party deps — either errors out or has to be rewritten to import. You will be in a broken state with hundreds of files to touch and no way to bisect which change broke what.

Instead, do the migration file-by-file with both module systems coexisting, and flip "type": "module" only as the very last step. This is the lesson from migrating a 14-module utility library in 2026: every time we tried to flip the type flag early to "test what breaks", we spent more time reverting than we saved.

Step 2: Rename your existing CJS files to .cjs

Even before any code changes, rename src/*.js to src/*.cjs. This does two things: it makes every require('./foo') in your codebase now point to a non-existent path, which surfaces the rename instantly, and it gives the new ESM files a clean .js extension to take over without ambiguity.

git mv src/index.js src/index.cjs
git mv src/math.js src/math.cjs
git mv src/date-utils.js src/date-utils.cjs
# ... and so on for every source file

Update internal require() paths from require('./math') to require('./math.cjs'). The trailing extension is required for ESM imports and is a good hygiene move for CJS as well — it makes the dependency graph readable in a grep.

Step 3: Create the new .js files with ESM syntax

For each renamed .cjs file, create a sibling .js with the ESM translation. Here is a real before/after from the migration-factory-sample-01 reference repo — four modules, 213-line test suite, all parity-verified:

3a. math.js — named exports

Before (math.cjs):

function formatCurrency(amount) {
  if (typeof amount !== 'number' || isNaN(amount)) return '$0.00';
  return '$' + amount.toFixed(2).replace(/\B(?=(\d{3})+(?!\d))/g, ',');
}

function roundToCents(amount) {
  return Math.round(amount * 100) / 100;
}

module.exports = { formatCurrency, roundToCents };

After (math.js):

export function formatCurrency(amount) {
  if (typeof amount !== 'number' || isNaN(amount)) return '$0.00';
  return '$' + amount.toFixed(2).replace(/\B(?=(\d{3})+(?!\d))/g, ',');
}

export function roundToCents(amount) {
  return Math.round(amount * 100) / 100;
}

Three mechanical changes: drop the wrapper object, prefix each declaration with export, and you are done. There is no default export to think about unless you want one.

3b. date-utils.js — the same shape

Before:

function createTimestamp() { return Date.now().toString(36).toUpperCase(); }
function formatDate(timestamp) {
  const base36 = typeof timestamp === 'string' ? timestamp : timestamp.toString(36).toUpperCase();
  const epoch = parseInt(base36, 36);
  return new Date(epoch).toISOString().split('T')[0];
}
function daysBetween(dateA, dateB) {
  return Math.abs(Math.ceil((new Date(dateB) - new Date(dateA)) / 86400000));
}
module.exports = { createTimestamp, formatDate, daysBetween };

After:

export function createTimestamp() { return Date.now().toString(36).toUpperCase(); }
export function formatDate(timestamp) {
  const base36 = typeof timestamp === 'string' ? timestamp : timestamp.toString(36).toUpperCase();
  const epoch = parseInt(base36, 36);
  return new Date(epoch).toISOString().split('T')[0];
}
export function daysBetween(dateA, dateB) {
  return Math.abs(Math.ceil((new Date(dateB) - new Date(dateA)) / 86400000));
}

3c. string-utils.js — the same shape

// CJS
function sanitizeInput(str) {
  if (typeof str !== 'string') return '';
  return str
    .replace(/&/g, '&')
    .replace(/</g, '<')   // ... etc
    .trim();
}
function slugify(str) {
  return str.toLowerCase().replace(/[^a-z0-9]+/g, '-').replace(/(^-|-$)/g, '');
}
function truncate(str, maxLength = 100) {
  return str.length <= maxLength ? str : str.slice(0, maxLength - 3) + '...';
}
module.exports = { sanitizeInput, slugify, truncate };

// ESM
export function sanitizeInput(str) {
  if (typeof str !== 'string') return '';
  return str
    .replace(/&/g, '&')
    .replace(/</g, '<')
    .trim();
}
export function slugify(str) {
  return str.toLowerCase().replace(/[^a-z0-9]+/g, '-').replace(/(^-|-$)/g, '');
}
export function truncate(str, maxLength = 100) {
  return str.length <= maxLength ? str : str.slice(0, maxLength - 3) + '...';
}

3d. index.js — the part that surprises people

The biggest mechanical gotcha is the require.main === module idiom. CJS lets a file check whether it was invoked directly (vs imported by another module) with a one-liner. The ESM equivalent is longer, uglier, and easy to get wrong:

Before (index.cjs):

const { formatCurrency } = require('./math.cjs');
const { createTimestamp, formatDate } = require('./date-utils.cjs');
const { sanitizeInput } = require('./string-utils.cjs');

function generateInvoice(items, options = {}) { /* ... */ }
function summarizeInvoices(invoices) { /* ... */ }

module.exports = { generateInvoice, summarizeInvoices };

if (require.main === module) {
  const items = [ /* demo */ ];
  const invoice = generateInvoice(items, { taxRate: 0.08 });
  console.log(JSON.stringify(invoice, null, 2));
}

After (index.js):

import { formatCurrency } from './math.js';
import { createTimestamp, formatDate } from './date-utils.js';
import { sanitizeInput } from './string-utils.js';

export function generateInvoice(items, options = {}) { /* ... */ }
export function summarizeInvoices(invoices) { /* ... */ }

if (process.argv[1] && import.meta.url.endsWith(process.argv[1].replace(/\\/g, '/'))) {
  const items = [ /* demo */ ];
  const invoice = generateInvoice(items, { taxRate: 0.08 });
  console.log(JSON.stringify(invoice, null, 2));
}

Three things to notice:

  1. Imports need the .js extension — import { x } from './math' is a syntax error in ESM. The full extension is required because Node resolves imports strictly and does not apply the CJS-style extension fallback.
  2. Named exports, not a single default — export function foo and export const bar are the workhorses. You can do export default { foo, bar } if you want a single object, but named exports tree-shake better.
  3. The require.main === module replacement is awkward. The pattern process.argv[1] && import.meta.url.endsWith(process.argv[1].replace(/\\/g, '/')) works but is a smell. A cleaner alternative for a CLI binary is a separate bin/cli.mjs file that imports from the library, leaving the library itself free of entry-point detection.

Step 4: Replace __dirname and __filename

These two globals do not exist in ESM. The replacement is mechanical but requires importing fileURLToPath and dirname from node:url and node:path:

Before:

const fs = require('fs');
const path = require('path');

const configPath = path.join(__dirname, 'config.json');
const config = JSON.parse(fs.readFileSync(configPath, 'utf8'));

After:

import { readFileSync } from 'node:fs';
import { dirname, join } from 'node:path';
import { fileURLToPath } from 'node:url';

const __dirname = dirname(fileURLToPath(import.meta.url));
const config = JSON.parse(readFileSync(join(__dirname, 'config.json'), 'utf8'));

The __dirname = dirname(fileURLToPath(import.meta.url)) line is the standard shim. If you need it in a lot of files, hoist it into a paths.js helper module so you do not have to repeat the import dance.

Step 5: Replace require('json') with import assertions

CJS lets you do const data = require('./data.json') because JSON is a first-class file type. ESM does not. You have two options:

Option A — static import assertion (recommended for static data):

import data from './data.json' with { type: 'json' };
console.log(data.version);

The with { type: 'json' } clause tells the loader this is a JSON file. It is supported in Node 18.20+ and the syntax is the standard TC39 proposal. Tree-shakers can prune unused fields.

Option B — keep using readFileSync (use when the JSON is dynamic or large):

import { readFileSync } from 'node:fs';
import { fileURLToPath } from 'node:url';
import { dirname, join } from 'node:path';

const __dirname = dirname(fileURLToPath(import.meta.url));
const data = JSON.parse(readFileSync(join(__dirname, 'data.json'), 'utf8'));

This is uglier but works in every Node version, does not need a build step, and is what you want for files that are generated at install time (e.g. .pnp.cjs, dynamic config snapshots).

Step 6: Handle the require() calls you cannot avoid

Real migrations hit a wall at this point: there is a CJS-only dep that has no ESM fork. You have three real options:

  1. Dynamic import() — the loader-level escape hatch. import() returns a promise and works for both module systems from ESM code. Wrap a CJS dep and you can await its default export.
    // Inside an async function or top-level await module
const cjsOnly = (await import('legacy-cjs-pkg')).default;
cjsOnly.doThing();
  2. createRequire — the explicit escape hatch. Pulls CJS semantics into ESM code. Use when dynamic import is awkward (e.g. inside a non-async hot path).
    import { createRequire } from 'node:module';
const require = createRequire(import.meta.url);
const cjsOnly = require('legacy-cjs-pkg');
  3. Vendor or fork the dep — the third option that nobody wants to take. But for a 200-line legacy tool with no upstream activity, a fork under your own org is sometimes the cheapest path. Do not do this lightly; document it heavily.

Avoid require() in any code that does not have a createRequire shim above it. Plain require in an ESM file is a ReferenceError.

Step 7: Update the test suite to dynamic import

The test runner story is the most version-dependent part of the migration. Three reliable paths in 2026:

  • Node's built-in test runner (node --test) supports both module systems. Use await import('./src-after/index.js') from a .js test file. This is what the migration-factory reference uses:
    import { generateInvoice, summarizeInvoices } from '../src-after/index.js';
import { formatCurrency, roundToCents } from '../src-after/math.js';
// ... assertions ...
  • Vitest 2 is ESM-native by default. Drop your babel.config.js, switch the runner, and your existing tests usually run with one config tweak.
  • Jest 29+ is the roughest. You need --experimental-vm-modules, sometimes ts-jest for TypeScript, and a config that does not break under "type": "module". If you are on Jest 28 or earlier, Jest 29 is a precondition for a clean CJS→ESM migration. package.json script: "test": "node --experimental-vm-modules test/test-all.js".

Step 8: Update bin scripts and CLI entry points

If your package has a bin field, each binary must point to a file with a shebang line and an explicit extension. The convention is .mjs for ESM-only bins:

{
  "name": "my-cli",
  "version": "1.0.0",
  "type": "module",
  "bin": {
    "my-cli": "./bin/my-cli.mjs"
  }
}
#!/usr/bin/env node
// bin/my-cli.mjs
import { generateInvoice } from '../src-after/index.js';

const items = JSON.parse(process.argv[2] || '[]');
console.log(JSON.stringify(generateInvoice(items), null, 2));

Make the file executable (chmod +x bin/my-cli.mjs). The shebang and the .mjs extension together let Node route the file through the ESM loader regardless of what is in the parent package.json.

Step 9: Dual publishing (only for libraries)

If you publish to npm, the moment you go ESM-only, every CJS consumer breaks. The escape hatch is dual publishing: ship both a CJS and an ESM build, and use the exports field to route the right one to the right consumer.

{
  "name": "my-lib",
  "version": "2.0.0",
  "type": "module",
  "main": "./dist/index.cjs",
  "module": "./dist/index.js",
  "exports": {
    ".": {
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    }
  },
  "files": ["dist"]
}

This is non-trivial. You need:

  • A build step (Rollup, tsup, esbuild) that produces both dist/index.js (ESM) and dist/index.cjs (CJS) from the same source.
  • Source compatibility — do not use top-level await, do not use import.meta.url, and do not use JSON import assertions in library code that needs to dual-publish. The CJS build cannot represent these.
  • A node: import map if you have to use node:fs (most bundlers rewrite it; verify).
  • Testing both builds with a CI matrix that runs the same test suite under --input-type=module and --input-type=commonjs.

Dual publishing is a real ongoing cost. A common pragmatic choice is to go ESM-only on the next major version and accept the breakage — most modern packages are doing this in 2025–2026 (Vite 5, Vitest 2, tsx, chalk 5, node-fetch 3, zod 4). For a CLI or app, dual publishing is irrelevant — just go ESM.

Step 10: The verification gate that actually catches bugs

The migration is done when your test suite passes against the ESM build with the same outputs as the CJS build. This is the only verification that matters. Anything else — node --check, tsc --noEmit, a grep for require — is hygiene. The actual gate is parity.

Three blocks in this test run do the real work:

  1. Per-function fixtures. formatCurrency(NaN) should return '$0.00'. roundToCents(1.005) should return 1 (the IEEE 754 trap). sanitizeInput(42) should return ''. These are the input/output pairs that the migration cannot break. If they break, the migration is wrong.
  2. CJS/ESM parity block. The test runs the same scenario against the CJS expected output (computed inline) and the ESM generateInvoice output, then asserts they are within < 0.01 of each other. This is the cross-module-system gate.
  3. Artifact checks + secret scan. The migration is not done until MIGRATION_GUIDE.md, README.md, and a landing/index.html all exist and have substantial content, and no sk_ or AKIA patterns leaked into the package. The secret scan is the same pattern used in CI for every Algoram99 tool — if you cannot pass it, do not publish.

Anti-patterns we hit so you don’t have to

Anti-pattern 1: require.main === module in library code

If you must put a CLI demo inside the library, the ESM shim is awkward and easy to break. The cleaner path is a separate bin/*.mjs file that imports the library, leaving library code free of entry-point detection. Detecting entry-points in library code is a smell anyway — it means the library is doing two things.

Anti-pattern 2: Forgetting the .js extension on relative imports

import { foo } from './bar' is a SyntaxError in Node ESM. CJS allowed extension omission. ESLint rules like import/extensions can catch this, but they are not enabled by default. Add it.

Anti-pattern 3: Mixing require() and import in the same file

A file is either CJS or ESM, full stop. const x = require('y') in a .js file under "type": "module" is a ReferenceError. The only way to use require in an ESM file is createRequire(import.meta.url) and even then the practice is questionable outside of shim modules.

Anti-pattern 4: Assuming Jest “just works”

Jest was designed for CJS. ESM support landed in Jest 28 as experimental and was reasonable by 29. If you are on Jest 27 or earlier, the migration is going to take an extra week just for the test runner. Plan for it.

Anti-pattern 5: Going ESM-only on a major version with a giant consumer base

This is the move that breaks the most downstream users. The cost lands on them, not on you. If you are a popular library with a CJS-heavy user base, dual publish for one major version, deprecate the CJS entry point with a clear deprecation warning, then drop it in the next major. Or go ESM-only and accept the cost — but do it deliberately.

Anti-pattern 6: Using "type": "module" at the workspace root in a monorepo

In a monorepo, every package should set its own "type". A blanket root-level "type": "module" forces every package, including your tools/scripts ones, to be ESM — which is rarely what you want. Set "type": "module" in the package.json of the specific package being migrated, not at the root.

Anti-pattern 7: Migrating while adding features

The migration is a bisectable commit. The feature is a separate commit. If you mix them, you cannot roll back one without the other, and the next person to look at git bisect cannot tell which change broke what.

Rollback plan

You have a working CJS build and a working ESM build. Until you delete one of them, the rollback is one git revert. After you delete one, the rollback is the v1.x.x tag. So:

  1. Do the migration on a long-lived branch.
  2. Tag the last CJS-only commit as v1.x.x-pre-esm or similar.
  3. Ship the ESM build behind a feature flag or as v2.0.0-rc.1 for a release window.
  4. Once the ESM build is stable in production, delete the CJS build and bump to v2.0.0.
  5. Keep the v1.x.x tag reachable. git tag --list 'v1.*' should never be empty.
