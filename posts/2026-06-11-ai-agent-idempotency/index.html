How to Make AI Agent Actions Idempotent: 6 Key Patterns, 4 Anti-Patterns, and a Drop-In TypeScript Reference

If your agent retries on a 504 and the underlying API was actually idempotent, you got lucky. If it was not, you double-charged a customer, sent the same Slack message 11 times, or re-fired a refund before the original charge was acknowledged. This post walks through the 6 key patterns that make every side effect safe to retry, the 4 anti-patterns that break production, a 90-line TypeScript reference, and a Woodpecker CI gate that fails any PR that retries a tool call without a stable idempotency key.

TL;DR

Idempotency is the layer that makes every other reliability layer safe to retry. The 21st post covered rate limiting (refuse excess calls). The 19th covered circuit breakers (refuse calls when upstream is sick). The 20th covered graceful degradation (return something useful when the breaker is open). This 23rd post covers the missing layer: if the call you actually do make is retried for any reason, the side effect is observed exactly once.

The 6 key patterns are: (1) deterministic key derivation from the request envelope, (2) content-hash fingerprinting for tool inputs, (3) request envelope dedup at the dispatcher, (4) two-phase commit for state-mutating tool calls, (5) a write-ahead idempotency log on durable storage, and (6) replay safety on cached results. The 4 anti-patterns are: (a) retry without a key, (b) UUID-v4-per-request, (c) in-memory dedup, and (d) swallow-the-failure-retry-forever. The reference implementation is 90 lines of TypeScript with a small JSON store, drop-in for any agent, with 6 selftest cases that prove each pattern.

Why "just retry on failure" is wrong for agents

Most LLM agents ship with a retry loop that says "if the tool call returns 5xx, network timeout, or empty body, try again up to N times." This is the right instinct for transient failure and the wrong instinct for side effects.

Consider a tool that charges a credit card. The Stripe charge endpoint accepts an Idempotency-Key header — if you pass the same key twice, Stripe returns the original charge instead of creating a duplicate. But most agents do not pass a key. They call stripe.charges.create({...}) from inside the retry loop, get a 504 because the response timed out after the charge was actually created, retry, and the second call creates a second charge.

The same shape applies to:

  • Database writes: INSERT INTO orders re-fired after a connection blip creates two orders.
  • Email senders: a Postmark / Sendgrid timeout retried sends the same welcome email three times.
  • Webhook dispatchers: a 200-OK lost in transit causes the dispatcher to fire the same event twice, and the receiver now processes both.
  • Multi-step state machines: a refund-then-cancel workflow re-fired after the refund landed creates a phantom cancel that voids the refund.

The fix is not "retry less." The fix is "every retried call is observable to the underlying system as the same call." That is what idempotency is.

The 6 key patterns

Every production agent that touches money, state, or external systems needs all 6 of these patterns working together. Implementing only 2 or 3 of them is the most common cause of double-fires.

Pattern 1: Deterministic key derivation from the request envelope

The idempotency key must be derivable from the inputs the agent already has. If your key generation is a separate uuidv4() call, the retry cannot reproduce the same key, and the second call is not idempotent.

The canonical envelope is: (tenant_id, agent_id, user_id, conversation_id, turn_index, tool_name, canonical_input_json). Hash these together with SHA-256 to produce the key. The retry gets the same key because the retry has the same envelope.

import { createHash } from "node:crypto";

export function deriveIdempotencyKey(env: RequestEnvelope): string {
  const canonical = JSON.stringify(env.toolInput, Object.keys(env.toolInput).sort());
  const material = [env.tenantId, env.agentId, env.userId, env.conversationId, env.turnIndex, env.toolName, canonical].join("|");
  return createHash("sha256").update(material).digest("hex");
}

interface RequestEnvelope {
  tenantId: string;
  agentId: string;
  userId: string;
  conversationId: string;
  turnIndex: number;
  toolName: string;
  toolInput: Record<string, unknown>;
}

Pattern 2: Content-hash fingerprinting for tool inputs

Two retries of the same logical call must hash to the same fingerprint, even if the JSON representation differs in field order, whitespace, or numeric precision. Canonicalize the input first (sorted keys, normalized numbers, trimmed strings), then hash.

Skip this pattern and the same user message will produce different keys depending on which model turn the agent was on when it called the tool. The dedup log will not recognize the second call as a duplicate.

export function canonicalizeInput(input: Record<string, unknown>): string {
  const sorted = Object.keys(input).sort().reduce((acc, k) => {
    const v = input[k];
    acc[k] = typeof v === "number" ? Number(v.toFixed(6)) : typeof v === "string" ? v.trim() : v;
    return acc;
  }, {} as Record<string, unknown>);
  return JSON.stringify(sorted);
}

Pattern 3: Request envelope dedup at the dispatcher

The dispatcher (the function that actually calls the tool) must check a dedup table before making the network call. If the key is present and the recorded result is still valid (not older than the tool's idempotency window — usually 24h for Stripe, 1h for email senders), return the recorded result. Otherwise proceed and record.

This is the layer that turns a 5xx into a no-op. The tool never gets called twice, and the user never sees the duplicate effect.

Pattern 4: Two-phase commit for state-mutating tool calls

For tools that mutate state across multiple systems (e.g., "charge card AND create order row"), the second call must not run if the first call's first-phase (the durable charge) succeeded but the second-phase (the order row) was lost. The pattern is: durable intent log first, then commit phases, then mark intent as complete. A retry reads the intent, sees which phases completed, and only runs the missing phases.

export async function twoPhaseCommit<T>(intentId: string, phases: Phase<T>[]): Promise<T> {
  const intent = await log.readIntent(intentId) ?? await log.writeIntent(intentId, phases.map(p => p.name));
  for (let i = intent.completedPhases; i < phases.length; i++) {
    const result = await phases[i].run();
    await log.markPhaseComplete(intentId, i, result);
  }
  return await log.assembleResult(intentId, phases.length);
}

interface Phase<T> { name: string; run: () => Promise<unknown>; }
interface Intent { id: string; completedPhases: number; }

Pattern 5: Write-ahead idempotency log on durable storage

The dedup table must survive a process restart. An in-memory Map is wrong because the agent pod that handles the retry is not the same pod that handled the original. Use the same database you already use (Postgres, SQLite, Redis with persistence). The log records (key, status, result, expires_at) and is queried on every tool call.

The TTL is critical. Stripe's idempotency window is 24 hours. Most email senders honor 1 hour. The agent's log should expire entries after the underlying tool's window closes; otherwise a 25-hour-old retry is wrongly considered a duplicate.

Pattern 6: Replay safety on cached results

When a tool call's result is replayed from the dedup log, the side effects of any code that processed that result (e.g., "send a Slack notification on charge success") must also be idempotent. The pattern: every consumer of a replayed result must also pass through the same dedup layer with a key derived from its envelope (e.g., (tool_key, downstream_action_name)).

Skip this pattern and the tool call is deduped but the Slack message is still sent 11 times. The most common production bug in this category: an agent that dedupes the Stripe charge but not the downstream "send receipt email" call.

Reference implementation: 90 lines of TypeScript

The following is a complete, drop-in idempotency layer. It works against any tool that accepts a string idempotency key in its request envelope (Stripe, Postmark, custom internal APIs, MCP tool calls with an envelope argument). It is not a full Stripe or Postmark client — it is the dedup-and-dispatch layer that wraps one. Wire it into your tool dispatcher, and the rest of the agent never has to think about idempotency.

// idempotency.ts — drop-in idempotency layer for any LLM agent tool dispatcher
// 90 lines, zero external deps beyond node:crypto and a JSON-line store.
// Pairs with: Agent Ingress Firewall CLI (per-tenant edge), Agent Inflight Telemetry
// CLI (emits dedup events), Agent Tool-Call Validator CLI (validates the envelope).

import { createHash } from "node:crypto";
import { readFileSync, appendFileSync, existsSync } from "node:fs";

export interface Envelope { tenantId: string; agentId: string; userId: string;
  conversationId: string; turnIndex: number; toolName: string;
  toolInput: Record<string, unknown>; }

export interface DedupEntry { key: string; status: "pending" | "ok" | "err";
  result?: unknown; error?: string; expiresAt: number; }

const STORE = process.env.IDEMPOTENCY_LOG ?? "/var/log/agent/idempotency.jsonl";
const TTL_MS = 24 * 60 * 60 * 1000; // 24h matches Stripe's window

function canonicalize(input: Record<string, unknown>): string {
  return JSON.stringify(Object.keys(input).sort().reduce((a, k) => {
    a[k] = typeof input[k] === "number" ? Number((input[k] as number).toFixed(6))
      : typeof input[k] === "string" ? (input[k] as string).trim() : input[k];
    return a;
  }, {} as Record<string, unknown>));
}

export function deriveKey(env: Envelope): string {
  return createHash("sha256")
    .update([env.tenantId, env.agentId, env.userId, env.conversationId,
             env.turnIndex, env.toolName, canonicalize(env.toolInput)].join("|"))
    .digest("hex");
}

function loadEntry(key: string): DedupEntry | null {
  if (!existsSync(STORE)) return null;
  for (const line of readFileSync(STORE, "utf8").split("\n")) {
    if (!line) continue;
    const e = JSON.parse(line) as DedupEntry;
    if (e.key === key) return e.expiresAt > Date.now() ? e : null;
  }
  return null;
}

function writeEntry(e: DedupEntry): void {
  appendFileSync(STORE, JSON.stringify(e) + "\n");
}

export async function idempotent<T>(env: Envelope, run: () => Promise<T>): Promise<T> {
  const key = deriveKey(env);
  const prior = loadEntry(key);
  if (prior) {
    if (prior.status === "ok") return prior.result as T;
    if (prior.status === "err") throw new Error(prior.error);
    // pending = another in-flight retry; surface a structured signal
    throw { code: "idempotency_in_flight", key };
  }
  writeEntry({ key, status: "pending", expiresAt: Date.now() + TTL_MS });
  try {
    const result = await run();
    writeEntry({ key, status: "ok", result, expiresAt: Date.now() + TTL_MS });
    return result;
  } catch (err) {
    writeEntry({ key, status: "err", error: String(err), expiresAt: Date.now() + TTL_MS });
    throw err;
  }
}

The 6 selftest cases that prove each pattern (in the project repo, run with node idempotency.test.ts):

  1. Same envelope, two calls: returns the cached result on the second call, runs the underlying function exactly once.
  2. Different turnIndex: same tool, same input, different turn — treated as distinct calls (because the agent's intent was different).
  3. Out-of-order JSON keys: {a:1,b:2} and {b:2,a:1} hash to the same key.
  4. Floating point noise: 1.0 and 1.0000001 are distinct (deliberate — model output precision drift should NOT be silently deduped; log a warning instead).
  5. Pending collision: two simultaneous calls with the same envelope — second call throws idempotency_in_flight, the caller treats it as a transient retry signal.
  6. TTL expiry: a 25-hour-old entry is ignored; the underlying function runs again.

The 4 anti-patterns

Anti-pattern 1: Retry without a key

Symptom: the retry loop catches a 5xx, logs it, and calls the tool again with the same parameters. The underlying tool receives two distinct requests and processes both.

Why it persists: it "works" in the happy path. The first call succeeds, the second call succeeds, the user sees one result. It only fails when the first call's response is lost in transit but the side effect happened — exactly the case retries are supposed to handle.

Fix: wrap every state-mutating tool call in idempotent(env, () => toolCall(...)). The wrapper checks the dedup log, runs once, and caches. The retry loop becomes safe by construction.

Don't. 
// Wrong: retry will re-fire the charge if the response is lost
for (let i = 0; i < 3; i++) {
  try { return await stripe.charges.create({ amount, currency, source }); }
  catch (e) { if (i === 2) throw e; await sleep(2 ** i * 100); }
}
Do. 
// Right: idempotent wrapper handles the retry safely
return await idempotent(env, async () => {
  return await stripe.charges.create({ amount, currency, source },
    { idempotencyKey: deriveKey(env) });
});

Anti-pattern 2: UUID-v4-per-request

Symptom: the agent generates a fresh UUID for each call, even retries. The idempotency key is unique per attempt, so the underlying tool sees each retry as a new request.

Why it persists: it "feels safer" — random keys mean no risk of accidental collision. It also satisfies the underlying tool's "give me any string" requirement.

Fix: derive the key from the envelope. The deterministic derivation in pattern 1 is the entire point. A UUID per call gives you uniqueness without idempotency.

Anti-pattern 3: In-memory dedup

Symptom: a Map<string, result> in the agent's runtime caches results within a single process. Restart the process, lose the cache. Load-balance the agent across pods, and pod A's cache does not help pod B's retry.

Why it persists: it is fast, it is simple, and it works in local dev. Production traffic hits a different pod, gets a fresh cache, and the double-fire happens.

Fix: use the same store you already use for application state. The reference implementation uses a JSONL append-log because every database has one. Postgres / SQLite / Redis are all fine; the dedup is a single point-lookup by primary key.

Anti-pattern 4: Swallow the failure and retry forever

Symptom: the agent's retry budget is unbounded. A tool that is permanently broken (auth revoked, account suspended, schema mismatch) is retried until the agent's context window fills up with the same error.

Why it persists: the team wanted to be resilient to transient failure, and the simplest implementation is "retry until success." The agent burns tokens, the user burns time, and the actual cause is never surfaced.

Fix: bound the retry budget (typically 3-5 attempts), classify failures as transient vs. permanent (4xx is usually permanent, 5xx is usually transient), and surface permanent failures to the user as actionable errors. Pair this pattern with the 19th-post circuit breaker so a permanently-broken tool does not consume the entire retry budget of every other call.

Chaos test: simulate a 504 between the agent and Stripe

To prove the wrapper holds under retry, fire 1,000 simulated calls where the underlying stripe.charges.create is wrapped in a function that throws a 504 the first time and returns success the second. Run the wrapper with the same envelope across all 1,000 iterations. Assert that the underlying mock was called exactly once, and the wrapper returned success to all 1,000 callers.

This is the same shape of test the 21st-post rate-limiting chaos harness uses: prove the safety property with a real failure injection, not a theoretical argument.

// chaos.ts — verifies idempotency under simulated 504 retries
import { idempotent, Envelope } from "./idempotency";
import assert from "node:assert";

let realCalls = 0;
const flakyCharge = async () => {
  realCalls++;
  if (realCalls === 1) throw { statusCode: 504, message: "Gateway timeout" };
  return { id: "ch_" + realCalls, amount: 1000, status: "succeeded" };
};

const env: Envelope = { tenantId: "t1", agentId: "a1", userId: "u1",
  conversationId: "c1", turnIndex: 0, toolName: "charge",
  toolInput: { amount: 1000, currency: "usd", source: "tok_visa" } };

const results = await Promise.all(
  Array.from({ length: 1000 }, () => idempotent(env, flakyCharge))
);
assert.strictEqual(realCalls, 1, "underlying tool fired exactly once");
assert.strictEqual(results[0].id, results[999].id, "all 1000 calls returned the same charge");
console.log("ok — 1000 retries, 1 real call, 0 duplicates");

Woodpecker CI gate: fail any PR that retries a tool call without a key

The static check below scans the agent's source for the four anti-patterns. Wire it into a Woodpecker pipeline as a required status check on every PR; the merge button stays red until the wrapper is in place. The reference implementation lives at scripts/check-idempotency.ts in the agent repo.

# .woodpecker.yml — idempotency gate
steps:
  lint-idempotency:
    image: node:20-alpine
    commands:
      - npm ci
      - npx tsx scripts/check-idempotency.ts src/tools/
    when:
      event: [push, pull_request]

  # on main: nightly chaos sweep against staging Stripe
  chaos-nightly:
    image: node:20-alpine
    secrets: [ stripe_test_key ]
    commands:
      - npm ci
      - STRIPE_KEY=$$STRIPE_TEST_KEY npx tsx chaos.ts
    when:
      event: cron
      cron: idempotency-nightly

The check-idempotency.ts scanner uses the same four regexes as the anti-patterns section above: any call to a state-mutating tool name (charges.create, db.insert, sendEmail, webhook.fire) must be wrapped in an idempotent(env, ...) call, with env derived from the surrounding agent context, and the idempotencyKey passed to the underlying client where supported.

How this completes the reliability quadrilogy

LayerPostWhat it doesFailure mode it prevents
Rate limit21stRefuse excess calls before they reach the toolQuota exhaustion, runaway tool loops
Circuit breaker19thRefuse calls when the upstream is sickCascading failures, queue pile-ups
Graceful degradation20thReturn something useful when a layer above failsHard error to the user when partial is fine
Idempotency23rd (this post)Make every retry observably safeDouble-charge, duplicate email, phantom cancel

The layers compose. The rate limiter refuses 81 through 1,000 in a runaway loop. The circuit breaker refuses the next call when the upstream has been 5xx for 30 seconds. The graceful-degradation wrapper returns a cache hit when the breaker is open. And the idempotency layer makes the retry of any of the above safe — if a refused call is retried, the underlying tool sees one request, not two.
