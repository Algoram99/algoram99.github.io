Human-in-the-Loop AI Agents: 6 Patterns, 5 Anti-Patterns, and a Drop-In Approval Runtime

Your agent can read databases, call APIs, send emails, and write files. The question is not whether it can — it's whether it should. Here's how to build a human-in-the-loop layer that gates irreversible actions, routes uncertain decisions to human reviewers, and keeps a full audit trail for every action the agent takes.

⚠️ TL;DR

Full autonomy is a liability, not a feature. Production agents need a human-in-the-loop layer that sits between the LLM's decision and the actual execution of side-effectful actions. Six patterns make this work: (1) an approval gate that blocks writes, deletes, sends, and purchases until a human approves, (2) confidence score thresholding that auto-approves high-certainty output and routes everything else to review, (3) an async human review queue that batches low-priority decisions so reviewers aren't interrupted for every trivial call, (4) escalation with context packets that gives reviewers the full reasoning trace and proposed action in one screen, (5) time-bounded auto-approve that prevents the system from blocking forever when no reviewer is online, and (6) an audit trail with replay that records every decision — approved, rejected, auto-approved, or timed out — for compliance and debugging. This post gives you all six as copy-paste TypeScript, plus five anti-patterns that make your HITL layer worse than useless, plus a 130-line runtime you can drop into any agent.

The Problem: Agents That Act Without Asking

Here's a real production failure mode. Your customer support agent reads a user's complaint, determines that a refund is appropriate, and calls processRefund(orderId, amount). The refund goes through. No human ever saw it.

Was the refund correct? Maybe. The LLM had the order history, the complaint text, and the refund policy. It made a reasonable decision. But what if the order was already partially refunded last week? What if the customer is a known fraud risk? What if the amount was wrong because the agent misread the currency? You'll find out when the customer complains again — or when the finance team flags the discrepancy at month-end close.

The fix is not to remove the agent's ability to act. The fix is to insert a human checkpoint at the boundary between deciding and doing. That checkpoint is the human-in-the-loop layer.

But building a HITL layer that actually works — one that doesn't destroy latency, doesn't drown reviewers in trivial approvals, and doesn't become a rubber-stamp formality — requires careful design. This post covers the six patterns that work in production and the five anti-patterns that will get you paged at 3 AM.

Pattern 1: Approval Gate Before Irreversible Actions

The most fundamental HITL pattern: classify every action as read-only or side-effectful, and require human approval before executing any side-effectful action. Read-only actions (queries, searches, computations) flow through immediately. Side-effectful actions (writes, deletes, sends, purchases, API calls that change external state) block until a human approves.

The key insight is that the gate must be at the execution boundary, not at the LLM call boundary. The LLM can propose actions freely; the gate intercepts the proposal before it reaches the actual tool call.

// Classify tools by risk level
type RiskLevel = 'read-only' | 'side-effect';

const TOOL_RISK: Record<string, RiskLevel> = {
  'searchDocs': 'read-only',
  'getOrderHistory': 'read-only',
  'calculateRefund': 'read-only',
  'processRefund': 'side-effect',
  'sendEmail': 'side-effect',
  'deleteRecord': 'side-effect',
  'createDeployment': 'side-effect',
  'purchaseCredits': 'side-effect',
};

async function gatedExecute(
  toolName: string,
  args: Record<string, unknown>,
  context: ActionContext
): Promise<ToolResult> {
  const risk = TOOL_RISK[toolName] ?? 'side-effect';

  // Read-only tools execute immediately — no gate
  if (risk === 'read-only') {
    return executeTool(toolName, args);
  }

  // Side-effect tools require approval
  const approval = await requestApproval({
    tool: toolName,
    args,
    context,
    reason: `Executing side-effectful action: ${toolName}`,
  });

  if (approval.decision === 'approved') {
    return executeTool(toolName, args);
  }

  // Rejected — return the rejection reason to the LLM
  return {
    ok: false,
    error: `Action rejected by reviewer: ${approval.reason}`,
  };
}

The requestApproval() function pushes the action to a review queue (async) or blocks on a synchronous approval channel (for high-urgency contexts). The LLM receives the rejection reason and can adjust its plan accordingly — try a different approach, ask the user for clarification, or escalate to a more senior reviewer.

Pattern 2: Confidence Score Thresholding

Not every action needs human review. If your agent is 99% confident it should call searchDocs() (a read-only query), blocking on approval is pure latency overhead. Confidence thresholding routes high-certainty decisions through automatically and sends low-certainty ones to the review queue.

The threshold should be configurable per tool and per risk level. A read-only search might auto-approve at 80% confidence. A refund might require 95% confidence to auto-approve and route everything below that to a human. A database deletion might never auto-approve regardless of confidence.

interface ConfidenceConfig {
  tool: string;
  autoApproveThreshold: number;  // 0-1, above this = auto-approve
  hardBlock: boolean;             // true = always require human approval
}

const CONFIDENCE_CONFIG: Record<string, ConfidenceConfig> = {
  'searchDocs':            { tool: 'searchDocs',            autoApproveThreshold: 0.70, hardBlock: false },
  'getOrderHistory':       { tool: 'getOrderHistory',       autoApproveThreshold: 0.80, hardBlock: false },
  'processRefund':         { tool: 'processRefund',         autoApproveThreshold: 0.95, hardBlock: false },
  'sendEmail':             { tool: 'sendEmail',             autoApproveThreshold: 0.90, hardBlock: false },
  'deleteRecord':          { tool: 'deleteRecord',          autoApproveThreshold: 1.01, hardBlock: true  },
  'purchaseCredits':       { tool: 'purchaseCredits',       autoApproveThreshold: 1.01, hardBlock: true  },
};

function routeByConfidence(
  toolName: string,
  confidence: number,
  args: Record<string, unknown>
): 'auto-approve' | 'review' {
  const cfg = CONFIDENCE_CONFIG[toolName];
  if (!cfg) return 'review'; // unknown tools always go to review

  if (cfg.hardBlock) return 'review'; // never auto-approve hard-blocked tools

  if (confidence >= cfg.autoApproveThreshold) return 'auto-approve';

  return 'review';
}

Where does the confidence score come from? Three common approaches: (1) the LLM's own logprob-based confidence if the provider exposes it, (2) a separate evaluator LLM call that scores the proposed action, or (3) a heuristic based on whether the action matches historical patterns. Option 2 is the most reliable — a second model evaluating the first model's proposal catches errors that the first model would never flag on its own. For more on building evaluator pipelines, see our AI Agent Eval Harness guide.

Pattern 3: Async Human Review Queue

When confidence thresholding routes an action to review, the agent should not block synchronously. Instead, the action goes into an async review queue, and the agent either falls back to a safe default, informs the user that a review is pending, or picks an alternative path that doesn't require the gated action.

The review queue batches low-priority decisions so reviewers can process them in batches rather than being interrupted for every trivial call. Each queued item carries: the proposed action, the reasoning trace that led to it, the confidence score, and a deadline after which the system takes a safe fallback.

interface ReviewItem {
  id: string;
  tool: string;
  args: Record<string, unknown>;
  reasoningTrace: string;       // LLM's chain-of-thought leading to this action
  confidence: number;
  submittedAt: number;          // epoch ms
  deadline: number;             // epoch ms — after this, fallback fires
  fallbackAction: 'skip' | 'safe-default' | 'escalate';
  safeDefaultArgs?: Record<string, unknown>;
  status: 'pending' | 'approved' | 'rejected' | 'expired';
  reviewer?: string;
  reviewedAt?: number;
  reviewNote?: string;
}

const reviewQueue: ReviewItem[] = [];

async function enqueueForReview(
  tool: string,
  args: Record<string, unknown>,
  reasoningTrace: string,
  confidence: number,
  options: { deadlineMs: number; fallback: ReviewItem['fallbackAction']; safeDefaultArgs?: Record<string, unknown> }
): Promise<string> {
  const id = `rvw_${Date.now()}_${Math.random().toString(36).slice(2, 8)}`;
  const item: ReviewItem = {
    id,
    tool,
    args,
    reasoningTrace,
    confidence,
    submittedAt: Date.now(),
    deadline: Date.now() + options.deadlineMs,
    fallbackAction: options.fallback,
    safeDefaultArgs: options.safeDefaultArgs,
    status: 'pending',
  };
  reviewQueue.push(item);
  // Notify reviewers via Slack/email/dashboard
  await notifyReviewers(item);
  return id;
}

// Background sweeper: check for expired items and apply fallbacks
async function processExpirations(): Promise<void> {
  const now = Date.now();
  for (const item of reviewQueue) {
    if (item.status === 'pending' && now > item.deadline) {
      item.status = 'expired';
      await applyFallback(item);
    }
  }
}

async function applyFallback(item: ReviewItem): Promise<void> {
  switch (item.fallbackAction) {
    case 'skip':
      // Do nothing — the agent already moved on
      break;
    case 'safe-default':
      if (item.safeDefaultArgs) {
        await executeTool(item.tool, item.safeDefaultArgs);
      }
      break;
    case 'escalate':
      // Escalate to a senior reviewer or paging system
      await pageSeniorReviewer(item);
      break;
  }
}

The fallback strategy is critical. Without it, items pile up in the queue indefinitely. skip is the safest default for non-urgent actions. safe-default works when you have a conservative alternative (e.g., for a refund that wasn't reviewed in time, the safe default might be to issue a store credit instead of a cash refund). escalate should be reserved for actions where doing nothing is worse than doing the wrong thing.

Pattern 4: Escalation with Context Packets

When an action lands in the review queue, the reviewer should not have to dig through logs to understand what the agent is trying to do and why. The escalation context packet is a structured bundle that gives the reviewer everything they need on a single screen: the user's original request, the agent's reasoning trace, the proposed action and arguments, the confidence score, the risk classification, and any relevant historical context.

interface EscalationPacket {
  // What triggered this
  userRequest: string;
  conversationId: string;

  // What the agent wants to do
  proposedTool: string;
  proposedArgs: Record<string, unknown>;
  riskLevel: RiskLevel;

  // Why the agent chose this
  reasoningTrace: string;
  confidence: number;
  confidenceReason: string;       // "matched 3/4 historical patterns"

  // What the reviewer needs to decide
  decisionOptions: ('approve' | 'reject' | 'modify')[];
  modifyHints: string[];          // e.g., "amount can be adjusted", "recipient can be changed"

  // What happens if they don't decide
  deadline: string;               // ISO timestamp
  fallbackAction: string;         // human-readable description

  // Historical context (last 3 similar actions)
  history: Array<{
    timestamp: string;
    tool: string;
    args: Record<string, unknown>;
    outcome: 'success' | 'failure' | 'rolled-back';
    note: string;
  }>;
}

function buildEscalationPacket(
  item: ReviewItem,
  userRequest: string,
  conversationId: string,
  history: EscalationPacket['history']
): EscalationPacket {
  return {
    userRequest,
    conversationId,
    proposedTool: item.tool,
    proposedArgs: item.args,
    riskLevel: TOOL_RISK[item.tool] ?? 'side-effect',
    reasoningTrace: item.reasoningTrace,
    confidence: item.confidence,
    confidenceReason: classifyConfidenceSource(item.confidence),
    decisionOptions: getDecisionOptions(item.tool),
    modifyHints: getModifyHints(item.tool),
    deadline: new Date(item.deadline).toISOString(),
    fallbackAction: describeFallback(item.fallbackAction),
    history,
  };
}

The goal of the context packet is decision latency: the time between a reviewer seeing the packet and making a decision. A well-structured packet lets a reviewer decide in under 30 seconds. A poorly structured one — where the reviewer has to open three dashboards and read a 200-line log — turns a 30-second decision into a 10-minute investigation, and the queue backs up.

This is also where structured logging pays off. If your agent's reasoning trace is structured (not freeform prose), the escalation packet can render it as a readable summary instead of a wall of text.

Pattern 5: Time-Bounded Auto-Approve

What happens when no reviewer is available? The agent submitted a refund request at 2 AM on a Sunday. The review queue has 12 items. The deadline on the oldest one expires in 30 minutes. Without time-bounded auto-approve, the item either expires (and the fallback fires) or blocks indefinitely (and the user gives up).

Time-bounded auto-approve is a configurable policy that lets certain classes of action auto-approve after a defined waiting period, as long as no explicit rejection has been received. It's not a replacement for human review — it's a safety valve for when human review is unavailable and the cost of inaction exceeds the risk of action.

interface AutoApprovePolicy {
  tool: string;
  enabled: boolean;
  waitMs: number;               // minimum time in queue before auto-approve fires
  maxDailyAutoApproves: number;  // circuit breaker: stop auto-approving after N/day
  requireMinConfidence: number;  // only auto-approve if confidence >= this
}

const AUTO_APPROVE_POLICIES: Record<string, AutoApprovePolicy> = {
  'processRefund': {
    tool: 'processRefund',
    enabled: true,
    waitMs: 2 * 60 * 60 * 1000,  // 2 hours
    maxDailyAutoApproves: 10,
    requireMinConfidence: 0.85,
  },
  'sendEmail': {
    tool: 'sendEmail',
    enabled: false,  // never auto-approve emails — always require human review
    waitMs: Infinity,
    maxDailyAutoApproves: 0,
    requireMinConfidence: 1.01,
  },
  // deleteRecord and purchaseCredits have no policy — they never auto-approve
};

const dailyAutoApproveCounts: Record<string, number> = {};

function shouldAutoApprove(item: ReviewItem): boolean {
  const policy = AUTO_APPROVE_POLICIES[item.tool];
  if (!policy || !policy.enabled) return false;

  // Check minimum confidence
  if (item.confidence < policy.requireMinConfidence) return false;

  // Check minimum wait time
  const elapsed = Date.now() - item.submittedAt;
  if (elapsed < policy.waitMs) return false;

  // Check daily circuit breaker
  const today = new Date().toISOString().slice(0, 10);
  const key = `${item.tool}_${today}`;
  if ((dailyAutoApproveCounts[key] ?? 0) >= policy.maxDailyAutoApproves) return false;

  return true;
}

The maxDailyAutoApproves circuit breaker is essential. Without it, a bug that generates 500 refund requests at 2 AM could auto-approve all of them before a human arrives in the morning. The circuit breaker caps the blast radius: even if auto-approve is enabled, it stops after a configurable number of approvals per tool per day.

Pattern 6: Audit Trail with Replay

Every decision — approved, rejected, auto-approved, expired, or modified — must be recorded in an immutable audit trail. This is not optional. If a customer asks "why was my refund rejected?" or a compliance auditor asks "who approved this deployment?", you need to produce the full decision history.

The audit trail should support replay: given a decision record, you should be able to reconstruct the exact state of the agent, the user request, the reasoning trace, the proposed action, and the reviewer's decision. This is the same principle as retry-policy idempotency — the decision must be reproducible from its recorded inputs.

interface AuditEntry {
  id: string;
  timestamp: string;             // ISO 8601
  conversationId: string;
  userId?: string;

  // The decision
  tool: string;
  proposedArgs: Record<string, unknown>;
  finalArgs?: Record<string, unknown>;  // if modified during review
  confidence: number;

  // The outcome
  decision: 'approved' | 'rejected' | 'auto-approved' | 'expired' | 'modified';
  decisionSource: 'human' | 'auto-approve' | 'expiry' | 'system';
  reviewerId?: string;
  reviewNote?: string;

  // The context (for replay)
  userRequest: string;
  reasoningTrace: string;
  escalationPacketId?: string;

  // The result
  executedAt?: string;
  executionResult?: 'success' | 'failure' | 'rolled-back';
  executionError?: string;
}

const auditLog: AuditEntry[] = [];

function recordDecision(entry: Omit<AuditEntry, 'id' | 'timestamp'>): AuditEntry {
  const full: AuditEntry = {
    ...entry,
    id: `aud_${Date.now()}_${Math.random().toString(36).slice(2, 8)}`,
    timestamp: new Date().toISOString(),
  };
  auditLog.push(full);
  // Also write to durable storage (database, append-only log, S3)
  persistAuditEntry(full);
  return full;
}

function replayDecision(auditId: string): ReplayResult {
  const entry = auditLog.find(a => a.id === auditId);
  if (!entry) throw new Error(`Audit entry ${auditId} not found`);

  return {
    userRequest: entry.userRequest,
    reasoningTrace: entry.reasoningTrace,
    proposedAction: { tool: entry.tool, args: entry.proposedArgs },
    finalAction: entry.finalArgs
      ? { tool: entry.tool, args: entry.finalArgs }
      : { tool: entry.tool, args: entry.proposedArgs },
    decision: entry.decision,
    decisionSource: entry.decisionSource,
    reviewer: entry.reviewerId,
    reviewNote: entry.reviewNote,
    executed: entry.executionResult === 'success',
    rolledBack: entry.executionResult === 'rolled-back',
  };
}

The audit trail is also your debugging tool. When an agent makes a bad decision, the audit entry tells you exactly what went wrong: was the confidence score too high? Did the reviewer rubber-stamp it? Did the auto-approve policy fire when it shouldn't have? Without the trail, you're guessing. With it, you're reading a timeline.

This connects directly to agent observability — the audit trail is the structured, queryable layer that makes agent behavior debuggable.

Five Anti-Patterns That Will Get You Paged

❌ Anti-Pattern 1: Approve-Everything Default

The mistake: The HITL layer exists, but the default confidence threshold is set so low (or the auto-approve policy so permissive) that 99% of actions pass through without human review.

Why it happens: Initial deployment generates too many review requests. Reviewers complain. The team lowers thresholds to reduce noise. Gradually, the gate becomes meaningless.

The fix: Set thresholds based on action risk, not reviewer workload. If reviewers are overwhelmed, the answer is better confidence scoring and smarter routing — not lowering the bar. Track the approval rate per tool: if it's above 95%, your gate is not actually gating anything. Investigate whether the actions are genuinely low-risk or whether the threshold needs raising.

❌ Anti-Pattern 2: Synchronous Blocking on Every Call

The mistake: Every tool call — including read-only queries — blocks on a synchronous human approval. The agent's latency goes from 200ms to 30 seconds. Users abandon.

Why it happens: The team treats all tool calls as equally risky. "Better safe than sorry" becomes "every search needs a stamp."

The fix: Classify tools into risk tiers. Read-only tools (search, get, list, calculate) execute immediately. Side-effect tools (write, delete, send, purchase) go through the gate. This is Pattern 1 — and it exists precisely because blocking everything is worse than not having a gate at all.

❌ Anti-Pattern 3: No Context in Approval Requests

The mistake: The approval request shows "Agent wants to call processRefund" with no further context. The reviewer has to open the conversation log, read the agent's reasoning, check the order details, and then decide. This turns a 30-second decision into a 5-minute investigation.

Why it happens: The approval notification was built as an afterthought. The team focused on the gate mechanism and forgot about the reviewer experience.

The fix: Build the escalation context packet (Pattern 4) as a first-class deliverable, not a nice-to-have. The packet must include: the user's request, the agent's reasoning trace, the proposed action and arguments, the confidence score, the risk level, the deadline, the fallback action, and recent history. A reviewer should be able to decide from the packet alone without opening any other tool.

❌ Anti-Pattern 4: Rubber-Stamp Approvals

The mistake: Reviewers click "Approve" on every item without reading it. The gate exists but provides no actual human judgment.

Why it happens: Cognitive fatigue. When the queue has 50 items and each one takes 30 seconds to review properly, the reviewer's brain switches to auto-pilot. The approval rate approaches 100%, and the gate becomes theater.

The fix: Track reviewer behavior. If a reviewer's approval rate is above 98% over a week, either (a) the routing is sending them too many trivial items — improve confidence thresholds, or (b) the reviewer needs more context per item — improve the escalation packet. Also consider calibration sessions: periodically inject known-bad actions into the queue to test whether reviewers catch them. If reviewers approve planted bad actions, the review process needs restructuring.

❌ Anti-Pattern 5: No Rollback After Approval

The mistake: A reviewer approves an action that turns out to be wrong. But the system has no mechanism to reverse it. The refund went through. The email was sent. The deployment is live. The mistake is permanent.

Why it happens: The team built the approval gate but not the reversal mechanism. They assumed approvals would always be correct.

The fix: Every side-effectful action should have a compensating action. processRefund → reverseRefund. sendEmail → sendRetractionEmail. createDeployment → rollbackDeployment. Not all compensating actions are perfect (you can't un-send an email), but they limit the damage. The audit trail (Pattern 6) should track whether a decision was rolled back and why. When a rollback fires, it should trigger an alert so the team can investigate the root cause — why was a wrong action approved in the first place?

The Full Runtime: 130 Lines of Copy-Paste HITL

Here is the complete HITL runtime combining all six patterns. It includes: risk classification, confidence thresholding, async review queue, escalation packet builder, time-bounded auto-approve with circuit breaker, and audit trail with replay.

// human-in-the-loop.ts — drop-in HITL runtime for AI agents
// Requirements: none (uses native Promise, no external deps)

type RiskLevel = 'read-only' | 'side-effect';
type Decision = 'approved' | 'rejected' | 'auto-approved' | 'expired';

interface ActionContext {
  userRequest: string;
  conversationId: string;
  reasoningTrace: string;
}

interface ReviewItem {
  id: string;
  tool: string;
  args: Record<string, unknown>;
  confidence: number;
  context: ActionContext;
  submittedAt: number;
  deadline: number;
  status: 'pending' | 'approved' | 'rejected' | 'expired';
  reviewer?: string;
}

interface AuditEntry {
  id: string;
  timestamp: string;
  tool: string;
  args: Record<string, unknown>;
  confidence: number;
  decision: Decision;
  reviewer?: string;
  context: ActionContext;
  result?: string;
}

const TOOL_RISK: Record<string, RiskLevel> = {};
const CONFIDENCE_THRESHOLD: Record<string, number> = {};
const AUTO_APPROVE: Record<string, { waitMs: number; maxDaily: number; minConf: number }> = {};
const reviewQueue: ReviewItem[] = [];
const auditLog: AuditEntry[] = [];
const dailyCounts: Record<string, number> = {};

export function registerTool(
  name: string,
  risk: RiskLevel,
  threshold: number,
  autoApprove?: { waitMs: number; maxDaily: number; minConf: number }
): void {
  TOOL_RISK[name] = risk;
  CONFIDENCE_THRESHOLD[name] = threshold;
  if (autoApprove) AUTO_APPROVE[name] = autoApprove;
}

export async function hitlExecute(
  tool: string,
  args: Record<string, unknown>,
  confidence: number,
  context: ActionContext,
  onApprove: (args: Record<string, unknown>) => Promise<string>
): Promise<{ ok: boolean; result?: string; error?: string; decision: Decision }> {
  const risk = TOOL_RISK[tool] ?? 'side-effect';

  // Pattern 1: read-only bypass
  if (risk === 'read-only') {
    const result = await onApprove(args);
    audit(tool, args, confidence, 'auto-approved', context, result);
    return { ok: true, result, decision: 'auto-approved' };
  }

  // Pattern 2: confidence threshold
  if (confidence >= (CONFIDENCE_THRESHOLD[tool] ?? 1.01)) {
    const result = await onApprove(args);
    audit(tool, args, confidence, 'auto-approved', context, result);
    return { ok: true, result, decision: 'auto-approved' };
  }

  // Pattern 3: enqueue for async review
  const id = enqueue(tool, args, confidence, context);

  // Pattern 5: check time-bounded auto-approve
  await sleep(100); // yield to event loop
  const item = reviewQueue.find(r => r.id === id);
  if (!item) return { ok: false, error: 'Review item lost', decision: 'rejected' };

  // Check auto-approve policy
  if (canAutoApprove(tool, confidence)) {
    item.status = 'approved';
    const result = await onApprove(args);
    audit(tool, args, confidence, 'auto-approved', context, result);
    return { ok: true, result, decision: 'auto-approved' };
  }

  // Route to async review — caller handles the wait/fallback
  return {
    ok: false,
    error: `Action ${tool} queued for human review (id: ${id}). Confidence ${confidence.toFixed(2)} below threshold.`,
    decision: 'expired', // caller should handle the pending state
  };
}

export function buildPacket(item: ReviewItem, history: AuditEntry[]): Record<string, unknown> {
  return {
    tool: item.tool,
    args: item.args,
    confidence: item.confidence,
    reasoning: item.context.reasoningTrace,
    userRequest: item.context.userRequest,
    deadline: new Date(item.deadline).toISOString(),
    recentHistory: history.slice(-3).map(h => ({
      decision: h.decision, result: h.result, timestamp: h.timestamp,
    })),
  };
}

export function replayDecision(auditId: string): AuditEntry | undefined {
  return auditLog.find(a => a.id === auditId);
}

// --- Internal helpers ---

function enqueue(
  tool: string,
  args: Record<string, unknown>,
  confidence: number,
  context: ActionContext
): string {
  const id = `rvw_${Date.now()}_${Math.random().toString(36).slice(2, 8)}`;
  reviewQueue.push({
    id, tool, args, confidence, context,
    submittedAt: Date.now(),
    deadline: Date.now() + 3600_000, // 1 hour default
    status: 'pending',
  });
  return id;
}

function canAutoApprove(tool: string, confidence: number): boolean {
  const policy = AUTO_APPROVE[tool];
  if (!policy) return false;
  if (confidence < policy.minConf) return false;
  const today = new Date().toISOString().slice(0, 10);
  const key = `${tool}_${today}`;
  if ((dailyCounts[key] ?? 0) >= policy.maxDaily) return false;
  dailyCounts[key] = (dailyCounts[key] ?? 0) + 1;
  return true;
}

function audit(
  tool: string,
  args: Record<string, unknown>,
  confidence: number,
  decision: Decision,
  context: ActionContext,
  result?: string
): void {
  auditLog.push({
    id: `aud_${Date.now()}_${Math.random().toString(36).slice(2, 8)}`,
    timestamp: new Date().toISOString(),
    tool, args, confidence, decision, context, result,
  });
}

function sleep(ms: number): Promise<void> {
  return new Promise(resolve => setTimeout(resolve, ms));
}

// --- Woodpecker CI gate (optional): assert HITL coverage ---
// Add this to your test suite to enforce that every side-effect tool has a threshold
export function assertHitlCoverage(tools: string[]): string[] {
  const violations: string[] = [];
  for (const t of tools) {
    if (TOOL_RISK[t] === 'side-effect' && !(t in CONFIDENCE_THRESHOLD)) {
      violations.push(`${t}: side-effect tool without confidence threshold`);
    }
  }
  return violations;
}

CI Gate: Enforce HITL Coverage in Your Pipeline

Add this to your .woodpecker.yml to fail the build if any side-effect tool is missing a confidence threshold or HITL registration:

# .woodpecker.yml — HITL coverage gate
steps:
  hitl-coverage:
    image: node:22-slim
    commands:
      - node -e "
        const { registerTool, assertHitlCoverage } = require('./src/human-in-the-loop');
        // Register tools that are known safe
        registerTool('searchDocs', 'read-only', 0);
        registerTool('getOrderHistory', 'read-only', 0);
        registerTool('processRefund', 'side-effect', 0.95);
        registerTool('sendEmail', 'side-effect', 0.90);
        registerTool('deleteRecord', 'side-effect', 1.01);
        registerTool('purchaseCredits', 'side-effect', 1.01);
        const violations = assertHitlCoverage([
          'searchDocs', 'getOrderHistory', 'processRefund',
          'sendEmail', 'deleteRecord', 'purchaseCredits',
        ]);
        if (violations.length > 0) {
          console.error('HITL coverage violations:');
          violations.forEach(v => console.error('  - ' + v));
          process.exit(1);
        }
        console.log('HITL coverage: all tools registered.');
      "

This gate ensures that when a new tool is added to the codebase, the developer must explicitly register it with a risk level and confidence threshold. If they forget, the build fails. This is the same philosophy as the Woodpecker CI migration gate — enforce policy at the pipeline level, not at code review.

Pattern Summary

Pattern What It Does Without It
1. Approval Gate Blocks side-effectful actions until approved Agent executes writes/deletes/sends with no oversight
2. Confidence Threshold Auto-approves high-certainty, routes rest to review Every action blocks (latency) or nothing blocks (no safety)
3. Async Review Queue Batches low-priority decisions for batch review Synchronous blocking destroys latency; reviewers overwhelmed
4. Escalation Packets Gives reviewers full context on one screen Reviewers dig through logs; 30s decision becomes 5min investigation
5. Time-Bounded Auto-Approve Prevents indefinite blocking when reviewers unavailable Queue backs up overnight; users abandon
6. Audit Trail Records every decision for compliance and debugging No way to answer "who approved this?" or "why was this rejected?"

Putting It All Together

Start with Pattern 1 (approval gate) — it's the minimum viable HITL layer. Once that's in place, add Pattern 2 (confidence thresholding) to reduce noise. Then Pattern 6 (audit trail) for compliance. Then Patterns 3-5 to optimize reviewer experience and handle edge cases.

The most common deployment mistake is implementing all six patterns simultaneously. Start with the gate, measure the approval rate, then layer in the optimizations. Each pattern solves a specific failure mode — deploy them in response to observed problems, not as a speculative architecture.

For agents that interact with external systems via MCP, pair this HITL layer with the prompt injection defense patterns — injection attacks bypass HITL by tricking the agent into classifying malicious actions as safe. And for agents that store state across sessions, the memory architecture patterns ensure that HITL decisions persist and inform future routing.
