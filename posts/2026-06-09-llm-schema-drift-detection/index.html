How to Catch Silent LLM Schema Drift

JSON-mode and function-calling guarantees stop being guarantees the moment a model is upgraded, a prompt template is refactored, a library version bumps, or a fallback provider is swapped. This post shows you how to detect that drift in CI before users do, with a copy-paste TypeScript module, a Woodpecker gate, and an alerts runbook.

TL;DR

Schema drift = a previously-valid LLM response shape that suddenly fails downstream validation. It is silent because it is probabilistic: 1 in 200 responses fails Zod validation, gets caught by a generic try/catch, returns a 500 to the user, and never makes it to your error tracker with enough context to see the pattern.

The fix is a 3-signal drift detector that runs on every LLM call: (1) Zod schema validity, (2) golden-response fingerprint similarity, (3) tokenizer-distance signal. Combined into a single driftScore ∈ [0, 1] and asserted at PR time (fail above 0.03) and at runtime (alert above 0.10), you catch drift within one commit instead of one customer ticket.

1. Why "JSON mode: true" is not enough

Every major provider now exposes a JSON mode or a function-calling API that promises "valid JSON conforming to your schema." This is true, with three asterisks that production engineers learn the hard way:

  • Asterisk 1: validity ≠ usefulness. {"answer": "I cannot help with that"} is valid JSON that passes any schema with an answer: string field. The drift you care about is the drift in content, not syntax.
  • Asterisk 2: function-calling is a structured-output attempt, not a guarantee. A model that picks the wrong argument type ("5" instead of 5), adds an unexpected key, or returns a different shape when the prompt is refactored downstream is still using "function calling" correctly from the provider's perspective.
  • Asterisk 3: the schema is a contract with the model, not with the deployment. When you change the prompt, change the model version, or change the libraries, the contract is renegotiated silently. The first 199 calls work; the 200th fails; the 500th fails consistently; you find out three weeks later from a customer.

3. The 3-signal drift detector

A useful drift detector must catch all 4 root causes. One signal is not enough:

  • Zod schema validity alone misses content drift (refusals, wrong-key-but-still-valid answers).
  • Token-by-token string equality misses acceptable paraphrases and breaks on every model upgrade.
  • Embedding cosine similarity alone is too forgiving (refusals can score 0.85 against a valid answer if both are "explaining something technical").

Combine them. Each signal covers a different failure mode, and a weighted composite catches the union.

3.1. The signal formulas

// Signal 1: schema_validity
// Returns 1.0 if Zod parse succeeded, 0.0 otherwise.
const schema_validity = (response: string, schema: ZodSchema) => {
  try {
    const parsed = JSON.parse(response);
    return schema.safeParse(parsed).success ? 1.0 : 0.0;
  } catch { return 0.0; }
};

// Signal 2: golden_fingerprint_similarity
// Hashes the parsed response (sorted keys, normalized whitespace) and
// compares against a frozen golden-dataset fingerprint. Range [0, 1].
import { createHash } from "node:crypto";
const fingerprint = (obj: unknown): string => {
  const canon = JSON.stringify(obj, Object.keys(obj as object).sort());
  return createHash("sha256").update(canon).digest("hex").slice(0, 16);
};
const golden_fingerprint_similarity = (response: string, golden: string[]) => {
  try {
    const fp = fingerprint(JSON.parse(response));
    return golden.includes(fp) ? 1.0 : 0.0;
  } catch { return 0.0; }
};

// Signal 3: tokenizer_distance_signal
// 1 - normalized Levenshtein distance over tokenized strings.
// Robust to model-upgrade paraphrases. Threshold tuned per schema.
const tokenize = (s: string) => s.toLowerCase().match(/[a-z0-9]+/g) || [];
const levenshtein = (a: string[], b: string[]) => {
  const m = a.length, n = b.length;
  const dp = Array.from({ length: m + 1 }, (_, i) =>
    Array.from({ length: n + 1 }, (_, j) => (i === 0 ? j : j === 0 ? i : 0))
  );
  for (let i = 1; i <= m; i++)
    for (let j = 1; j <= n; j++)
      dp[i][j] = a[i-1] === b[j-1]
        ? dp[i-1][j-1]
        : 1 + Math.min(dp[i-1][j], dp[i][j-1], dp[i-1][j-1]);
  return dp[m][n];
};
const tokenizer_distance_signal = (response: string, baseline: string) => {
  const a = tokenize(response), b = tokenize(baseline);
  const max = Math.max(a.length, b.length, 1);
  return 1 - levenshtein(a, b) / max;
};

3.2. The composite drift score

// Composite weights: schema validity is the strict floor; tokenizer
// distance catches paraphrases; golden fingerprint catches content
// regressions. Tune on a labeled 200-sample drift dataset.
const driftScore = (
  response: string,
  schema: ZodSchema,
  goldenFingerprints: string[],
  baseline: string,
) => {
  const s1 = schema_validity(response, schema);
  const s2 = golden_fingerprint_similarity(response, goldenFingerprints);
  const s3 = tokenizer_distance_signal(response, baseline);
  // Floor: if schema is invalid, signal 2 and 3 are not meaningful.
  // Multiply by 0.5 so a single bad signal doesn't fully tank the score.
  return s1 === 0 ? 0 : 0.5 * s1 + 0.3 * s2 + 0.2 * s3;
};

4. The Woodpecker CI gate

The drift detector needs to run in two places: in CI on every PR (fail above 0.03 drift across a 50-sample golden dataset) and in production on every live call (alert above 0.10 with a Slack/PagerDuty hook).

4.1. The reference Woodpecker pipeline

when:
  - pull_request
  - push

          SCORE=$(jq -r '.aggregateDrift' drift-report.json)
          if [ "$(echo "$SCORE > 0.03" | bc -l)" -eq 1 ]; then
            echo "::error file=drift-report.json::drift score $SCORE exceeds 0.03 threshold"
            exit 1
          fi
        fi

  upload-artifact:

      - curl -fsS -H "X-CI-Token: $DRIFT_REPORT_TOKEN" \
          --data-binary @drift-report.json \
          https://drift.internal.algoram99.com/api/v1/reports

labels:
  host: algoram88-mac

4.2. What tests/drift/run-golden.ts does

  1. Loads tests/drift/golden-dataset.jsonl (50 input/expected pairs, frozen in git).
  2. For each pair, calls the production LLM (the same model + same prompt + same library version that runs in prod).
  3. Computes driftScore for every response.
  4. Aggregates the median, p95, and max across the 50 pairs.
  5. Writes drift-report.json with { aggregateDrift, p95Drift, maxDrift, perSample: [...] }.
  6. Returns exit code 0 if aggregateDrift <= 0.03, non-zero otherwise.

The 0.03 threshold is the empirical sweet spot for gpt-4o-class models on a 50-sample dataset. Below 0.03 means "paraphrases only, schema and content intact." Above 0.03 means "at least one sample drifted meaningfully." Tune on your own dataset; the Schema Drift Detector CLI ships a --calibrate flag that bootstraps a threshold from a labeled 200-sample drift set.

5. The runtime alert

CI gates catch drift that you introduced. Runtime alerts catch drift that the provider introduced between your CI run and now. Both are needed; the provider will drift the model at midnight on a Tuesday with no announcement.

5.1. The runtime hook

// In your LLM call wrapper:
import { driftScore } from "./drift";
import { alerts } from "./alerts";

async function callLLM(prompt: string, schema: ZodSchema) {
  const response = await provider.complete(prompt);
  const score = driftScore(
    response,
    schema,
    await loadGoldenFingerprints(),
    await loadBaselineFor(prompt),
  );
  if (score < 0.10) {
    // Below the runtime floor; log only.
    return { response, driftScore: score };
  }
  // Above the runtime floor; alert.
  await alerts.send({
    channel: "llm-drift",
    severity: score < 0.30 ? "warn" : "page",
    payload: { prompt, response, score, schema: schema.description },
  });
  return { response, driftScore: score };
}

6. The 4 anti-patterns that hide drift

Anti-pattern 1: Silent try/catch around LLM calls

// BAD
try {
  return JSON.parse(await llm.complete(prompt));
} catch (e) {
  return { error: "Something went wrong" };
}

This is the #1 cause of silent drift. The Zod parse fails 1 in 200 times, the catch returns a generic error, the user retries, the next call works, and your error tracker never sees a pattern. After 6 weeks of this, you have 14,000 silent failures in your logs and zero alerts. Never catch an LLM parse error without recording the response that failed in a way you can query.

Anti-pattern 2: Schema-only testing

// BAD
it("extracts the user", async () => {
  const result = await extractUser("Jane is 30 years old");
  expect(UserSchema.safeParse(result).success).toBe(true);
});

This passes on the day you write it, the day the model is upgraded, and the day the model starts refusing to extract PII — because the model can return { "user": "I cannot extract personal information" } and the schema is still valid. Always assert on content too: expect(result.user).toBe("Jane"), not just UserSchema.safeParse(...).success.

Anti-pattern 3: Baseline freezing without re-baselining

// BAD
// In your CI:
const expected = fs.readFileSync("golden.json", "utf8");
expect(response).toBe(expected);

Strict equality freezes you to one model version. A model upgrade breaks every test, the team gets alert fatigue, and the next time drift actually matters the team ignores the alert. Use the 3-signal composite (schema + fingerprint + tokenizer distance) instead, with a threshold that allows legitimate paraphrases but fails on real drift.

Anti-pattern 4: Skipping golden dataset updates

A golden dataset that hasn't been updated in 6 months is a fossil. It tests what the model did 6 months ago, not what the model does today. Re-baseline the dataset (with code review) on every quarterly model upgrade; reject PRs that touch the dataset without a corresponding code change to handle the new shape.
