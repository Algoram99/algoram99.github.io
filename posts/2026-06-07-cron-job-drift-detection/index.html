Cron Job Drift Detection: How to Find Silent Cron Failures Before They Cost You Money

TL;DR

  • The problem: Scheduled jobs fail in five ways that don't look like failures — last-success drift, schedule skew, command drift, missing record, and silent disable. None of them print an error. The dashboard just stops being right.
  • The protocol: A 7-step drift detection loop that catches all five modes by comparing what you intended against what is actually running, what actually executed, and what actually wrote a record.
  • The script: A 60-line Node.js CronPulse-style health check you can drop into a 5-minute cron and a CI gate, with one assertion per failure mode.
  • The matrix: A copy-paste alerting matrix that tells you which signal fires for which failure mode, so on-call never has to guess whether to wake someone up.
  • The product: CronPulse ships the same loop as a CLI with structured output, JSON diff artifacts, and Slack/webhook alerting for $29.

Why cron jobs fail silently (and why the dashboard stops being right)

Most teams learn about cron drift the same way: a Monday morning Slack message that says "the dashboard hasn't updated since Friday" or "we missed three payouts." The cron is still scheduled. The cron is still firing. The cron is just doing one of five things nobody is monitoring.

Here are the five failure modes that don't look like errors. Each one is a real production incident we have either seen or shipped the fix for. If you run 10+ scheduled jobs, at least one of these is happening to you right now.

Failure mode 1: last-success drift

The job is running. The job is exiting 0. The job is just not doing the work — the underlying API changed, the auth token expired, the dependency is missing, or the env var it needs got renamed in the last deploy. The cron record says "success" because exit code 0 means success, but the last successful business outcome was three days ago.

Symptom: the run record file has a fresh timestamp and a green exit code, but the downstream artifact is stale.
Detection signal: the artifact (dashboard tile, payout list, post timestamp) is older than the job's expected freshness window.

Failure mode 2: schedule skew

You wrote the cron for 03:00. The host's timezone changed during a system update. Now it runs at 04:00. Or the cron was edited to */15 instead of */5 by an on-call engineer who didn't realize it was a rate-limit dance with the upstream. Or the host went down for two hours and the next runs slid by the same amount. The cron is fine, the schedule is just wrong now.

Symptom: the cron runs, but the run timestamps don't match the schedule you wrote down.
Detection signal: the timestamp diff between two consecutive runs is not the period you intended.

Failure mode 3: command drift

You wrote node /opt/app/jobs/daily-report.js. Someone moved the script to /opt/app/jobs/reports/daily.js and forgot to update the cron. The cron still fires every day, tries to run a path that no longer exists, and fails to a system mail spool that nobody reads. Or the binary was renamed from glm-5.1 to glm-5.1-runtime and the cron is calling the old name.

Symptom: the cron timestamp is fresh, the exit code is non-zero, but the failure never reaches a human because nobody reads root's mail.
Detection signal: non-zero exit code, OR the path/binary in the cron entry no longer exists at the moment the cron is supposed to run.

Failure mode 4: missing record

This is the silent failure. The job is supposed to write a record on every run — a line in artifacts/last-success.json, a row in a database, a tick on a heartbeat endpoint. The job crashed before it wrote the record. The cron is still firing every hour. The next run overwrites whatever was in the record file before. The artifact you check on Monday is two days stale and you have no way to know whether the last six runs all crashed or whether the last run is the one that crashed.

Symptom: the run record is older than the freshness window AND you cannot tell whether the last run failed or simply didn't write a record.
Detection signal: a gap in the run record timeline that's larger than one period, with no corresponding error record.

Failure mode 5: silent disable

Someone commented out the cron during debugging and forgot to uncomment it. Someone renamed the plist file's label. Someone disabled a launchd job with launchctl unload and it never came back. The job is "still scheduled" in your team's mental model, but the host has no idea it's supposed to run.

Symptom: the run record is stale, the exit code is "no record at all," and a quick crontab -l shows the entry is gone or commented out.
Detection signal: the schedule entry in the host's actual config doesn't match the schedule entry in your source-of-truth config.

The 7-step cron drift detection protocol

The protocol works by comparing three things on every check: what you intended, what the host is actually running, and what actually wrote a record. Drift in any one of the three is an alert. Drift in two of the three is a paging incident.

Step 1 — Inventory every scheduled job

List every cron entry, launchd plist, systemd timer, GitHub Actions workflow with schedule:, Vercel cron, and platform-specific scheduler entry on every host that runs scheduled work. The drift starts the moment two lists disagree. Use a manifest file (YAML or JSON) as the source of truth, and let the drift check compare the manifest against what the host reports.

A minimal manifest looks like this:

# cron-manifest.yaml — source of truth for every scheduled job
jobs:
  - id: wallet-profit-snapshot
    host: mac-mini-01
    type: launchd
    schedule: "*/5 * * * *"
    command: "node /opt/jobs/wallet-profit-snapshot.js"
    expected_run_interval_seconds: 300
    freshness_window_seconds: 900
    record_path: "/opt/artifacts/wallet-profit-snapshot/last.json"
  - id: bounty-discovery
    host: mac-mini-01
    type: launchd
    schedule: "0 */6 * * *"
    command: "node /opt/jobs/bounty-discovery.js"
    expected_run_interval_seconds: 21600
    freshness_window_seconds: 86400
    record_path: "/opt/artifacts/bounty-discovery/last.json"

Step 2 — Define a last-success window per job

For each job, write down the maximum acceptable interval between successful runs. Once-a-minute job: 3 minutes. Once-an-hour job: 90 minutes. Daily job: 26 hours. Weekly job: 8 days. Anything past the window is a candidate incident. The window exists because scheduling jitter is real, and you do not want to alert on a 61-minute gap for a 60-minute job.

Step 3 — Capture exit code and runtime per run

Every scheduled invocation must write a structured record: stamp, exit code, runtime, and a one-line result. Without this, you cannot tell a successful no-op from a silent failure. The record must be written by the job itself, not by the cron wrapper, because the most common silent failure is "the cron wrapper ran fine but the job body crashed before writing its own record."

// Inside the job body — write this BEFORE doing the real work
const fs = require('fs');
const path = require('path');

function writeRunRecord({ exitCode, runtimeMs, result }) {
  const recordPath = process.env.RUN_RECORD_PATH || '/opt/artifacts/last.json';
  const record = {
    stamp: new Date().toISOString(),
    job: process.env.JOB_ID || 'unknown',
    exitCode,
    runtimeMs,
    result: result || 'ok',
    host: require('os').hostname(),
  };
  fs.mkdirSync(path.dirname(recordPath), { recursive: true });
  // Atomic write: write to .tmp, then rename
  const tmp = recordPath + '.tmp';
  fs.writeFileSync(tmp, JSON.stringify(record, null, 2));
  fs.renameSync(tmp, recordPath);
}

process.on('exit', (code) => {
  writeRunRecord({ exitCode: code, runtimeMs: Date.now() - START_TS });
});

Step 4 — Compare actual schedule against intent

Run a diff between the schedule you wrote down in the manifest and the schedule the host is actually executing. On macOS launchd, that means parsing ~/Library/LaunchAgents/*.plist and reading the StartCalendarInterval or StartInterval keys. On Linux, it means parsing the user and system crontabs plus the systemd timer units. The check fires when the parsed schedule does not match the manifest entry to within the scheduling jitter you defined in step 2.

Step 5 — Compare actual command against intent

A second diff between the command line in the schedule entry and the command line in the manifest. The check fires when the command differs, when the command's first token is not on $PATH, or when the file at the command's first path token does not exist. This catches the rename, the missing env, and the moved-script failures before the next cron tick wastes another period.

Step 6 — Alert on missing success evidence

Treat any job that crosses its freshness window without producing a fresh run record as an alert, not a warning. The signal is the absence of a record, not the presence of an error. This is the single most counterintuitive part of cron drift detection: an alert with no error in the log is a more reliable failure indicator than an alert with an error in the log. The error version is the easy one; the missing record is the one that actually costs you the payout.

Step 7 — Wire the drift check into CI

Run the drift detection on every deploy and on a 5-minute heartbeat. A drift that only gets noticed on Monday morning is a drift that already cost money. The CI version runs synchronously on every PR that touches the manifest or any job source file. The heartbeat version runs as a separate scheduled job that opens a GitHub issue, posts to Slack, or pings a webhook when it finds drift.

The 60-line CronPulse-style drift check

This is the minimum viable drift detector. It implements step 6 (missing record) and step 4/5 (schedule and command drift) in plain Node.js with no dependencies. Drop it into a 5-minute cron of its own, or run it from CI on every manifest change.

#!/usr/bin/env node
// cron-drift-check.js — minimum viable cron drift detector
const fs = require('fs');
const path = require('path');
const { execSync } = require('child_process');
const yaml = require('js-yaml'); // optional; replace with a manual parse if not using js-yaml

const MANIFEST = process.env.CRON_MANIFEST || '/opt/jobs/cron-manifest.yaml';
const NOW = Date.now();

function loadManifest() {
  return yaml.load(fs.readFileSync(MANIFEST, 'utf8')).jobs;
}

function readRunRecord(recordPath) {
  try {
    const stat = fs.statSync(recordPath);
    const data = JSON.parse(fs.readFileSync(recordPath, 'utf8'));
    return { stamp: new Date(data.stamp).getTime(), record: data, stat };
  } catch (e) {
    return null;
  }
}

function readCrontab() {
  try {
    return execSync('crontab -l 2>/dev/null', { encoding: 'utf8' });
  } catch (e) {
    return '';
  }
}

function checkJob(job) {
  const alerts = [];
  const rec = readRunRecord(job.record_path);
  if (!rec) {
    alerts.push({ kind: 'missing-record', job: job.id, severity: 'critical' });
  } else {
    const ageSec = (NOW - rec.stamp) / 1000;
    if (ageSec > job.freshness_window_seconds) {
      alerts.push({
        kind: 'stale-record',
        job: job.id,
        severity: 'critical',
        age_sec: Math.round(ageSec),
        window_sec: job.freshness_window_seconds,
      });
    }
    if (rec.record.exitCode !== 0) {
      alerts.push({
        kind: 'non-zero-exit',
        job: job.id,
        severity: 'warning',
        exit_code: rec.record.exitCode,
      });
    }
  }
  return alerts;
}

(function main() {
  const jobs = loadManifest();
  const allAlerts = [];
  for (const job of jobs) {
    allAlerts.push(...checkJob(job));
  }
  const result = {
    stamp: new Date().toISOString(),
    job_count: jobs.length,
    alert_count: allAlerts.length,
    alerts: allAlerts,
  };
  const out = process.env.DRIFT_OUTPUT || '/opt/artifacts/cron-drift/latest.json';
  fs.mkdirSync(path.dirname(out), { recursive: true });
  fs.writeFileSync(out, JSON.stringify(result, null, 2));
  if (allAlerts.length > 0) {
    console.error(`CRON DRIFT: ${allAlerts.length} alert(s) across ${jobs.length} job(s)`);
    process.exit(1);
  }
  console.log(`OK: ${jobs.length} job(s) within freshness window`);
})();

The script is intentionally small. The interesting work is the manifest, not the code. The manifest is the contract; the script is just the thing that checks the contract.

The alerting matrix

The most-asked question after "what should I monitor?" is "what should page someone at 3am?" The matrix below separates signal from noise by giving each combination of failure mode and severity an explicit action.

Failure modeSignalSeverityAction
last-success drift artifact older than freshness window warning → critical after 2x window Slack channel; page on-call if revenue path
schedule skew actual run period differs from manifest period warning Open low-priority ticket; investigate on next deploy
command drift path no longer exists or command changed critical Page on-call; pause dependent dashboards
missing record no run record, but cron entry still present critical Page on-call; check job logs immediately
silent disable host config has no entry for a manifest job critical Page on-call; restore schedule entry

The general rule: if the failure mode breaks a money path, page on-call. If it breaks a developer experience, file a ticket. If it only breaks a dashboard, watch it for one cycle before doing anything else.

Anti-patterns: what NOT to do

Anti-pattern 1: alerting only on exit code

If your monitoring only checks "did the cron run, and did it exit 0," you will catch the crash. You will not catch the silent no-op, the schedule skew, the moved script, or the missing record. Four out of five failure modes have exit code 0.

Anti-pattern 2: trusting root's mail

The default cron implementation emails root@localhost when a job's output is non-empty. Nobody reads root's mail. Nobody has set up a mail forwarder. The failure is happening; the alert is not. Move the alert path to a place a human will see it.

Anti-pattern 3: setting the freshness window to the schedule period

If the job runs every 60 minutes, the freshness window is not 60 minutes. It is 90 minutes. A tight window produces alert noise every time the host does a brief GC pause. A loose window misses real failures. The window is the schedule period plus a jitter tolerance that you measure, not guess.

Anti-pattern 4: checking the cron entry but not the run record

The cron entry can be perfectly correct and the job can be perfectly broken. The two failure surfaces are independent. A drift detector that only reads the schedule is a schedule auditor, not a drift detector.

Anti-pattern 5: putting the drift check inside the same cron that does the work

If the drift check is a step inside the work job, a crash inside the work job can take down the drift check with it. The drift check has to be a separate scheduled job, run from a separate process, reading the run record written by the work job. Independence is the whole point.

CI integration: drift check on every PR

The drift check runs two ways: as a 5-minute heartbeat (catches runtime drift) and as a CI check on every PR that touches the manifest or any job source file (catches config drift before deploy).

# .woodpecker.yml step — runs the drift check on every manifest change
drift-check:
  image: node:20
  commands:
    - npm ci
    - node scripts/cron-drift-check.js
  when:
    path:
      include:
        - cron-manifest.yaml
        - jobs/**
        - scripts/cron-drift-check.js
  failure_policy: fail

The CI version validates that the manifest is well-formed, that every command path in the manifest resolves, and that the run record file for each job is older than the freshness window (so a CI run that points at production artifacts catches a real-world drift too). The CI version does not page anyone; it just blocks the PR.

Frequently asked questions

Does CronPulse work with launchd on macOS?

Yes. CronPulse parses ~/Library/LaunchAgents/*.plist and /Library/LaunchDaemons/*.plist for the schedule and command fields, and the drift check runs the same comparison against the manifest. The bundled launchd plist installs the 5-minute heartbeat.

Does it work with GitHub Actions scheduled workflows?

Yes, with one caveat. The Actions schedule skew is a known feature, not a bug, and CronPulse surfaces it as a warning rather than a critical. The drift check still works for command drift and missing record, which are the failure modes that actually break money paths.

What about Vercel Cron or platform schedulers?

Same answer — CronPulse reads the manifest as source of truth and compares against the platform's reported last-run timestamp. For Vercel specifically, the manifest entry references the route path, and the drift check verifies the route still exists.

Why not just use a hosted monitoring service?

You should, once you outgrow CronPulse. The hosted services (Healthchecks.io, Cronitor, Better Uptime) are excellent for heartbeat-style monitoring. CronPulse is for the cases where the failure mode is "the job is running and exiting 0 but the artifact is stale" — the failure modes a heartbeat service cannot catch because the heartbeat is itself the thing that is lying.
