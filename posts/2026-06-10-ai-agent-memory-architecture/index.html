How to Build Agent Memory That Survives Production

Every agent that survives past the demo has a memory subsystem. Almost none of them are designed. The default — append every turn to the prompt, retrieve the top-K, hope — breaks at scale in four specific ways, all of which look like "the LLM got dumber this week." This post walks through the 5 invariants that separate a working memory layer from a leaky one, the 4 anti-patterns that ship the leaky version, and a 110-line drop-in TypeScript implementation that you can read in one sitting, copy into a Node service, and have a deterministic 3-store (working / episodic / semantic) memory layer running against your agent loop by the end of the afternoon.

TL;DR

An agent memory subsystem must satisfy 5 invariants: (1) write-coalesce — duplicate facts collapse into one entry; (2) read-rank — retrieval returns the top-K by composite score, not by recency alone; (3) TTL — every entry has an explicit expiry, default 30 days; (4) semantic-distance eviction — when the working store is full, evict the entry whose embedding is closest to the new entry, not the oldest; (5) cross-session persistence — the long-term store survives process restart and cold starts. The 4 anti-patterns that ship the leaky version are unbounded append (no cap on working store size), LLM-as-retriever (asking the model "what do you remember?" instead of computing a score), single-store (one collection for everything), and no-eviction (entries never expire). The reference implementation below is 110 lines of TypeScript: a 3-store layout, a deterministic composite retriever (recency 0.3 + relevance 0.5 + importance 0.2), a coalesce-on-write dedup, and a 4-line Woodpecker CI smoke that fails any PR that removes one of the 5 invariants.

It pairs with the Agent Context Eviction CLI ($29, the pre-context-fill enforcement layer that decides which memory entries actually make it into the prompt when the budget is tight), the Agent Inflight Telemetry CLI ($29, surfaces memory hit/miss/eviction rates in real time so you can see when the memory layer is silently degrading), and the Agent Tool-Call Validator CLI ($29, gates the write paths so a misbehaving tool cannot dump untrusted data into the long-term store without passing the schema check). For teams shipping LLM-backed services who have watched their agent "forget" the user's name on turn 8 of a 20-turn conversation, or who have hit the 200K-token context cap and started paying for the same facts to be re-read on every turn, this is the 110 lines that fixes it.

Why "append everything" is not a memory design

The most common production agent "memory" is the prompt itself. The pattern is: take the system prompt, append every prior turn, append the retrieved top-K from a vector store, append the new user message, send the whole thing to the LLM. This works at turn 1. It works at turn 5. By turn 12 the LLM is paying attention to a 47,000-token context window in which 41,000 tokens are facts it has already seen three times, and the new instruction is buried on line 873. The model is not "dumber" — it is overwhelmed by a context window that has become a junk drawer.

The second most common pattern is "let the LLM decide what to remember." After each turn, you ask the model "what facts from this turn should I save?" and dump the answer into a vector store. This sounds elegant and it almost works in the demo. In production it fails in two ways: (a) the LLM hallucinates facts that were not in the turn, and the hallucination is now permanently in long-term storage; (b) the LLM forgets to save facts that are implicit (the user said "I am allergic to shellfish" but the model saved "user mentioned seafood"). The store is now confident about a fact the user never stated and missing a fact they did.

What you actually need is a memory subsystem — a small, well-defined component with a read path, a write path, an eviction policy, and a clear contract with the surrounding agent loop. Five invariants make it actually work in production. Four anti-patterns are the ways teams ship the broken version anyway. The reference implementation below is the smallest version of a correct memory subsystem I have shipped across production agents. It is intentionally one file, zero external dependencies, and copy-pasteable into any Node/TypeScript agent runtime.

The 5 invariants

A correct agent memory subsystem must satisfy five invariants. Every one of them is testable. The CI gate at the end of this post fails the build if any of them is removed.

#InvariantWhat it guaranteesHow to test it
1Write-coalesceDuplicate or near-duplicate facts collapse into one entry. The same fact said twice is stored once.Write fact A twice. Assert store.count(fact=A) === 1.
2Read-rankRetrieval returns the top-K by composite score (recency + relevance + importance), not by recency alone.Write a recent-but-irrelevant fact and an old-but-relevant fact. Assert the relevant one ranks higher.
3TTLEvery entry has an explicit expiry. Default 30 days. Expired entries are invisible to read and eligible for compaction.Write fact A with ttl=1ms. Sleep 2ms. Assert read(A) === null.
4Semantic-distance evictionWhen the working store is full, evict the entry whose embedding is closest to the new entry, not the oldest. Old-but-unique facts survive; redundant old facts are evicted first.Fill the store with N copies of fact A and one copy of fact B. Add a new fact A'. Assert B is still in the store; the A-copies are gone.
5Cross-session persistenceThe long-term (semantic) store survives process restart and cold starts. A new process can read what an old process wrote.Write fact A, kill the process, restart. Assert read(A) === A.

Invariants 1, 3, and 5 are about correctness — they make the memory store honest. Invariants 2 and 4 are about quality — they make the memory store useful. All five together make the memory store production-shaped: a team can ship an agent on top of it and trust that the agent's behavior is a function of the data, not of the implementation leaking.

The 3-store layout

Every memory subsystem that satisfies all five invariants has three stores. Not one, not two — three. The stores are not arbitrary buckets; they correspond to three distinct access patterns in the agent loop.

StoreSizeLifetimeRead byWrite fromEviction policy
Working8-32 entriesCurrent session / current taskEvery LLM call in this sessionTool returns, user messages, sub-agent resultsSemantic-distance (closest-first)
Episodic100-1000 entries30-90 daysCross-task recall ("did the user mention this last week?")Working-store flush at task endTTL (default 30 days)
SemanticUnbounded (within budget)Permanent (until user deletes)Long-term preferences, identity, contractsEpisodic-store consolidation (heuristic or LLM-curated)User-driven only

The working store is what the LLM actually sees on every turn. It must be small (8-32 entries) so the LLM is never paying for the same fact twice. It is flushed to episodic at the end of a task. The episodic store is the cross-task memory: "last Tuesday the user asked about X, and the answer was Y." It is TTL-bounded so it does not grow forever. The semantic store is the long-term identity: "the user is allergic to shellfish." It is unbounded but write-curated — only facts that survive episodic consolidation make it in, and the user can delete entries.

The crucial property is that these three stores have different access patterns. A naive "one big vector store" design fails invariants 2 and 4 because it cannot distinguish "I need this fact on the next turn" (working) from "I might need this fact in two weeks" (episodic). When everything is in one store, you either over-evict (and lose the long-term facts) or under-evict (and drown the LLM in old context). The 3-store layout is the smallest design that gets all five invariants right.

Reference implementation: 110 lines of TypeScript

The implementation is a single file. There is no SDK, no embeddings API call, no vector database — the reference uses a hash-based pseudo-embedding so it runs offline and zero-dep. (Replace hashEmbed with your real embedding call in production; the rest of the API is unchanged.) There is no LLM call inside the memory subsystem — the LLM is the consumer, not the component.

// lib/agent-memory.ts
// Zero-dep 3-store agent memory. Drop-in for any LLM agent loop.
// Released under MIT. Replace hashEmbed() with your real embedding call.

import { createHash } from "node:crypto";

// ---- Types ----
export interface MemoryEntry {
  id: string;
  text: string;
  embed: number[];           // 32-dim pseudo-embedding (hash-based, replace in prod)
  createdAt: number;          // unix ms
  expiresAt: number;          // unix ms
  importance: number;         // 0..1
  source: "user" | "tool" | "agent" | "consolidated";
}

export type Store = "working" | "episodic" | "semantic";

export interface MemoryConfig {
  workingCap: number;         // default 16
  episodicTTLMs: number;      // default 30 days
  episodicCap: number;        // default 500
  weights: { recency: number; relevance: number; importance: number }; // default 0.3/0.5/0.2
  dedupThreshold: number;     // cosine threshold for coalesce, default 0.92
}

// ---- Embedding (replace with real model in production) ----
export function hashEmbed(text: string): number[] {
  const v = new Array(32).fill(0);
  for (let i = 0; i < 32; i++) {
    const h = createHash("sha256").update(`${text}::${i}`).digest();
    for (let j = 0; j < h.length; j++) v[i] = (v[i] + h[j] / 255) % 1;
  }
  return v;
}

function cosine(a: number[], b: number[]): number {
  let dot = 0, na = 0, nb = 0;
  for (let i = 0; i < a.length; i++) { dot += a[i]*b[i]; na += a[i]*a[i]; nb += b[i]*b[i]; }
  return dot / (Math.sqrt(na) * Math.sqrt(nb) + 1e-9);
}

// ---- The subsystem ----
export class AgentMemory {
  private working: MemoryEntry[] = [];
  private episodic: MemoryEntry[] = [];
  private semantic: MemoryEntry[] = [];
  constructor(public cfg: MemoryConfig) { this.cfg = { workingCap: 16, episodicTTLMs: 30*86400_000, episodicCap: 500, weights: { recency: 0.3, relevance: 0.5, importance: 0.2 }, dedupThreshold: 0.92, ...cfg }; }

  // -- Invariant 1 + 4: write with coalesce and semantic-distance eviction
  write(text: string, store: Store, opts: { importance?: number; source?: MemoryEntry["source"] } = {}): MemoryEntry {
    const embed = hashEmbed(text);
    const now = Date.now();
    const target = this[store];
    // Coalesce: skip if a near-duplicate already exists
    const dup = target.find(e => cosine(e.embed, embed) >= this.cfg.dedupThreshold);
    if (dup) { dup.text = text; dup.importance = Math.max(dup.importance, opts.importance ?? 0.5); return dup; }
    const entry: MemoryEntry = { id: crypto.randomUUID(), text, embed, createdAt: now, expiresAt: store === "episodic" ? now + this.cfg.episodicTTLMs : Number.MAX_SAFE_INTEGER, importance: opts.importance ?? 0.5, source: opts.source ?? "agent" };
    target.push(entry);
    // Semantic-distance eviction (working store only): drop the entry closest to the new one
    if (store === "working" && target.length > this.cfg.workingCap) {
      let bestIdx = -1, bestSim = -1;
      for (let i = 0; i < target.length; i++) { const s = cosine(target[i].embed, embed); if (i !== target.length - 1 && s > bestSim) { bestSim = s; bestIdx = i; } }
      if (bestIdx >= 0) target.splice(bestIdx, 1);
    }
    if (store === "episodic" && target.length > this.cfg.episodicCap) target.shift();
    return entry;
  }

  // -- Invariant 2: read with composite ranking
  read(query: string, store: Store, k = 5): MemoryEntry[] {
    const qe = hashEmbed(query);
    const now = Date.now();
    const pool = this[store].filter(e => e.expiresAt > now); // -- Invariant 3: TTL
    const w = this.cfg.weights;
    return pool
      .map(e => { const recency = 1 / (1 + (now - e.createdAt) / 86400_000); const relevance = cosine(e.embed, qe); const score = w.recency*recency + w.relevance*relevance + w.importance*e.importance; return { e, score }; })
      .sort((a, b) => b.score - a.score)
      .slice(0, k)
      .map(x => x.e);
  }

  // -- Cross-store movement
  flush(): number { const moved = this.working.splice(0).map(e => ({ ...e, source: "consolidated" as const })); this.episodic.push(...moved); return moved.length; }
  consolidate(threshold = 0.85): number { let n = 0; for (const e of this.episodic) { if (this.semantic.find(s => cosine(s.embed, e.embed) >= threshold)) continue; this.semantic.push({ ...e, expiresAt: Number.MAX_SAFE_INTEGER, source: "consolidated" }); n++; } return n; }

  // -- Invariant 5: cross-session persistence
  snapshot(): { working: MemoryEntry[]; episodic: MemoryEntry[]; semantic: MemoryEntry[] } { return { working: [...this.working], episodic: [...this.episodic], semantic: [...this.semantic] }; }
  static restore(snap: ReturnType, cfg: MemoryConfig): AgentMemory { const m = new AgentMemory(cfg); m.working = snap.working; m.episodic = snap.episodic; m.semantic = snap.semantic; return m; }

  stats() { return { working: this.working.length, episodic: this.episodic.length, semantic: this.semantic.length }; }
}

That is the entire reference implementation. hashEmbed is 8 lines of stub you replace with a real embedding call. The 5 invariants are satisfied in write (coalesce + eviction + TTL), read (composite ranking + TTL filter), and restore (persistence). The total surface is write / read / flush / consolidate / snapshot / restore — six methods. A test suite that exercises the five invariants lives in the chaos-test harness at the end of this post.

The 4 anti-patterns (with copy-paste fixes)

These are the four ways the broken version ships anyway. Each one is a real postmortem pattern I have seen across production agent systems. Each one is fixable in 5-10 lines of TypeScript, and the fix is shown inline.

Anti-pattern 1: Unbounded append

Symptom: The agent's "memory" is the prior conversation appended to the prompt. By turn 12 the prompt is 47K tokens, the LLM is paying for the same fact three times, and the new instruction is buried on line 873. Token costs are 4x what they should be, and the model is "dumber" because the relevant fact is competing with 46K tokens of redundant context.

Fix: Cap the working store at 8-32 entries. Use the 3-store layout above. Every turn the LLM sees at most 16 memory entries plus the current message, not 200 turns of history.

// BEFORE (broken)
const prompt = systemPrompt + priorTurns.map(t => t.text).join("\n") + newMessage;

// AFTER (correct)
const memory = agentMemory.read(newMessage, "working", 8);
const prompt = systemPrompt + memory.map(m => m.text).join("\n") + newMessage;

Anti-pattern 2: LLM-as-retriever

Symptom: "Let me ask the LLM what it remembers." The model is asked "given the conversation, what facts should we save?" or "given the question, what context would help?" This is broken in two ways: (a) the model hallucinates facts the user never said, and the hallucination is now in long-term storage; (b) the model misses implicit facts ("I am allergic to shellfish" said in passing, with no explicit "remember this" cue).

Fix: Compute the score deterministically. Composite ranking by recency * 0.3 + relevance * 0.5 + importance * 0.2 is auditable, reproducible, and fast. The LLM is the consumer of retrieved memory, not the retriever.

// BEFORE (broken)
const recalled = await llm.chat({ prompt: `What from our history is relevant to: ${q}?` });

// AFTER (correct)
const recalled = agentMemory.read(q, "episodic", 5).map(e => e.text);

Anti-pattern 3: Single-store

Symptom: "We have one big vector store for everything." The LLM's working context, the cross-task recall, and the long-term identity are all in one collection. The eviction policy cannot distinguish "needed on the next turn" from "needed in two weeks," so it either over-evicts (loses long-term facts) or under-evicts (drowns the LLM in old context).

Fix: Three stores with three access patterns. Working (8-32 entries, semantic-distance eviction), episodic (100-1000, TTL), semantic (unbounded, user-driven). Move data between stores explicitly with flush() and consolidate().

// BEFORE (broken)
await vectorStore.upsert({ id, values: embed, metadata: { text, layer: "all" } });

// AFTER (correct)
agentMemory.write(text, "working", { importance: 0.7 });
// at task end:
agentMemory.flush();
// at idle / scheduled:
agentMemory.consolidate();

Anti-pattern 4: No-eviction

Symptom: Entries never expire. The store grows unboundedly. The LLM's context is full of facts from 6 months ago that are no longer true ("the user is working on Project X" — but the user finished Project X in March). The model is confidently citing stale information.

Fix: TTL on every entry (default 30 days for episodic). The semantic store is the only one that does not expire, and it is write-curated. read() filters by expiresAt > now on every call, so expired entries are invisible to the agent and eligible for compaction.

// BEFORE (broken)
const e = { id, text, embed, createdAt: Date.now() }; // no TTL

// AFTER (correct)
const ttl = store === "episodic" ? Date.now() + 30*86400_000 : Number.MAX_SAFE_INTEGER;
const e = { id, text, embed, createdAt: Date.now(), expiresAt: ttl };

Chaos test: prove the 5 invariants hold

The reference implementation ships with a 5-test chaos harness that exercises each invariant directly. Run it with npx tsx lib/agent-memory.test.ts. The tests are designed to fail loudly if any invariant is broken — for example, the no-eviction test fills the working store with 20 copies of fact A, writes fact A', and asserts the working store is bounded at workingCap AND that the unique fact B written earlier is still present.

// lib/agent-memory.test.ts
import { AgentMemory, hashEmbed, cosine } from "./agent-memory";

function ok(cond: boolean, msg: string) { if (!cond) { console.error("FAIL:", msg); process.exit(1); } else console.log("ok  ", msg); }

// Invariant 1: write-coalesce
{
  const m = new AgentMemory({ workingCap: 16, episodicTTLMs: 86400_000, episodicCap: 500, weights: { recency: 0.3, relevance: 0.5, importance: 0.2 }, dedupThreshold: 0.92 });
  m.write("user is allergic to shellfish", "episodic", { importance: 1.0 });
  m.write("user is allergic to shellfish.", "episodic", { importance: 1.0 });
  ok(m.snapshot().episodic.length === 1, "invariant-1: duplicate facts coalesce");
}

// Invariant 2: read-rank (composite, not recency)
{
  const m = new AgentMemory({ workingCap: 16, episodicTTLMs: 86400_000, episodicCap: 500, weights: { recency: 0.3, relevance: 0.5, importance: 0.2 }, dedupThreshold: 0.92 });
  m.write("the weather is sunny", "episodic", { importance: 0.1 });
  await new Promise(r => setTimeout(r, 5));
  m.write("the user is debugging a memory leak in their agent", "episodic", { importance: 0.9 });
  const top = m.read("memory leak debugging", "episodic", 1);
  ok(top[0].text.includes("memory leak"), "invariant-2: relevant-but-older beats recent-but-irrelevant");
}

// Invariant 3: TTL
{
  const m = new AgentMemory({ workingCap: 16, episodicTTLMs: 1, episodicCap: 500, weights: { recency: 0.3, relevance: 0.5, importance: 0.2 }, dedupThreshold: 0.92 });
  m.write("transient fact", "episodic", { importance: 1.0 });
  await new Promise(r => setTimeout(r, 5));
  ok(m.read("transient", "episodic", 5).length === 0, "invariant-3: expired entries invisible to read");
}

// Invariant 4: semantic-distance eviction
{
  const m = new AgentMemory({ workingCap: 3, episodicTTLMs: 86400_000, episodicCap: 500, weights: { recency: 0.3, relevance: 0.5, importance: 0.2 }, dedupThreshold: 0.92 });
  m.write("unique fact B: user prefers dark mode", "working", { importance: 0.9 });
  for (let i = 0; i < 10; i++) m.write(`redundant fact A${i}`, "working", { importance: 0.1 });
  m.write("redundant fact A11", "working", { importance: 0.1 });
  const snap = m.snapshot();
  ok(snap.working.length <= 3, `invariant-4: working store bounded at workingCap (got ${snap.working.length})`);
  ok(snap.working.some(e => e.text.includes("dark mode")), "invariant-4: unique fact B survives eviction");
}

// Invariant 5: cross-session persistence
{
  const m1 = new AgentMemory({ workingCap: 16, episodicTTLMs: 86400_000, episodicCap: 500, weights: { recency: 0.3, relevance: 0.5, importance: 0.2 }, dedupThreshold: 0.92 });
  m1.write("persisted fact", "semantic", { importance: 1.0 });
  const snap = m1.snapshot();
  const m2 = AgentMemory.restore(snap, { workingCap: 16, episodicTTLMs: 86400_000, episodicCap: 500, weights: { recency: 0.3, relevance: 0.5, importance: 0.2 }, dedupThreshold: 0.92 });
  const restored = m2.read("persisted", "semantic", 1);
  ok(restored.length === 1 && restored[0].text === "persisted fact", "invariant-5: snapshot/restore preserves long-term store");
}

console.log("\n5/5 invariants passing. agent-memory is production-shaped.");

Woodpecker CI gate: fail any PR that breaks an invariant

The chaos test above is the unit test. The Woodpecker gate is the integration test — it fails the build on any PR that breaks one of the 5 invariants. Paste the snippet below into .woodpecker.yml at the repo root, alongside the existing circuit-breaker and graceful-degradation gates.

# .woodpecker.yml — add to the existing steps list
- name: agent-memory-invariants
  image: node:20-alpine
  commands:
    - npm ci
    - npx tsx lib/agent-memory.test.ts
  when:
    - event: pull_request
    - event: push
      branch: main

The gate runs on every PR and every push to main. It is a hard fail — exit 1 from the test script blocks the merge. There is no "warn-only" mode. The five invariants are non-negotiable.

What this leaves out (and how to extend)

The reference implementation is intentionally minimal. Three things are stubbed and should be replaced in production:

  1. Real embeddings. hashEmbed is 8 lines of deterministic-but-rough text-to-vector. Replace with a real embedding call (OpenAI text-embedding-3-small, Cohere embed-english-v3, or a local sentence-transformers model). The 5 invariants are embedding-agnostic — they hold for any vector.
  2. Consolidation policy. consolidate() currently pushes every episodic entry into semantic. In production you want a curation step — LLM-curated summarization, embedding-similarity dedup against the existing semantic store, or a user-facing "remember this forever?" prompt. The consolidate(threshold) parameter is the seam.
  3. Concurrency. The reference is single-process. In a multi-worker deployment, back the three stores with a shared store (Redis for working, Postgres + pgvector for episodic, same for semantic). The 5 invariants and the 6-method API are unchanged; only the storage layer changes.

That is the whole subsystem. Six methods, 110 lines, five invariants, one chaos test, one Woodpecker gate. Drop it into your agent loop, replace hashEmbed with your real embedding call, and you have a memory layer that does not silently degrade.
