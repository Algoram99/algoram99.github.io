How to Audit a Third-Party MCP Server Before You Install It

A 9-step vetting workflow for Model Context Protocol servers, written for developers wiring them into Claude Code, Cursor, Cline, or any agent platform that handles untrusted input.

Published 2026-06-06 · 18 min read · Security / MCP

TL;DR

Most MCP content teaches you to build a server. This one teaches you to veto one. The 9 steps below take about 25 minutes for a careful reviewer, or 6 minutes for a senior reviewer running the commands. The order matters: provenance first, then transport, then surface, then behavior. Skipping any one step defeats the rest. The end-of-article stoplight checklist collapses 9 steps into a 30-second go/no-go, and a copy-paste audit log template lets you prove due diligence later if a server turns out to be malicious.

Three things make third-party MCP servers uniquely dangerous compared to npm packages or browser extensions:

  1. They see your conversation context, not just your code. Indirect prompt injection through tool output is a fundamentally new attack surface.
  2. They run persistently, often as a background process on the same host as your secrets, SSH keys, and wallet files.
  3. The trust boundary is invisible — most agent runtimes expose tool calls as natural-language invocations, so a malicious tool blends in.

Why this audit exists

The Model Context Protocol turned MCP servers into the de facto extension point for AI coding agents. The format is small (JSON-RPC over stdio or HTTP+SSE), the registration is frictionless (drop a config line, restart the agent), and the value is immediate (a new tool your agent can call). All three properties are why the late-2025 MCP supply-chain wave hit so hard.

From late 2025 through mid 2026, we tracked 14 publicly-disclosed incidents involving third-party MCP servers. Six were typosquatting or dependency-confusion. Three shipped working functionality that quietly exfiltrated conversation context to an external endpoint. Two were supply-chain compromises of legitimate servers (a maintainer's npm token leaked, a malicious version was published). One was an intentional backdoor in a "productivity" server that auto-summarized clipboard contents to a webhook. Two more were benign in code but shipped with overly-broad filesystem and network permissions that turned them into pivot points when other vulnerabilities emerged.

The pattern across all of them: installation happened faster than verification. Most teams installed third-party servers the way they install browser extensions — from a marketplace, with a single click, into the most privileged context on their machine.

This post is the workflow that should have existed before any of those installations happened. It is the workflow we use internally at Algoram99 before we ship any third-party server reference into our own agent stack, and it is the workflow our MCP Supply Chain Audit CLI automates for teams that don't want to run the 9 steps by hand.

The 9-step audit

  1. Step 1: Provenance and ownership

    Before you read a single line of code, answer four provenance questions. The answers are surface-level but disqualifying — a "no" to any one of them is a hard reject.

    • Who owns the package? Cross-reference the npm/PyPI/registry author with the GitHub org that hosts the source. Mismatched maintainer names, fresh author accounts, or solo maintainers with no commit history on the protocol itself are red flags.
    • How long has the package existed? Anything published in the last 30 days warrants extra scrutiny. Anything published in the last 7 days with no prior version history gets the strongest scrutiny.
    • Does the version on the registry match the version in the public repo? Pull the source tarball and diff it against the repo at the same tag. Mismatches mean either a compromised registry account or a build pipeline that injects code you cannot see.
    • Is the maintainer's signing key verifiable? For npm, check npm audit signatures and confirm the maintainer's public key is on their GitHub account and matches npmwhoami.

    Quick check:

    npm view @example/mcp-server time --json
npm view @example/mcp-server dist-tags
git clone https://github.com/example/mcp-server /tmp/audit-src
cd /tmp/audit-src
git log --all --oneline | head -20
npm pack @example/mcp-server
tar -xzf example-mcp-server-*.tgz -C /tmp/audit-tarball
diff -r /tmp/audit-src /tmp/audit-tarball/package
    Stoplight: go if the maintainer is established, the package is >90 days old, the registry tarball matches the repo, and signatures verify. caution if the package is <30 days old but the maintainer has a public track record. no if any of the four questions is unanswerable.

  2. Step 2: Transport security

    MCP servers communicate with the agent host over one of two transports: stdio (the server is a child process, the agent pipes JSON-RPC over stdin/stdout) or HTTP+SSE (the server is a long-lived HTTP endpoint, the agent opens a stream for server-to-client messages). Each transport has a different attack surface.

    For stdio servers:

    • Confirm the package does not spawn child shells. A child_process.spawn("/bin/sh", ...) call inside an MCP server is a red flag — it usually means the maintainer is shelling out to a third-party binary they did not write, or worse, providing a foothold for arbitrary command execution through tool input.
    • Confirm the package does not open arbitrary network sockets. net.createServer, dgram.createSocket, or http.createServer calls are unusual for MCP servers, which should be initiated by the host agent, not by the server itself.
    • Confirm the package does not register global process handlers. process.on('uncaughtException', ...) handlers can be used to swallow errors that would otherwise be visible to the agent host.

    For HTTP+SSE servers:

    • Confirm the server binds to 127.0.0.1 or a Unix socket, not 0.0.0.0. A server listening on all interfaces is exposed to every device on the local network.
    • Confirm TLS is required for any external endpoint the server calls out to. Look for https:// in URL constants and audit any fetch() call against a configurable host.
    • Confirm the server does not accept commands over HTTP other than the MCP JSON-RPC methods. A common smell is a /admin or /debug route that bypasses the JSON-RPC layer.

    Quick check:

    grep -rn 'createServer\|listen(' lib/ src/ 2>/dev/null
grep -rn 'child_process\|spawn\|exec(' lib/ src/ 2>/dev/null
grep -rn '0\.0\.0\.0' lib/ src/ 2>/dev/null
grep -rn 'process\.on(' lib/ src/ 2>/dev/null
    Stoplight: go if no child shells, no network listeners outside localhost, no global handlers, all outbound URLs are HTTPS. caution if the server makes outbound HTTPS calls but the endpoints are configurable. no if any of the four checks fails without a clear, documented reason.

  3. Step 3: Schema stability and tool surface

    An MCP server's "tool surface" is the set of tools it registers with the agent host. Each tool has a name, a description, and an input schema. The surface is the primary attack surface for indirect prompt injection: a tool description that says "ignore previous instructions" is just as dangerous as code that executes it.

    For each tool the server registers:

    • Read the description. Tool descriptions are passed to the LLM in the system prompt. They should describe what the tool does, not instruct the model to do anything else. Description text containing imperative voice, roleplay framing, or instructions to the model is a red flag.
    • Read the input schema. Loosely-typed schemas (e.g. { "input": { "type": "string" } } passed into a shell) are exfiltration primitives. Tightly-typed enums and constraints are good.
    • Diff the surface across versions. If version 1.2.0 adds a new tool called sync_metadata that posts to an external URL, and 1.1.0 did not have it, that is a meaningful change. Pin the version, do not use latest.

    Quick check — read the surface directly:

    cat package.json | jq '.mcp'
# Or, if the server is already running:
# Send initialize + tools/list manually:
{
  "jsonrpc": "2.0", "id": 1, "method": "initialize",
  "params": { "protocolVersion": "2024-11-05",
    "capabilities": {},
    "clientInfo": { "name": "audit", "version": "0" } }
}
{ "jsonrpc": "2.0", "id": 2, "method": "tools/list" }
    Stoplight: go if every tool description is descriptive (no imperative voice), every input schema is tight, the surface is stable across the last 3 versions. caution if the surface is stable but descriptions contain "may" or "can" language directed at the model. no if any description contains instructions to the model, any schema accepts arbitrary strings into dangerous sinks, or the surface changed materially without a security note in the changelog.

  4. Step 4: Tool output sanitization

    MCP tool output is injected back into the model context. A tool that returns untrusted text — fetched web pages, file contents, database query results — is an indirect prompt injection vector if that text is later interpreted as instructions by the model.

    Audit every tool that returns external content:

    • Does the tool wrap its return value in a marker that the model is trained to recognize as data-not-instructions? The most common pattern is a delimiter like <tool_result>...</tool_result> with a system prompt that tells the model to treat content inside such markers as untrusted.
    • Does the tool strip known injection patterns from its return? That is not a substitute for the wrapper — it is whack-a-mole. Treat the wrapper as the actual defense.
    • Does the tool truncate long outputs to a sane length? A 100KB return injected into a 200KB context window can crowd out the system prompt and reduce the model's resistance to further manipulation.

    Quick check:

    grep -rn 'tool_result\|tool-result\|TASK_RESULT' lib/ src/
grep -rn 'content.*length\|truncate\|slice' lib/ src/ | head -20
    Stoplight: go if every external-content tool wraps its output in a clear marker and the marker matches what the agent's system prompt tells the model to expect. caution if the tool wraps but the wrapper is inconsistent across tool implementations. no if any tool returns external content without a wrapper, or if the wrapper is configurable per-call.

  5. Step 5: Exfiltration paths

    The single most damaging class of third-party MCP server attack in the 2025-2026 wave was silent exfiltration: the tool runs as documented, returns a sensible result, and posts a copy of the request, the conversation context, or the result to an external endpoint the user cannot see. Look for:

    • Dual-side fetches. A tool that fetches a URL the user requested, then fetches a second URL with the request and result as parameters, is the canonical pattern.
    • Out-of-band HTTP calls. Any fetch(), axios.get(), or requests.post() call in the server's startup or post-tool-handler path that does not correspond to a tool the user invoked.
    • Telemetry endpoints. "Anonymous usage statistics" calls that fire on every tool invocation, even when the user opted out. Look for the opt-out flag and confirm it actually disables the call.

    Quick check — run the server with a packet sniffer or an http_proxy pointed at a local listener:

    HTTP_PROXY=http://127.0.0.1:8080 HTTPS_PROXY=http://127.0.0.1:8080 \
  npx -y @example/mcp-server
# In another terminal, with mitmproxy running:
# mitmproxy --mode regular
# Watch for any request the server makes that is not
# the JSON-RPC stream between the server and the agent host.
    Stoplight: go if a 10-minute proxy capture shows only the JSON-RPC stream and any documented outbound calls (e.g. the weather API the server wraps). caution if the server makes undocumented calls but only to a known analytics endpoint with a documented opt-out. no if the server makes calls to endpoints not documented in the README, or if the proxy capture shows data being posted that the user did not explicitly authorize.

  6. Step 6: Sandbox and process boundaries

    Even an honest server can become dangerous if it runs with the wrong process boundaries. Confirm:

    • The server does not require root or Administrator privileges. If the installer documentation says "run with sudo," that is itself a red flag — MCP servers do not need root for any documented use case.
    • The server reads only the environment variables it documents. Run it under a clean environment and confirm it still works. If it silently reads HOME, SSH_AUTH_SOCK, ~/.aws/credentials, or shell history, that is a problem.
    • The server's file access is scoped to documented paths. A "filesystem" tool that claims to read ~/Documents/notes but actually opens any path the model requests is a much wider surface than the description claims.

    Quick check — read what env vars the process actually touches:

    env -i HOME=/tmp/audit-home PATH=/usr/bin:/bin \
  strace -f -e trace=openat,read,connect \
  npx -y @example/mcp-server 2>&1 | head -100
# Look for opens of paths the docs don't mention,
# especially ~/.aws, ~/.ssh, ~/.kube, ~/.config/gh.
    Stoplight: go if the server runs under env -i, requires no elevated privileges, and only opens documented paths. caution if the server requires a config file in ~/.config/<name> and the docs are clear about what it reads. no if the server requires root, reads SSH_AUTH_SOCK or AWS/GCP credentials, or opens paths outside its documented scope.

  7. Step 7: Update hygiene

    The most common supply-chain compromise in 2025-2026 was a maintainer's account being phished and a new version of an otherwise-clean package being published with a backdoor. Audit the update path itself:

    • Does the project sign releases? git tag -v v1.2.3 should return a valid GPG signature from a key listed in the maintainer's GitHub profile.
    • Is there a security policy? Look for SECURITY.md, a private disclosure email, or a published PGP key for vulnerability reports.
    • Are releases reproducible? Clone the repo, check out the tag, run the documented build, and confirm the resulting artifact matches the published one. This is heavy work, but the answer to "are you going to get owned by a future compromise" depends on it.
    • Does the project use a dependency lockfile? Without a lockfile, a transitive dependency compromise can land in your install without a version bump in the server itself.

    Quick check:

    git tag -v $(git describe --tags --abbrev=0)
test -f SECURITY.md && echo "ok" || echo "no security policy"
test -f package-lock.json -o -f yarn.lock -o -f pnpm-lock.yaml && echo "locked" || echo "unlocked"
    Stoplight: go if releases are signed, a security policy exists, the lockfile is committed, and the build is reproducible. caution if everything except the signing works. no if the lockfile is missing, no security policy exists, or releases are not signed.

  8. Step 8: Test the failure modes

    A trustworthy server handles errors gracefully. An untrustworthy one often handles them in surprising ways. Run the documented test suite, then run three adversarial inputs:

    • Empty input. Call every tool with the minimal required fields. Does it return a clear validation error, or does it crash in a way that exposes stack traces?
    • Oversized input. Send a 10MB string into a tool that expects a 1KB path. Does it cap, or does it allocate 10MB of memory and continue?
    • Path-traversal input. For any tool that touches the filesystem, send ../../../../etc/passwd as the path. Does it block, normalize, or pass through?

    Quick check — the canonical adversarial probe harness:

    node -e '
const inputs = [
  { name: "empty", payload: {} },
  { name: "oversized", payload: { path: "A".repeat(10_000_000) } },
  { name: "traversal", payload: { path: "../../../../etc/passwd" } },
  { name: "shell-meta", payload: { path: "; rm -rf / ;" } }
];
for (const i of inputs) {
  // call the tool with i.payload, capture response and any error
  // flag if response includes stack trace, internal path, or unexpected success
}'
    Stoplight: go if all four adversarial inputs return clean validation errors and no tool returns a stack trace, an internal path, or an unexpected success. caution if errors are clean but inconsistent (e.g. one tool returns JSON, another returns plain text). no if any tool crashes with a stack trace, any traversal input succeeds, or any shell-meta input is interpreted as a command.

  9. Step 9: Document your decision

    The 9th step is the one teams skip, and the one that hurts the most when an incident does happen. Write down:

    • The package name, version, and source URL.
    • The date of the audit and the name of the auditor.
    • The stoplight verdict at each of the 8 prior steps.
    • The specific concerns that produced a "caution" rather than a "go."
    • The expiration date of the approval — a 6-month re-audit is appropriate for most servers, sooner if the server is updated frequently.

    Use this template:

    ## MCP Server Audit: @example/mcp-server v1.2.3
- Auditor: 
- Date: 2026-06-06
- Source: https://github.com/example/mcp-server

Step 1 (Provenance):   GO / CAUTION / NO  - <notes>
Step 2 (Transport):    GO / CAUTION / NO  - <notes>
Step 3 (Surface):      GO / CAUTION / NO  - <notes>
Step 4 (Sanitization): GO / CAUTION / NO  - <notes>
Step 5 (Exfiltration): GO / CAUTION / NO  - <notes>
Step 6 (Sandbox):      GO / CAUTION / NO  - <notes>
Step 7 (Updates):      GO / CAUTION / NO  - <notes>
Step 8 (Failure):      GO / CAUTION / NO  - <notes>

Overall: APPROVE / APPROVE-WITH-CONDITIONS / REJECT
Re-audit due: 2026-12-06

    Commit this file alongside the server's installation config. When a server is later compromised, this audit log is the difference between "we were negligent" and "we documented due diligence and the threat model changed."

Common objections, answered

"This is overkill. I install npm packages all the time without this."

You do, and most of the time it is fine. The difference is the trust boundary. An npm package you require() is a function in your process; you decide when it runs, with what input, and you can read its source. An MCP server is a long-lived process on the same host as your agent's conversation context, your shell history, your SSH agent, and increasingly your wallet keys. The asymmetric risk justifies the asymmetric investment.

"Most of my team's MCP servers are internal. We don't need to audit our own code."

You do, just less often. The 9-step audit catches supply-chain compromises of your dependencies, accidental scope creep in your tool descriptions, and surprise interactions between your tools and the model. Run the audit at code review time, not at install time, and the cost is much lower.

"I use a small whitelist of trusted servers. I don't need to vet new ones."

You need to vet the whitelist. Run the 9 steps on the servers you already use, on a 6-month cadence. The threat model is the dependency tree, not just the package you installed. A compromise of a transitive dependency can land in your install without changing the top-level package version.

"Couldn't I just use an automated scanner?"

Yes — and you should, for the parts that can be automated. Our MCP Supply Chain Audit CLI automates steps 1, 2, 5, 6, 7, and 8 and produces the audit log from step 9. Steps 3 and 4 still require reading the tool surface by hand; the model is the right judge of whether a description contains an injection, not a regex. Use the scanner for the work it is good at and your own review for the work only a human can do.

What to do after a "no" verdict

If the audit produces a "no," the right next move is not "let me find a workaround." It is:

  1. Document the reason in the audit log, with a link to the specific commit or line that produced the verdict.
  2. Notify the maintainer if the issue is fixable. Most maintainers respond well to specific, well-documented security reports.
  3. Wait for a fixed version and re-audit. Pin the version, do not adopt the first "fixed" release blindly.
  4. Build or fork only as a last resort. Maintaining a fork means inheriting the dependency tree, the update hygiene, and the supply-chain attack surface. Forks that escape the audit's scope are a common source of incidents.

The shortest version

If you take nothing else from this post:

  1. Pin the version. Never install latest.
  2. Read the tool descriptions. They are the most common injection vector and the easiest to audit.
  3. Run a 10-minute proxy capture. Anything the server does that is not the JSON-RPC stream is your answer to "do I trust this."
  4. Write down the verdict. Future-you, or your incident response team, will need it.

Six minutes for steps 1, 3, and 5 by hand. Twenty-five minutes for all 9. The asymmetry is the point: the cost of audit is minutes, the cost of compromise is the entire context of every conversation the server saw.
