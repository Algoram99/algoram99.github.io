How to Migrate from GitHub Actions to a Self-Hosted Woodpecker CI (Step by Step)

TL;DR. GitHub Actions is a great hosted CI until it isn't: free-tier caps, an org-level disable from a billing incident, a privacy requirement that pushes CI off the GitHub runner pool, or a need for a runner inside your own VPC. Self-hosted Woodpecker is a 1-binary server + 1-binary agent that reads .woodpecker.yml from each repo, talks to GitHub over an OAuth2 app, and exposes the same status checks GitHub Actions does. The migration is a translation exercise, not a rewrite — about 80% of workflows map line-for-line, the rest are usually matrix strategy or composite actions. Run both pipelines in parallel for one to two weeks, compare artifact hashes, then delete the .github/workflows/ directory.

Why migrate off GitHub Actions

Most teams don't migrate for ideology. The most common triggers we see in the wild:

  • Free-tier cap. 2,000 minutes/month per private repo on GitHub Free gets used up by a single test matrix. Self-hosted runners do not count toward that cap.
  • Org-level disable. A billing incident, a security review, or a policy violation can flip GitHub Actions off for an account with the error 422: Actions has been disabled for this user. There is no UI toggle on a personal account to re-enable it. New .github/workflows/*.yml files will never execute.
  • Compliance / data residency. Code never leaves your network. Build artifacts and test logs stay on hardware you control.
  • Cost ceiling on Team / Enterprise. Per-minute pricing compounds. A small internal cluster running on a spare NUC is often an order of magnitude cheaper.
  • Local development parity. The same Woodpecker stack that runs in CI can run on a developer laptop against the same .woodpecker.yml, which closes the "works on my machine" gap.

If none of those apply, GitHub Actions is fine. The migration cost is real; don't pay it for fashion.

When Woodpecker is the right answer (and when it isn't)

Pick Woodpecker if…Stay on GitHub Actions if…
You want a single static binary on a Linux box you ownYou want zero ops and the free tier is enough
You need to run jobs on a GPU, a Mac, or an arm64 box you already haveYour matrix only needs GitHub-hosted Linux/Windows/macOS
You need 100+ parallel jobs and the per-minute bill hurtsYou rarely exceed 20 concurrent jobs
You have a 5–50 repo org and one engineer willing to own the CIYou have a 500+ repo org and a platform team already in GitHub
Compliance forbids code from leaving your VPCYou are SOC2 / ISO27001 and GitHub is already an in-scope vendor

Prerequisites

  • A Linux box (or VM, or container host) reachable from the public internet if you want to receive webhooks. A Raspberry Pi 4 with 4 GB RAM is enough for tens of builds per day.
  • Docker installed, or the willingness to run two static binaries under systemd.
  • A GitHub account (or GitHub Enterprise) with permission to register OAuth apps and install them on target repos.
  • One hour of uninterrupted time the first time. Subsequent repos take about five minutes each.

Step 1: Stand up the Woodpecker server + agent

The fastest way is the official Docker Compose file. The smallest viable stack is two services: the server (UI + API) and an agent (runs the actual build steps).

services:
  woodpecker-server:
    image: woodpeckerci/woodpecker-server:v3.15.0
    restart: unless-stopped
    ports:
      - "127.0.0.1:8100:8000"   # bind to loopback; tunnel handles public access
    volumes:
      - woodpecker-data:/var/lib/woodpecker
    environment:
      - WOODPECKER_OPEN=true
      - WOODPECKER_ADMIN=your-github-username
      - WOODPECKER_GITHUB=true
      - WOODPECKER_GITHUB_CLIENT=xxxxxxxx
      - WOODPECKER_GITHUB_SECRET=yyyyyyyy
      - WOODPECKER_AGENT_SECRET=zzzzzzzz
      - WOODPECKER_HOST=https://ci.example.com
      - WOODPECKER_SERVER_ADDR=:8000

  woodpecker-agent:
    image: woodpeckerci/woodpecker-agent:v3.15.0
    restart: unless-stopped
    depends_on: [woodpecker-server]
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
    environment:
      - WOODPECKER_SERVER=woodpecker-server:9000
      - WOODPECKER_AGENT_SECRET=zzzzzzzz
      - WOODPECKER_MAX_WORKFLOWS=4

volumes:
  woodpecker-data: {}

Note the 127.0.0.1:8100 bind on the server port. You do not want the Woodpecker UI exposed to the internet with no auth. Run a Cloudflare quick-tunnel, a Tailscale Funnel, or a Caddy reverse proxy in front of it. The agent can stay on the internal Docker network.

Pitfall: the distroless woodpecker-server image has no wget or curl. If you try to add a healthcheck: with wget --spider ..., the container will fail healthchecks until you switch to test: or run a sidecar. Either remove the healthcheck or run woodpecker-server:v3.15.0 (not :distroless) and use a real wget.

Step 2: Register a GitHub OAuth2 app

This is the single most-failed step in the migration, because the official Woodpecker docs warn explicitly about a thing most people miss: register an OAuth2 App, not a GitHub App. GitHub Apps and OAuth2 Apps share a settings page but the OAuth flow Woodpecker uses is the older authorization_code flow.

  1. Visit https://github.com/settings/developers → New OAuth App.
  2. Application name: Woodpecker CI (local) (or your org's equivalent).
  3. Homepage URL: your tunnel URL, e.g. https://ci.example.com.
  4. Authorization callback URL: https://ci.example.com/authorize — note the trailing /authorize, not /oauth/callback or anything else. Woodpecker hardcodes this path.
  5. Generate a client secret.
  6. Paste client ID and secret into WOODPECKER_GITHUB_CLIENT and WOODPECKER_GITHUB_SECRET from Step 1 and restart.

If you register a GitHub App by accident, login will fail with 400 Bad Request on the callback. The error message is unhelpful. Re-register as an OAuth2 App.

Step 3: Activate the repo and prove a hello-world build

Browse to your tunnel URL, sign in with GitHub, click Repositories, and activate a throwaway repo first. Drop this in the repo root:

when:
  event: [push, manual]

steps:
  hello:
    image: alpine:3.20
    commands:
      - echo "woodpecker alive at $(date -u +%FT%TZ)"

Push to main. The build should turn green in under 30 seconds. If it does, your server, agent, OAuth2, and webhook are all wired correctly. The remainder of the migration is content.

Step 4: Translate a real workflow

Most GitHub Actions workflows translate to Woodpecker with three changes. Here is a representative example.

Before (GitHub Actions)

name: build
on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npm test
        env:
          CI: true
          DATABASE_URL: ${{ secrets.DATABASE_URL }}

After (Woodpecker)

when:
  event: [push, pull_request, manual]
  branch: [main]

steps:
  test:
    image: node:20
    commands:
      - npm ci
      - npm test
    environment:
      CI: 'true'
      DATABASE_URL:
        from_secret: database_url
    when:
      path: [src/**, package.json, package-lock.json]

What changed and why:

  • actions/checkout@v4 is implicit. Woodpecker clones the repo into /woodpecker/src before any step runs. You do not check it out again.
  • actions/setup-node@v4 is replaced by a base image: node:20. The cache: 'npm' becomes a cache: plugin block if you want it, or a commands line that warms ~/.npm via a mounted volume. For most repos, deleting node_modules on each run and re-running npm ci is faster than cache hydration.
  • ${{ secrets.DATABASE_URL }} becomes from_secret: database_url. The case-insensitive key is the secret name you set in the Woodpecker repo settings (snake-cased on first save).
  • The on.push.branches and on.pull_request collapse into a top-level when: block. There is no if: inside steps; you set the gate at the step level with another when:.
  • The path: gate at the end skips the build when only docs change. GitHub Actions users get this for free with paths: at the top; in Woodpecker it lives at the step level.

The things that do not translate

  • Composite actions (action.yml in a subfolder). Woodpecker has plugins, not reusable step collections. The path is to either inline the steps in .woodpecker.yml or convert the composite into a Docker image you reference by tag.
  • Matrix with dynamic axes. Static matrices work; building a 12-axis matrix from the previous step's output does not. Restructure as one step that loops internally.
  • workflow_call reusable workflows. No equivalent. Promote the body into a shared Docker image or copy-paste.
  • OIDC cloud deploy (GCP / AWS). Woodpecker has plugins but the OIDC token format is different. You typically use a long-lived service-account JSON stored as a Woodpecker secret, not a short-lived OIDC token.

Step 5: Migrate secrets

  1. Inventory: gh secret list --json name,visibility,updatedAt on each repo.
  2. Export values to a local file outside the repo with the same names.
  3. In the Woodpecker UI, go to the repo → Secrets → Add Secret. Paste, name, save.
  4. Repeat for org-level secrets: Woodpecker supports Organization secrets that propagate to all repos, similar to GitHub.
Security. Woodpecker stores secrets in the server database. The server volume (woodpecker-data in the compose file above) must be on encrypted disk, the host must be patched, and WOODPECKER_AGENT_SECRET must be a 32+ byte random string. If the agent is compromised, it can read any secret for any active repo.

Step 6: Bridge the webhook so pushes trigger builds

Woodpecker exposes a per-repo webhook URL like https://ci.example.com/hook?access_token=…. For brand-new repos, the easiest path is to add the webhook by hand under Repository → Settings → Webhooks on GitHub. For org-wide rollout, the cleaner path is a Cloudflare Worker that catches the GitHub push and pull_request events and forwards them to Woodpecker. The pattern is the same as the GitHub App webhook delivery: verify the X-Hub-Signature-256 header against your webhook secret, then fetch the Woodpecker hook URL.

Test the bridge by pushing a single-character commit to a non-default branch and watching the Woodpecker UI. The build should appear within 5 seconds.

Step 7: Run both pipelines in parallel, then cut over

Do not delete .github/workflows/ on day one. Run Woodpecker as the new pipeline and leave GitHub Actions as a shadow checker for one to two weeks. Compare:

  • Status check result (green / red).
  • Artifact SHA256 if you upload binaries.
  • Wall-clock duration (Woodpecker is usually faster on a local network).
  • Test failure messages. If the test fails on Woodpecker but passes on GitHub Actions, the cause is almost always a difference in base image (alpine vs debian), a missing actions/checkout clone side-effect, or a network access requirement (Woodpecker containers do not have outbound to GitHub's metadata server).

After a clean two-week overlap, delete .github/workflows/ in a single commit, watch for any workflow file the team forgot about (PR templates, contribution guides referencing workflows, etc.), and confirm the org's Settings → Actions → General is set to "Disallow all actions" to make the migration irreversible.

Verification gates that catch silent regressions

The migration is not "done" when the first green build shows up. It is done when the following all pass:

  1. Status check parity. Every GitHub branch protection rule that referenced build / test now references the Woodpecker step name. Required status checks are a string match on the step display name.
  2. Secret parity. gh secret list count equals the Woodpecker secrets list count, names match case-insensitively, and at least one downstream test exercises each secret (otherwise missing secrets look fine until the day they aren't).
  3. Artifact parity. If GitHub Actions uploaded a binary, the Woodpecker build uploads the same bytes. Compare SHA256.
  4. Cron parity. If you had a schedule: job (nightly build, weekly deploy), the cron: block in .woodpecker.yml produces the same artifact on the same cadence. schedule: in GitHub Actions and cron: in Woodpecker have different time zones — GitHub uses UTC, Woodpecker uses the server's local time unless you set WOODPECKER_CRON_TIMEZONE.
  5. PR preview parity. If you used pull_request to deploy a preview, the Woodpecker pull_request event produces a working preview URL.

Rollback plan

The rollback story is part of why the migration is low-risk: you keep .github/workflows/ until the Woodpecker pipeline is stable. If Woodpecker breaks, the next push will still trigger GitHub Actions (assuming the org-level disable has not happened). For the case where the disable has happened, the rollback story is more interesting:

  • Keep a bare-bones deploy.yml on a separate provider (GitLab CI, CircleCI, Drone) for at least 30 days post-migration. Treat it as cold insurance.
  • Snapshot the Woodpecker server volume nightly. A corrupted SQLite database can be reconstructed from the webhook log if you keep it, but it is faster to roll back to last night's snapshot.
  • Document the OAuth2 app credentials in your password manager. If the dev who set up the OAuth2 app leaves and the org needs to rotate, the rotation is a 5-minute job, not a 5-day archeology project.

Anti-patterns we hit so you don't have to

  1. Storing the OAuth2 client secret in .woodpecker.yml. The file is committed to the repo. The secret goes in the Woodpecker repo's secret store, period.
  2. Sharing the WOODPECKER_AGENT_SECRET across environments. One secret per server. Rotation is a server restart.
  3. Running the agent with WOODEPECKER_MAX_WORKFLOWS=99 on a 4 GB Pi. Each workflow spins a Docker container. Set the max to floor(RAM_GB / 1.5).
  4. Reaching for cron at the top of .woodpecker.yml when you only need a nightly rebuild. A cron trigger fires on the server clock. A push trigger rebuilds on every merge. If you only want nightly, cron is right. If you want "on merge AND at 03:00 for safety", declare both.
  5. Mounting /var/run/docker.sock from the agent into a build step. It is tempting for "let the test spin up Postgres." It also gives the test root on the host. Spin up Postgres as a service container or a sidecar, not via the Docker socket.
  6. Skipping the parallel-run period because Woodpecker "looks fine." The parallel run is where you find the 3% of edge cases: a step that needs an apt package not in the alpine image, a Go test that needs CGO_ENABLED=1, a deploy that needs the GitHub Actions GITHUB_TOKEN (which does not exist on Woodpecker — generate a PAT).
