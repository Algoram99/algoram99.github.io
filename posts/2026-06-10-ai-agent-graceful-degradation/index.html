AI Agent Graceful Degradation Patterns: Return Useful, Not Nothing

Your circuit breaker trips, the primary model times out, the tool returns 500. What does the user see? If the answer is a stack trace, a 503, or a vague "try again later" — you don't have a graceful-degradation layer. You have a failure surface. This post lays out the 6 patterns that separate agents that degrade well from agents that crash, plus a 110-line TypeScript reference, 4 anti-patterns to avoid, and a Woodpecker CI gate that fails any PR that ships silent degradation.

TL;DR — Graceful degradation for AI agents means returning something useful on partial failure, not throwing or returning empty. Six patterns that work together: (1) structured error contracts the caller can branch on, (2) cached fallbacks keyed on the input signature, (3) model-tier downgrades from the primary to a smaller model, (4) partial responses with a confidence score, (5) user-visible degradation signal so the UI can render an honest "less reliable" badge, and (6) degradation telemetry that lets your circuit breaker (the 19th-post guide) learn from real failure shape. The TypeScript reference below wires all six into a single degrade() function you can drop into any agent loop. The Woodpecker CI gate fails when degradation goes silent.

Why graceful degradation is the missing half of agent reliability

The previous post in this series, Circuit Breaker for LLM APIs, covered the stop the bleeding half of agent reliability: when the upstream is unhealthy, stop calling it. But a circuit breaker that only stops the bleeding leaves the user staring at a "Service Unavailable" page. That's not reliability — that's a polite 503.

Reliability is the property that holds when something has gone wrong. The three things an agent must do on a partial failure are: (a) return some value to the user, (b) signal the value's quality so downstream code and the UI can render it honestly, and (c) emit telemetry that the circuit breaker can use to decide when the upstream is healthy again. Skip any of the three and you have a different failure mode — silent corruption, opaque UX, or breakers that never recover.

The six patterns below cover all three. They're ordered from the cheapest (error contracts) to the most expensive (degradation telemetry), but in practice you want all of them wired up — each one fixes a failure mode the others can't.

Pattern 1: Structured error contracts

The base layer. Every failure path in your agent must return an object with a stable shape: { ok: false, code, message, retriable, fallback }. The caller branches on code, not on the exception type or the message string. The fallback field is the bridge to pattern 2 — it tells the caller "here's the cached answer, but it's stale, render it with a confidence badge."

The classic anti-pattern is to throw a string and let the caller string-match: catch (e) { if (e.message.includes("rate limit")) ... }. That breaks the moment the upstream changes its error wording. The fix is to map upstream error shapes to your own enum at the boundary, and only your own enum touches the rest of the code.

Pattern 2: Cached fallbacks

For high-traffic deterministic queries ("what's the status of order #12345", "summarize ticket #ABC"), a cache layer in front of the LLM turns an upstream outage into a degraded-but-correct response. The cache key should be the semantic signature of the request, not the literal prompt — the same logical question phrased two different ways should hit the same cache slot.

Two design choices matter. First, stale-while-revalidate: serve the cached answer immediately, mark it stale, refresh in the background. The user gets a fast response; the cache self-heals. Second, confidence discount: cached answers get a confidence: 0.7 cap instead of 1.0, so the UI can render them as "based on data from 2 hours ago" without lying.

Pattern 3: Model-tier downgrades

When the primary model (say, a frontier reasoning model) is timing out but a smaller model on a different provider is still healthy, downgrade. The smaller model's answer is usually wrong on harder questions, but it's right on the 60% of queries that don't need full reasoning power. The user gets an answer instead of a timeout.

The downgrade tier list is built from your eval data, not from vibes. If your eval shows the small model gets 60% of queries correct and the big model gets 80%, the downgrade is worth it when the big model is in a breaker-OPEN state and the user is blocked. If the small model only gets 30%, the downgrade is worse than nothing — show the user the breaker error and let them retry later.

Pattern 4: Partial responses with confidence

When a stream is interrupted mid-response (network drop, breaker trip, model stall), don't throw the partial tokens away. Return them with a partial: true flag and a confidence score that reflects how much of the planned response was delivered. The caller decides: short partial → try to recover, long partial → ship it as a degraded response.

The 19th-post circuit breaker is what triggers this path. When the breaker trips during an in-flight stream, it aborts the stream and the partial-tokens buffer is handed to the degradation layer. Without this layer, those tokens are dropped on the floor and the user sees nothing.

Pattern 5: User-visible degradation signal

The UI must render degraded responses differently from healthy ones. A response served from cache, from a downgraded model, or as a partial should show a small badge: "less reliable than usual" or "based on 2-hour-old data." This is the honest-UX half of graceful degradation. Without it, the user has no way to know that a "no" from the downgraded model might actually be a "yes" from the primary model that they should retry.

The signal is a boolean or enum on the response object (degraded: true | "cached" | "downgraded" | "partial"), and the UI tests for it the same way it tests for ok. The most common anti-pattern is to log the degradation but not propagate it — the response is degraded in your metrics but the UI shows it identically to a healthy response.

Pattern 6: Degradation telemetry

The circuit breaker from the 19th-post guide needs to know why the upstream is unhealthy, not just that it is. Degradation telemetry is the channel: every degrade() call emits a metric with the code, the fallback used, and the duration. When the breaker sees that 90% of the last 1000 calls degraded to "downgraded," it knows the primary is down. When it sees 90% degraded to "partial" with the same code, it knows the upstream is returning corrupt data — different breaker behavior.

The cheapest place to store this is a counter per code in your existing metrics pipeline (Prometheus, OpenTelemetry, CloudWatch — the backend doesn't matter as long as the breaker can read it). A daily review of degradation rates per upstream is the single best signal of "is this provider degrading without anyone noticing."

The 110-line TypeScript reference

The function below wires all six patterns into a single degrade() wrapper you can drop into any agent loop. The shape is guard + fallback + telemetry — the guard classifies the failure, the fallback returns a useful value, the telemetry emits the signal.

// agent-degradation.ts
// Drop into any agent loop. Returns { ok, value, degraded, confidence, code, fallback }.

type ErrorCode =
  | "rate_limited"      // 429, retriable
  | "timeout"           // upstream slow, retriable
  | "breaker_open"      // circuit breaker tripped
  | "upstream_5xx"      // 500/502/503/504
  | "schema_invalid"    // upstream returned bad JSON
  | "stream_aborted"    // partial response
  | "unknown";          // catch-all

type FallbackKind = "none" | "cached" | "downgraded" | "partial" | "synthetic";

interface Degraded<T> {
  ok: boolean;
  value?: T;
  degraded: boolean;
  confidence: number;       // 0.0 - 1.0
  code?: ErrorCode;
  fallback?: FallbackKind;
  message?: string;
}

// 1. Classify upstream errors into our enum.
function classifyError(err: unknown): { code: ErrorCode; retriable: boolean } {
  if (err instanceof Error) {
    if (err.name === "AbortError") return { code: "stream_aborted", retriable: false };
    const msg = err.message.toLowerCase();
    if (msg.includes("429") || msg.includes("rate")) return { code: "rate_limited", retriable: true };
    if (msg.includes("timeout") || msg.includes("econnreset")) return { code: "timeout", retriable: true };
    if (msg.includes("breaker") || msg.includes("open")) return { code: "breaker_open", retriable: false };
    if (msg.match(/5\d\d/)) return { code: "upstream_5xx", retriable: true };
  }
  return { code: "unknown", retriable: false };
}

// 2. Cache lookup. Returns null on miss. Stale entries are flagged.
async function cacheLookup<T>(key: string): Promise<{ value: T; stale: boolean } | null> {
  // Replace with your cache (Redis, KV, in-memory LRU).
  // null = miss. { value, stale: true } = hit but needs refresh.
  return null;
}

// 3. Downgrade to a smaller model. Returns null if the small model also fails.
async function downgrade<T>(input: unknown): Promise<T | null> {
  try { return await callSmallerModel(input); } catch { return null; }
}

// 4. The main degradation wrapper.
export async function degrade<T>(
  primary: () => Promise<T>,
  opts: { cacheKey?: string; partialBuffer?: T; confidenceFloor?: number }
): Promise<Degraded<T>> {
  const confidenceFloor = opts.confidenceFloor ?? 0.5;
  const startedAt = Date.now();

  // Try primary first.
  try {
    const value = await primary();
    return { ok: true, value, degraded: false, confidence: 1.0 };
  } catch (err) {
    const { code, retriable } = classifyError(err);
    emitMetric("agent.degrade", { code, durationMs: Date.now() - startedAt });

    // Path 1: cached fallback.
    if (opts.cacheKey) {
      const hit = await cacheLookup<T>(opts.cacheKey);
      if (hit) {
        return {
          ok: true, value: hit.value, degraded: true,
          confidence: hit.stale ? 0.7 : 0.85,
          code, fallback: "cached",
          message: hit.stale ? "Served from stale cache" : "Served from cache",
        };
      }
    }

    // Path 2: model downgrade.
    if (retriable) {
      const downgraded = await downgrade<T>(/* input from primary closure */);
      if (downgraded !== null) {
        return {
          ok: true, value: downgraded, degraded: true,
          confidence: 0.6, // smaller model = lower confidence
          code, fallback: "downgraded",
          message: "Served by smaller model",
        };
      }
    }

    // Path 3: partial response (stream was aborted but produced some output).
    if (code === "stream_aborted" && opts.partialBuffer) {
      return {
        ok: true, value: opts.partialBuffer, degraded: true,
        confidence: Math.max(0.4, partialCompleteness(opts.partialBuffer)),
        code, fallback: "partial",
        message: "Partial response from interrupted stream",
      };
    }

    // No fallback worked. Return structured error.
    return {
      ok: false, degraded: true,
      confidence: 0, code, fallback: "none",
      message: retriable ? "Transient failure, retry suggested" : "Permanent failure",
    };
  }
}

// 5. Heuristic: how complete is a partial response?
function partialCompleteness(partial: unknown): number {
  if (typeof partial === "string") return Math.min(1, partial.length / 500);
  if (typeof partial === "object" && partial !== null) {
    const fields = Object.keys(partial).length;
    return Math.min(1, fields / 6); // expect ~6 fields
  }
  return 0.3;
}

// 6. Telemetry hook. Wire to your metrics pipeline.
function emitMetric(name: string, fields: Record<string, unknown>): void {
  // Replace with: prometheus.counter(name).inc(1, fields);
  // Or: otel.metrics.getMeter("agent").createCounter(name).add(1, fields);
  console.log(JSON.stringify({ metric: name, ...fields }));
}

Three things to notice in the implementation. First, classifyError() is the only place that touches the upstream's raw error shape — the rest of the code branches on the ErrorCode enum, so changing the upstream's error wording never breaks the degradation layer. Second, the degrade() function never throws — even when every fallback fails, it returns a { ok: false, degraded: true, code } object, which the caller can branch on safely. Third, the emitMetric() call happens before the fallback paths, so the circuit breaker sees the failure classification even on the calls that the degradation layer successfully recovers from.

4 anti-patterns to avoid

Anti-pattern 1: Silent fallback

Wrapping the primary call in a try/catch that returns a hard-coded "Sorry, I can't help with that right now" string. The user sees a response, your metrics show a successful call, and the breaker has no signal. Fix: every fallback must set degraded: true and the telemetry hook must fire.

Anti-pattern 2: Logging the degradation but not propagating it

The response is degraded in your logs but the API response shape is identical to a healthy response. Downstream callers and the UI have no way to render it honestly. Fix: include degraded and fallback in the response object; the UI tests for them the same way it tests for ok.

Anti-pattern 3: Throwing on every error and hoping the caller catches

Sometimes the upstream returns 200 with a malformed body. Throwing a TypeError in your agent and hoping the HTTP layer turns it into a 500 means the caller gets an HTTP error, not a structured degradation. Fix: validate the upstream response shape inside the primary function and return a classified error, not an exception, when the shape is wrong.

Anti-pattern 4: Caching the prompt instead of the intent

Two users asking the same question with slightly different wording miss the cache and hit a dead upstream. Fix: normalize the input to a canonical intent signature before keying the cache, and store the canonical form alongside the cached value.

Woodpecker CI gate: fail on silent degradation

The hardest part of graceful degradation is making sure it doesn't accidentally go silent. The Woodpecker CI gate below fails any PR that introduces a try/catch around an upstream call without a corresponding degrade() wrapper. It runs on every PR and on nightly.

# .woodpecker.yml — degradation gate
when:
  - event: pull_request
  - event: cron
    cron: "nightly-degradation-audit"

steps:
  - name: degradation-audit
    image: node:20
    commands:
      # 1. Every try/catch around a fetch/openai/anthropic call must be inside a degrade() wrapper.
      - node scripts/audit-degradation.mjs
      # 2. Every response that contains a fallback must include the degraded signal in the type.
      - node scripts/audit-degraded-signal.mjs
      # 3. Nightly: run the full chaos test (kill the upstream, confirm degrade() returns useful values).
      - npm run test:chaos-degradation || (test "$CI_COMMIT_EVENT" = "cron" && exit 1)

The audit-degradation.mjs script is a 30-line AST walk: find every try { ... await openai... } catch block, and assert that the catch block either calls degrade() or throws a Degraded object. If a PR introduces a raw try/catch around an LLM call, the gate fails with the file and line number. Nightly, the chaos test kills the upstream and runs the full eval suite — every eval case must still produce a { ok: true, degraded: true } response, not an exception.
