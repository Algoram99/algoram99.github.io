AI Agent Testing Pyramid: 5 Levels, 4 Anti-Patterns, and a Drop-In Test Runner

If your team either runs full LLM evals on every PR (slow, expensive, flaky, and almost nobody reads the failure) or skips straight to a manual smoke test in production — you ship agents blind. This post walks through the 5 levels of an LLM-native testing pyramid, the 4 anti-patterns that waste CI cycles or ship broken agents, a 90-line TypeScript pyramid runner, and a Woodpecker CI gate that runs the matching tier for the matching change type.

TL;DR

The classic Mike Cohn test pyramid (unit → integration → end-to-end) breaks down for LLM agents because the "unit" of an agent is not a function call — it is a tool call shape, an output schema, a multi-step trace, a behavioral grader verdict, and a prompt+model+fixture snapshot. A working AI agent testing pyramid has five levels, not three:

  1. Unit — deterministic tool-call shape (does the agent produce the right JSON shape for search_docs(query, limit)?)
  2. Contract — LLM output schema (does the response match the Zod/JSON-Schema contract the downstream consumer expects?)
  3. Integration — multi-step trace replay (does the agent's trace over a fixed input match the recorded golden trace?)
  4. Eval — behavioral scoring with graders (does the agent pass a rubric on a held-out scenario set?)
  5. Regression — prompt + model + fixture snapshots (did a prompt edit, model swap, or fixture change break anything?)

Each tier has a different cost, a different flake profile, and a different blast radius. The pyramid runner picks the right tier for the right diff (a tool registry change triggers unit + contract; a prompt change triggers regression; a model version bump triggers regression + eval).

Who this is for. Engineering teams who have shipped an agent that returned a 4-argument tool call when only 3 were defined, or who found out about a model-swap regression three weeks after a quiet dependency bump, or who have 800 eval rows but no idea which layer of the pyramid their PR is breaking.

The 5 levels — what each tier catches and what it costs

The single most common failure mode in agent CI is conflating these tiers. A team runs a 600-row eval suite on every PR, takes 18 minutes, and 5% of runs flake because the eval grader is itself LLM-based. Meanwhile a one-line tool-call shape bug ships because nobody runs a 30-millisecond schema test on the agent's tool registry.

Level 1 — Unit (tool-call shape)

The agent runtime is a loop: prompt → LLM → tool call → tool result → prompt. The single highest-leverage test you can write is to assert that the tool call the LLM produces is shape-valid before it ever hits the real tool. The test is 100% deterministic because the LLM call is mocked with a recorded response.

// unit-tier: tool-call shape (deterministic, mocked LLM)
import { validateToolCall } from '@algoram99/agent-tool-call-validator';

const result = validateToolCall(
  { name: 'search_docs', args: { query: 'rate limiting', limit: 5 } },
  { name: 'search_docs', args: { query: 'string', limit: 'int ≤ 100' } }
);
assert(result.valid === true);
assert(result.violations.length === 0);

// Negative case: extra argument
const bad = validateToolCall(
  { name: 'search_docs', args: { query: 'rate limiting', limit: 5, deprecated_flag: true } },
  { name: 'search_docs', args: { query: 'string', limit: 'int ≤ 100' } }
);
assert(bad.valid === false);
assert(bad.violations.includes('unexpected-arg:deprecated_flag'));

This tier is where the Agent Tool-Call Validator lives. It runs in <1 second for 1000 tool specs and is fully deterministic. A failing unit test is a ship blocker: it means the agent runtime is about to call a tool that does not exist or pass the wrong shape, and the failure will be a runtime exception in production.

Level 2 — Contract (LLM output schema)

Once the tool call is shape-valid, the next question is: does the final LLM output (the text the user sees, or the JSON the downstream consumer parses) match the contract that the consumer expects? This is where LLM schema-drift detection lives — the 17th post in this series walks the full contract-tier pattern.

// contract-tier: LLM output schema (deterministic, mocked LLM)
import { z } from 'zod';
import { assertSchema } from '@algoram99/agent-schema-drift-detector';

const AgentResponse = z.object({
  answer: z.string().min(1),
  confidence: z.number().min(0).max(1),
  citations: z.array(z.string().url()).min(1),
});

const llmOutput = {
  answer: 'Rate limiting uses a token bucket per tenant.',
  confidence: 0.92,
  citations: ['https://example.com/rate-limiting'],
};

const r = assertSchema(AgentResponse, llmOutput, { name: 'agent-response-v3' });
assert(r.ok === true);

// Negative case: missing required field
const bad = assertSchema(AgentResponse, { answer: 'x' }, { name: 'agent-response-v3' });
assert(bad.ok === false);
assert(bad.errors[0].path === 'confidence');

The contract tier is the second-fastest gate in your pipeline. The Agent Schema Drift Detector handles the snapshot diff side; the Agent Ingress Firewall handles the same contract check for tool-call responses coming into the agent from untrusted MCP servers.

Why this tier is often skipped. Teams that come from a "test pyramid = unit + e2e" mindset assume contract tests are duplicative with unit tests. They are not. Unit tests verify the LLM-emitted tool call shape; contract tests verify the LLM-emitted final-output shape. Two different code paths, two different consumers, two different failure modes.

Level 3 — Integration (multi-step trace replay)

Once the tool call is valid AND the output schema matches, the next question is: did the agent take the right path through the right tools? This is where you replay a recorded golden trace and assert the new run's trace matches it (allowing for known non-determinism in tool timestamps, trace IDs, and similar).

// integration-tier: multi-step trace replay (deterministic given fixed seed)
import { replayTrace } from '@algoram99/agent-trace-replay';
import { readFileSync } from 'fs';

const golden = JSON.parse(readFileSync('tests/fixtures/golden-trace-rate-q.jsonl', 'utf8'));
const verdicts = replayTrace({
  golden,
  actual: runAgent({ prompt: 'How does rate limiting work?' }),
  stepClasses: ['tool_name', 'tool_args_shape', 'step_count', 'final_answer_schema'],
});

assert(verdicts.tool_name === 'match');
assert(verdicts.tool_args_shape === 'match');
assert(verdicts.step_count === 'match');
assert(verdicts.final_answer_schema === 'match');
assert(verdicts.sessionVerdict === 'PASS');

The integration tier is also where you assert the agent's behavior under load and cost constraints. The 21st post on rate limiting shows a 1000-tool-call chaos test that asserts the per-cost surface trips, not just the per-IP surface — an integration-tier test that catches a class of bugs (token-bucket bursts that exhaust the cost budget but stay under the per-IP limit) that no unit or contract test can detect.

Capture-side infra is the Agent Inflight Telemetry CLI; replay-side is the Agent Trace Replay CLI.

Level 4 — Eval (behavioral scoring)

The eval tier is the one every team starts with and the one that gives the worst ROI when run on every PR. Evals are slow (5-20 minutes), expensive (real LLM calls), and have medium flake (the grader is often an LLM with temperature). The eval tier is the 18th post on eval harnesses, and the core lesson there is: evals belong on the merge-to-main pipeline, not on every PR.

// eval-tier: behavioral scoring (slow, real LLM calls, run on merge-to-main)
import { EvalHarness } from '@algoram99/agent-eval-harness';

const harness = new EvalHarness({
  scenarios: 'evals/scenarios/rate-limiting-questions.jsonl',
  grader: 'rubric-v3',
  model: 'gpt-5.5',
  concurrency: 4,
});

const report = await harness.run({ failOnScoreBelow: 0.85 });
assert(report.passRate >= 0.85);
assert(report.medianLatencyMs <= 8000);
assert(report.totalCostUsd <= 5.00);

The Agent Eval Harness CLI captures the pass rate, median latency, and total cost of the eval run, so you can gate merges on "pass rate ≥ 85% AND median latency ≤ 8s AND total cost ≤ $5."

Level 5 — Regression (prompt + model + fixture snapshots)

The regression tier is the one that catches the most common real-world failure: a prompt edit, a model version bump, or a tool-fixture change that quietly shifts behavior on inputs that were not in the eval set. This is the 25th post on prompt regression testing, sharpened into a pyramid layer.

// regression-tier: prompt + model + fixture snapshot diff
import { RegressionHarness } from '@algoram99/prompt-regression-cli';

const reg = new RegressionHarness({
  fixturesDir: 'tests/fixtures/regression/',
  promptDir: 'prompts/',
  models: ['gpt-5.5', 'claude-sonnet-4.6'],
  thresholds: { similarity: 0.92, tokenBudget: 1.10, schemaMatch: true },
});

const report = await reg.run();
assert(report.diffByModel.gpt_5_5.similarity >= 0.92);
assert(report.diffByModel.claude_sonnet_4_6.tokenBudgetMultiplier <= 1.10);
assert(report.diffByModel.gpt_5_5.schemaMatch === true);

Regression is the tier that catches the silent $400/day cost inflation that comes from swapping gpt-5.5 for gpt-5.5-2025-12-01 when the new version has a 7% token-count regression. The Prompt Regression CLI captures this; the Prompt Mutator CLI generates new candidate prompts to feed the regression suite.

The 4 anti-patterns that waste your CI cycles or ship broken agents

Anti-pattern 1 — Skip unit + contract, run evals on every PR

The most expensive mistake. A team with 600 eval scenarios runs the full eval suite on every PR. CI takes 18 minutes, 5% of runs flake because the grader is itself an LLM with temperature, and the team starts ignoring CI failures ("oh, eval flake again, just retry"). Meanwhile a one-line tool-call shape bug ships because nobody runs the 30-millisecond schema test that would have caught it.

Symptom. CI takes >15 minutes, eval flakes are common, and unit-test coverage on the agent runtime is <40%.

Fix. Run unit + contract on every PR. Run integration on every PR. Run eval only on merge-to-main and on a nightly schedule. The pyramid runner below enforces this.

Anti-pattern 2 — Run only the real LLM, never mock it

The "tests must use the real LLM" school. Every test makes a real API call. The test suite costs $40 per run, takes 12 minutes, and 3% of runs hit rate limits. Worse, the team can no longer test offline or in CI that has no network egress.

Symptom. CI is >10x more expensive than it should be, fails when rate-limited, and cannot run in air-gapped environments.

Fix. Mock the LLM at the unit and contract tiers (record responses once, replay them; the response is deterministic given the same prompt and temperature=0). Reserve real LLM calls for the integration and eval tiers. The regression tier uses a recorded cache for fast iteration and a sampled live run for confidence.

Anti-pattern 3 — Eval as the only quality gate

You have 800 eval rows. You removed the unit tests because "the evals cover it." Now a one-line change to the tool registry breaks the agent for 12% of calls, the eval grader is itself an LLM that gives partial credit, and the eval pass rate drops from 92% to 89% — below your 90% gate, but you have no idea which test or which input is failing.

Symptom. Single quality gate (eval pass rate), no diagnostic depth, and failures point to "the eval suite" rather than to a specific code path.

Fix. The eval is a summary signal, not a diagnostic signal. The unit and contract tiers are the diagnostic signals. When the eval pass rate drops, the pyramid runner points you at the matching unit or contract test that should have caught the same bug at 1000x speed.

Anti-pattern 4 — One golden fixture per prompt

The team has a single "golden" example per prompt. They change the prompt slightly, the single golden output no longer matches, they update the golden, and ship. The regression suite is structurally a tautology — it always passes by construction because the only fixture is the one that was just updated.

Symptom. Regression suite always passes, even when the prompt change visibly degrades behavior on inputs not in the golden fixture.

Fix. Minimum 20 fixtures per prompt: 5 happy path, 5 edge cases (empty input, very long input, unicode, non-English, conflicting instructions), 5 adversarial (prompt-injection-shaped input, off-topic input, tool-failure-shaped input), 5 regression-pin (snapshots from past production failures that must not recur). The Prompt Regression CLI ships with a fixture-coverage reporter that fails the build if any prompt has <20 fixtures.

A 90-line TypeScript pyramid runner

The pyramid runner picks the right tier for the right diff. A change to tools/registry.json triggers unit + contract. A change to prompts/*.md triggers regression. A change to package.json (model version) triggers regression + eval. The runner is intentionally small — it is a router, not an executor; each tier calls out to its existing CLI.

// pyramid-runner.ts — picks the right tier for the right diff
import { execSync } from 'child_process';
import { readFileSync, existsSync } from 'fs';
import { join } from 'path';

type Tier = 'unit' | 'contract' | 'integration' | 'eval' | 'regression';

interface DiffInfo { files: string[]; hasPromptChange: boolean; hasModelChange: boolean; hasToolChange: boolean; hasFixtureChange: boolean; }

function detectDiff(): DiffInfo {
  const diff = execSync('git diff --name-only origin/main...HEAD', { encoding: 'utf8' });
  const files = diff.split('\n').filter(Boolean);
  return {
    files,
    hasPromptChange: files.some(f => f.startsWith('prompts/') && f.endsWith('.md')),
    hasModelChange: files.some(f => f === 'package.json' || f === 'models.lock'),
    hasToolChange: files.some(f => f.startsWith('tools/')),
    hasFixtureChange: files.some(f => f.startsWith('tests/fixtures/')),
  };
}

function selectTiers(d: DiffInfo): Tier[] {
  const tiers: Tier[] = [];
  if (d.hasToolChange) tiers.push('unit', 'contract');
  if (d.hasFixtureChange) tiers.push('integration');
  if (d.hasPromptChange) tiers.push('regression');
  if (d.hasModelChange) tiers.push('regression', 'eval');
  if (tiers.length === 0) tiers.push('unit', 'contract', 'integration');
  return tiers;
}

function runTier(tier: Tier): { tier: string; ok: boolean; durationMs: number } {
  const start = Date.now();
  const cmd: Record<Tier, string> = {
    unit: 'npx @algoram99/agent-tool-call-validator selftest',
    contract: 'npx @algoram99/agent-schema-drift-detector selftest',
    integration: 'npx @algoram99/agent-trace-replay selftest',
    eval: 'npx @algoram99/agent-eval-harness run --gate merge-to-main',
    regression: 'npx @algoram99/prompt-regression-cli selftest',
  };
  try { execSync(cmd[tier], { stdio: 'pipe' }); return { tier, ok: true, durationMs: Date.now() - start }; }
  catch (e) { return { tier, ok: false, durationMs: Date.now() - start }; }
}

const diff = detectDiff();
const tiers = selectTiers(diff);
console.log(`Pyramid tiers selected for diff: ${tiers.join(', ')}`);
const results = tiers.map(runTier);
const failed = results.filter(r => !r.ok);
if (failed.length > 0) {
  console.error(`FAIL: ${failed.map(f => f.tier).join(', ')}`);
  process.exit(1);
}
console.log(`PASS: ${results.length} tiers in ${results.reduce((a, r) => a + r.durationMs, 0)}ms`);

The 6 selftest cases (every pyramid runner must pass these)

  1. Tool-only diff → unit + contract fire, integration + eval + regression do not fire.
  2. Prompt-only diff → regression fires, unit + contract + eval do not fire.
  3. Model-version diff (package.json) → regression + eval fire.
  4. Fixture-only diff → integration fires.
  5. Empty diff (no changes vs main) → all 5 tiers fire (defensive default).
  6. Multi-category diff (tool + prompt + model) → unit + contract + regression + eval all fire; integration fires only if fixtures are also touched.

Woodpecker CI gate — fail any PR that breaks the pyramid

The pyramid runner is the engine. The Woodpecker CI gate is the enforcement. The gate below is 30 lines of YAML that fails any PR that touches an agent runtime file without running the matching pyramid tier. It pairs with the 10th post on CI for AI agents.

# .woodpecker.yml — AI agent testing pyramid gate
steps:
  pyramid:
    image: node:20
    commands:
      - npm ci
      - npx tsx pyramid-runner.ts
    when:
      path:
        include:
          - tools/**/*
          - prompts/**/*.md
          - tests/fixtures/**/*
          - package.json
          - models.lock
          - src/agent/**/*.ts
  eval_nightly:
    image: node:20
    commands:
      - npm ci
      - npx @algoram99/agent-eval-harness run --gate nightly
    when:
      event: cron
      cron: agent_pyramid_eval
What this gate catches. A PR that changes tools/registry.json without running unit tests → fails. A PR that changes a prompt without running regression tests → fails. A PR that bumps a model version without running regression + eval → fails. A PR that touches a runtime file and silently slips through because "we'll catch it in eval" → fails.
