MCP Dynamic Client Registration: OAuth Setup for Remote MCP Servers

Published 2026-07-05 · 48th live post · MCP dynamic client registration, OAuth, protected resource metadata, remote MCP servers

MCP dynamic client registration is where a remote Model Context Protocol server stops being a local developer toy and starts behaving like an OAuth-protected resource. The hard part is not adding a login button. The hard part is making the MCP server discoverable as a protected resource, choosing the right authorization server, registering clients safely, binding tokens to the right audience, and failing clearly when a client or provider does not support dynamic registration.

TLDR for search and SGE: A remote MCP server that requires OAuth should publish protected resource metadata, point clients to the authorization server metadata, support PKCE, validate redirect URIs, bind access tokens to the MCP resource, and protect against confused-deputy token replay. Dynamic Client Registration (DCR) is useful when many MCP clients need to register automatically, but it needs a fallback path for enterprise clients that require pre-registered OAuth applications.

Why this long-tail matters now

The exact phrase MCP dynamic client registration is already showing up in search suggestions, along with operational variants like mcp dynamic client registration not supported, github mcp dynamic client registration, vscode mcp dynamic client registration, mcp oauth dynamic client registration, mcp protected resource metadata, and mcp confused deputy. That is a strong signal: builders are not only reading the Model Context Protocol spec; they are trying to make remote OAuth flows work across real clients.

The gap is practical. OAuth documents describe authorization servers, protected resources, metadata, redirect URIs, and registration endpoints. MCP documents describe the authorization profile for MCP transports. Teams still need a checklist that turns those pieces into deployable remote MCP server behavior.

Source evidence used for this guide

  • MCP Authorization specification, 2025-06-18: states that a protected MCP server acts as an OAuth 2.1 resource server, and references OAuth 2.0 Authorization Server Metadata, OAuth 2.0 Dynamic Client Registration, and OAuth 2.0 Protected Resource Metadata.
  • RFC 9728 — OAuth 2.0 Protected Resource Metadata: defines a metadata format an OAuth client or authorization server can use to obtain information needed to interact with a protected resource.
  • RFC 8414 — OAuth 2.0 Authorization Server Metadata: defines how a client discovers authorization server endpoints and capabilities, including PKCE methods.
  • RFC 7591 — OAuth 2.0 Dynamic Client Registration Protocol: defines mechanisms for dynamically registering OAuth clients with authorization servers.

The roles: do not make the MCP server do every OAuth job

The clean mental model is simple: the remote MCP server is the protected resource. The OAuth provider is the authorization server. The editor, agent host, or MCP client is the OAuth client. The user is the resource owner. Mixing those roles creates insecure shortcuts.

RoleIn a remote MCP deploymentWhat it must publish or validate
Protected resourceYour MCP server endpoint.Protected resource metadata, resource identifier, token audience, required scopes.
Authorization serverIdentity provider or OAuth service that issues tokens.Authorization endpoint, token endpoint, issuer, supported grant types, PKCE support, optional DCR endpoint.
OAuth clientClaude Desktop, VS Code extension, custom agent runtime, or gateway.Client registration, redirect URI, PKCE challenge, token storage, refresh behavior.
Resource ownerThe human or organization authorizing MCP access.Consent boundary and revocation expectations.

Pattern 1: publish protected resource metadata first

Before worrying about client registration, make the MCP server discoverable as a protected resource. The protected resource metadata document tells clients which authorization servers can issue tokens for this resource, what resource identifier to use, and which capabilities or scopes are relevant.

{
  "resource": "https://mcp.example.com/mcp",
  "authorization_servers": [
    "https://auth.example.com"
  ],
  "scopes_supported": [
    "mcp:tools:list",
    "mcp:tools:call",
    "mcp:resources:read"
  ],
  "bearer_methods_supported": ["header"],
  "resource_documentation": "https://mcp.example.com/docs/oauth"
}

Keep this document boring and stable. If the resource identifier changes, old access tokens may no longer validate. If the authorization server list is wrong, clients may obtain a valid token for the wrong audience and still fail against the MCP server.

Pattern 2: discover authorization server metadata before assuming endpoints

A common bad implementation hardcodes /authorize, /token, and /register paths. That works against one provider and fails everywhere else. The client should discover authorization server metadata and read the actual endpoint URLs and supported features.

async function fetchJson(url) {
  const res = await fetch(url, { headers: { accept: "application/json" } });
  if (!res.ok) throw new Error(`${url} returned ${res.status}`);
  return res.json();
}

async function discoverOAuth(resourceMetadataUrl) {
  const resource = await fetchJson(resourceMetadataUrl);
  const issuer = resource.authorization_servers?.[0];
  if (!issuer) throw new Error("protected resource metadata has no authorization server");
  const authMeta = await fetchJson(`${issuer.replace(/\/$/, "")}/.well-known/oauth-authorization-server`);
  for (const field of ["issuer", "authorization_endpoint", "token_endpoint"]) {
    if (!authMeta[field]) throw new Error(`authorization metadata missing ${field}`);
  }
  return { resource, authMeta };
}

Authorization server metadata is also where you learn whether PKCE methods are supported, which token endpoint auth methods exist, and whether dynamic client registration is available.

Pattern 3: use Dynamic Client Registration only when the provider actually supports it

Dynamic Client Registration lets an MCP client register itself with the authorization server instead of asking an administrator to create an OAuth application by hand. This is valuable for open ecosystems: many editors, agent hosts, and client runtimes can connect without a custom onboarding ticket.

But the long-tail query mcp dynamic client registration not supported exists for a reason. Some providers disable DCR. Some enterprise tenants allow only pre-approved apps. Some local identity stacks support authorization code flow but not registration. Your implementation must detect this and fail with a useful setup path.

Provider stateClient behaviorUser-facing setup text
registration_endpoint presentRegister dynamically, store returned client ID, continue with PKCE."Client registered automatically."
No registration endpointRequire configured client_id and allowed redirect URI."Dynamic registration is not supported. Create an OAuth app and paste the client ID."
DCR endpoint rejects metadataShow exact rejected field, do not retry blindly."Provider rejected redirect URI / grant type / scope. Fix app metadata."
Enterprise policy blocks DCRSwitch to pre-registered client mode."Your tenant blocks dynamic client registration. Use administrator-created app mode."

Pattern 4: bind the token to the MCP resource

The confused-deputy risk is straightforward: a client obtains a token for one resource and presents it to another. If the receiving MCP server accepts it, the authorization server becomes a deputy for unintended access. The fix is audience binding. The token must name the protected MCP resource, and the MCP server must validate that audience before serving tools or resources.

function assertTokenAudience(claims, expectedResource) {
  const aud = Array.isArray(claims.aud) ? claims.aud : [claims.aud];
  if (!aud.includes(expectedResource)) {
    throw new Error(`token audience mismatch: expected ${expectedResource}`);
  }
}

Do this check at the MCP boundary, not inside individual tools. Tool-level checks are still useful for scope, but audience belongs to the resource server gate.

Pattern 5: require PKCE for public MCP clients

Most desktop and agent-host MCP clients are public clients. They cannot safely keep a client secret. PKCE is the protection that binds the authorization request to the token exchange. If the authorization server metadata does not advertise a supported PKCE method, treat that as a deployment incompatibility for public clients.

import crypto from "node:crypto";

function base64url(buffer) {
  return buffer.toString("base64").replace(/=/g, "").replace(/\+/g, "-").replace(/\//g, "_");
}

export function createPkcePair() {
  const verifier = base64url(crypto.randomBytes(32));
  const challenge = base64url(crypto.createHash("sha256").update(verifier).digest());
  return { verifier, challenge, method: "S256" };
}

Pattern 6: treat redirect URIs as an allowlist, not a suggestion

Redirect URI validation is one of the easiest places to ship a vulnerability. Do not accept wildcard redirects. Do not normalize away path differences. Do not let a client register https://example.com.evil.test/callback because it "starts with" a trusted domain. Exact match is the default; loopback redirects for local clients should be handled as a narrow special case.

function assertAllowedRedirectUri(uri, allowed) {
  let parsed;
  try { parsed = new URL(uri); } catch { throw new Error("invalid redirect URI"); }
  if (!allowed.includes(parsed.toString())) {
    throw new Error(`redirect URI not allowlisted: ${parsed.toString()}`);
  }
}

Reference implementation: OAuth metadata checker for MCP deployments

This zero-dependency Node script is designed for CI. It checks a protected-resource metadata endpoint, discovers the authorization server metadata, verifies PKCE support, detects whether DCR is available, and emits a clear verdict for remote MCP setup.

// mcp-oauth-readiness.mjs
// Usage: node mcp-oauth-readiness.mjs https://mcp.example.com/.well-known/oauth-protected-resource
import https from "node:https";

const url = process.argv[2];
if (!url) throw new Error("usage: node mcp-oauth-readiness.mjs <protected-resource-metadata-url>");

function getJson(target) {
  return new Promise((resolve, reject) => {
    https.get(target, { headers: { accept: "application/json" } }, res => {
      let body = "";
      res.setEncoding("utf8");
      res.on("data", chunk => body += chunk);
      res.on("end", () => {
        if (res.statusCode < 200 || res.statusCode >= 300) return reject(new Error(`${target} returned ${res.statusCode}`));
        try { resolve(JSON.parse(body)); } catch (e) { reject(new Error(`${target} did not return JSON`)); }
      });
    }).on("error", reject).setTimeout(10_000, function () {
      this.destroy(new Error(`timeout fetching ${target}`));
    });
  });
}

function requireField(obj, field, label) {
  if (!obj || !obj[field]) throw new Error(`${label} missing ${field}`);
  return obj[field];
}

function wellKnownAuthUrl(issuer) {
  return issuer.replace(/\/$/, "") + "/.well-known/oauth-authorization-server";
}

const resource = await getJson(url);
const resourceId = requireField(resource, "resource", "protected resource metadata");
const authorizationServers = requireField(resource, "authorization_servers", "protected resource metadata");
if (!Array.isArray(authorizationServers) || authorizationServers.length === 0) {
  throw new Error("authorization_servers must be a non-empty array");
}

const issuer = authorizationServers[0];
const auth = await getJson(wellKnownAuthUrl(issuer));
for (const field of ["issuer", "authorization_endpoint", "token_endpoint"]) {
  requireField(auth, field, "authorization server metadata");
}
const pkce = auth.code_challenge_methods_supported || [];
const hasS256 = Array.isArray(pkce) && pkce.includes("S256");
const dcr = Boolean(auth.registration_endpoint);
const scopes = resource.scopes_supported || auth.scopes_supported || [];

const verdict = {
  ok: hasS256,
  resource: resourceId,
  issuer: auth.issuer,
  authorization_endpoint: auth.authorization_endpoint,
  token_endpoint: auth.token_endpoint,
  dynamic_client_registration: dcr ? "available" : "not_supported_use_pre_registered_client",
  pkce_s256: hasS256,
  scopes_supported: scopes,
  checks: [
    "protected_resource_metadata_present",
    "authorization_server_metadata_present",
    hasS256 ? "pkce_s256_present" : "pkce_s256_missing",
    dcr ? "registration_endpoint_present" : "registration_endpoint_missing"
  ]
};
console.log(JSON.stringify(verdict, null, 2));
if (!verdict.ok) process.exit(1);

Woodpecker CI gate for remote MCP OAuth readiness

For Algoram99-owned repositories, the CI gate belongs in Woodpecker, not GitHub Actions. Keep the gate read-only: it should fetch metadata, validate shape, and fail if the deployment is not ready. It should not create clients, rotate secrets, or request real tokens in CI.

steps:
  mcp-oauth-readiness:

Five anti-patterns that break MCP OAuth deployments

1. Treating DCR as mandatory everywhere

Some providers do not expose a registration endpoint. A production client needs a pre-registered app fallback.

2. Accepting any bearer token

A token that validates cryptographically can still be for the wrong audience. Check the MCP resource identifier.

3. Wildcard redirect URIs

Convenient redirects become token interception bugs. Use exact allowlists and narrow loopback exceptions.

4. Hardcoded OAuth endpoints

Discovery exists because providers do not agree on paths, features, or supported token auth methods.

5. Scopes with no tool mapping

If mcp:tools:call and mcp:resources:read do not map to concrete handlers, consent becomes decorative.

The deployment checklist

  1. Publish protected resource metadata for the remote MCP endpoint.
  2. List one or more authorization servers that are allowed to issue tokens for that resource.
  3. Fetch authorization server metadata and verify issuer, authorization endpoint, token endpoint, and PKCE support.
  4. Detect whether registration_endpoint exists; if not, document pre-registered client setup.
  5. Use PKCE for public clients and never require a client secret in a desktop client.
  6. Validate redirect URIs exactly during registration and authorization.
  7. Bind access tokens to the MCP resource and validate audience at the resource boundary.
  8. Map OAuth scopes to MCP capabilities: list tools, call tools, read resources, write resources, or admin operations.
  9. Return clear WWW-Authenticate errors that point clients to metadata instead of opaque 401s.
  10. Add a Woodpecker CI metadata gate so endpoint drift fails before release.
