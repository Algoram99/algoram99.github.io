AI Agent Deployment Checklist: 8 Gates for Shipping LLM Agents to Production

Published 2026-07-03 · 44th live post · AI agents, deployment, CI, Woodpecker, rollback

Shipping an LLM-powered agent is not the same as shipping a web endpoint. The agent has prompts, skills, tool permissions, model routes, memory, logs, and cost surfaces that can change without a traditional code diff. This checklist gives teams one deploy gate that catches those changes before the canary receives real users.

Short answer for search and SGE: a production AI-agent deployment checklist needs eight gates: skill lifecycle lock, environment audit, config drift detection, secrets hygiene, SLO baseline, cost attribution cap, trace replay readiness, and canary rollback readiness. Each gate needs an owner, a pass condition, and a rollback action. If a gate cannot be verified by a deterministic command, it is a note, not a deploy control.

Why ordinary deploy checklists miss agent failures

A normal deployment checklist asks whether tests passed, migrations ran, the build artifact exists, and the health check is green. Those are still necessary. They are not sufficient for agents because the failure modes are not only binary up/down failures. A prompt edit can change tool-call behavior while the process stays healthy. A newly loaded skill can expand the runtime's authority without touching application code. A fallback model can double token cost after an outage. A redaction rule can be removed from a logger and still leave every HTTP health check green.

The checklist below treats the agent runtime as a system of contracts. Every contract is verified before release. The goal is not bureaucracy. The goal is to make the risky parts of an agent visible at the exact moment when a deployment can still be stopped cheaply.

The eight deployment gates

Gate 1: lock the skill lifecycle

Agent skills are operational code even when they are written in Markdown. A skill can change tool selection, approval boundaries, prompt structure, and memory behavior. Before deployment, create a resolved skill manifest containing every skill name, version, file hash, declared capability, and hook. The runtime should load only the skills in that manifest. If someone edits a skill after review, the deploy fails instead of quietly mixing reviewed code with unreviewed operating instructions.

For this layer, the related Agent Skill Lifecycle CLI is the catalog fit: it audits skill shape, catches phantom capability names, and gives the release process a lock artifact to compare.

Gate 2 and 3: audit environment and config drift

The second gate proves the host is the host you think it is. Record the Node version, package manager, service user, working directory, required binaries, env-var names, open ports, and outbound network policy. The pass condition is not "the app started"; the pass condition is that the deploy target matches the manifest the team approved.

The third gate catches the hand-edit that does not show up in git. Hash the production config tree, compare it to the committed hash manifest, and fail on any unapproved change. Do not normalize away meaningful differences. If MODEL=fast was changed to MODEL=smart on the host, the deploy should explain that exact axis before traffic moves. The Agent Config Drift Detector CLI maps to this gate.

Gate 4: secrets hygiene before any canary traffic

An agent deployment is not ready if its logs can preserve secrets. Run redaction fixtures for API keys, GitHub tokens, cloud keys, live payment keys, mnemonic phrases, wallet private keys, database URLs, and generic bearer tokens. Then scan a representative session log and confirm the report masks values instead of copying them. This must cover inputs and outputs because model output can leak a secret it saw earlier.

The Agent Secrets Audit CLI is the post-hoc audit layer. Pair it with runtime redaction from the structured logging guide so secrets are prevented first and detected second.

Gate 5 and 6: SLOs and cost caps

A release can be functionally correct and still not be shippable. If p95 latency doubles, tool success falls, or the cost per task jumps from $0.03 to $0.41, the canary is telling you something tests did not. Compute a baseline from the last known-good release, then let the first canary batch compare itself against that baseline. Treat cost as an SLO, not a monthly surprise.

Use the Agent SLO Tracker CLI for availability and latency, and pair it with the cost surfaces described in the LLM cost reduction guide. The deploy gate should fail if a model route, fallback chain, or prompt expansion violates the budget.

Gate 7: replay traces, do not trust vibes

Before release, replay a small corpus of real traces against the new runtime in a staging mirror. The replay should compare tool names, argument shapes, result shapes, policy verdicts, token counts, and final answer class. It does not need the same exact tokens; it does need the same operational behavior. If the new runtime calls a destructive tool where the old runtime only asked for approval, the deploy should stop.

This is where Agent Trace Replay CLI fits. It complements the audit trail: audit proves what happened; replay proves whether the new version would still do the same kind of thing.

Gate 8: prove rollback before rollout

Rollback for agents is not only "deploy the old container." The agent may have sent an email, opened a pull request, wrote a file, called a billing API, or delegated to another worker. Every state-mutating tool needs an idempotency key, a side-effect receipt, and a compensating action. The canary should be allowed to touch only actions that have rollback semantics. Public, financial, destructive, and privacy-impacting actions require human approval until the receipts prove the rollback path works.

The deeper pattern is covered in the idempotency guide, the permission model, and the human-in-the-loop guide.

A compact TypeScript deploy gate runner

type Gate = { name: string; run: () => Promise<{ ok: boolean; detail: string }> };

const gates: Gate[] = [
  { name: "skill-lock", run: () => sh("node scripts/check-skill-lock.mjs") },
  { name: "environment", run: () => sh("node scripts/check-env.mjs") },
  { name: "config-drift", run: () => sh("node scripts/config-drift.mjs") },
  { name: "secrets", run: () => sh("node scripts/secrets-selftest.mjs") },
  { name: "slo", run: () => sh("node scripts/slo-canary.mjs") },
  { name: "cost", run: () => sh("node scripts/cost-cap.mjs") },
  { name: "trace-replay", run: () => sh("node scripts/replay-golden-traces.mjs") },
  { name: "rollback", run: () => sh("node scripts/rollback-readiness.mjs") },
];

async function main() {
  for (const gate of gates) {
    const result = await gate.run();
    console.log(`${gate.name}: ${result.ok ? "PASS" : "FAIL"} ${result.detail}`);
    if (!result.ok) process.exit(1);
  }
}
main().catch(err => { console.error(err); process.exit(1); });

The important property is sequencing. The deploy stops at the first failed gate and prints a repairable reason. That is better than a 4,000-line release report where the dangerous failure is buried halfway down.

Woodpecker CI pattern

when:
  event: [push, pull_request, manual]
steps:
  agent_deploy_check:
    image: node:22-alpine
    commands:
      - npm ci
      - node scripts/agent-deploy-check.mjs
      - node scripts/render-deploy-summary.mjs

Run the gate on every pull request that touches prompts, skills, config, tools, model routes, memory, logging, redaction, or deployment files. On main, run it again before canary promotion. For Algoram99 infrastructure, Woodpecker is the release gate, not GitHub Actions.

Five anti-patterns

  1. Health-check-only deploys: the server is up, but the agent now calls the wrong tool. Add trace replay.
  2. Manual checklist in a doc: nobody knows which boxes were actually verified. Convert every box to a command.
  3. No cost gate: a fallback model makes the release unaffordable while still correct. Treat dollars per task as a release metric.
  4. Canary without rollback: the canary can mutate state but cannot compensate. Block mutating tools until rollback receipts exist.
  5. Secrets checked only at ingress: model output and logs can leak what input filters caught earlier. Scan both sides.

Definition of done

The deployment checklist is complete when a release manager can point at one CI run and answer: which skills loaded, which host ran, which config hashes matched, which redaction fixtures passed, which SLOs stayed within threshold, which cost cap held, which golden traces replayed, and which rollback command would run if the canary failed. If any answer is "we would inspect it manually after the incident," the checklist is not finished.

Keep the checklist small enough that engineers actually run it. Eight gates is enough to catch the agent-specific failures without turning release into paperwork. When a new class of incident appears, add one deterministic probe or tighten one pass condition; do not add a vague reminder. The checklist compounds only when each item can fail the deploy before customers become the monitoring system.
