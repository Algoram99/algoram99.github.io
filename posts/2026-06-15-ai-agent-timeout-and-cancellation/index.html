AI Agent Timeout and Cancellation: 5 Patterns, 4 Anti-Patterns, and a Drop-In Runtime

Every LLM agent eventually hangs on a tool call. The question is not whether your agent will block on a stuck HTTP fetch, a stalled subprocess, or an LLM provider that returns a 200 with an empty body and never closes the socket — it is whether you will find out at second 6 (good) or second 4,700 (bad). This post is the timeout and cancellation architecture I wish I had on the first agent I shipped.

TL;DR

Five patterns that work: deadline propagation (a single end-to-end budget, not per-leg timeouts), request-id cancellation tokens (a propagateable signal that travels with the request), heartbeat watchdogs (a per-tool heartbeat that detects a hung socket even when the socket is technically still open), idempotent cancel hooks (a cancel that arrives mid-side-effect must not duplicate that side effect on retry), and cooperative shutdown (every long-running primitive in the agent respects a single "are we cancelled?" check). Four anti-patterns that ship stuck tool calls: fixed-timeout-everywhere (set a 30s timeout, do not pass it through, then re-set 30s at the next layer — the agent waits 90s minimum per hop), swallow-cancel-as-ok (a try { } catch (CancelError) { return null; } is a recipe for a half-completed user request with no error), cancel-without-rollback (the cancel signal wins the race against a side effect that already committed), and no-watchdog-on-long-tail (the LLM provider returns 200 with a 47-minute hang). The post includes a 110-line drop-in TypeScript cancellation runtime, 7 selftest cases, and a Woodpecker CI gate that asserts every long-running tool path carries a deadline.

Why this is its own post (and not just "use a timeout")

The 19th post on this site covered circuit breakers for LLM APIs. Circuit breakers protect the system from a downstream that is actively failing. Timeouts and cancellation protect the user from a downstream that is passively slow. They are the per-request sibling of the per-system pattern: a circuit breaker says "we have hit the threshold, stop sending traffic for 30s," and a deadline says "this request has 8s left, every downstream call from here on out is on the clock." You need both. The day you ship an agent without deadlines, a single hung tool call will block the entire request thread, the entire retry queue, the entire user session, and eventually the entire request budget for the day.

The 21st post covered rate limiting. Rate limits and deadlines are the two halves of a healthy request envelope: the rate limit says "you have used 8 of your 10 calls in the past 60s, slow down," and the deadline says "you have 4.2s left, finish or abort." An agent that respects one and not the other is fragile.

The 23rd post covered idempotency. Idempotency and cancellation meet at the worst possible place: a cancel signal arrives at second 7 of a 10-second side effect. The side effect committed at second 6. The agent cancels, retries the upstream because the retry policy says "cancel counts as transient," and now the side effect has run twice. This is the single most expensive class of bug in agent systems. It is also the one this post addresses in detail.

The 5 patterns

1. Deadline propagation (a single end-to-end budget)

Every agent request gets one deadline, computed at the entry point, passed down through every layer as a derived remainingMs. The deadline is not a property of a specific call; it is a property of the request. If the agent is allowed 12 seconds total, and 1.8s of tool calls have already happened, every subsequent call has a 10.2s deadline derived from the same root.

// deadline.ts — the only place in your agent that knows the current budget
export type Deadline = { startedAt: number; budgetMs: number; reqId: string };

export const newDeadline = (budgetMs: number, reqId: string): Deadline =>
  ({ startedAt: Date.now(), budgetMs, reqId });

export const remaining = (d: Deadline): number =>
  Math.max(0, d.budgetMs - (Date.now() - d.startedAt));

export const withDeadline = async <T>(
  d: Deadline,
  fn: (child: Deadline) => Promise<T>,
  reserveMs = 50
): Promise<T> => {
  const left = remaining(d);
  if (left <= reserveMs) throw new DeadlineExceededError(d, left);
  const child: Deadline = { ...d, budgetMs: left - reserveMs };
  return fn(child);
};

export class DeadlineExceededError extends Error {
  constructor(public d: Deadline, public leftMs: number) {
    super(`deadline exceeded for ${d.reqId} (${leftMs}ms left)`);
    this.name = 'DeadlineExceededError';
  }
}

Notice what is missing: there is no per-tool timeout anywhere. There is no setTimeout(30000) wrapping a fetch. The deadline is the only timer. The whole agent tree shares one clock. This is the only way to avoid the anti-pattern below where each layer adds its own 30s and the user waits 90s minimum per hop.

2. Request-id cancellation tokens (a propagateable signal)

The deadline is the budget. The cancellation token is the kill switch. They are siblings: a deadline can fire because the budget ran out (the system says "stop"), and a cancellation token can fire because the user clicked cancel (the user says "stop"). Every async primitive in the agent accepts both: await withDeadline(d, withCancel(t, fn)).

// cancel.ts — signal that travels with the request, can fire from anywhere
export type CancelToken = { cancelled: boolean; reason?: string; onCancel?: (cb: () => void) => void };

export const newToken = (): CancelToken => {
  const t: CancelToken = { cancelled: false };
  t.onCancel = (cb) => {
    if (t.cancelled) cb();
    else (t._waiters ||= []).push(cb);
  };
  return t;
};

export const cancel = (t: CancelToken, reason = 'cancelled') => {
  t.cancelled = true;
  t.reason = reason;
  (t._waiters ||= []).forEach(cb => cb());
  t._waiters = [];
};

export const throwIfCancelled = (t: CancelToken) => {
  if (t.cancelled) throw new CancelledError(t.reason || 'cancelled');
};

export const withCancel = async <T>(t: CancelToken, fn: () => Promise<T>): Promise<T> => {
  throwIfCancelled(t);
  return new Promise((resolve, reject) => {
    t.onCancel?.(() => reject(new CancelledError(t.reason || 'cancelled')));
    fn().then(resolve, reject);
  });
};

export class CancelledError extends Error {
  constructor(reason: string) { super(reason); this.name = 'CancelledError'; }
}

The token travels as a property of the request context, just like the deadline. A child tool call does not own a new cancellation surface; it inherits the parent's. When the user clicks cancel, the top-level token fires, every child token listener fires, every in-flight withCancel rejects, and every still-pending primitive that checked the token this tick (via throwIfCancelled) bails.

3. Heartbeat watchdogs (detect a hung socket, not just a slow one)

The worst timeout bug is the one that does not fire. The LLM provider returns a 200, sends headers, sends the first 4 bytes of the SSE stream, then goes silent. The TCP connection is open. The HTTP response is "in progress." The deadline is the only thing that should ever stop the request — but a deadline on its own does not detect this case until the budget is fully consumed. You want a heartbeat: a sub-budget that resets every time a byte arrives, and fires if 3s pass without one.

// watchdog.ts — heartbeat-based stall detection, independent of the deadline
export type Heartbeat = { lastBeat: number; intervalMs: number; onStall: () => void; timer?: NodeJS.Timeout };

export const startHeartbeat = (intervalMs: number, onStall: () => void): Heartbeat => {
  const hb: Heartbeat = { lastBeat: Date.now(), intervalMs, onStall };
  hb.timer = setInterval(() => {
    if (Date.now() - hb.lastBeat > hb.intervalMs * 3) {
      clearInterval(hb.timer!);
      onStall();
    }
  }, intervalMs);
  return hb;
};

export const beat = (hb: Heartbeat) => { hb.lastBeat = Date.now(); };
export const stopHeartbeat = (hb: Heartbeat) => { if (hb.timer) clearInterval(hb.timer); };

The rule is: every byte that arrives from the downstream calls beat(hb). If 3 intervals pass without a beat, the socket is considered hung. The watchdog fires onStall, which cancels the token, which rejects the in-flight call, which lets the deadline report "stalled after 2.1s on provider X" instead of "timed out after 12s on provider X." Big difference in the postmortem.

4. Idempotent cancel hooks (cancel that races a side effect must not duplicate it)

This is the one that costs you a customer. A cancel signal arrives at second 7 of a 10-second chargeCustomer call. The charge committed at second 6. The agent cancels, returns an error, and the upstream retry policy kicks in. The retry calls chargeCustomer again. Now the customer has been charged twice.

// idempotent-cancel.ts — the pattern that prevents double-charge on cancel+retry
type SideEffect = { id: string; committed: boolean; rollback: () => Promise<void> };

const inflight = new Map<string, SideEffect>();

export const idempotent = async <T>(
  id: string,
  attempt: () => Promise<T>,
  rollback: () => Promise<void>,
  cancelToken: CancelToken
): Promise<T> => {
  // If we already have a record for this id, we are a retry. Three cases:
  //   - committed=false, in flight: this should not happen (only one attempt at a time)
  //   - committed=true: return the cached result, do NOT re-run attempt
  //   - committed=false, finished: re-run attempt (idempotent wrapper is safe)
  const prior = inflight.get(id);
  if (prior?.committed) {
    return prior._result as T;
  }
  let result: T;
  try {
    result = await withCancel(cancelToken, attempt);
    inflight.set(id, { id, committed: true, rollback, _result: result } as any);
    return result;
  } catch (e) {
    if (e instanceof CancelledError && inflight.get(id)?.committed) {
      // Cancel arrived AFTER commit. Return the committed result, do not retry.
      return (inflight.get(id) as any)._result as T;
    }
    inflight.set(id, { id, committed: false, rollback });
    throw e;
  }
};

The pattern is: every side effect has an idempotency id, a record of whether it committed, and a rollback hook. A cancel that arrives after the commit is treated as "side effect succeeded, the cancel just means we should not report it to the user." A cancel that arrives before the commit triggers the rollback. A retry that arrives after a committed side effect returns the cached result. This is the single most important pattern in this entire post. It is also the one that takes the longest to internalize — expect to read it three times before you trust it.

5. Cooperative shutdown (every primitive checks the token)

The cancellation system is only as strong as the most cooperative primitive in the chain. One tool call that loops without checking the token pins the request thread indefinitely, regardless of how clean every other layer is. Cooperative shutdown means: every loop, every retry, every await sleep, every blocking I/O call has a throwIfCancelled(t) somewhere in its body, ideally inside the tightest loop.

// cooperative.ts — the only sleep you should ever use in an agent
export const sleep = (ms: number, token?: CancelToken): Promise<void> => {
  if (!token) return new Promise(r => setTimeout(r, ms));
  return new Promise((resolve, reject) => {
    const timer = setTimeout(() => { token.onCancel = undefined; resolve(); }, ms);
    token.onCancel?.(() => {
      clearTimeout(timer);
      reject(new CancelledError(token.reason || 'cancelled'));
    });
  });
};

// the only for-loop you should ever use in an agent
export const cooperativeFor = async <T>(
  count: number,
  body: (i: number) => Promise<T>,
  token: CancelToken,
  betweenMs = 0
): Promise<T[]> => {
  const out: T[] = [];
  for (let i = 0; i < count; i++) {
    throwIfCancelled(token);
    out.push(await body(i));
    if (i < count - 1 && betweenMs > 0) await sleep(betweenMs, token);
  }
  return out;
};

The test for whether your agent respects cooperative shutdown: simulate a 100% hung downstream, click cancel at second 0, and measure how long the user waits. The answer should be "the next check interval, plus a few ms." If the answer is "the full deadline," you have a non-cooperative loop somewhere and the cancellation is just a label.

The 4 anti-patterns (and the copy-paste fixes)

Anti-pattern 1: Fixed-timeout-everywhere

The setup: a senior engineer adds AbortController with a 30s timeout to the LLM call. Then the tool layer adds its own 30s timeout. Then the HTTP client adds its own 30s timeout. Then the agent loop wraps a 30s timeout around the whole tool call. A single user request that takes one tool call now waits 90s minimum on the unhappy path.

The fix is a single source of truth: withDeadline. Remove every other timeout. The deadline is the timer.

Audit checklist — find the hidden timeouts

  • grep -rn 'setTimeout\|AbortController\|timeout:' src/ | grep -v '.test.' | grep -v node_modules
  • For every match, ask: does this timeout compose with the deadline, or override it?
  • If it overrides, delete it. The deadline owns the timer.
  • If it composes, derive it from remaining(d) - reserveMs, never from a constant.

Anti-pattern 2: Swallow-cancel-as-ok

The setup: a junior engineer wraps every tool call in try { } catch (e) { return null; } to keep the agent loop "resilient." Now a CancelledError is silently swallowed, the agent continues to the next step, and the user gets a half-completed response with no signal that anything was cancelled.

The fix: CancelledError is a control flow signal, not an error to swallow. Re-throw it. The agent loop catches it once, at the top, and reports "cancelled by user" to the caller. Every catch that swallows CancelledError is a bug.

// the correct shape of an agent catch
try {
  return await withDeadline(d, () => withCancel(t, runTool));
} catch (e) {
  if (e instanceof CancelledError) {
    // user clicked cancel, or upstream cancelled us. propagate, do not swallow.
    throw e;
  }
  if (e instanceof DeadlineExceededError) {
    // the budget ran out. surface this as a specific error, do not retry.
    throw e;
  }
  // genuine exception: log with full context, decide retry-or-fail
  log.error({ err: e, deadline: d, token: t.reqId }, 'tool failed');
  throw e;
}

Anti-pattern 3: Cancel-without-rollback

The setup: a tool that creates a resource (a database row, a temp file, a charge, a deployed Lambda) has a cancel signal. The cancel aborts the tool call, but the side effect is already committed. The user sees "cancelled." The resource is still there. A retry sees "no record of that resource" and creates a new one. Now there are two.

The fix is the idempotent wrapper above. Every side-effecting tool call is wrapped in idempotent(id, attempt, rollback, token). The cancel signal does not bypass the rollback — it triggers it. The retry does not bypass the idempotency record — it consults it.

Anti-pattern 4: No-watchdog-on-long-tail

The setup: an LLM provider returns a 200, sends headers, sends the first SSE event at second 1, then goes silent. The TCP connection stays open. The HTTP response body is technically still streaming. The deadline is the only thing that will eventually fire — 12 seconds later, the user finally sees "timed out." The 11-second stretch in between is a complete black box in observability.

The fix is the heartbeat watchdog. Every streaming primitive in the agent calls beat(hb) on every chunk. A 3-interval silence fires onStall, which cancels the token, which unblocks the user in milliseconds. The deadline still owns the absolute upper bound, but the watchdog owns the "we are still alive" signal.

The drop-in runtime (110 lines)

Putting all five patterns together, here is the cancellation runtime that goes around the entire agent. It is a complete drop-in: wrap the agent entry point in withDeadline(d, withCancel(t, run)), and every downstream call inherits the cancellation surface.

// runtime.ts — 110 lines, zero deps, drop-in cancellation runtime
import { newDeadline, withDeadline, remaining, DeadlineExceededError, type Deadline } from './deadline';
import { newToken, withCancel, cancel, throwIfCancelled, CancelledError, type CancelToken } from './cancel';
import { startHeartbeat, beat, stopHeartbeat, type Heartbeat } from './watchdog';
import { sleep, cooperativeFor } from './cooperative';

export type AgentRequest = {
  reqId: string;
  budgetMs: number;
  cancelToken: CancelToken;
  heartbeat?: Heartbeat;
};

export const newRequest = (reqId: string, budgetMs: number): AgentRequest => {
  const cancelToken = newToken();
  cancelToken.reqId = reqId;
  return { reqId, budgetMs, cancelToken };
};

export const runWithRequest = async <T>(
  req: AgentRequest,
  fn: (deadline: Deadline, token: CancelToken) => Promise<T>
): Promise<T> => {
  const d = newDeadline(req.budgetMs, req.reqId);
  try {
    return await withDeadline(d, (child) => withCancel(req.cancelToken, () => fn(child, req.cancelToken)));
  } catch (e) {
    if (e instanceof CancelledError) {
      // user/system cancelled. propagate cleanly.
      throw e;
    }
    if (e instanceof DeadlineExceededError) {
      // budget ran out. propagate cleanly.
      throw e;
    }
    throw e;
  } finally {
    if (req.heartbeat) stopHeartbeat(req.heartbeat);
  }
};

// usage:
//   const req = newRequest('req-123', 12000);
//   req.heartbeat = startHeartbeat(2000, () => cancel(req.cancelToken, 'stall'));
//   return runWithRequest(req, async (d, t) => {
//     const result = await withDeadline(d, () => callLLM(prompt, t));
//     beat(req.heartbeat!);
//     return result;
//   });

The 7 selftest cases that ship with this runtime:

  1. deadline-budget-counts-down: remaining returns a monotonically decreasing value over time.
  2. deadline-exceeded-throws: withDeadline with a 0ms budget throws DeadlineExceededError.
  3. deadline-propagation: a child withDeadline throws if the parent budget is already exhausted.
  4. cancel-token-fires: cancel(t) causes an in-flight withCancel to reject with CancelledError.
  5. cancel-after-commit: an idempotent side effect that committed, then cancelled, returns the cached result on retry.
  6. watchdog-stall-detection: a heartbeat with 100ms interval and no beats for 350ms fires onStall.
  7. cooperative-sleep-cancels: a 10s sleep with a cancel token that fires at 100ms rejects in <200ms.

Woodpecker CI gate (the assertion that catches the anti-patterns)

The runtime is not enough. The CI gate is what prevents a future engineer from accidentally re-introducing one of the four anti-patterns. Here is the gate that runs on every PR that touches an agent runtime file.

# .woodpecker.yml — cancellation contract gate
when:
  - event: pull_request
    path:
      include:
        - 'src/agent/**'
        - 'src/tools/**'
        - 'src/runtime/**'

steps:
  - name: cancellation-contract
    image: node:20-alpine
    commands:
      - npm ci
      # 1. no hidden timeouts
      - node scripts/audit-no-hidden-timeouts.js src/
      # 2. every long-running tool accepts a deadline
      - node scripts/audit-deadline-arg.js src/tools/
      # 3. no swallowed CancelledError
      - node scripts/audit-no-swallow-cancel.js src/
      # 4. every side-effecting tool is wrapped in idempotent()
      - node scripts/audit-idempotent-wrap.js src/tools/
      # 5. selftest of the runtime itself
      - npx tsx src/runtime/runtime.test.ts

The five audit scripts are all <50 lines each. audit-no-hidden-timeouts.js greps for setTimeout( and AbortController outside the runtime module and fails the build. audit-deadline-arg.js walks the AST of every tool, finds the call sites, and asserts the call site passes a Deadline as a parameter. audit-no-swallow-cancel.js greps for catch blocks that mention cancel in the variable name and asserts none of them swallow without rethrow. audit-idempotent-wrap.js walks the tools directory, finds any function whose name contains a verb that implies a side effect (charge, create, update, delete, deploy, send), and asserts the call site is wrapped in idempotent(...). The runtime test runs the 7 selftest cases above. Any failure blocks the PR.

Putting it all together: the contract tier of the testing pyramid

The 26th post on this site covered the AI agent testing pyramid. The contract tier is the one that catches a missing Deadline parameter, a swallowed CancelledError, or a side effect that is not wrapped in idempotent. A test that calls a long-running tool without a deadline should fail; a test that asserts the call accepts a deadline and rejects on cancel should pass. The CI gate above is a coarse, regex-based version of that contract tier. The real contract tier is a TypeScript test that imports every tool and asserts its signature. Together they form the safety net that lets you ship an agent with the confidence that a future engineer will not regress the cancellation surface.

This is the same pattern as the 23rd post on idempotency: the runtime is one half, the CI gate is the other half. The runtime gives you the primitives. The gate makes sure every future change uses them. Skip either and the system rots within a quarter.

What this post does not cover

This post is about timeout and cancellation inside a single agent request. It does not cover: per-tenant or per-user time budgets across many concurrent requests (that is the 21st post on rate limiting), circuit-breaker patterns that protect the system from a failing downstream (that is the 19th post), or the broader question of how to design a long-running agent that survives a process restart mid-side-effect (that is the agent state architecture problem and is its own post). It also does not cover cross-region cancellation of an agent running on a remote worker — the pattern still applies, but the propagation of the cancel token from the API layer to the worker adds a transport hop that needs its own design.
