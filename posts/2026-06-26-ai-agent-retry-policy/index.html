AI Agent Retry Policy: 6 Patterns, 5 Anti-Patterns, and a Drop-In Retry Runtime

Your agent hit a 429. It retried. That retry also got 429'd. It retried again. Twenty minutes later, you had burned through a week of API credits retrying a call that was never going to succeed because the provider was down. Here are six patterns that prevent that, five anti-patterns that cause it, and a 120-line runtime you can drop in today.

TL;DR

  1. Classify before retrying. 429, 503, and timeouts are retryable. 400, 401, 403, and 422 are not. Retrying a malformed-request 400 wastes tokens.
  2. Full jitter, not equal jitter. delay = random(0, min(cap, base * 2^attempt)). Full jitter prevents thundering herds; equal jitter leaves a synchronized floor.
  3. Token-bucket budget. Cap retries per time window (e.g., 50 retries per 60 seconds). When the bucket is empty, the call fails fast instead of queuing behind 200 pending retries.
  4. Check idempotency before retrying. A charge_customer call is not safe to retry blindly. A generate_text call is. Use idempotency keys for write operations.
  5. Gate retry on circuit-breaker state. If the circuit breaker for this endpoint is open, do not retry — the call will fail immediately. Let the circuit breaker recover on its own schedule.
  6. Fallback to a cheaper model. When the primary model returns 429, retry on a smaller model. The response quality drops, but the agent stays alive instead of stalling.

Why LLM agents need a different retry policy than web services

Traditional retry logic (e.g., urllib3 Retry, axios-retry) assumes that the remote endpoint is a stateless HTTP API where retrying a GET request is always safe and the cost of a retry is measured in milliseconds of latency. LLM agents break both assumptions:

  • Each retry costs real money. An LLM call to GPT-4-class or Claude-class models costs $0.01–$0.10+ per call. An unbounded retry loop at 3am can rack up hundreds of dollars before the on-call engineer wakes up.
  • Retrying a tool call is not always safe. If the agent called send_email and got a timeout, the email may have been sent — retrying sends a duplicate. If the agent called charge_customer and got a 502, the charge may have gone through — retrying double-charges.
  • Rate limits are account-level, not request-level. A 429 on one agent call means the entire account is rate-limited. Retrying immediately (even with backoff) competes with every other call the agent is making, creating a cascade where all calls slow down because they are all retrying simultaneously.
  • Model availability is non-uniform. The primary model may be overloaded (429) while a fallback model is available. A retry policy that only retries the same model leaves the fallback capacity unused.

Pattern 1: Retryable-error classification

The first line of defense is knowing which errors are worth retrying at all. The general principle: retry transient failures, not permanent ones.

HTTP StatusRetryable?Reason
429 (Rate Limited)YesTransient — the quota will refill. Back off and retry.
500 (Internal Server Error)YesTransient — the provider had an internal issue. Usually safe to retry.
502 (Bad Gateway)YesTransient — upstream proxy failed. Retry with backoff.
503 (Service Unavailable)YesTransient — service is overloaded. Back off and retry.
504 (Gateway Timeout)YesTransient — upstream timed out. Retry, but check if the operation was already executed.
408 (Request Timeout)YesTransient — network issue. Retry (check idempotency for writes).
400 (Bad Request)NoPermanent — your request is malformed. Retrying the same payload will get the same error.
401 (Unauthorized)NoPermanent — your API key is invalid or expired. Fix the key, not the retry.
403 (Forbidden)NoPermanent — your key lacks permissions. No retry will fix this.
404 (Not Found)NoPermanent — model or endpoint doesn't exist. Fix the model name.
422 (Unprocessable)NoPermanent — the request violates schema constraints. Fix the payload.

In TypeScript, the classification is a pure function:

function isRetryable(status: number, errorType?: string): boolean {
  // Explicit non-retryable: 4xx client errors (except 408, 429)
  if (status === 400 || status === 401 || status === 403 ||
      status === 404 || status === 422 || status === 413) {
    return false;
  }
  // Explicit retryable: rate limits, server errors, timeouts
  if (status === 429 || status === 500 || status === 502 ||
      status === 503 || status === 504 || status === 408) {
    return true;
  }
  // Network-level errors (ECONNRESET, ETIMEDOUT, ENOTFOUND)
  if (errorType && (errorType.includes('ECONNRESET') ||
                    errorType.includes('ETIMEDOUT') ||
                    errorType.includes('EAI_AGAIN'))) {
    return true;
  }
  return false;
}

Common mistake: treating 500 as always-retryable

Some LLM providers return HTTP 500 for invalid input that their validation missed (e.g., a prompt that exceeds the context window but wasn't caught by the pre-flight check). If you see the same 500 error on the same payload twice, stop retrying — it's a permanent error wearing a transient error's status code. Track the retry count per request hash and bail after 2 identical 500s.

Pattern 2: Exponential backoff with full jitter

Exponential backoff increases the delay between retries: 1s, 2s, 4s, 8s, 16s. This gives the overloaded service time to recover. But naive exponential backoff has a problem: if 100 agents all hit a 429 at the same time, they all back off to the same schedule and all retry simultaneously — a thundering herd.

The solution is jitter — randomizing the delay. There are two common jitter strategies:

  • Equal jitter: delay = cap/2 + random(0, cap/2). This keeps half the exponential growth and randomizes the other half. Problem: the fixed half still creates a synchronized burst at each retry level.
  • Full jitter: delay = random(0, min(cap, base * 2^attempt)). This completely randomizes the delay within the exponential envelope. No two agents retry at the same millisecond.

Full jitter is the AWS-recommended strategy (see Exponential Backoff and Jitter by Marc Brooker). For LLM agents, always use full jitter:

function fullJitterDelay(
  attempt: number,
  baseMs: number = 1000,
  capMs: number = 30000
): number {
  const exponential = Math.min(capMs, baseMs * Math.pow(2, attempt));
  return Math.random() * exponential;
}

// Example delays (will vary due to randomness):
// attempt 0: random(0, 1000)     -> ~500ms average
// attempt 1: random(0, 2000)     -> ~1000ms average
// attempt 2: random(0, 4000)     -> ~2000ms average
// attempt 3: random(0, 8000)     -> ~4000ms average
// attempt 4: random(0, 16000)    -> ~8000ms average
// attempt 5+: random(0, 30000)   -> ~15000ms average (capped)

The cap is critical: without it, attempt 10 would produce a delay of 1000 * 2^10 = 1,024,000ms (17 minutes), and your agent would appear frozen. A 30-second cap means the worst-case delay is 30s, which is long enough for most rate limits to reset but short enough that the agent stays responsive.

Pattern 3: Token-bucket retry budget

Exponential backoff limits the rate of retries for a single call. But what about the aggregate? If your agent makes 100 concurrent LLM calls and each one retries 5 times, that's 500 retry calls in a few minutes — enough to trigger another rate limit and restart the cycle.

A token-bucket budget caps the total number of retries per time window. Think of it as a bucket that holds tokens. Each retry consumes one token. Tokens refill at a fixed rate (e.g., 1 token per second, bucket capacity 50). When the bucket is empty, the retry is rejected — the call fails fast instead of queuing.

class RetryBudget {
  private tokens: number;
  private lastRefill: number;

  constructor(
    private capacity: number = 50,
    private refillRatePerSec: number = 1
  ) {
    this.tokens = capacity;
    this.lastRefill = Date.now();
  }

  tryConsume(): boolean {
    this.refill();
    if (this.tokens >= 1) {
      this.tokens -= 1;
      return true;
    }
    return false; // Budget exhausted -- fail fast
  }

  private refill(): void {
    const now = Date.now();
    const elapsedSec = (now - this.lastRefill) / 1000;
    this.tokens = Math.min(
      this.capacity,
      this.tokens + elapsedSec * this.refillRatePerSec
    );
    this.lastRefill = now;
  }

  get available(): number {
    this.refill();
    return Math.floor(this.tokens);
  }
}

With a capacity of 50 and a refill rate of 1/second, the agent can burst 50 retries immediately (for a brief outage), then sustain 1 retry per second for the duration of the outage. This prevents the retry cascade where every call's backoff timer expires at the same time.

Pattern 4: Idempotency-aware retry decisions

This is the pattern most agent frameworks get wrong. When an LLM agent calls a tool (e.g., send_email, create_charge, write_file) and gets a timeout or 5xx, the tool may have already executed — the failure was in the response, not the execution. Retrying blindly means executing the side effect twice.

The solution: classify each tool call as safe-to-retry or unsafe-to-retry, and for unsafe operations, require an idempotency key before retrying.

Operation TypeSafe to Retry?Example
Read-only (GET)Yesget_balance, search_web, read_file
LLM text generationYesgenerate_text, chat_completion
Create with idempotency keyYes (with key)create_charge(idempotency_key=uuid)
Create without idempotency keyNosend_email (may double-send)
Update (PUT)Yesupdate_record(id, data) (same data = same result)
Increment/update (PATCH)Noincrement_counter (may double-count)
DeleteMaybedelete_record(id) (second call usually 404, not harmful)
 
type RetrySafety = 'safe' | 'unsafe' | 'requires_key';

function classifyRetrySafety(
  toolName: string,
  hasIdempotencyKey: boolean
): RetrySafety {
  const safeTools = [
    'generate_text', 'chat_completion', 'get_balance',
    'search_web', 'read_file', 'list_records'
  ];
  const unsafeTools = [
    'send_email', 'send_sms', 'post_tweet',
    'increment_counter', 'transfer_funds'
  ];
  const keyRequiredTools = [
    'create_charge', 'create_order', 'create_subscription'
  ];

  if (safeTools.includes(toolName)) return 'safe';
  if (keyRequiredTools.includes(toolName)) {
    return hasIdempotencyKey ? 'safe' : 'requires_key';
  }
  if (unsafeTools.includes(toolName)) return 'unsafe';
  return 'unsafe'; // Default: treat unknown tools as unsafe
}

For more on the idempotency patterns that make tool calls safe to retry, see our deep dive on AI agent idempotency — the idempotency key is the mechanism that turns "unsafe to retry" into "safe to retry."

Pattern 5: Circuit-breaker-gated retry

A circuit breaker tracks the failure rate of a downstream service. When failures exceed a threshold, the circuit opens — all calls to that service fail immediately, without waiting for a timeout. The circuit stays open for a cooldown period, then enters a half-open state where a limited number of calls are allowed through to test if the service has recovered.

If your agent retries through an open circuit breaker, the retry fails immediately (because the circuit is open), and you waste a retry budget token on a call that was never going to succeed. The retry policy must check the circuit breaker state before consuming a retry token:

async function retryWithCircuitBreaker(
  fn: () => Promise,
  circuitBreaker: CircuitBreaker,
  budget: RetryBudget,
  maxAttempts: number = 5
): Promise {
  let lastError: Error | undefined;

  for (let attempt = 0; attempt < maxAttempts; attempt++) {
    // Gate: if the circuit is open, don't retry -- fail fast
    if (circuitBreaker.isOpen()) {
      throw new Error(
        `Circuit breaker open for ${circuitBreaker.service}. ` +
        `Not retrying. Last error: ${lastError?.message ?? 'unknown'}`
      );
    }

    // Gate: check the retry budget before consuming a token
    if (attempt > 0 && !budget.tryConsume()) {
      throw new Error(
        `Retry budget exhausted (${budget.available} tokens). ` +
        `Failing fast to prevent retry storm.`
      );
    }

    try {
      const result = await fn();
      circuitBreaker.recordSuccess();
      return result;
    } catch (err) {
      lastError = err as Error;
      const status = (err as any).status ?? (err as any).statusCode;
      if (!isRetryable(status, (err as any).code)) {
        throw err; // Non-retryable -- don't waste budget
      }
      circuitBreaker.recordFailure();

      if (attempt < maxAttempts - 1) {
        const delay = fullJitterDelay(attempt);
        await new Promise(r => setTimeout(r, delay));
      }
    }
  }

  throw lastError ?? new Error('Retry exhausted');
}

This pattern pairs naturally with our LLM API circuit breaker post — the circuit breaker decides when to stop calling, and the retry policy decides how to call within the window where the circuit is closed.

Pattern 6: Model fallback chain

When the primary model returns 429 (rate limited), retrying the same model is often futile — the rate limit is per-account, and retrying the same model just re-triggers the limit. A more resilient approach: fall back to a different, cheaper model that isn't rate-limited.

The trade-off is response quality: a GPT-4-class model produces better output than a GPT-3.5-class model. But a degraded response is better than no response. The fallback chain should go from most-capable to least-capable:

const MODEL_FALLBACK_CHAIN = [
  { model: 'gpt-4-turbo',  maxRetries: 2, reason: 'primary' },
  { model: 'gpt-4o-mini',   maxRetries: 2, reason: 'primary_429' },
  { model: 'gpt-3.5-turbo', maxRetries: 1, reason: 'mini_429' },
];

async function callWithFallback(
  prompt: string,
  budget: RetryBudget
): Promise<{ text: string; model: string; degraded: boolean }> {
  for (const entry of MODEL_FALLBACK_CHAIN) {
    try {
      const result = await retryWithBudget(
        () => llmCall(entry.model, prompt),
        budget,
        entry.maxRetries
      );
      return {
        text: result,
        model: entry.model,
        degraded: entry.model !== MODEL_FALLBACK_CHAIN[0].model,
      };
    } catch (err) {
      const status = (err as any).status;
      // Only fall through to next model on 429/503
      if (status !== 429 && status !== 503) throw err;
      // Otherwise try the next model in the chain
    }
  }
  throw new Error('All models in fallback chain exhausted');
}

The degraded flag lets the agent (and the observability layer) know that the response came from a fallback model, so it can be treated with appropriate caution — for example, a degraded response might skip autonomous tool execution and surface to the user for confirmation.

For more on what happens when an agent must continue operating in degraded mode, see our post on graceful degradation for AI agents.

Anti-patterns (and how to fix each one)

Anti-pattern 1: Fixed-interval retry (amplifies load)

The problem: setTimeout(retry, 1000) on every failure. If the service is overloaded, retrying every 1 second adds steady load to an already-overloaded service. With multiple agents, they all retry on the same 1-second clock.

Fix: Use full-jitter exponential backoff (Pattern 2). Replace setTimeout(retry, 1000) with setTimeout(retry, fullJitterDelay(attempt)).

Anti-pattern 2: Retry-everything (wastes tokens on permanent errors)

The problem: Wrapping the LLM call in a blanket try/catch that retries on any error. A 401 (bad API key) gets retried 5 times, wasting 5 calls that all fail for the same reason.

Fix: Classify the error before retrying (Pattern 1). Check isRetryable(status) and short-circuit for permanent errors.

Anti-pattern 3: Infinite retry with no budget (burns API spend)

The problem: while (true) { try { return await call(); } catch { await sleep(1000); } }. If the provider is down for 4 hours, this loop runs 14,400 times. At $0.03 per call, that's $432 burned overnight.

Fix: Enforce a token-bucket budget (Pattern 3). When budget.tryConsume() returns false, fail fast. Set the capacity and refill rate based on what you can afford: capacity = maxMonthlyRetries / (30 * 24 * 60).

Anti-pattern 4: Retrying non-idempotent writes (double-executes side effects)

The problem: The agent calls send_email(to, subject, body), gets a 504 timeout, and the retry policy retries. The first call's email was sent — the timeout was on the response. The retry sends a duplicate email.

Fix: Classify tool-call safety (Pattern 4). For unsafe operations, either (a) require an idempotency key from the tool implementation, or (b) skip retry and surface the ambiguity to the agent for a decision. Never retry a write operation blindly.

Anti-pattern 5: Retrying through a tripped circuit breaker (defeats the circuit breaker)

The problem: The circuit breaker for the LLM API has opened after 10 consecutive failures. The retry policy doesn't check circuit state and retries anyway. Each retry hits the open circuit and fails immediately — but it still consumes a retry budget token and adds latency.

Fix: Gate retry on circuit-breaker state (Pattern 5). Check circuitBreaker.isOpen() before consuming a retry token. If open, fail fast with a clear error message.

The complete retry runtime (120 lines)

Here is a drop-in retry runtime that combines all six patterns. It handles error classification, full-jitter backoff, token-bucket budget enforcement, idempotency-aware decisions, circuit-breaker gating, and model fallback. Zero dependencies, Node 18+ stdlib only.

// retry-runtime.ts -- zero-dependency retry policy for LLM agents
// Patterns: classification + full-jitter + token-bucket + idempotency + circuit-breaker + fallback

export type RetrySafety = 'safe' | 'unsafe' | 'requires_key';

export interface RetryConfig {
  maxAttempts: number;       // per-call max retries (default: 5)
  baseDelayMs: number;       // base for exponential (default: 1000)
  capDelayMs: number;        // max delay cap (default: 30000)
  budgetCapacity: number;    // token-bucket size (default: 50)
  budgetRefillPerSec: number;// token refill rate (default: 1)
}

export const DEFAULT_RETRY_CONFIG: RetryConfig = {
  maxAttempts: 5, baseDelayMs: 1000, capDelayMs: 30000,
  budgetCapacity: 50, budgetRefillPerSec: 1,
};

// --- Pattern 1: Error classification ---
export function isRetryable(status: number, errCode?: string): boolean {
  if ([400, 401, 403, 404, 422, 413].includes(status)) return false;
  if ([429, 500, 502, 503, 504, 408].includes(status)) return true;
  if (errCode && ['ECONNRESET', 'ETIMEDOUT', 'EAI_AGAIN'].some(c => errCode.includes(c))) return true;
  return false;
}

// --- Pattern 2: Full-jitter backoff ---
export function fullJitterDelay(attempt: number, baseMs = 1000, capMs = 30000): number {
  const exp = Math.min(capMs, baseMs * 2 ** attempt);
  return Math.floor(Math.random() * exp);
}

// --- Pattern 3: Token-bucket budget ---
export class RetryBudget {
  private tokens: number;
  private lastRefill = Date.now();
  constructor(private cap = 50, private perSec = 1) { this.tokens = cap; }
  tryConsume(): boolean {
    this.refill();
    if (this.tokens >= 1) { this.tokens -= 1; return true; }
    return false;
  }
  get available(): number { this.refill(); return Math.floor(this.tokens); }
  private refill(): void {
    const elapsed = (Date.now() - this.lastRefill) / 1000;
    this.tokens = Math.min(this.cap, this.tokens + elapsed * this.perSec);
    this.lastRefill = Date.now();
  }
}

// --- Pattern 4: Idempotency-aware classification ---
export function classifyTool(tool: string, hasKey: boolean): RetrySafety {
  const safe = ['generate_text', 'chat_completion', 'get_balance', 'search_web', 'read_file'];
  const keyed = ['create_charge', 'create_order', 'create_subscription'];
  if (safe.includes(tool)) return 'safe';
  if (keyed.includes(tool)) return hasKey ? 'safe' : 'requires_key';
  return 'unsafe';
}

// --- Pattern 5: Circuit breaker interface ---
export interface CircuitBreaker {
  isOpen(): boolean;
  recordSuccess(): void;
  recordFailure(): void;
  readonly service: string;
}

// --- Combined retry executor ---
export async function withRetry<T>(
  fn: () => Promise<T>,
  opts: {
    config?: Partial<RetryConfig>;
    budget?: RetryBudget;
    breaker?: CircuitBreaker;
    toolName?: string;
    hasIdempotencyKey?: boolean;
    onRetry?: (attempt: number, delay: number, error: Error) => void;
  } = {}
): Promise<T> {
  const cfg = { ...DEFAULT_RETRY_CONFIG, ...opts.config };
  const budget = opts.budget ?? new RetryBudget(cfg.budgetCapacity, cfg.budgetRefillPerSec);

  // Pattern 4: Check idempotency safety before retrying
  if (opts.toolName) {
    const safety = classifyTool(opts.toolName, opts.hasIdempotencyKey ?? false);
    if (safety === 'unsafe') {
      return fn(); // Single attempt only -- no retry for unsafe tools
    }
  }

  let lastErr: Error | undefined;
  for (let attempt = 0; attempt < cfg.maxAttempts; attempt++) {
    // Pattern 5: Circuit-breaker gate
    if (opts.breaker?.isOpen()) {
      throw new Error(`Circuit open for ${opts.breaker.service}; failing fast`);
    }
    // Pattern 3: Budget gate (skip on first attempt)
    if (attempt > 0 && !budget.tryConsume()) {
      throw new Error(`Retry budget exhausted (${budget.available} tokens); failing fast`);
    }
    try {
      const result = await fn();
      opts.breaker?.recordSuccess();
      return result;
    } catch (err) {
      lastErr = err as Error;
      const status = (err as any).status ?? (err as any).statusCode;
      // Pattern 1: Classify before retrying
      if (!isRetryable(status, (err as any).code)) throw err;
      opts.breaker?.recordFailure();
      if (attempt < cfg.maxAttempts - 1) {
        // Pattern 2: Full-jitter delay
        const delay = fullJitterDelay(attempt, cfg.baseDelayMs, cfg.capDelayMs);
        opts.onRetry?.(attempt + 1, delay, lastErr);
        await new Promise(r => setTimeout(r, delay));
      }
    }
  }
  throw lastErr ?? new Error('Retry exhausted');
}

// --- Pattern 6: Model fallback chain ---
export async function withFallback<T>(
  models: string[],
  callFn: (model: string) => Promise<T>,
  budget: RetryBudget,
  config?: Partial<RetryConfig>
): Promise<T & { model: string; degraded: boolean }> {
  for (let i = 0; i < models.length; i++) {
    try {
      const result = await withRetry(() => callFn(models[i]), { budget, config });
      return { ...result, model: models[i], degraded: i > 0 } as any;
    } catch (err) {
      const status = (err as any).status;
      if (status !== 429 && status !== 503) throw err;
      if (i === models.length - 1) throw err;
    }
  }
  throw new Error('All fallback models exhausted');
}

    { toolName: 'generate_text', config: { maxAttempts: 5 } }
