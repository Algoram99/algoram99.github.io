MCP Server Testing: 7 Checks Every Model Context Protocol Server Should Pass Before Production

A reproducible testing stack for MCP servers — schema, idempotency, error envelope, latency, payload, transport round-trip, and security regression — with copy-paste fixtures and a zero-dependency CLI.

Testing MCP Verification 14 min read Updated 2026-06-05

TL;DR. An MCP server is a JSON-RPC endpoint that the model treats as a remote function call. That means it has all the testing obligations of a public HTTP service, plus three the model adds: schema conformance for the model to discover tools, error envelopes the model can parse, and idempotency because the model will retry. The 7 checks below are what we run against every MCP server before merge, against every third-party server before we adopt it, and as a nightly regression on every server in our fleet. They are cheap, parallel, and can run in CI on every pull request. The last section shows the one-line CI gate using a zero-dependency CLI we open-sourced.

Why MCP servers need their own test stack

Most MCP server testing advice in the wild falls into one of two traps. The first is "just unit-test your tool handlers" — useful, but it leaves the protocol, the transport, the error envelope, and the schema surface untested. The model interacts with your server through JSON-RPC; if that contract drifts, no amount of unit-testing your internal logic will catch it. The second trap is "spin up an LLM and run it end-to-end" — slow, expensive, flaky, and useless as a CI gate. The model is the system under test only for evaluation, not for verification.

A real MCP test stack lives one layer below the model. It speaks raw JSON-RPC, asserts on the protocol contract, treats your server as a black box, and catches the regressions that show up the moment a tool's schema, an error code, or a transport detail changes. The 7 checks below are the ones we run. They map to the mcp-server-tester-cli we ship, but every check is small enough to re-implement in your own harness if you prefer.

Scope: what these 7 checks cover

  • Servers, not clients. The tests target a running MCP server, not a host application or an LLM client.
  • All three transports. Stdio, HTTP+SSE, and the Streamable HTTP transport introduced in the 2025-03 spec. The same seven checks apply; only the harness configuration changes.
  • Black-box by default. The tests speak JSON-RPC and HTTP. They do not import your server's code. That means they catch regressions that white-box tests miss — including the regressions introduced by a dependency upgrade that changes a default.
  • CI-friendly. Every check exits non-zero on failure. The whole suite runs in under 10 seconds for a 20-tool server on a laptop. The total runtime is bounded by the slowest latency check, which you can tune.

Check 1 — Schema conformance of tools/list

The tools/list response is the contract between the model and your server. The model cannot read your code, the tool description, the parameter types, or the return shape unless they are present, correct, and parseable against the JSON Schema you declared. This check verifies four things in one pass: every tool has a non-empty name, a non-empty description, an inputSchema of type object, and a list of required properties that all exist in properties.

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list"
}

The fixture asserts the response shape:

// pseudo-code; mcp-server-tester-cli runs this in JSON
assert(response.result.tools.length > 0, "tools/list returned zero tools");
for (const tool of response.result.tools) {
  assert(/^[a-z][a-z0-9_]{0,63}$/.test(tool.name), "tool name shape: " + tool.name);
  assert(tool.description.length >= 16, "tool description too short: " + tool.name);
  assert(tool.inputSchema.type === "object", "inputSchema must be object: " + tool.name);
  assert(tool.inputSchema.additionalProperties === false, "lock the schema: " + tool.name);
  for (const req of (tool.inputSchema.required ?? [])) {
    assert(tool.inputSchema.properties[req] !== undefined, "missing required prop: " + tool.name + "." + req);
  }
}

Run it as a one-liner:

mcp-server-tester check schema \
  --server ./dist/index.js \
  --transport stdio

The check passes when every tool in the response satisfies all four assertions, fails with a per-tool report when any does not, and exits non-zero on any failure so CI catches the regression on the first PR.

Anti-pattern: the open-extension schema

Anti-pattern. A tool that declares {"type": "object"} for inputSchema without additionalProperties: false. The model can add fields your handler isn't expecting. In one audit we ran, a tool accepted {"path": "/etc/passwd", "mode": "exec"} when it had only declared path. The handler forwarded the unknown field to a downstream library, which executed it. Lock the schema down — the field is one line in the JSON Schema for a reason.

Check 2 — Idempotency of tools/call

The model will retry. Sometimes twice, sometimes ten times. A tool that creates a resource, sends a message, or moves money has to be idempotent under retry, or the model will produce duplicate side effects the user notices. The check fires the same tools/call three times with the same arguments and asserts the response is identical for calls 1 through 3, OR that a documented idempotency key is honored across retries.

{
  "jsonrpc": "2.0",
  "id": 100,
  "method": "tools/call",
  "params": {
    "name": "create_issue",
    "arguments": {
      "title": "Test issue for idempotency",
      "body": "created by mcp-server-tester",
      "idempotency_key": "test-2026-06-05-001"
    }
  }
}

The harness captures the first response, replays the same request two more times, and compares:

const first = await call({ name: "create_issue", arguments: { ...fixture, idempotency_key: "test-2026-06-05-001" } });
const second = await call({ ...first.params });
const third = await call({ ...first.params });
assert(extractId(first) === extractId(second), "idempotency: call 1 vs 2 produced different IDs");
assert(extractId(second) === extractId(third), "idempotency: call 2 vs 3 produced different IDs");

Pass when the resource ID is stable across retries. Fail with the divergent IDs when it isn't. Tools that don't take an idempotency key need a documented opt-out: a non_idempotent: true field in the tool's metadata, or a header that disables the test for that tool.

Check 3 — Error envelope shape

MCP inherits JSON-RPC 2.0's error model. The model has to be able to parse a failure and decide whether to retry, surface the error to the user, or fall back to a different tool. Three failure modes show up in production: the tool raised an exception (code -32603), the tool received invalid arguments (code -32602), or the tool refused on policy grounds (a custom code, usually in the -32000 to -32099 range). The check fires each of these and asserts the error envelope matches the spec.

// 1) call a non-existent tool
assertError({ id: 200, method: "tools/call", params: { name: "nope_does_not_exist" } }, -32601);

// 2) call with malformed arguments
assertError({ id: 201, method: "tools/call", params: { name: "create_issue", arguments: { title: 12345 } } }, -32602);

// 3) call with a permission-denied argument
assertError({ id: 202, method: "tools/call", params: { name: "read_file", arguments: { path: "/etc/shadow" } } }, -32050);

The third code is the one teams get wrong. -32603 ("internal error") is the lazy default. It tells the model nothing about whether to retry, surface, or fall back. A well-designed server returns a typed error code per failure class and a data field with a structured reason. The check passes when the response carries the expected code and a non-empty data object; fails when the server collapsed every error into -32603.

Check 4 — Latency under representative load

An MCP server that responds in 4 seconds is a tool the model will time out on. The model's tool-call budget is usually 5-10 seconds, and 1-2 seconds of that is the model's own reasoning. A reasonable target is p95 latency under 1500ms for read tools and under 3000ms for write tools, measured against the server running in your staging environment with realistic data volumes.

The check fires 50 read calls in parallel and asserts p50, p95, and p99 are under threshold:

mcp-server-tester check latency \
  --server ./dist/index.js \
  --transport stdio \
  --read-tool list_files \
  --concurrency 10 \
  --requests 50 \
  --p95-max-ms 1500

Pass when p95 is under 1500ms. Fail with a per-percentile report when it isn't. A regression in latency is often a regression in the database query underneath the tool, not in the MCP layer — but the MCP layer is where the model notices, so the test belongs here.

Anti-pattern: the "I'll optimize later" cold start

Anti-pattern. A server that responds in 80ms on the second call but 6 seconds on the first. Cold-start latency is the latency the model sees on the first turn of a new session, which is also the turn that sets the user's first impression. Either warm the server at boot (a no-op tools/list against an in-memory store) or accept a cold-start SLA and document it. Don't ship a 6-second p99 and discover it from a user complaint.

Check 5 — Payload size and shape

Tool output goes into the model's context. A 200KB response from a list_files tool is a 50,000-token bill to the next call. The check asserts every tool response is under a configurable byte cap and structured in a way the model can parse without ambiguity.

// for each tool, fire a representative call and assert the response is bounded
const r = await call({ name: "list_files", arguments: { path: "/" } });
assert(Buffer.byteLength(JSON.stringify(r.result)) < 64 * 1024, "list_files response exceeded 64KB");
assert(Array.isArray(r.result.content), "list_files must return a content array");
for (const block of r.result.content) {
  assert(["text", "image", "resource"].includes(block.type), "unknown content block: " + block.type);
}

The 64KB cap is a starting point; tighten it for tools you know are small (a get_user tool has no business returning 64KB) and loosen it for tools that are explicitly batch-oriented (a bulk_export tool may return more, but should chunk by default). The shape assertion catches a class of bug where a refactor changes a return value from a string to an object, or vice versa, and the model's prompt breaks silently.

Check 6 — Transport round-trip

The protocol is the same across transports, but the transport isn't. Stdio, HTTP+SSE, and Streamable HTTP each have their own failure modes: stdio servers can deadlock on a long-running tool that doesn't flush stdout, HTTP+SSE can drop the SSE connection after a proxy timeout, Streamable HTTP can be tripped up by an Origin check that wasn't there yesterday. The check exercises the round-trip the way a real client would: a handshake, a tools/list, a tools/call, and a clean close.

mcp-server-tester check transport \
  --server ./dist/index.js \
  --transport http-sse \
  --endpoint http://localhost:3000/mcp \
  --round-trips 5

The harness runs 5 full round-trips (initialize → tools/list → tools/call → close) and asserts: the server returned a valid initialize response with a server name and version, every subsequent call completed within the latency budget, the SSE connection stayed open across the round-trip (no reconnect), and the close handshake completed cleanly. Pass when all 5 round-trips succeed; fail with the failing round-trip number and the dropped message when any doesn't.

Check 7 — Security regression

The last check is the one that connects this stack to the 32-point security audit checklist we published earlier. It runs a small subset of the security checks against the live server: input validation against the schema, transport hardening headers, prompt-injection-shaped tool descriptions, and the basic auth/secret posture. It is not a substitute for the full audit, but it is a fast regression net that catches the "we accidentally weakened the schema in a refactor" case.

mcp-server-tester check security \
  --server ./dist/index.js \
  --transport stdio \
  --fail-on high

Pass when no high-severity findings are present. Fail with a per-finding report otherwise. The 7-check suite is designed so the security check is the last gate — if checks 1 through 6 all pass, the server is in a state where the security check has something meaningful to verify.

Running the 7 checks as a CI gate

The 7 checks are useful as a review aid, but reviews drift. The only way to make them durable is to run them on every pull request. We use a small CLI that wraps the checks into a single command. It is open-sourced, zero-dependency, and runs in under 10 seconds for a typical server.

The full suite as a one-line CI gate:

# In your CI workflow (GitHub Actions, Woodpecker, or anything else):
- name: MCP server test suite
  run: |
    npx -y @alg99/mcp-server-tester-cli run \
      --server ./dist/index.js \
      --transport stdio \
      --suite 7-checks \
      --report ./mcp-test-report.json \
      --fail-on any

The --fail-on flag accepts any, high, medium, or low. We default to any in PR builds and high in the nightly cron. The --report flag writes a JSON report suitable for posting as a CI artifact or uploading to a test-results dashboard.

Adopting a third-party MCP server? Run the suite first

The 7 checks also work against servers you don't own. The only difference is you point the harness at a network endpoint instead of a local binary. Run the suite against any MCP server before you wire it into a production agent, especially if the server is going to touch money, send messages, or mutate state on behalf of the user.

mcp-server-tester run \
  --server https://mcp.example.com/v1 \
  --transport streamable-http \
  --suite 7-checks \
  --fail-on high

The output is the same JSON report. The interpretation is the same: 7 passes means the server meets the bar, any fail means the bar isn't met and you should either pick a different server, run the server with reduced permissions, or pin the version you tested against and accept the regression risk.

Anti-patterns we hit so you don't have to

Three anti-patterns account for roughly half of the failures we see when teams add the 7-check suite to an existing server.

  1. The "schema is documentation" anti-pattern. The team treats inputSchema as a hint, not a contract. The handler accepts whatever the JSON-RPC layer hands it, and the schema is generated from the TypeScript types at build time, not from a hand-written JSON Schema. Result: the model can call the tool with arguments the schema doesn't declare, and the suite fails on Check 1. Fix: hand-write the JSON Schema, or use zod-to-json-schema with an explicit .strict() on every object.
  2. The "errors are strings" anti-pattern. The server catches every exception, formats it as a string, and returns it inside a successful response. The model can't tell a 200 from a 500, the suite fails on Check 3, and the user gets a hallucinated "success" message. Fix: catch at the boundary, return a structured error envelope with a documented code and a data field.
  3. The "latency is a deployment problem" anti-pattern. The team treats latency as something to fix in production with a CDN or a cache, and ships the server with a 4-second p95. The model times out, the test fails on Check 4, and the team blames the test for being "too strict." Fix: pick a target latency (1500ms read / 3000ms write is a sensible default) and refuse to merge a PR that breaks it. The cache is an optimization, not a substitute for a fast server.

What this suite does not cover

Three areas are deliberately out of scope of the 7-check suite.

  • Model evaluation. Whether the model picks the right tool, hallucinates a path, or ignores a system prompt is a model-evaluation problem, not a server-testing problem. Run an eval suite (Promptfoo, DeepEval, Inspect) alongside this 7-check suite. The two stacks are complementary: this one verifies the server, the eval suite verifies the model.
  • Load and chaos testing. A 50-request latency check is not a load test. For load, use k6, Locust, or vegeta against a staging instance. For chaos, use Litmus or a manual kill-and-recover. The 7-check suite is the fast feedback loop; load and chaos are the slow ones.
  • Compliance and privacy reviews. GDPR, SOC 2, HIPAA, and similar reviews live in a different universe. A passing 7-check suite is necessary but not sufficient for compliance. Run your compliance review on its own cadence, with its own evidence trail, and reference the 7-check report as one input among many.

Next steps

  1. Pick one MCP server you own. Run the 7-check suite against it. Triage the findings. Expect 1-2 failures on the first run; that's the suite earning its keep.
  2. Add the CLI to your CI as a required check. The first run is the worst one; the second is a baseline.
  3. Wire the 7-check suite into the 32-point security audit we published earlier. The two complement each other: the 7-check suite runs on every PR, the security audit runs nightly and on release.
