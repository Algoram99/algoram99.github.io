MCP Server Testing: 7 Checks That Catch Tool Failures Before Release

Most MCP server outages don't come from a missing tool. They come from a tool that claims to work, returns a 200, and silently corrupts the agent's next decision. Here's a verification stack that catches those failures before your users do.

Published 2026-06-05 · ~12 min read · Algoram99
TL;DR. A reliable MCP server passes seven classes of checks: (1) JSON Schema validity for every tool input and output, (2) idempotency on repeat invocation, (3) stable error envelopes, (4) latency budgets per tool, (5) payload size boundaries, (6) transport round-trips, and (7) security surface review (no shell-out, no path traversal, no silent credential logging). Each section below has a copy-paste test you can run against any MCP server in under five minutes.

Why MCP testing is its own discipline

The Model Context Protocol is intentionally thin: a JSON-RPC surface where an LLM client calls tools/call and gets a result or an error back. That thinness is a strength for interop, and a trap for verification. There is no canonical "MCP test framework." Most teams inherit their habits from REST testing, where a 200 means success, schema is a nice-to-have, and idempotency is a database concern.

None of those assumptions survive contact with an LLM agent. A 200 from tools/call is not a guarantee that the agent can use the result — the response could be the wrong shape, a stringified stack trace masquerading as a tool result, or a payload so large that the model truncates it before reasoning about it. The seven checks below cover the failure modes that show up in production traces but never in unit tests.

Check 1 — JSON Schema validity for inputs and outputs

Every tool you expose must publish a JSON Schema in its inputSchema field, and the result payload must match the outputSchema you declared (or, if you didn't declare one, the structural shape your tool returns must still be stable). Most teams write a schema once, then drift from it as the implementation evolves.

What to test

  • For every tool, tools/list returns a non-empty inputSchema with type: "object" and at least one properties entry.
  • For every required field, omitting it returns a JSON-RPC error with code: -32602 (Invalid params), not a 500 or a stringified stack.
  • For every output, the structuredContent field parses against the declared outputSchema with no missing keys and no extra keys (if your schema uses additionalProperties: false).

Copy-paste test (Node.js)

import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import ajv from "ajv";

const client = new Client({ name: "schema-verify", version: "1.0.0" });
await client.connect(transport);

const { tools } = await client.listTools();
const validator = new ajv({ allErrors: true, strict: false });

let failures = 0;
for (const tool of tools) {
  if (!tool.inputSchema || tool.inputSchema.type !== "object") {
    console.error(`FAIL  ${tool.name}: missing or non-object inputSchema`);
    failures++;
    continue;
  }
  if (!validator.compile(tool.inputSchema)) {
    console.error(`FAIL  ${tool.name}: inputSchema is not a valid JSON Schema`);
    failures++;
    continue;
  }
  // Probe a required-field violation
  try {
    await client.callTool({ name: tool.name, arguments: {} });
    console.error(`FAIL  ${tool.name}: accepted empty arguments without error`);
    failures++;
  } catch (err) {
    if (err.code !== -32602) {
      console.error(`FAIL  ${tool.name}: wrong error code for missing required: ${err.code}`);
      failures++;
    }
  }
}
process.exit(failures === 0 ? 0 : 1);
Anti-pattern. Returning { ok: true, data: null } with no error code on a schema violation. The agent treats ok: true as success and proceeds to act on null. Always throw a structured error with the right JSON-RPC code.

Check 2 — Idempotency on repeat invocation

Agents retry. Sometimes the retry is intentional, sometimes the model decides to "double check" by calling the same tool twice. If your tool creates a side effect on the first call, the second call must be a no-op (or a clearly-tagged conflict error) — not a duplicate write, double charge, or repeat email.

What to test

  • Call the same tool twice with the same arguments in quick succession. The second call must either return the same result (idempotent) or return a structured "already executed" error.
  • For mutating tools, the second call should NOT increment any external counter (database row count, payment, log line, etc.).
  • If you use an idempotency_key parameter, two calls with the same key must produce the same result regardless of intermediate state.

Copy-paste test

const args = { path: "/tmp/idem-test.txt", content: "hello" };
const r1 = await client.callTool({ name: "fs.write", arguments: args });
const r2 = await client.callTool({ name: "fs.write", arguments: args });
assert.deepEqual(r1.structuredContent, r2.structuredContent,
  "Repeat call must return identical result");
Anti-pattern. Using timestamp or random ID inside the tool to "deduplicate" calls. The agent doesn't see that internal ID. Either accept an explicit idempotency_key argument or make the operation genuinely idempotent at the resource layer.

Check 3 — Stable, machine-parseable error envelopes

When a tool fails, the agent needs to recover. A raw exception string is not recoverable. A JSON-RPC error with a stable code, a human-readable message, and an optional data field is recoverable.

What to test

  • Every error path returns a code in the standard JSON-RPC range, plus a domain-specific code in data.code if you need finer granularity.
  • The message field is human-readable (the model uses it for self-correction) but never contains stack traces, file paths from the server host, or credentials.
  • Errors are deterministic: the same bad input produces the same error code, not a different one each time.

Copy-paste test

// Trigger a known failure (e.g. reading a non-existent file)
let err;
try {
  await client.callTool({ name: "fs.read", arguments: { path: "/nope/missing.txt" } });
} catch (e) { err = e; }

assert.ok(err, "Expected an error for missing file");
assert.equal(err.code, -32602, "Wrong JSON-RPC code");
assert.ok(err.message.length > 0 && err.message.length < 500,
  "Message should be informative but not a stack trace");
assert.ok(!/at \w+\.js:\d+/.test(err.message),
  "Message leaked a stack trace");
Anti-pattern. Including the server's absolute path in the error message. "ENOENT: no such file or directory, open '/home/ubuntu/.mcp/secrets/keys.json'" is a real-world example we have seen. The agent echoes this to the user. Use a generic "resource not found" message and put the actual path in a redacted data.requested_path field.

Check 4 — Latency budgets per tool

An MCP tool that takes 30 seconds to return will cause the agent to either time out, hallucinate a result, or hang the entire conversation. Each tool needs a documented latency budget, and your tests should assert it.

What to test

  • Run each tool 10 times, measure p50, p95, and p99 latency.
  • Assert p95 is below your documented budget (e.g. 2 seconds for a lookup, 10 seconds for a generation).
  • For long-running tools, verify the server actually streams progress or accepts cancellation rather than holding the connection open.

Copy-paste test

const samples = [];
for (let i = 0; i < 10; i++) {
  const t0 = performance.now();
  await client.callTool({ name: "search.lookup", arguments: { q: "test" } });
  samples.push(performance.now() - t0);
}
samples.sort((a, b) => a - b);
const p95 = samples[Math.floor(samples.length * 0.95)];
assert.ok(p95 < 2000, `p95 ${p95.toFixed(0)}ms exceeds 2s budget`);
Tip. A latency check that runs once and asserts a single number is theater. Real budgets are p95 over a sample size, and they should be measured in CI, not just locally.

Check 5 — Payload size boundaries

LLMs have context windows. An MCP tool that returns a 4 MB JSON blob to a model with a 200 K token context will silently truncate or fail to fit. The fix is not "make the tool return less" — the fix is to make the tool return the right amount, and to fail loudly when the result is too large for the declared contract.

What to test

  • For tools that read files or query large lists, test with empty input, normal input, and a deliberately oversized input.
  • Assert that oversize results are truncated to a sane limit AND return a truncated: true flag in the structured content.
  • Assert the result payload never exceeds a documented per-tool byte ceiling (e.g. 256 KB for a single tool response).

Copy-paste test

const r = await client.callTool({ name: "log.tail", arguments: { lines: 1_000_000 } });
const bytes = Buffer.byteLength(JSON.stringify(r.structuredContent));
assert.ok(bytes < 256 * 1024, `Result ${bytes} bytes exceeds 256 KB cap`);
assert.equal(r.structuredContent.truncated, true,
  "Oversize request must be marked truncated");

Check 6 — Transport round-trips

MCP runs over stdio, HTTP+SSE, and streamable HTTP. Each transport has different failure modes: stdio buffers, SSE timeouts, HTTP connection reuse. Your tests must cover the actual transport your client uses, not just the local in-memory transport.

What to test

  • Spawn the server as a subprocess and verify stdio transport works with non-trivial messages (large payloads, unicode, binary).
  • For HTTP transports, verify the server handles connection close mid-response gracefully and that reconnection resumes the conversation state correctly.
  • Verify the server enforces a Content-Length header for stdio messages and doesn't rely on EOF as a delimiter.
Anti-pattern. Testing only with InMemoryTransport from the SDK. It will not catch the most common production bug: a server that works fine in tests but hangs the first time it receives a 64 KB payload over real stdio because the developer never set readBufferSize.

Check 7 — Security surface review

The most expensive MCP failures are not crashes — they are security incidents. An MCP server is, by definition, a way for an LLM to call code on a user's machine. That code path must be tight.

What to test

  • No shell-out. No tool wraps child_process.exec, os.system, or subprocess.Popen with a string built from tool arguments. Use execFile with an argv array, or just don't shell out.
  • No path traversal. File-reading tools must canonicalize and resolve paths, then verify the resolved path is inside an allowed root. ../ must not escape.
  • No silent credential logging. Grep your tool implementation for console.log, logger.info, and structured log fields that touch the request object. If the user passes a token, the server must never echo it back to the agent.
  • No DNS rebinding on HTTP transports. Verify the server validates the Origin header and binds to localhost only, or runs behind a reverse proxy that does.

Copy-paste test (path traversal)

// The tool should refuse to read outside the allowed root
try {
  await client.callTool({
    name: "fs.read",
    arguments: { path: "../../../../etc/passwd" }
  });
  assert.fail("Tool must reject path traversal");
} catch (err) {
  assert.equal(err.code, -32602, "Wrong error code for traversal");
}

Putting it all together

Seven checks sounds like a lot, but the implementation is small. A single test file per tool, run on every PR, catches the failure modes that would otherwise show up in user-reported bugs three days after release.

The shape of the harness matters less than the discipline: every tool gets the same seven checks, every PR runs them, every regression is caught before it ships. What we left out

Two checks we did not cover because they deserve their own posts: prompt-injection resistance (an MCP server should never treat tool input as instructions to itself) and cross-tool side effects (calling tool A should not silently invalidate state that tool B depends on). Both are real, both are out of scope for a single checklist, and both are on the Algoram99 shipping roadmap.

If you ship MCP servers, run these seven checks today. The 30 minutes you spend wiring them into CI will save you the 30 hours you would otherwise spend triaging a postmortem.
