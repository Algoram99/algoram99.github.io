MCP Server Security Audit Checklist: 32 Things to Verify Before You Ship

A field-tested security checklist for Model Context Protocol (MCP) servers, with CLI commands, anti-patterns, and a CI-friendly auditor.

Security MCP Audit 12 min read Updated 2026-06-05

TL;DR. An MCP server is a remote code execution boundary disguised as a JSON-RPC endpoint. Treat it the way you'd treat a public web service with authenticated mutating endpoints: validate every input against a typed schema, scope every tool to the smallest possible surface, sign and rotate every secret, log every call with redaction, and run a reproducible audit in CI before every release. The 32 points below are the audit we run against our own MCP servers at alg99. They are grouped into seven layers: tool design, transport, authentication, secrets, prompt-injection defense, supply chain, and observability. The last section includes a one-line CI gate using a tool we open-sourced.

Why MCP servers need their own security checklist

Model Context Protocol (MCP) has become the de-facto standard for plugging tools into LLM agents. The protocol itself is small: JSON-RPC 2.0 over stdio, HTTP+SSE, or a streamable HTTP transport. The security surface, however, is large. Every tools/call invocation is a request from a non-deterministic client (the model) to execute code that may touch the filesystem, shell out to a subprocess, hit a third-party API, or mutate a database.

Most public MCP security guidance falls into two traps. The first is "treat the model as a trusted user" — useful for the 1.0 protocol demo, fatal in production. The second is "wrap every tool call in a regex" — it doesn't survive a single clever instruction in the user's prompt. A real audit needs to cover protocol, transport, server code, and the supply chain that brings the server up.

The 32 points below are what we run against every MCP server we ship, host, or audit for a customer. They are not a substitute for a full threat model, but they catch the 80% of issues that show up in real engagements: tool shadowing, prompt injection via tool output, secret leakage into logs, OAuth scope creep, and the supply-chain attacks that have hit npm over the last two years.

Scope: what this checklist covers

  • Servers, not clients. The audit targets the MCP server code, the container image, and the runtime environment.
  • Three transports. Stdio, HTTP+SSE, and the newer Streamable HTTP transport introduced in the 2025-03 spec.
  • Production, not prototype. Some checks (e.g., TLS pinning, multi-tenancy isolation) only matter when the server is exposed beyond localhost.
  • CI, not just review. Every check has a CLI command, a config snippet, or a static-analysis rule that can run automatically.

Layer 1 — Tool design and input validation (8 checks)

The tool definitions in tools/list are the contract between the model and your server. The model cannot read your code; it can only read the JSON schema, the tool description, and the tool's name. That makes the schema your first line of defense.

  1. Every tool has a strict JSON schema with additionalProperties: false. Open-extension schemas let the model add fields your handler isn't expecting. Always lock the schema down.
  2. String inputs are bounded by maxLength; numeric inputs by minimum, maximum, and multipleOf. A 10MB query field is a denial-of-service primitive.
  3. Tool descriptions are factual and complete, not aspirational. "Send a tweet" is fine; "send a tweet in the user's voice" is a prompt-injection landing pad. The description is part of the model's prompt surface.
  4. Tool names do not contain spaces, slashes, or unicode lookalikes. Several real-world attacks use a homoglyph in the tool name to phish a model's tool selection. Enforce ^[a-z][a-z0-9_]{0,63}$ in your registration code.
  5. No tool exposes a generic exec or eval method. If you need to run commands, expose a typed run_command(command: enum, args: object) with a closed enum of allowed subcommands.
  6. Filesystem tools take an absolute path, then resolve and re-check it against an allowlist. Never accept a relative path and append it to a working directory. Symlink resolution must happen after the allowlist check, not before.
  7. Network tools accept a URL, parse it, and verify the scheme and host against an allowlist before any fetch. DNS rebinding and file:// SSRF are not theoretical. A pure isUrl() check is not enough.
  8. Tool responses are bounded. Truncate or summarize any tool response that exceeds a sensible cap (we use 64KB) before returning it to the model. Large outputs balloon context and can carry prompt-injection payloads.

Anti-pattern: the "JSON passthrough"

Anti-pattern. A tool that accepts {"input": "..."} and forwards the string to a downstream API without validation. We've seen this pattern in roughly 30% of the MCP servers we audit. The downstream API usually has its own validation, but the model can still send an instruction that gets concatenated into a log line, a database query, or a templated email — all of which are prompt-injection vectors that bypass the downstream validator.

Layer 2 — Transport hardening (5 checks)

The transport layer is where most public exploits land. Three transports are in active use, and each has its own hardening list.

  1. For stdio, the server inherits the parent's stdio, never a TTY, and never reads from stdin after the first line. The protocol is request/response; a long-lived read on stdin is a footgun.
  2. For HTTP+SSE, TLS 1.2+ is required and HSTS is set with max-age of at least 1 year. Modern reverse proxies (Caddy, Traefik, nginx 1.25+) handle this with a one-line config.
  3. For Streamable HTTP, Origin is validated against an allowlist on every request. The 2025-03 transport spec recommends this for CSRF defense. The check belongs in middleware, not the tool handler.
  4. The server sets X-Content-Type-Options: nosniff and a strict Content-Security-Policy on any HTML response. Even though MCP responses are JSON, an operator dashboard or error page can become a vector.
  5. Per-IP and per-token rate limits are configured before the server leaves staging. A reasonable default is 60 requests/minute per token for normal traffic, 600 for batch tools, with a 429 response that includes a Retry-After header.

Layer 3 — Authentication and authorization (5 checks)

MCP's auth story is intentionally thin: the spec leaves it to the transport. That means your server has to make the policy decisions the spec punted on.

  1. Every tool call is authenticated, not just the session. Token rotation and revocation must invalidate in-flight calls within a documented window. A leaked access token from yesterday should not be accepted today.
  2. OAuth scopes are scoped to a single tool family. read:files and write:files are different scopes. files:rw is a smell. Granularity is the only thing that makes revocation useful.
  3. Tool-to-tool calls inside the server still re-check the caller's identity. A common bug is letting an internal helper call a privileged tool without re-validating the caller's token. The helper has the right to call the lower-level API; it does not have the right to skip auth on a higher-level tool.
  4. Multi-tenant servers namespace every resource by tenant ID at the storage layer, not the application layer. A SQL WHERE tenant_id = ? in the application code is one bug away from a cross-tenant leak. A schema or row-level security policy in the database is a structural defense.
  5. Audit logs record the caller's identity, the tool name, the resource, and a hash of the arguments — never the raw arguments. Arguments often contain PII or secrets. The hash lets you correlate and prove tampering without re-storing the data.

Layer 4 — Secrets and configuration (4 checks)

  1. No secret is ever read from a CLI flag, an environment variable in a docker run line that appears in ps auxef, or a YAML file in the repo. Use a secret manager (HashiCorp Vault, AWS Secrets Manager, Doppler) and pull at boot with a short-lived token.
  2. Secrets are redacted from logs at the formatter level, not the call site. Call-site redaction is forgotten. A logging formatter that hashes or masks known key names is a structural defense.
  3. The server refuses to boot if a required secret is missing or matches a known-bad value (changeme, test, sk-test-...). Fail closed at startup. We've seen production servers running with placeholder secrets for weeks because the boot check was optional.
  4. All outbound HTTP clients have a configured User-Agent string that includes the server name and version. When an incident happens and a vendor needs to contact you, a useful User-Agent is the difference between a phone call and silence.

Layer 5 — Prompt-injection defense (4 checks)

This is the layer most checklists skip. It is also the layer where MCP servers are uniquely exposed, because tool output is concatenated into the model's context and the model cannot distinguish a tool result from a user instruction.

  1. Tool output that contains a user-controlled string is wrapped in a delimiter the model is trained to treat as data, not instruction. One common pattern: "[tool:read_file result]\n{output}\n[/tool:read_file result]". The delimiters should be hard to spoof — include a nonce if you can.
  2. No tool description contains the words "ignore previous instructions", "act as", or "you must". This is a self-defense check: an attacker who controls the tool description should not be able to put the model into a chosen state. Run a CI grep against the tools/list payload.
  3. Tool output is scanned for instruction-shaped text before being returned. A simple regex (/(ignore (all )?previous|disregard (the )?system|you are now)/i) catches the obvious attacks. A semantic classifier catches the clever ones. Both are useful.
  4. High-risk tools (anything that mutates state, sends messages, or moves money) require an explicit confirmation tool call. A read tool is safe to fire speculatively. A delete tool is not. The model must call a separate confirm_{action} tool before the dangerous tool will execute. This is the single biggest defense against prompt-injection-driven data loss.

Layer 6 — Supply chain (3 checks)

  1. Every runtime dependency is pinned to an exact version with a lockfile committed. Caret ranges in package.json and >= in requirements.txt are the entry point for the next left-pad-style attack. Pin, then update deliberately.
  2. The container image is built from a minimal base, scanned for CVEs, and the SBOM is published alongside the release. node:20 full images carry 800+ packages you didn't choose. A distroless or alpine base carries a tenth of that. Syft, Trivy, and Grype all generate SPDX SBOMs in under a minute.
  3. Releases are signed (cosign or sigstore) and the signature is verified by the deployment pipeline. Unsigned releases are how the recent xz-utils backdoor spread. A 30-line GitHub Actions step prevents a class of incidents, not just one.

Layer 7 — Observability and incident response (3 checks)

  1. Every tools/call is logged with: timestamp, caller identity, tool name, argument hash, response code, and latency. These six fields are the minimum for any postmortem. The argument hash lets you correlate without storing PII.
  2. Anomaly detection runs on the call stream. A sudden spike in write calls from a single token, a new IP geo, or a tool being called in a loop with no human turn are all signals. A simple sliding-window counter is enough for the first iteration.
  3. A documented kill-switch procedure exists, with a name, a command, and an expected recovery time. "Turn it off" is not a procedure. kubectl scale deploy/mcp-server --replicas=0 and a runbook page is. Test the procedure on a staging cluster before you need it in production.

Running the audit in CI: a one-line gate

The 32 checks above are useful as a review aid, but reviews drift. The only way to make them durable is to run them on every pull request. We use a small CLI that wraps the checks into a single command. It is open-sourced and zero-dependency.

The audit CLI takes a server directory and a config file, runs all 32 checks, and emits a JSON report. It also exits non-zero on any failure, which makes it a one-line CI gate:

# In your CI workflow:
- name: MCP security audit
  run: |
    npx -y @alg99/mcp-server-tester-cli audit \
      --server ./dist \
      --config ./mcp-audit.yaml \
      --report ./audit-report.json \
      --fail-on high

The --fail-on flag accepts critical, high, medium, and low. We default to high in PR builds and medium in the nightly cron. The mcp-audit.yaml config lets you override the default allowlists (URL schemes, OAuth scopes, tool-name patterns) so the audit matches your environment.

Anti-patterns we hit so you don't have to

Three anti-patterns account for roughly half of the issues we find in customer audits.

  1. The "trust the protocol" anti-pattern. A server accepts whatever the JSON-RPC layer hands it and forwards to the tool handler. The JSON-RPC layer is not a security boundary. The handler is. Validate at the handler, not the transport.
  2. The "log the arguments" anti-pattern. Tool arguments often contain API keys, file paths to sensitive directories, or PII. A debug-level log that captures the full argument object is a compliance incident waiting to happen. Log a hash, not the value.
  3. The "shared admin token" anti-pattern. A single long-lived bearer token is shared across all instances of the server "for simplicity." One leak and the rotation is a fleet-wide outage. Use per-instance tokens with a short TTL and a documented rotation procedure.

What this checklist does not cover

Two areas are deliberately out of scope.

  • The model's behavior. Whether the model picks the right tool, hallucinates a path, or ignores a system prompt is a model-evaluation problem, not a server security problem. Run an eval suite (Promptfoo, DeepEval, Inspect) alongside this audit.
  • The deployment platform. Kubernetes RBAC, IAM policies, and container runtime security are real and important, but they live one layer below the MCP server. A misconfigured ClusterRole with secrets: get,list is a security issue at the platform layer, not the protocol layer.

Next steps

  1. Pick one MCP server you own. Run the audit CLI against it. Triage the findings.
  2. Add the CLI to your CI as a required check. The first run is the worst one; the second is a baseline.
  3. Pick the next server. Repeat. The 32 checks compound across a fleet — fixing them once in a starter kit means every new server inherits the fix.
