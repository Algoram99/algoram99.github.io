How to Implement Rate Limiting for AI Agents

A single-tenant fixed-window counter is not rate limiting — it is a polite suggestion that one runaway loop will ignore. AI agents have six independent rate surfaces (per-IP, per-tenant, per-session, per-tool-call, per-token-budget, per-cost-budget) and a real limiter has to enforce all six, fail open to degradation when the limit trips, and emit telemetry the upstream circuit breaker can use to half-open. This post walks through a 110-line TypeScript token-bucket implementation, the 4 anti-patterns that quietly let one bad tenant burn your monthly budget in 90 seconds, and a chaos harness that simulates a runaway tool-call loop to prove the limiter actually trips.

TL;DR

An AI-agent rate limiter must enforce 6 surfaces (per-IP, per-tenant, per-session, per-tool-call, per-token-budget, per-cost-budget) and use a token-bucket with a sliding-window cost gate — not a fixed-window counter. The reference implementation below is 110 lines of TypeScript: zero dependencies, per-tenant state in a Map, atomic refill, a cost gate that subtracts USD rather than requests, and a structured RateLimitVerdict the caller branches on instead of HTTP 429 + pray.

It pairs with the Agent Ingress Firewall CLI ($29, the per-tenant layer that sits before the limiter) and the Agent Inflight Telemetry CLI ($29, surfaces the live quota state in your dashboard). It also closes the reliability trilogy with the 19th-post circuit breaker (protects the upstream after the limiter passes) and the 20th-post graceful-degradation wrapper (handles the case where the limiter trips). The chaos-test harness at the end fires 1,000 tool calls in 60 seconds from a single simulated tenant and verifies the limiter refuses calls 81 through 1,000.

Why a fixed-window HTTP rate limiter is wrong for AI agents

You have probably seen the standard express-rate-limit recipe: a Redis counter keyed on IP, incremented on each request, reset every 60 seconds. That works for protecting a login endpoint from credential-stuffing. It fails for AI agents for three structural reasons.

  1. Agents are not request-volume-heavy — they are cost-volume-heavy. One agent can make 4 API calls a minute and still rack up $40 of OpenAI charges if each call streams 30,000 output tokens. A counter that caps requests-per-minute sees 4 calls and says "you're fine." A counter that caps USD-per-minute sees $40 and says "stop." You need the second one, and it has to be a sliding window over a configurable cost model (input tokens, output tokens, cached tokens, tool calls).
  2. Agents are multi-tenant by API key, not by IP. Behind a single corporate NAT you might have 50 paying tenants. Behind a single paying tenant you might have 200 employees. Per-IP is the wrong axis. Per-API-key (or per-tenant-id-from-the-JWT) is the right axis, and that means the limiter state lives in your app or in a shared store keyed on the tenant, not in Redis keyed on the source IP.
  3. Agents can enter runaway loops. A ReAct-style agent that retries a failing tool 30 times in 8 seconds is not a DDoS attack — it is a logic bug or a poison tool result. A fixed-window counter sees 30 requests, may not trip if the window is generous, and by the time it does trip the agent has already burned $12. The right shape is a token bucket with a low burst and a sustained refill — so a single burst of 30 in 8 seconds drains the bucket and forces a cooldown.

What you need is an agent-aware limiter: same sliding-window intuition, but with 6 enforcement surfaces, a token-bucket that fills with USD rather than requests, and a structured verdict the rest of the code can branch on. The reference implementation below is the smallest version of that I have shipped across multi-tenant production agents. It is intentionally one file, zero dependencies, and copy-pasteable into any Node/TypeScript runtime.

The 6 enforcement surfaces

Every rate limiter is a state machine plus a verdict. The state machine tracks the recent cost of a tenant's activity across several axes. The verdict tells the caller why the call is allowed or denied. For AI agents, the state machine has six independent surfaces, not one:

#SurfaceWhat it capsDefault tripFailure mode it catches
1Per-IPRequests per minute from a source IP120 rpmCredential stuffing, bot scans, misconfigured client retrying forever
2Per-tenantRequests per minute from a tenant id60 rpmOne paying customer hogging shared capacity
3Per-sessionTool calls inside one agent session50 callsRunaway ReAct loop, infinite tool retry
4Per-tool-callCalls to a specific expensive tool (web search, code exec)10/min per toolTool-loop-bomb, expensive side-effect amplification
5Per-token-budgetInput + output tokens per hour500k tok/hrVerbose prompt regression, model upgrade drift, accidental full-corpus paste
6Per-cost-budgetUSD per hour per tenant$5/hr (configurable per tier)The most important one. Catches a runaway agent before the bill arrives.

The first two are familiar from any HTTP rate limiter. The third is unique to agent runtimes: an agent session is its own unit of work, and it can be loop-bombed even if the per-tenant counter is fine. The fourth is the per-tool guard — one bad agent can call web_search 1,000 times even if its total requests are under the tenant cap. The fifth is the token-budget guard — the same way Schema Drift Detection (the 17th post) catches format drift, the token-budget guard catches length drift. The sixth is the cost-budget guard, and it is the one that has to exist for the limiter to be a cost limiter rather than just a request limiter.

All six are evaluated at call-begin, in order. The first one that trips wins. The verdict includes which surface tripped, what the current utilization is, and how long until the bucket refills. The caller branches on the verdict and either runs the call, runs a degraded call, or returns a structured error that the 20th-post graceful-degradation wrapper can render honestly.

Reference implementation: 110 lines of TypeScript

The implementation is a single file. There is no Redis dependency in the core (you can add one with a thin adapter for cross-process state), no fixed-window counter, no request-counting-only mode. The limiter's only job is to decide should this call go through right now, accounting for tokens and USD as first-class citizens.

// lib/agent-rate-limiter.ts
// Zero-dep token-bucket rate limiter for AI agents. 6 surfaces:
// per-IP, per-tenant, per-session, per-tool-call, per-token-budget, per-cost-budget.
// Atomic refill, sliding-window cost gate, structured verdict.
// Released under MIT.

export type Surface = "ip" | "tenant" | "session" | "tool" | "tokens" | "cost";

export interface Bucket {
  capacity: number;       // max units (requests, tokens, cents-USD, tool-calls)
  refillPerSec: number;   // sustained refill rate
  tokens: number;         // current available units
  lastRefillMs: number;   // last time we refilled
}

export interface RateLimitVerdict {
  ok: boolean;
  surface?: Surface;       // which surface tripped (if !ok)
  reason?: string;         // human-readable
  retryAfterMs?: number;   // when the bucket will refill enough
  remaining?: number;      // remaining capacity on the tripped surface
}

export interface CostModel {
  inputTokenUsd: number;   // e.g. 0.000005 for gpt-4o-mini input
  outputTokenUsd: number;  // e.g. 0.000015 for gpt-4o-mini output
  cachedInputUsd: number;  // e.g. 0.00000125 for cached reads
}

export interface LimiterConfig {
  perIp: { rpm: number; burst: number };
  perTenant: { rpm: number; burst: number };
  perSession: { calls: number; burst: number };
  perTool: { cpm: number; burst: number };
  perTokens: { perHour: number; burst: number };
  perCost: { centsPerHour: number; burst: number };  // store USD as cents (integer)
  cost: CostModel;
}

export class AgentRateLimiter {
  private ip = new Map<string, Bucket>();
  private tenant = new Map<string, Bucket>();
  private session = new Map<string, Bucket>();
  private tool = new Map<string, Bucket>();
  private tokens = new Map<string, Bucket>();
  private cost = new Map<string, Bucket>();

  constructor(private cfg: LimiterConfig) {}

  // Atomic refill: returns the bucket's current tokens after adding
  // (now - lastRefillMs) * refillPerSec / 1000, capped at capacity.
  private refill(b: Bucket, now: number): Bucket {
    const elapsed = (now - b.lastRefillMs) / 1000;
    const refilled = Math.min(b.capacity, b.tokens + elapsed * b.refillPerSec);
    return { ...b, tokens: refilled, lastRefillMs: now };
  }

  private check(map: Map<string, Bucket>, key: string, cap: number, refill: number, now: number, burst: number): { ok: boolean; b: Bucket; retryMs: number } {
    const b = this.refill(map.get(key) ?? { capacity: cap, refillPerSec: refill / 60, tokens: burst, lastRefillMs: now }, now);
    if (b.tokens >= 1) {
      const updated = { ...b, tokens: b.tokens - 1 };
      map.set(key, updated);
      return { ok: true, b: updated, retryMs: 0 };
    }
    const retryMs = Math.ceil((1 - b.tokens) / b.refillPerSec * 1000);
    map.set(key, b);
    return { ok: false, b, retryMs };
  }

  // The single entry point. Caller passes identifying keys + an estimated cost.
  // The estimated cost is OPTIONAL — for hard-cap enforcement the caller can
  // pre-charge and refund after the call returns with the real token count.
  check(args: {
    ip: string; tenant: string; session: string; tool: string;
    estimatedInputTokens?: number; estimatedOutputTokens?: number;
    now?: number;
  }): RateLimitVerdict {
    const now = args.now ?? Date.now();
    const cfg = this.cfg;

    // Surface 1: per-IP
    let r = this.check(this.ip, args.ip, cfg.perIp.rpm, cfg.perIp.rpm, now, cfg.perIp.burst);
    if (!r.ok) return { ok: false, surface: "ip", reason: `per-IP ${cfg.perIp.rpm} rpm exceeded`, retryAfterMs: r.retryMs, remaining: 0 };

    // Surface 2: per-tenant
    r = this.check(this.tenant, args.tenant, cfg.perTenant.rpm, cfg.perTenant.rpm, now, cfg.perTenant.burst);
    if (!r.ok) return { ok: false, surface: "tenant", reason: `tenant ${cfg.perTenant.rpm} rpm exceeded`, retryAfterMs: r.retryMs, remaining: 0 };

    // Surface 3: per-session (tool-call counter)
    r = this.check(this.session, args.session, cfg.perSession.calls, cfg.perSession.calls / 60, now, cfg.perSession.burst);
    if (!r.ok) return { ok: false, surface: "session", reason: `session ${cfg.perSession.calls} calls exceeded`, retryAfterMs: r.retryMs, remaining: 0 };

    // Surface 4: per-tool-call
    r = this.check(this.tool, `${args.tenant}:${args.tool}`, cfg.perTool.cpm, cfg.perTool.cpm / 60, now, cfg.perTool.burst);
    if (!r.ok) return { ok: false, surface: "tool", reason: `tool ${args.tool} ${cfg.perTool.cpm} cpm exceeded`, retryAfterMs: r.retryMs, remaining: 0 };

    // Surface 5: per-token-budget (pre-charge estimated tokens)
    if (args.estimatedInputTokens !== undefined || args.estimatedOutputTokens !== undefined) {
      const est = (args.estimatedInputTokens ?? 0) + (args.estimatedOutputTokens ?? 0);
      const key = args.tenant;
      const b = this.refill(this.tokens.get(key) ?? { capacity: cfg.perTokens.perHour, refillPerSec: cfg.perTokens.perHour / 3600, tokens: cfg.perTokens.burst, lastRefillMs: now }, now);
      if (b.tokens >= est) {
        this.tokens.set(key, { ...b, tokens: b.tokens - est });
      } else {
        this.tokens.set(key, b);
        const retryMs = Math.ceil((est - b.tokens) / b.refillPerSec * 1000);
        return { ok: false, surface: "tokens", reason: `tenant token budget exceeded (need ${est}, have ${Math.floor(b.tokens)})`, retryAfterMs: retryMs, remaining: Math.floor(b.tokens) };
      }
    }

    // Surface 6: per-cost-budget (pre-charge estimated USD as integer cents)
    if (args.estimatedInputTokens !== undefined || args.estimatedOutputTokens !== undefined) {
      const costCents = Math.ceil(((args.estimatedInputTokens ?? 0) * cfg.cost.inputTokenUsd + (args.estimatedOutputTokens ?? 0) * cfg.cost.outputTokenUsd) * 100);
      const key = args.tenant;
      const b = this.refill(this.cost.get(key) ?? { capacity: cfg.perCost.centsPerHour, refillPerSec: cfg.perCost.centsPerHour / 3600, tokens: cfg.perCost.burst, lastRefillMs: now }, now);
      if (b.tokens >= costCents) {
        this.cost.set(key, { ...b, tokens: b.tokens - costCents });
      } else {
        this.cost.set(key, b);
        const retryMs = Math.ceil((costCents - b.tokens) / b.refillPerSec * 1000);
        return { ok: false, surface: "cost", reason: `tenant cost budget exceeded (need $${(costCents/100).toFixed(2)}, have $${(b.tokens/100).toFixed(2)})`, retryAfterMs: retryMs, remaining: Math.floor(b.tokens) };
      }
    }

    return { ok: true, remaining: r.b.tokens };
  }
}

Why token-bucket + sliding cost, not fixed-window counter

The reference uses a token-bucket. Each surface has a capacity (the burst ceiling) and a refillPerSec (the sustained rate). A burst of 30 requests in 8 seconds drains the per-tenant bucket from 30 to 0, then the next 30 requests get refused with a retryAfterMs that tells the caller exactly when one token is available. That is the right shape for AI agents because:

  • Burst is real. A multi-step agent legitimately fires 5-8 tool calls in 2 seconds. The bucket has to be able to absorb that without tripping. A fixed-window counter would either over-grant (60 rpm window, but the first 60 in the first 8 seconds leave 0 for the rest of the minute) or over-deny (1 rpm to be safe, and the user is throttled for legitimate work).
  • Refill is steady. After a burst, the bucket refills at the configured rate, so a tenant that hits the cap once gets a predictable cooldown, not a "wait until the next minute boundary" mystery.
  • Sliding cost is the honest shape. A 60-second window resets at minute boundaries, which means a tenant can fire 60 calls at :59 and another 60 at :01 and never be rate-limited, even though they made 120 calls in 2 seconds. The token-bucket does not have that gap. The cost surface compounds the protection by capping USD directly.

The cost surface is the most important. The other 5 surfaces protect your infrastructure; the cost surface protects your wallet. A tenant that hits 60 rpm on a small model is fine. A tenant that hits 60 rpm on a reasoning model that streams 8,000 output tokens per call is on track for a $400 bill. The cost surface catches the second case before the bill arrives.

The 4 anti-patterns

Most "rate limiters" in agent codebases I have reviewed get at least one of these wrong. Each anti-pattern has a copy-paste fix below.

Anti-pattern 1: Per-IP only

The classic mistake. You set up express-rate-limit keyed on req.ip, point it at the agent endpoint, and ship it. Six weeks later one of your paying customers has a runaway agent that fires 4,000 requests in 10 minutes — all from the same corporate NAT — and the per-IP limiter never trips because the IP is the same as 49 other tenants' traffic.

Fix: key the limiter on the tenant id (from the API key, JWT, or session cookie), not on the source IP. Per-IP is still useful as a coarse first layer against credential-stuffing, but it must never be the only layer. The reference implementation keys surfaces 2-6 on the tenant id explicitly.

// WRONG
const limiter = rateLimit({ windowMs: 60_000, max: 60, keyGenerator: (req) => req.ip });

// RIGHT
const verdict = limiter.check({
  ip: req.ip,
  tenant: req.auth.tenantId,         // from JWT, not IP
  session: req.sessionId,
  tool: req.body.tool,
  estimatedInputTokens: estimateInputTokens(req.body),
  estimatedOutputTokens: estimateOutputTokens(req.body),
});

Anti-pattern 2: Ignore tool-call cost

You have a per-tenant RPM cap. You do not have a per-tool cap. A tenant writes an agent that calls web_search 200 times in a minute, each call costing $0.03 (because web search has its own per-call surcharge on most providers). The per-tenant cap of 60 rpm trips, but only after the first 60 calls have already cost the tenant $1.80, and the user retries past the limiter and the cost compounds.

Fix: the per-tool surface (surface 4) is keyed on ${tenant}:${tool}, so each tool has its own bucket. A misbehaving web_search caller hits the per-tool cap and the per-tool verdict is returned, while code_exec and file_read are unaffected. The reference implementation already does this; the mistake is deploying without it.

Anti-pattern 3: Fixed-window burst

You use Redis with INCR + EXPIRE on a 60-second window. Tenant fires 60 calls at :59.999 and another 60 calls at :00.001. The counter resets at the window boundary, so the tenant made 120 calls in 2 milliseconds and your limiter said nothing. The reason is that fixed-window counters have a known 2x burst at the boundary.

Fix: use a token-bucket (or a sliding-window log if you need exact accounting) and refill continuously. The reference implementation does this. If you must use Redis for cross-process state, the equivalent is a Lua script that reads, refills, decrements, and writes back atomically — the GCRA (Generic Cell Rate Algorithm) is the production name for this pattern.

Anti-pattern 4: Hard-fail without degradation

The limiter returns HTTP 429, the agent loop catches it, the agent retries, the limiter 429s again, the agent retries, and 30 seconds later the user sees "rate limited." The agent has not fallen back to a smaller model, has not served a cached answer, has not surfaced an honest "you've hit the per-minute cost cap" message. It just gave the user a worse experience than the underlying API could have provided.

Fix: when the cost or token surface trips, do not return 429 — return a structured RateLimitVerdict with surface: "cost" and let the 20th-post graceful-degradation wrapper decide whether to downgrade to a cheaper model, serve a cached answer, or render an honest "this session has hit its budget" message. The wrapper's confidence floor (0.4-1.0) maps cleanly onto how aggressive the fallback is.

// WRONG
if (!verdict.ok) return res.status(429).json({ error: "rate_limited" });

// RIGHT
if (!verdict.ok) {
  // Wire into the 20th-post degrade() wrapper.
  const degraded = await degrade(req.body, { rateLimit: verdict });
  if (degraded.confidence < 0.4) {
    return res.status(429).json({ error: verdict.reason, retryAfterMs: verdict.retryAfterMs, surface: verdict.surface });
  }
  return res.json(degraded);
}

Chaos test: simulate a runaway tool-call loop

The harness below fires 1,000 simulated tool calls from a single tenant in 60 seconds, with 50 input tokens and 800 output tokens per call, and asserts the limiter refuses calls past the per-tenant burst. Run it as part of the pre-merge gate.

// test/rate-limiter.chaos.test.ts
import { AgentRateLimiter } from "../lib/agent-rate-limiter";
import { strict as assert } from "node:assert";

const cfg = {
  perIp: { rpm: 120, burst: 30 },
  perTenant: { rpm: 60, burst: 30 },
  perSession: { calls: 50, burst: 50 },
  perTool: { cpm: 10, burst: 10 },
  perTokens: { perHour: 500_000, burst: 50_000 },
  perCost: { centsPerHour: 500, burst: 50 },   // $5/hr ceiling
  cost: { inputTokenUsd: 0.000005, outputTokenUsd: 0.000015, cachedInputUsd: 0.00000125 },
};

const lim = new AgentRateLimiter(cfg);
const TENANT = "tenant-bomb";
let allowed = 0;
let refused: Record<string, number> = { ip: 0, tenant: 0, session: 0, tool: 0, tokens: 0, cost: 0 };

// Fire 1,000 calls in 60 simulated seconds. The harness below uses
// real time so the bucket actually refills — not all 1,000 fire
// in the same millisecond, which would over-test the burst.
for (let i = 0; i < 1000; i++) {
  const v = lim.check({
    ip: "10.0.0.1",
    tenant: TENANT,
    session: "session-1",
    tool: "web_search",
    estimatedInputTokens: 50,
    estimatedOutputTokens: 800,
  });
  if (v.ok) allowed++;
  else refused[v.surface!]++;
  await new Promise((r) => setTimeout(r, 60));   // ~16 calls/sec sustained
}

assert(allowed <= 1000, "limiter should not allow more than total attempts");
assert(refused.tenant + refused.cost > 0, "limiter must trip on per-tenant OR per-cost surface");
assert(refused.cost > 0, "the per-cost surface must trip in a runaway scenario");
console.log("OK", { allowed, refused });

Woodpecker CI gate: fail any PR that removes the cost surface

The 30-line Woodpecker step below fails any PR that removes the per-cost surface from the limiter config, removes the cost map from the limiter, or sets perCost.centsPerHour to zero (which would silently disable the cost gate). Pair this with the 20th-post degradation gate so silent degradation AND silent cost-cap removal are both blocked at PR time.

# .woodpecker.yml
steps:
  - name: rate-limit-invariant-gate
    image: node:20-alpine
    commands:
      - |
        set -e
        # 1. Per-cost surface must exist in config
        grep -q "perCost:" lib/agent-rate-limiter.ts || (echo "FAIL: perCost surface removed" && exit 1)
        # 2. perCost.centsPerHour must be > 0
        grep -E "perCost\.centsPerHour:\s*[1-9]" lib/agent-rate-limiter.ts >/dev/null || (echo "FAIL: perCost.centsPerHour is 0" && exit 1)
        # 3. The cost Map must exist
        grep -q "private cost = new Map" lib/agent-rate-limiter.ts || (echo "FAIL: cost Map removed" && exit 1)
        # 4. Surface 6 must call cost Map
        grep -q "this.cost.set" lib/agent-rate-limiter.ts || (echo "FAIL: surface-6 write removed" && exit 1)
        # 5. Run the chaos test
        node --import tsx test/rate-limiter.chaos.test.ts
        echo "rate-limit gate: PASS"

How this completes the reliability trilogy

The 19th post covered the circuit breaker: protect the upstream from being overwhelmed. The 20th post covered graceful degradation: when the upstream does fail, return something useful instead of nothing. This post covers the missing third layer: protect your endpoint from the agent itself, with per-tenant cost enforcement that catches the runaway loop before it catches the bill.

Wired together, the stack is:

  1. Layer 0 (this post): the Agent Ingress Firewall CLI sits at the HTTP boundary and enforces per-tenant, per-tool, and per-cost quotas — the call never reaches the limiter if the firewall refuses it.
  2. Layer 1 (this post): the limiter enforces the 6 surfaces in-process, returning a structured RateLimitVerdict to the caller.
  3. Layer 2 (19th post): the circuit breaker sits in front of the upstream LLM API and protects the provider-side 429 / 5xx / cost-cap quota.
  4. Layer 3 (20th post): the graceful-degradation wrapper catches the structured verdict from any of the above layers and returns a degraded-but-useful response, or an honest structured error when the degradation confidence is below the floor.
  5. Layer 4 (16th post): the observability layer emits the limiter-trip metric, the breaker-state metric, and the degradation-confidence metric, all keyed on tenant id, so on-call has one dashboard for the full reliability stack.

That is the reliability trilogy done. 21st post live. The next 22nd-post topic that drops naturally out of this stack is per-tenant observability — what the dashboard actually has to show so on-call can answer "which tenant is over budget right now" in 5 seconds — but that is the next cycle. For this cycle: ship the limiter, ship the gate, ship the trilogy close.
