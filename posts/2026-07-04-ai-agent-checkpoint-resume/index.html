AI Agent Checkpoint Resume: 6 Patterns for Restarting Failed Agent Runs Safely

Published 2026-07-04 · 46th live post · AI agent checkpoint resume, durable execution, recovery, replay, TypeScript

AI agent checkpoint resume sounds like a small operational feature until the first long-running agent dies at step 18 of 23. Without a resumable boundary, the operator must either rerun the whole job, risk repeating side effects, or manually reconstruct which steps actually completed. That is how agents double-send emails, re-open pull requests, lose audit trails, and make operators afraid to run ambitious workflows.

TLDR for search and SGE: AI agent checkpoint resume means saving deterministic step state after each completed boundary so a failed or interrupted agent run can continue without replaying unsafe side effects. A production design needs explicit step IDs, stable input hashes, atomic checkpoint writes, dependency-aware cursors, idempotent replay rules, and a CI fixture that kills the process mid-run and proves the resumed run is equivalent to an uninterrupted one.

Why checkpoint/resume is not just retry logic

Retry logic answers a narrow question: should this failed operation be attempted again? AI agent retry policy covers that layer. Checkpoint/resume answers a larger question: after the whole agent process stops, which completed decisions, tool calls, approvals, files, and evidence packets can be trusted, and where should the next run continue?

That is why AI agent checkpoint resume belongs beside idempotency, tool-call audit trails, agent memory architecture, and deployment gates. A checkpoint is useful only if it records the right boundary, survives crashes, and can be verified before reuse.

Public discussion around agent checkpointing and durable execution is already splitting into two camps. One side treats checkpoints as enough. The other points out that distributed agents need more than snapshots: side-effect deduplication, external workflow state, and replay semantics. The practical middle ground for small teams is to implement a boring, explicit checkpoint/resume layer first, then graduate to heavier durable execution only when the workflow needs it.

The production failure modes

Rate-limit stormThe job retries every tool call or abandons a mostly finished run.Preserve completed steps, wait for budget, then resume only pending work.

Pattern 1: checkpoint explicit step boundaries, not raw prompt history

The first rule of AI agent checkpoint resume is that the checkpoint should not be a dumped conversation transcript. Prompt history is noisy, private, expensive to reload, and ambiguous. A useful checkpoint says: step ID, input hash, status, attempt count, output reference, error summary, dependencies, and timestamps. Store enough to resume safely, not enough to leak the whole run.

Use semantic step IDs such as observe, draft, verify, publish, or send-invoice. If the agent cannot name a step, it cannot resume it reliably. Step boundaries should be chosen around irreversible side effects and expensive work: after a source crawl, after a validated draft, after a CI verification report, after an approval receipt.

Pattern 2: hash the task and each step input

A checkpoint is only safe to reuse if the underlying task has not changed. Hash the normalized task envelope and each step input. On resume, compare the fresh plan against the stored checkpoint. If the task hash changes, start a new run. If one step input changes, reset that step and every dependent step. This prevents the subtle bug where a resumed agent publishes a draft generated for yesterday's requirements.

This also makes AI agent checkpoint resume auditable: the operator can prove that a resumed step ran against the same normalized input, or see exactly where drift forced a reset.

Pattern 3: write checkpoints atomically

A checkpoint file that can be half-written is not a checkpoint. Write to a temporary file, flush it, then rename it into place. In most local filesystems, rename is atomic inside the same directory. That gives you a clean old checkpoint or a clean new checkpoint, not a corrupt in-between JSON blob. The same rule applies if you store checkpoints in SQLite, Postgres, Redis, S3, or a workflow engine: updates must be transactional at the boundary you claim is durable.

Never mark a step done before the evidence is durable. If a step writes an output file, saves a pull request URL, or records an approval receipt, persist that output first, then mark the step done, then write the checkpoint.

Pattern 4: use dependency-aware cursors

Linear cursor-only resume works for simple jobs. Real agents branch: observe two sources in parallel, draft three sections, verify all of them, then publish. Store dependencies per step and resume the first pending step whose dependencies are done. That lets a resumed run skip completed branches without pretending every workflow is a flat list.

This is also where multi-agent orchestration needs a contract. A parent agent should checkpoint delegation packets and child results, not just the final synthesis. If a child agent times out, the parent should know which child result is missing and whether the completed children are still valid.

Pattern 5: pair replay with idempotency keys

Checkpoint/resume without idempotency is unsafe. If a step sends an email, creates an invoice, opens a PR, updates a database, or deploys a site, it needs an idempotency key derived from the run ID and step ID. On resume, the agent asks the destination system for the prior receipt before doing the side effect again. If the receipt exists, mark the step done. If it does not, execute once with the same idempotency key.

This is the bridge between AI agent checkpoint resume and side-effect safety. The checkpoint says what the agent believes. The idempotency receipt proves what the outside world accepted.

Pattern 6: verify resumed equivalence in CI

A checkpoint/resume layer must be tested by killing it. The fixture should run a four-step job, stop the process after step two, load the checkpoint, resume, and compare the final summary against a clean uninterrupted run. Add cases for changed task hash, changed step input, corrupted checkpoint schema, interrupted running status, and a failed side-effect receipt lookup.

For Algoram99-owned repositories, that fixture belongs in Woodpecker CI. It should be local, deterministic, and free: no live LLM call, no paid API call, no external workflow engine required. The point is not to simulate intelligence. The point is to prove the recovery contract.

Reference implementation: zero-dependency TypeScript checkpoint runtime

// checkpoint-resume.ts
// Zero-dependency reference runtime for resumable AI agent jobs.
// It stores only deterministic step boundaries, not raw prompts or secrets.
import fs from "node:fs";
import path from "node:path";
import crypto from "node:crypto";

type StepStatus = "pending" | "running" | "done" | "failed" | "skipped";
type ResumeMode = "fresh" | "resume" | "replay";

type Step = {
  id: string;
  dependsOn?: string[];
  inputHash: string;
  status: StepStatus;
  attempts: number;
  startedAt?: string;
  finishedAt?: string;
  outputRef?: string;
  error?: string;
};

type Checkpoint = {
  schema: "alg99.agent-checkpoint.v1";
  runId: string;
  taskHash: string;
  mode: ResumeMode;
  createdAt: string;
  updatedAt: string;
  cursor: number;
  steps: Step[];
  audit: Array<{ at: string; event: string; step?: string; reason?: string }>;
};

const now = () => new Date().toISOString();
const sha = (value: unknown) => crypto.createHash("sha256").update(JSON.stringify(value)).digest("hex");
const safeId = (s: string) => s.replace(/[^a-z0-9._-]/gi, "_").slice(0, 80);

function checkpointPath(dir: string, runId: string) {
  return path.join(dir, `${safeId(runId)}.checkpoint.json`);
}

function atomicWrite(file: string, obj: unknown) {
  fs.mkdirSync(path.dirname(file), { recursive: true });
  const tmp = `${file}.${process.pid}.tmp`;
  fs.writeFileSync(tmp, JSON.stringify(obj, null, 2));
  fs.renameSync(tmp, file);
}

function load(file: string): Checkpoint | null {
  if (!fs.existsSync(file)) return null;
  const parsed = JSON.parse(fs.readFileSync(file, "utf8"));
  if (parsed.schema !== "alg99.agent-checkpoint.v1") throw new Error("bad checkpoint schema");
  if (!Array.isArray(parsed.steps)) throw new Error("checkpoint missing steps");
  return parsed;
}

function create(runId: string, task: unknown, stepDefs: Array<{ id: string; dependsOn?: string[]; input: unknown }>): Checkpoint {
  const ids = new Set<string>();
  const steps: Step[] = stepDefs.map(def => {
    if (ids.has(def.id)) throw new Error(`duplicate step id: ${def.id}`);
    ids.add(def.id);
    return { id: def.id, dependsOn: def.dependsOn || [], inputHash: sha(def.input), status: "pending", attempts: 0 };
  });
  for (const step of steps) {
    for (const dep of step.dependsOn || []) {
      if (!ids.has(dep)) throw new Error(`unknown dependency ${dep} for ${step.id}`);
    }
  }
  return {
    schema: "alg99.agent-checkpoint.v1",
    runId,
    taskHash: sha(task),
    mode: "fresh",
    createdAt: now(),
    updatedAt: now(),
    cursor: 0,
    steps,
    audit: [{ at: now(), event: "created", reason: "fresh run" }]
  };
}

function reconcile(existing: Checkpoint | null, fresh: Checkpoint): Checkpoint {
  if (!existing) return fresh;
  if (existing.taskHash !== fresh.taskHash) throw new Error("task hash changed; start a new run id");
  const byId = new Map(existing.steps.map(s => [s.id, s]));
  const merged = { ...fresh, mode: "resume" as ResumeMode, createdAt: existing.createdAt, audit: existing.audit.slice() };
  merged.steps = fresh.steps.map(step => {
    const prev = byId.get(step.id);
    if (!prev) return step;
    if (prev.inputHash !== step.inputHash) return { ...step, status: "pending", attempts: prev.attempts, error: "input changed" };
    if (prev.status === "done") return prev;
    if (prev.status === "running") return { ...prev, status: "pending", error: "reset from interrupted running state" };
    return prev;
  });
  merged.cursor = Math.max(0, merged.steps.findIndex(s => s.status !== "done"));
  if (merged.cursor === -1) merged.cursor = merged.steps.length;
  merged.updatedAt = now();
  merged.audit.push({ at: now(), event: "reconciled", reason: "resume from checkpoint" });
  return merged;
}

function ready(step: Step, cp: Checkpoint) {
  return (step.dependsOn || []).every(dep => cp.steps.find(s => s.id === dep)?.status === "done");
}

async function run(cp: Checkpoint, file: string, handlers: Record<string, () => Promise<string>>) {
  for (let i = 0; i < cp.steps.length; i++) {
    const step = cp.steps[i];
    if (step.status === "done" || step.status === "skipped") continue;
    if (!ready(step, cp)) continue;
    const handler = handlers[step.id];
    if (!handler) throw new Error(`missing handler for ${step.id}`);
    step.status = "running";
    step.startedAt = now();
    step.attempts += 1;
    cp.cursor = i;
    cp.updatedAt = now();
    cp.audit.push({ at: now(), event: "started", step: step.id });
    atomicWrite(file, cp);
    try {
      const out = await handler();
      step.status = "done";
      step.outputRef = out;
      step.finishedAt = now();
      step.error = undefined;
      cp.audit.push({ at: now(), event: "finished", step: step.id });
    } catch (err) {
      step.status = "failed";
      step.finishedAt = now();
      step.error = String(err).slice(0, 300);
      cp.audit.push({ at: now(), event: "failed", step: step.id, reason: step.error });
      atomicWrite(file, cp);
      throw err;
    }
    cp.updatedAt = now();
    atomicWrite(file, cp);
  }
  return cp;
}

function summarize(cp: Checkpoint) {
  const counts = cp.steps.reduce<Record<string, number>>((acc, step) => {
    acc[step.status] = (acc[step.status] || 0) + 1;
    return acc;
  }, {});
  return { runId: cp.runId, mode: cp.mode, cursor: cp.cursor, counts, done: cp.steps.every(s => s.status === "done") };
}

async function main() {
  const dir = process.argv[2] || ".agent-checkpoints";
  const runId = process.argv[3] || "demo-run";
  const task = { goal: "publish verified article", repo: "alg99" };
  const stepDefs = [
    { id: "observe", input: { sources: ["repo", "search"] } },
    { id: "draft", dependsOn: ["observe"], input: { minWords: 1500 } },
    { id: "verify", dependsOn: ["draft"], input: { checks: ["links", "counts", "html"] } },
    { id: "publish", dependsOn: ["verify"], input: { branch: "main" } }
  ];
  const file = checkpointPath(dir, runId);
  const cp = reconcile(load(file), create(runId, task, stepDefs));
  const handlers = {
    observe: async () => "evidence/observe.json",
    draft: async () => "posts/draft.html",
    verify: async () => "reports/verify.json",
    publish: async () => "deploy/publish.txt"
  };
  await run(cp, file, handlers);
  console.log(JSON.stringify(summarize(cp), null, 2));
}

if (import.meta.url === `file://${process.argv[1]}`) {
  main().catch(err => { console.error(err.message); process.exit(1); });
}

Five anti-patterns that break checkpoint/resume

1. Transcript as checkpoint

Dumping the whole prompt history looks easy but does not define completed side effects, dependencies, or replay safety.

2. Done before durable evidence

If a step is marked done before its output reference or receipt is persisted, a crash creates a false checkpoint.

3. Retry non-idempotent writes

Resuming a send, charge, deploy, or database mutation without an idempotency key is a duplicate-action generator.

4. No schema version

Old checkpoints need a version check. Otherwise new code may misread old fields and resume from the wrong boundary.

5. Invisible resume mode

Operators should see when a run resumed, which steps were reused, and which steps reset. Hidden resume is debugging debt.

Where this fits in the Algoram99 stack

Use AI agent checkpoint resume as the recovery layer after the system already has tool validation, idempotency, and audit events. A good sequence is:

  1. Validate tool calls before execution with a schema gate.
  2. Wrap side effects with idempotency keys.
  3. Append a tamper-evident audit event for each external action.
  4. Write a checkpoint after each durable boundary.
  5. Use trace replay and deployment checks to prove resumed behavior did not drift.
