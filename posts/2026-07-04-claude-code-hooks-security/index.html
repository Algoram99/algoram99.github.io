Claude Code Hooks Security: 7 Guardrails for Safe PreToolUse and PostToolUse Automation

Published 2026-07-04 · 45th live post · Claude Code, hooks, AI agent security, PreToolUse, PostToolUse

Claude Code hooks are a sharp edge in the best sense: they let a team add deterministic controls around an agent that can read files, run shell commands, call tools, and edit a repository. The same hook can also become a bypassable permission theater if it is scoped loosely, logs secrets, or trusts the JSON payload it receives from an agent context.

Short answer for search and SGE: secure Claude Code hooks by narrowing matchers to the tools you actually gate, treating hook input as untrusted JSON, failing closed on dangerous PreToolUse cases, canonicalizing file paths before allowlist checks, redacting before logging, keeping PostToolUse hooks advisory unless the event supports blocking, and replaying hook fixtures in CI. If a hook cannot be tested with a representative input packet, it is not a security control yet.

Why hooks need their own security model

Claude Code hooks are local automation points in the agent lifecycle. Public documentation describes hook events such as PreToolUse, PostToolUse, notification-style events, and stop/subagent events, with matchers and command or HTTP handlers. That is exactly why they are useful: teams can inspect a pending tool call before it happens, emit evidence after it happens, or notify an operator when a long task reaches a boundary.

The problem is that hook automation lives between the model and the machine. If the hook is too permissive, the model can still run a risky command. If the hook is too broad, it blocks harmless work and operators turn it off. If the hook writes raw payloads to disk, the security control becomes a secret-retention system. If the hook only checks happy-path fields, a renamed payload shape can silently downgrade protection.

The right mental model is not "hooks make Claude Code safe." The right model is "hooks are a programmable policy boundary that must be versioned, tested, logged, and scoped like any other security-sensitive code path."

Guardrail 1: scope matchers like firewall rules

A hook with a broad matcher feels convenient during setup and dangerous during incident review. Treat matchers as firewall rules: the narrowest rule that covers the intended tool should win. A Bash policy should match Bash. A file-write policy should match file-writing tools. MCP tool policies should match the specific remote surface that carries the risk. Avoid a single catch-all hook that tries to understand every event and every tool shape.

Good scoping has two benefits. First, the policy code becomes smaller because it only handles one input family. Second, the incident timeline is easier to read: if a Bash hook allowed a Bash command, the owner knows exactly which policy needs repair. If a global hook allowed it, nobody knows whether the matcher, parser, or policy failed.

Guardrail 2: treat hook input as untrusted JSON

The input packet can contain tool names, tool arguments, paths, commands, metadata, transcripts, and environment details depending on the event. Parse it defensively. Unknown fields should not grant permission. Missing fields should not default to safe for destructive actions. Strings should be bounded before logging. Arrays and objects should be normalized before comparison.

The strongest hook runtimes follow a boring pattern: parse, normalize, classify, decide, emit. Do not let the policy branch directly on raw nested fields from the payload. Normalize the tool name, command, path, cwd, and actor into a small internal object, then make the policy decision from that object.

Guardrail 3: fail closed for PreToolUse, fail loud for everything else

PreToolUse is where blocking belongs. If Claude Code is about to run Bash, write a file, or call a high-risk tool, the hook should either allow the call or deny it before the side effect happens. If parsing fails for a high-risk tool, the safe default is deny with a clear reason. A malformed packet should not execute a shell command merely because the hook crashed.

PostToolUse is different. It is best for evidence: record what happened, scan returned output for secrets, update an audit trail, or trigger a notification. Unless the event explicitly supports blocking semantics for that lifecycle point, do not pretend a post-execution hook prevented the action. It observed the action. That observation is useful, but it is not authorization.

Guardrail 4: canonicalize paths before allowlist checks

Path policy is where many local-agent controls fail. Checking whether a path starts with ./src is not enough. Resolve the working directory. Resolve symlinks where possible. Collapse ... Compare the canonical target against canonical allowed roots. Then decide whether the tool can read, write, delete, or execute that path.

Use separate allowlists for read and write. Reading README.md and writing README.md are not the same risk. Reading .env and printing it into a prompt is worse than reading a source file. Writing a GitHub Pages post is lower risk than touching a deployment credential or wallet file. The hook should know the difference.

Guardrail 5: redact before logging, not after

Hook logs are attractive because they create local evidence. They are also dangerous because hooks see the exact payload that may contain credentials, private file paths, API output, or user text. Redact before the payload leaves memory. Store a finding like [GITHUB_PAT_REDACTED], a hash prefix, event type, tool name, and decision reason. Do not write the raw token and hope a later scanner catches it.

This pairs cleanly with the AI agent structured logging and AI agent audit trail patterns: structured events are useful only if they are safe to retain.

Guardrail 6: make every deny repairable

A deny message that says "blocked" creates pressure to disable the hook. A deny message that says "blocked: Bash command reads .env; use scripts/print-config-shape.mjs instead" teaches the operator and the agent how to recover. Security controls survive only when they are specific enough to be fixed quickly.

Repairable messages should include the policy name, normalized tool, risk class, and the smallest safe next step. Do not include the full command if it contains a secret. Do not include raw file contents. The audience is both the human and the next model turn, so keep it terse and operational.

Guardrail 7: replay hooks in CI

If a hook is supposed to block rm -rf, curl | sh, writes outside the repository, or secret-file reads, ship fixtures for those cases. Run them in CI every time hook code, settings, prompts, tool definitions, or agent permissions change. A hook that has never been replayed against a dangerous packet is a hope, not a gate.

For Algoram99-owned repositories, this belongs in Woodpecker CI rather than GitHub Actions. The hook suite should be fast, local, deterministic, and side-effect free. It should not call Claude Code or any paid API. It should feed JSON fixtures into the hook script and assert exit codes and structured decisions.

A compact PreToolUse guard

#!/usr/bin/env node
// .claude/hooks/pretool-guard.mjs
// Zero-dependency guard for representative Claude Code PreToolUse packets.

import fs from "node:fs";
import path from "node:path";

const raw = fs.readFileSync(0, "utf8") || "{}";
let event;
try {
  event = JSON.parse(raw);
} catch {
  deny("invalid-json", "Hook input was not valid JSON.");
}

const cwd = fs.realpathSync(process.cwd());
const allowedWriteRoots = [path.join(cwd, "src"), path.join(cwd, "posts"), path.join(cwd, ".claude")];
const secretPathHints = [".env", "id_rsa", "id_ed25519", "wallet", "mnemonic", "keychain", "credentials"];
const dangerousShell = [
  /\brm\s+-rf\b/,
  /\bcurl\b[\s\S]*\|\s*(sh|bash|zsh)\b/,
  /\bwget\b[\s\S]*\|\s*(sh|bash|zsh)\b/,
  /\bchmod\s+777\b/,
  /\b(printenv|env)\b[\s\S]*(curl|nc|telnet|python|node)/,
  /\.env\b[\s\S]*(cat|grep|sed|awk|curl|nc|python|node)/,
];

function normTool(e) {
  return String(e.tool_name || e.toolName || e.name || "").trim();
}

function normInput(e) {
  return e.tool_input || e.toolInput || e.input || e.arguments || {};
}

function redact(s) {
  return String(s)
    .replace(/sk-[A-Za-z0-9_-]{16,}/g, "[API_KEY_REDACTED]")
    .replace(/gh[pousr]_[A-Za-z0-9_]{20,}/g, "[GITHUB_TOKEN_REDACTED]")
    .replace(/xox[baprs]-[A-Za-z0-9-]{20,}/g, "[SLACK_TOKEN_REDACTED]")
    .replace(/AKIA[0-9A-Z]{16}/g, "[AWS_KEY_REDACTED]")
    .slice(0, 500);
}

function canonical(candidate) {
  const rawPath = String(candidate || "");
  if (!rawPath) return null;
  const absolute = path.isAbsolute(rawPath) ? rawPath : path.join(cwd, rawPath);
  return path.normalize(absolute);
}

function underAnyRoot(target, roots) {
  if (!target) return false;
  return roots.some(root => target === root || target.startsWith(root + path.sep));
}

function deny(code, reason, extra = {}) {
  const line = JSON.stringify({ ok: false, decision: "deny", code, reason, ...extra });
  console.error(line);
  process.exit(2);
}

function allow(reason, extra = {}) {
  console.log(JSON.stringify({ ok: true, decision: "allow", reason, ...extra }));
  process.exit(0);
}

const tool = normTool(event);
const input = normInput(event);
const command = String(input.command || input.cmd || "");
const targetPath = canonical(input.file_path || input.path || input.target || "");

if (!tool) deny("missing-tool", "No tool name present in hook packet.");

if (/bash|shell/i.test(tool)) {
  for (const pattern of dangerousShell) {
    if (pattern.test(command)) {
      deny("dangerous-shell", "Blocked risky shell command before execution.", {
        pattern: String(pattern),
        command_preview: redact(command),
      });
    }
  }
  allow("bash-command-passed-policy", { command_preview: redact(command) });
}

if (/write|edit|notebookedit/i.test(tool)) {
  if (!targetPath) deny("missing-path", "Write-like tool did not include a target path.");
  if (!underAnyRoot(targetPath, allowedWriteRoots)) {
    deny("write-outside-allowlist", "Write target is outside allowed repository roots.", { target: targetPath });
  }
  if (secretPathHints.some(hint => targetPath.toLowerCase().includes(hint))) {
    deny("secret-path-write", "Write target looks credential-adjacent.", { target: targetPath });
  }
  allow("write-target-passed-policy", { target: targetPath });
}

if (/read|grep|glob/i.test(tool)) {
  const joined = JSON.stringify(input).toLowerCase();
  if (secretPathHints.some(hint => joined.includes(hint))) {
    deny("secret-path-read", "Read/search request touches credential-shaped paths.");
  }
  allow("read-target-passed-policy");
}

allow("tool-not-in-high-risk-set", { tool });

This script is intentionally conservative. It is not a universal sanitizer, and it does not replace the Claude Code permission system. It gives the team a local, testable policy boundary for the riskiest command classes and path classes. Keep your real version in source control, with fixtures beside it.

The exact matcher surface should follow the current Claude Code documentation and the tool names your environment exposes. The security rule is stable: match narrowly, keep one policy per risk family, and test that the matcher actually fires.

Woodpecker CI gate

when:
  event: [push, pull_request, manual]
steps:
  claude_hooks_security:
    image: node:22-alpine
    commands:
      - node .claude/hooks/pretool-guard.mjs < test/fixtures/hook/bash-safe.json
      - '! node .claude/hooks/pretool-guard.mjs < test/fixtures/hook/bash-rm-rf.json'
      - '! node .claude/hooks/pretool-guard.mjs < test/fixtures/hook/bash-curl-pipe-sh.json'
      - '! node .claude/hooks/pretool-guard.mjs < test/fixtures/hook/read-env.json'
      - '! node .claude/hooks/pretool-guard.mjs < test/fixtures/hook/write-outside-repo.json'
      - node scripts/audit-claude-hook-settings.mjs

Use fixtures that mirror the real packets your Claude Code version emits. The gate should fail when the deny cases exit successfully and fail when the allow case exits with a denial. That catches both broken security and broken productivity.

Five anti-patterns

  1. One giant hook: a global hook tries to parse every event and tool, then misses the exact risky surface it was supposed to protect.
  2. Regex-only path policy: the hook checks a string but never canonicalizes paths, so traversal and symlinks become policy bypasses.
  3. Raw payload audit logs: the hook captures secrets while trying to prove it blocked secrets.
  4. PostToolUse as authorization: the hook records a dangerous action after it happened and the team calls that prevention.
  5. No fixture replay: the hook worked once manually, but a settings change stopped the matcher from firing and no CI test noticed.

Definition of done

A Claude Code hook security setup is done when a reviewer can point to four artifacts: the settings file that scopes each matcher, the hook script that makes a normalized allow/deny decision, the redacted evidence log that proves what happened without retaining secrets, and the CI run that replays allow and deny fixtures. Anything less is still useful automation, but it should not be described as a production security gate.

The practical goal is not to make the coding agent powerless. The goal is to make powerful actions explicit. When a hook blocks a destructive command before execution, records a redacted reason, and gives the agent a safe alternative, the operator gets speed and control at the same time.
