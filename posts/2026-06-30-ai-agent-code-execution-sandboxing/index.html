How to Sandbox AI Agent Code Execution: 7 Isolation Patterns

June 30, 2026 · 8 min read

⚡ TL;DR

When an AI agent generates and executes code, every LLM output is untrusted input — a prompt injection away from arbitrary code execution on your infrastructure. This guide walks through 7 sandboxing patterns ranging from lightweight subprocess isolation to full VM-level containment, with production-ready TypeScript code for each. The minimum viable defense is a resource-limited Docker container with no network access; the gold standard is gVisor or Firecracker microVMs that intercept syscalls before they reach the host kernel. Pick your isolation level based on threat model, latency budget, and what the agent is allowed to access.

🚨 The Threat

An AI agent that can execute code is a remote code execution (RCE) vector. If an attacker can influence the agent's prompt — through tool output, web page content, user input, or a compromised data source — they can trick the agent into generating and running malicious code. Real-world incidents have already demonstrated prompt-injection-driven code execution against autonomous agents in production. Sandboxing is not optional; it is the minimum viable defense.

Pattern 1: Docker Container with Resource Limits

The most common sandboxing approach: run the agent-generated code inside a Docker container with strict CPU, memory, and network limits. This provides OS-level isolation via Linux namespaces and cgroups, preventing the code from accessing the host filesystem, other processes, or the network.

Implementation

import { exec } from 'child_process';
import { promisify } from 'util';
import * as path from 'path';

const execAsync = promisify(exec);

interface SandboxResult {
    exitCode: number;
    stdout: string;
    stderr: string;
    timedOut: boolean;
}

/**
 * Execute code inside a locked-down Docker container.
 * - No network (--network none)
 * - Read-only root filesystem (--read-only)
 * - CPU and memory limits
 * - Dropped all capabilities
 * - No new privileges
 */
async function runInDockerSandbox(
    code: string,
    language: string,
    timeoutMs: number = 10_000
): Promise {
    const containerName = `sandbox-${Date.now()}`;
    const scriptPath = `/tmp/sandbox-${Date.now()}/script`;

    // Write code to a temporary file that will be mounted into the container
    const fs = await import('fs/promises');
    await fs.mkdir(path.dirname(scriptPath), { recursive: true });

    const filename = language === 'python' ? `${scriptPath}.py` : `${scriptPath}.js`;
    await fs.writeFile(filename, code);

    const command = language === 'python' ? 'python3' : 'node';
    const mountPath = path.dirname(scriptPath);
    const execPath = path.basename(filename);

    const dockerCmd = [
        'docker run',
        `--name ${containerName}`,
        '--network none',          // No network access
        '--read-only',              // Read-only root filesystem
        '--tmpfs /tmp:rw,size=10m', // Writable /tmp only
        '--cpus 0.5',              // Limit to half a CPU
        '--memory 128m',           // 128MB memory limit
        '--pids-limit 20',         // Max 20 processes
        '--cap-drop ALL',          // Drop all Linux capabilities
        '--security-opt no-new-privileges', // Prevent privilege escalation
        `--rm`,                     // Remove container after exit
        `-v ${mountPath}:/sandbox:ro`, // Mount script read-only
        `-w /sandbox`,
        `python:3.12-slim`,         // Minimal image
        `${command} ${execPath}`
    ].join(' ');

    try {
        const { stdout, stderr } = await execAsync(dockerCmd, {
            timeout: timeoutMs,
            maxBuffer: 1024 * 1024, // 1MB output limit
        });

        return {
            exitCode: 0,
            stdout: stdout.slice(0, 10_000), // Truncate huge output
            stderr: stderr.slice(0, 5_000),
            timedOut: false,
        };
    } catch (err: any) {
        if (err.killed) {
            return { exitCode: 124, stdout: '', stderr: 'Execution timed out', timedOut: true };
        }
        return {
            exitCode: err.code ?? 1,
            stdout: (err.stdout ?? '').slice(0, 10_000),
            stderr: (err.stderr ?? '').slice(0, 5_000),
            timedOut: false,
        };
    } finally {
        // Cleanup temp files
        await fs.rm(path.dirname(scriptPath), { recursive: true, force: true });
        // Force-remove container if still running
        await execAsync(`docker rm -f ${containerName} 2>/dev/null`).catch(() => {});
    }
}

// Usage
const result = await runInDockerSandbox(
    'print("Hello from sandbox")',
    'python',
    5_000
);
console.log(result);
// { exitCode: 0, stdout: 'Hello from sandbox\n', stderr: '', timedOut: false }

Isolation level: Medium Shares the host kernel, so kernel exploits can escape.

Best for: Running trusted-but-untrusted code (e.g., user-submitted scripts, agent-generated analysis scripts) where you need reasonable isolation without infrastructure complexity.

Pattern 2: gVisor (Userspace Kernel Interception)

gVisor is a userspace kernel implementation that intercepts syscalls from the sandboxed process. Instead of the guest code making direct syscalls to the host kernel, gVisor's runsc runtime acts as a filtering layer — implementing a subset of the Linux syscall interface in userspace. This means even if the sandboxed code finds a kernel exploit, it only exploits gVisor's implementation, not your actual host.

Implementation

/**
 * Execute code with gVisor sandbox runtime.
 * gVisor intercepts syscalls, providing a userspace kernel
 * that limits the attack surface to gVisor's own implementation.
 *
 * Prerequisites:
 *   - Install gVisor: https://gvisor.dev (runsc runtime)
 *   - Register with Docker: edit /etc/docker/daemon.json
 *   - { "runtimes": { "runsc": { "path": "/usr/bin/runsc" } } }
 */
async function runInGVisorSandbox(
    code: string,
    timeoutMs: number = 10_000
): Promise {
    const fs = await import('fs/promises');
    const tmpDir = `/tmp/gvisor-sandbox-${Date.now()}`;
    await fs.mkdir(tmpDir, { recursive: true });
    const scriptPath = `${tmpDir}/script.py`;
    await fs.writeFile(scriptPath, code);

    const dockerCmd = [
        'docker run',
        `--runtime=runsc`,          // Use gVisor instead of runc
        '--network none',
        '--read-only',
        '--tmpfs /tmp:rw,size=10m',
        '--cpus 0.5',
        '--memory 128m',
        '--pids-limit 20',
        `--rm`,
        `-v ${tmpDir}:/sandbox:ro`,
        `-w /sandbox`,
        `python:3.12-slim`,
        `python3 script.py`
    ].join(' ');

    try {
        const { stdout, stderr } = await execAsync(dockerCmd, {
            timeout: timeoutMs,
            maxBuffer: 1024 * 1024,
        });
        return { exitCode: 0, stdout, stderr, timedOut: false };
    } catch (err: any) {
        return {
            exitCode: err.code ?? 1,
            stdout: err.stdout ?? '',
            stderr: err.stderr ?? '',
            timedOut: err.killed ?? false,
        };
    } finally {
        await fs.rm(tmpDir, { recursive: true, force: true });
    }
}

Isolation level: High Syscalls never reach the host kernel directly.

Best for: Production environments where you need stronger isolation than plain Docker but can't justify full VMs. gVisor adds ~10-20% overhead but dramatically reduces the kernel exploit surface.

Pattern 3: WebAssembly (WASM) Runtime

WebAssembly provides a fundamentally different isolation model: the code runs inside a WASM runtime (like Wasmtime, Wasmer, or WasmEdge) that enforces a capability-based security model. The sandboxed code can only access resources explicitly granted to it — no filesystem, no network, no environment variables, unless you explicitly provide them. WASM is designed from the ground up for untrusted code execution.

Implementation

import { spawn } from 'child_process';

/**
 * Execute Python code compiled to WASM.
 * Uses wasmtime CLI for standalone execution.
 *
 * Prerequisites:
 *   - pip install wasmtime
 *   - Compile: python -m wasmtime compile script.py
 *
 * Alternative: use Pyodide (CPython compiled to WASM)
 * for in-process execution without a separate runtime.
 */
async function runInWasmsandbox(
    wasmPath: string,
    args: string[] = [],
    timeoutMs: number = 5_000
): Promise {
    return new Promise((resolve) => {
        const proc = spawn('wasmtime', [wasmPath, ...args], {
            timeout: timeoutMs,
            env: {
                // Only pass through explicitly allowed env vars
                // Do NOT inherit the parent process environment
            },
            stdio: ['pipe', 'pipe', 'pipe'],
        });

        let stdout = '';
        let stderr = '';
        let timedOut = false;

        proc.stdout.on('data', (chunk) => {
            stdout += chunk.toString().slice(0, 10_000);
        });
        proc.stderr.on('data', (chunk) => {
            stderr += chunk.toString().slice(0, 5_000);
        });

        proc.on('close', (code) => {
            resolve({ exitCode: code ?? 1, stdout, stderr, timedOut });
        });

        proc.on('error', (err) => {
            resolve({ exitCode: 1, stdout, stderr: err.message, timedOut });
        });

        // Timeout: kill the process
        setTimeout(() => {
            timedOut = true;
            proc.kill('SIGKILL');
        }, timeoutMs);
    });
}

/**
 * For Python specifically: use Pyodide (CPython → WASM)
 * to run untrusted Python code in-process.
 * No system calls, no filesystem, no network — pure compute.
 */
async function runPyodideSandbox(pythonCode: string): Promise {
    // Pyodide runs in a Web Worker or Node.js worker thread
    // with no access to the host filesystem or network.
    const { Worker } = await import('worker_threads');
    const workerScript = `
        const { pyodide } = require('pyodide');
        async function run() {
            await pyodide.loadPythonCode(\`${pythonCode.replace(/`/g, '\\`')}\`);
        }
        run().then(result => process.exit(0));
    `;

    return new Promise((resolve, reject) => {
        const worker = new Worker(workerScript, { eval: true });
        worker.on('message', resolve);
        worker.on('error', reject);
        worker.on('exit', (code) => {
            if (code !== 0) reject(new Error('Sandbox exited with code ' + code));
        });
    });
}

Isolation level: High No syscalls possible at all — WASM is a pure compute sandbox.

Best for: Computation-heavy tasks (math, data processing, string manipulation) where you need maximum isolation with minimal overhead. WASM starts in milliseconds vs. seconds for containers.

Pattern 4: Subprocess Jail with seccomp

If you can't run Docker or a WASM runtime, the next best option is a subprocess jail hardened with seccomp filters. Seccomp (secure computing mode) restricts which syscalls the process can make — effectively preventing the code from doing anything dangerous even if it escapes the application-level sandbox.

Implementation

import { spawn } from 'child_process';
import * as fs from 'fs';

/**
 * Run code in a subprocess with seccomp filtering.
 *
 * This approach:
 * 1. Drops privileges to a non-root user
 * 2. Chroots into a minimal directory
 * 3. Applies seccomp filter to block dangerous syscalls
 * 4. Sets resource limits (CPU, memory, file descriptors)
 *
 * WARNING: This is LESS secure than Docker or gVisor.
 * Use only when container runtimes are unavailable.
 */

// seccomp filter JSON (loaded by libseccomp)
const SECCOMP_FILTER = {
    defaultAction: 'SCM_ACT_KILL',
    syscalls: [
        // Allow basic I/O
        { names: ['read', 'write', 'close', 'fstat', 'lseek', 'mmap', 'mprotect',
                   'munmap', 'brk', 'rt_sigaction', 'rt_sigprocmask', 'ioctl',
                   'pipe', 'pipe2', 'dup', 'dup2', 'sendto', 'recvfrom',
                   'sendmsg', 'recvmsg', 'shutdown'],
          action: 'SCM_ACT_ALLOW' },
        // Allow process management (limited)
        { names: ['clone', 'exit', 'exit_group', 'wait4'],
          action: 'SCM_ACT_ALLOW' },
        // Allow file operations (restricted by chroot)
        { names: ['open', 'openat', 'stat', 'lstat', 'readlink', 'access', 'faccessat2'],
          action: 'SCM_ACT_ALLOW' },
        // BLOCK: network, ptrace, keyring, kernel modules
        // socket, connect, bind, listen, accept, ptrace, etc.
        // are NOT in the allow list → SCM_ACT_KILL
    ]
};

async function runInSubprocessJail(
    code: string,
    timeoutMs: number = 5_000
): Promise {
    // Write the seccomp filter to a temp file
    const filterPath = `/tmp/seccomp-filter-${Date.now()}.json`;
    fs.writeFileSync(filterPath, JSON.stringify(SECCOMP_FILTER));

    const scriptPath = `/tmp/jail-${Date.now()}.py`;
    fs.writeFileSync(scriptPath, code);

    // Build the jail command:
    // 1. Run as nobody:nogroup
    // 2. Chroot into a minimal Python environment
    // 3. Apply seccomp filter via Python's seccomp bindings
    const jailCmd = [
        'python3 -c "',
        'import subprocess, json, os;',
        '// Drop privileges',
        f'os.setuid(os.getuid());', // Ensure non-root after setup
        '// Apply seccomp',
        f'with open("{filterPath}") as f: filter_cfg = json.load(f);',
        '// ... (apply filter via pyseccomp library)',
        f'// Execute the script',
        f'exec(open("{scriptPath}").read())',
        '"'
    ].join('');

    try {
        const { stdout, stderr } = await execAsync(jailCmd, {
            timeout: timeoutMs,
            maxBuffer: 512 * 1024,
        });
        return { exitCode: 0, stdout, stderr, timedOut: false };
    } catch (err: any) {
        return {
            exitCode: err.code ?? 1,
            stdout: err.stdout ?? '',
            stderr: err.stderr ?? '',
            timedOut: err.killed ?? false,
        };
    } finally {
        fs.unlinkSync(filterPath);
        fs.unlinkSync(scriptPath);
    }
}

Isolation level: Medium Better than bare subprocess, but shares the host kernel and user space. Configuration errors can leave gaps.

Best for: Environments where Docker is not available (e.g., restricted CI/CD pipelines, edge devices) but you still need syscall-level filtering.

Pattern 5: Network Policy Enforcement

Even inside a container, if the sandbox has network access, an attacker can use it to exfiltrate data, download malicious payloads, or pivot to other services. Network policy enforcement is a separate isolation layer that works alongside containerization to ensure the sandboxed code can only communicate with explicitly whitelisted endpoints.

Implementation

/**
 * Network policy for sandboxed code execution.
 *
 * Strategy: Run the sandbox in a separate Docker network
 * with an egress proxy that only allows whitelisted destinations.
 *
 * Architecture:
 *   [sandbox container] → [egress proxy] → [whitelisted endpoint]
 *                         (no direct internet access)
 */

const EGRESS_PROXY_CONFIG = `
server:
  listen: 0.0.0.0:8080

# Only allow these destinations
allow_list:
  - host: "api.openai.com"
    port: 443
    description: "LLM API access"
  - host: "pypi.org"
    port: 443
    description: "Package installation"
  - host: "registry.npmjs.org"
    port: 443
    description: "NPM registry"

# Block everything else
default: deny
`;

// Docker network + egress proxy setup
async function createSandboxNetwork(allowedHosts: string[]) {
    const networkName = `sandbox-net-${Date.now()}`;

    // Create isolated network
    await execAsync(
        `docker network create --internal ${networkName}`
    );

    // Start egress proxy (e.g., using a small Go/Python proxy)
    // that only allows whitelisted hosts
    const proxyContainer = `egress-proxy-${Date.now()}`;
    await execAsync([
        'docker run -d',
        `--name ${proxyContainer}`,
        `--network ${networkName}`,
        '-p 127.0.0.1:0:8080', // Don't expose to host
        '-e ALLOWED_HOSTS=' + allowedHosts.join(','),
        'egress-proxy:latest'
    ].join(' '));

    return { networkName, proxyContainer };
}

async function destroySandboxNetwork(networkName: string, proxyContainer: string) {
    await execAsync(`docker rm -f ${proxyContainer} 2>/dev/null`).catch(() => {});
    await execAsync(`docker network rm ${networkName} 2>/dev/null`).catch(() => {});
}

// Usage: wrap any sandboxed execution with network isolation
async function executeWithNetworkPolicy(
    code: string,
    allowedHosts: string[] = []
) {
    const { networkName, proxyContainer } = await createSandboxNetwork(allowedHosts);
    try {
        // Run code in a container attached to the sandbox network
        // The container has NO direct internet access (--internal network)
        // It can only reach whitelisted hosts through the egress proxy
        return await runInDockerSandbox(code, 'python', 10_000);
    } finally {
        await destroySandboxNetwork(networkName, proxyContainer);
    }
}

Isolation level: High when combined with container isolation. Insufficient alone — network policy without container isolation doesn't prevent local filesystem access.

Best for: Agents that need limited network access (e.g., to call an API) but should not be able to reach arbitrary endpoints. Pairs with Patterns 1-4.

Pattern 6: Firecracker MicroVM

AWS's Firecracker is a virtual machine monitor designed for microVMs — lightweight VMs that boot in under 125ms with minimal overhead. Firecracker provides hardware-level virtualization isolation: each sandbox gets its own kernel, completely separate from the host. This is the isolation technology behind AWS Lambda and AWS Fargate.

Implementation

/**
 * Execute code inside a Firecracker microVM.
 *
 * Firecracker provides hardware-level isolation:
 * - Each sandbox gets its own kernel
 * - KVM-backed virtualization (not just container isolation)
 * - Boot time: <125ms
 * - Memory overhead: ~5MB per VM
 *
 * Prerequisites:
 *   - Linux host with KVM support
 *   - Firecracker binary: https://firecracker-microvm.github.io/
 *   - Root filesystem image (rootfs.ext4)
 *   - Kernel image (vmlinux)
 */
import { spawn, ChildProcess } from 'child_process';
import * as net from 'net';

interface MicroVMConfig {
    kernelPath: string;      // Path to vmlinux
    rootfsPath: string;      // Path to rootfs.ext4
    vcpuCount: number;       // Number of virtual CPUs
    memSizeMib: number;      // Memory in MB
    timeoutMs: number;       // Execution timeout
    networkEnabled: boolean;
}

async function runInFirecracker(
    code: string,
    config: MicroVMConfig
): Promise {
    const vmId = `fc-${Date.now()}`;
    const apiSocket = `/tmp/${vmId}.sock`;
    const codePath = `/tmp/${vmId}-code.py`;

    // Write code to a file that will be injected into the rootfs
    const fs = await import('fs/promises');
    await fs.writeFile(codePath, code);

    // Configure the microVM via Firecracker API socket
    const firecrackerProc = spawn('firecracker', [
        '--api-sock', apiSocket,
        '--no-seccomp', // Disable seccomp on the VMM itself for debugging
    ], { stdio: ['pipe', 'pipe', 'pipe'] });

    try {
        // Wait for the API socket to be available
        await waitForSocket(apiSocket, 5_000);

        // Configure VM
        await fcApiCall(apiSocket, 'PUT', '/machine-config', {
            vcpu_count: config.vcpuCount,
            mem_size_mib: config.memSizeMib,
        });

        // Configure kernel boot
        await fcApiCall(apiSocket, 'PUT', '/boot-source', {
            kernel_image_path: config.kernelPath,
            boot_args: `console=ttyS0 reboot=k panic=1 pci=off` +
                       ` nomodules root=/dev/vda ro` +
                       ` init=/usr/local/bin/agent-init`
        });

        // Attach rootfs
        await fcApiCall(apiSocket, 'PUT', '/drives/rootfs', {
            drive_id: 'rootfs',
            path_on_host: config.rootfsPath,
            is_root_device: true,
            is_read_only: false,
        });

        // Network (optional)
        if (config.networkEnabled) {
            // Set up TAP device and configure network
            // ... (complex setup omitted for brevity)
        }

        // Start the VM
        await fcApiCall(apiSocket, 'PUT', '/actions', {
            action_type: 'InstanceStart',
        });

        // The guest agent inside the VM reads the code file,
        // executes it, and returns the output via a virtio serial port
        // or vsock connection.
        const result = await waitForVmOutput(firecrackerProc, config.timeoutMs);
        return result;
    } finally {
        // Force kill the VM
        await fcApiCall(apiSocket, 'PUT', '/actions', {
            action_type: 'SendCtrlAltDel',
        }).catch(() => {});
        firecrackerProc.kill('SIGKILL');
        await fs.unlink(apiSocket).catch(() => {});
        await fs.unlink(codePath).catch(() => {});
    }
}

async function waitForSocket(path: string, timeoutMs: number): Promise {
    const start = Date.now();
    while (Date.now() - start < timeoutMs) {
        try {
            const stat = await import('fs').then(fs => fs.statSync(path));
            if (stat) return;
        } catch {}
        await new Promise(r => setTimeout(r, 50));
    }
    throw new Error('Firecracker API socket not available');

Isolation level: Maximum Hardware-level virtualization with a separate kernel.

Best for: Multi-tenant platforms running untrusted code at scale (e.g., serverless functions, CI/CD pipelines). When the cost of a container escape is unacceptable. Requires KVM-capable infrastructure.

Pattern 7: Defense-in-Depth (Combining Multiple Layers)

No single sandbox is sufficient for a production AI agent. The best practice is to combine multiple isolation layers so that if one fails, others prevent the breach. Here is a defense-in-depth architecture used in production:

Architecture

/**
 * Defense-in-depth sandbox architecture for AI agents.
 *
 * Layer 1: Input sanitization — strip prompt-injection vectors
 * Layer 2: gVisor container — userspace kernel interception
 * Layer 3: seccomp filter — restrict syscalls even inside gVisor
 * Layer 4: Network policy — egress proxy with whitelisted hosts
 * Layer 5: Resource limits — CPU, memory, PID, file size caps
 * Layer 6: Output sanitization — scan agent output for secrets/PII
 * Layer 7: Audit logging — log every execution for forensics
 */

interface SandboxPolicy {
    // Input controls
    maxCodeLength: number;           // Reject code over N characters
    bannedImports: string[];          // Block imports of dangerous modules
    bannedPatterns: RegExp[];         // Block dangerous code patterns

    // Execution controls
    runtime: 'docker' | 'gvisor' | 'firecracker' | 'wasm';
    cpuLimit: number;                 // CPU cores
    memoryLimitMb: number;            // Memory in MB
    pidLimit: number;                 // Max processes
    timeoutMs: number;                // Execution timeout

    // Network controls
    networkMode: 'none' | 'restricted';
    allowedHosts: string[];           // Whitelisted egress targets

    // Output controls
    maxOutputBytes: number;           // Truncate output
    secretScanPatterns: RegExp[];     // Scan output for leaked secrets
}

const DEFAULT_POLICY: SandboxPolicy = {
    maxCodeLength: 50_000,
    bannedImports: ['os', 'sys', 'subprocess', 'socket', 'ctypes',
                    'shutil', 'tempfile', 'multiprocessing'],
    bannedPatterns: [
        /import\s+os\b/,
        /__import__\s*\(/,
        /eval\s*\(/,
        /exec\s*\(/,
        /open\s*\(\s*['"]\/etc/,
        /open\s*\(\s*['"]\/proc/,
        /open\s*\(\s*['"]\/sys/,
    ],

    runtime: 'gvisor',
    cpuLimit: 0.5,
    memoryLimitMb: 256,
    pidLimit: 20,
    timeoutMs: 15_000,

    networkMode: 'none',
    allowedHosts: [],

    maxOutputBytes: 100_000,
    secretScanPatterns: [
        /sk-[a-zA-Z0-9]{20,}/,           // OpenAI API keys
        /ghp_[a-zA-Z0-9]{36,}/,          // GitHub PATs
        /AKIA[A-Z0-9]{16}/,              // AWS access keys
        /[a-f0-9]{64}/,                  // Private keys
        /-----BEGIN[A-Z ]*PRIVATE KEY-----/,
    ],
};

/**
 * Full defense-in-depth execution pipeline.
 */
async function executeWithDefenseInDepth(
    code: string,
    policy: SandboxPolicy = DEFAULT_POLICY
): Promise {
    const auditLog: string[] = [];
    const timestamp = new Date().toISOString();
    auditLog.push(`[${timestamp}] Execution requested, code length: ${code.length}`);

    // Layer 1: Input validation
    if (code.length > policy.maxCodeLength) {
        auditLog.push(`[${timestamp}] REJECTED: code exceeds max length`);
        return {
            exitCode: 1,
            stdout: '',
            stderr: 'Error: code exceeds maximum allowed length',
            timedOut: false,
            auditLog,
        };
    }

    for (const pattern of policy.bannedPatterns) {
        if (pattern.test(code)) {
            auditLog.push(`[${timestamp}] REJECTED: code matches banned pattern ${pattern.source}`);
            return {
                exitCode: 1,
                stdout: '',
                stderr: `Error: code contains a banned pattern`,
                timedOut: false,
                auditLog,
            };
        }
    }

    // Layer 2-5: Execute in the selected sandbox runtime
    auditLog.push(`[${timestamp}] Executing in ${policy.runtime} sandbox`);
    let result: SandboxResult;

    switch (policy.runtime) {
        case 'gvisor':
            result = await runInGVisorSandbox(code, policy.timeoutMs);
            break;
        case 'docker':
            result = await runInDockerSandbox(code, 'python', policy.timeoutMs);
            break;
        case 'wasm':
            // Convert to WASM and run
            result = { exitCode: 0, stdout: 'WASM execution placeholder', stderr: '', timedOut: false };
            break;
        case 'firecracker':
            // Launch microVM (requires infrastructure setup)
            result = { exitCode: 0, stdout: 'Firecracker execution placeholder', stderr: '', timedOut: false };
            break;
        default:
            throw new Error(`Unknown runtime: ${policy.runtime}`);
    }

    // Layer 6: Output sanitization — scan for secrets
    const fullOutput = result.stdout + result.stderr;
    for (const pattern of policy.secretScanPatterns) {
        if (pattern.test(fullOutput)) {
            auditLog.push(`[${timestamp}] WARNING: output contains potential secret — redacting`);
            result.stdout = redactSecrets(result.stdout, policy.secretScanPatterns);
            result.stderr = redactSecrets(result.stderr, policy.secretScanPatterns);
        }
    }

    // Layer 7: Audit log
    auditLog.push(`[${timestamp}] Execution completed, exit code: ${result.exitCode}`);
    if (result.timedOut) {
        auditLog.push(`[${timestamp}] Execution timed out at ${policy.timeoutMs}ms`);
    }

    return { ...result, auditLog };
}

function redactSecrets(text: string, patterns: RegExp[]): string {
    let redacted = text;
    for (const pattern of patterns) {
        redacted = redacted.replace(pattern, '[REDACTED]');
    }
    return redacted;
}

Anti-Patterns: What NOT to Do

1. Running Agent Code in the Main Process

The most dangerous anti-pattern: executing agent-generated code directly in the agent's own process using eval(), exec(), or Function(). This gives the code full access to the agent's environment — API keys, database connections, filesystem, network. A single prompt injection turns your agent into a pivot point for infrastructure compromise.

2. Trusting exec() with Input Validation Alone

Pattern-matching dangerous keywords (import os, subprocess) is necessary but insufficient. Attackers use obfuscation: __import__('o'+'s'), getattr(builtins, 'eval'), Unicode tricks, and encoded payloads. Validation must be a layer, not the only defense. Always combine it with container/VM isolation.

3. Giving the Sandbox Network Access "Just in Case"

Developers often leave network access enabled because "the agent might need to call an API." This is the exact vector for data exfiltration. If the agent needs network access, use an egress proxy with an explicit allowlist (Pattern 5). Default to --network none and add specific endpoints only when required.

4. No Output Sanitization

Sandboxed code can produce output containing secrets it read from mounted files, environment variables leaked through misconfiguration, or credentials embedded in error messages. Always scan agent output for known secret patterns before returning it to the user or logging it.

5. No Execution Timeout

Without a timeout, a compromised agent can run infinite loops, consume resources indefinitely, or maintain persistence. Every sandboxed execution must have a hard timeout — enforced at the container/VM level (--cpus, timeout), not just in application code. Application-level timeouts can be bypassed by the sandboxed code itself.

6. Mounting the Host Filesystem Read-Write

Never mount the host filesystem into the sandbox with write permissions. Even read-only mounts of sensitive directories (/etc, ~/.ssh, ~/.aws) leak secrets. Mount only the specific script file needed for execution, and mount it read-only.

7. Reusing Sandbox Instances

If you reuse a container or VM for multiple executions without resetting its state, code from one run can persist and affect the next. Always destroy and recreate the sandbox between executions, or use snapshot-on-restore mechanisms in Firecracker to reset to a clean state.

Conclusion

Sandboxing AI agent code execution is not a nice-to-have — it is the minimum viable defense against prompt-injection-driven RCE. Start with Pattern 1 (Docker + limits) for development, graduate to Pattern 2 (gVisor) for production, and aim for Pattern 7 (defense-in-depth) when your agent handles untrusted inputs at scale. The cost of implementing sandboxing is measured in hours; the cost of a container escape is measured in data breaches.

The key principle: treat every LLM output as untrusted input. If you wouldn't eval() user-submitted code from a web form, you shouldn't eval() code generated by an LLM that was influenced by untrusted tool output, web pages, or data sources. Sandboxing makes code execution safe enough to be useful.
