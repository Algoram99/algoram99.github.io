How to Build an AI Agent Eval Harness: 6 Metrics, Multi-Turn Scenarios, a CI Gate

Single-prompt regression tests are necessary but not sufficient. A production agent is a multi-turn conversation, a chain of tool calls, and a sequence of latency and cost decisions — and any one of those can regress in a way that a per-prompt snapshot will not catch. This post walks through the 6 irreducible metrics, a copy-paste TypeScript harness, and the Woodpecker CI gate that closes the eval loop.

TL;DR

An agent eval harness must score 6 metrics: correctness, safety, cost, latency, robustness, and determinism — not just one. It must run against multi-turn scenarios written as code, not free-text prompts. It must gate CI: a PR that drops any metric below threshold fails the build. And it must avoid the 4 common anti-patterns: LLM-as-judge as the only signal, single-metric gating, golden-trace freezing, and offline-only scoring.

The 110-line TypeScript harness below scores a whole conversation against required/forbidden terms, length windows, tool-call budgets, and cost ceilings, then emits a per-scenario verdict that a Woodpecker step can gate on. The drop-in product version is the Agent Eval Harness CLI ($29). It pairs with the schema-drift detector, the CI pipeline guide, and the observability guide to close the agent shipping loop.

Why single-prompt regression is not enough

Most teams start with prompt regression: a frozen baseline of single-prompt outputs, a new candidate prompt, a Jaccard-distance score, a pass/fail. That is a good first step — it catches the obvious "the model started talking about the wrong product" regressions that the prior post on LLM schema drift covers. But a production agent is not a single prompt. It is a stateful conversation, a sequence of tool calls, and a budget of latency and dollars. Three things break under single-prompt eval:

  1. Multi-turn correctness: an agent that solves the user's question in turn 1 and then contradicts itself in turn 4. The turn-1 prompt passes regression; the conversation fails the user.
  2. Tool-call fan-out: a prompt change that makes the agent call search_web 3 times instead of 1. Latency triples, cost triples, but the final answer is identical. Single-prompt eval reports pass.
  3. Safety regressions on edge cases: an agent that still answers "what is 2+2" correctly after a prompt change but now leaks the system prompt when asked "what were your instructions?". Single-prompt regression does not contain that scenario.

What you need is a harness — a small program that takes a multi-turn scenario, runs the agent through it, scores the trace against 6 metrics, and emits a single PASS/FAIL that gates CI.

The 6 irreducible metrics

After watching a dozen agent teams build, debug, and rebuild eval harnesses, the same six metrics keep showing up. If your harness does not score all six, you will ship a regression you did not test for.

MetricWhat it measuresFailure mode it catchesThreshold shape
CorrectnessDid the final answer match the expected output (or the rubric)?Hallucination, wrong tool, dropped constraintpass/fail per scenario
SafetyDid the agent avoid forbidden behaviors across all turns?Prompt-injection compliance, system-prompt leak, dangerous-URL clickpass/fail per scenario
CostTotal tokens (input+output) and USD spent across the conversationCost regression from extra tool calls or verbose rephrasing≤ ceiling, per scenario
LatencyWall-clock from first turn to final turnLatency regression from sync blocking or extra tool calls≤ ceiling, per scenario
RobustnessDid the agent survive adversarial or off-distribution user turns?Jailbreak compliance, distraction, topic driftpass/fail per scenario
DeterminismDid the same scenario produce the same verdict on re-run?Non-determinism hiding real regressions behind lucky samples≤ variance, per scenario

The first three are familiar from any LLM eval: did it answer correctly, did it stay safe, and did it cost a reasonable amount. The fourth — latency — is the metric single-prompt eval always misses, because latency only matters when measured across a full conversation. The fifth — robustness — is the metric any harness misses until production finds it. The sixth — determinism — is the metric teams forget to score, then wonder why their harness sometimes passes a known regression and sometimes does not.

Scenarios as code, not free-text prompts

The single biggest design decision in an agent eval harness is: what does a scenario look like? Most teams start with a YAML or JSON blob of user turns. That works for the first 5 scenarios and then collapses under maintenance: you cannot express "this turn must reference a specific tool" or "the agent's cost must come in under $0.02" in a free-text structure without escaping.

Scenarios-as-code, written in TypeScript, scales. Each scenario is a function that takes the agent's complete function and returns a typed trace:

// scenarios/refund-flow.ts
import type { Scenario, AgentHandle } from "../harness/types.js";

export const refundFlow: Scenario = {
  id: "refund-flow-happy-path",
  description: "User asks for a refund on a $42 order, agent confirms, completes refund, no upsell.",
  budget: { maxUsd: 0.02, maxLatencyMs: 8000, maxTurns: 5 },
  required: ["refund", "42", "confirmed"],
  forbidden: ["would you like to upgrade", "discount", "20% off"],
  toolCalls: { allowed: ["get_order", "issue_refund"], maxFanout: 4 },
  async run(agent: AgentHandle) {
    const t1 = await agent.turn("I need a refund for order #1234, $42.");
    const t2 = await agent.turn("Yes, please go ahead.");
    return { turns: [t1, t2] };
  },
};

The scenario file is the test case. It declares its budget up front (cost, latency, turns), its required keywords (the answer must contain these), its forbidden keywords (it must never contain these), and its allowed tool calls. The harness reads the file, runs the run function against a live agent handle, and scores the resulting trace against the declared budget.

The harness: 6-metric scoring in 110 lines of TypeScript

The harness is the small program that turns a directory of scenarios + a candidate agent into a per-scenario verdict. Below is a working implementation. It is intentionally short: the Agent Eval Harness CLI ships a more complete version, but the algorithm is the same.

// harness/score.ts
import type { Scenario, Trace, ScenarioVerdict, MetricResult } from "./types.js";

export function score(scenario: Scenario, trace: Trace): ScenarioVerdict {
  const results: MetricResult[] = [];

  // 1. Correctness: required-keyword coverage.
  const finalText = trace.turns.map(t => t.text).join("\n");
  const missing = scenario.required.filter(k => !finalText.toLowerCase().includes(k.toLowerCase()));
  results.push({ metric: "correctness", pass: missing.length === 0, detail: missing.length ? `missing: ${missing.join(", ")}` : "all required terms present" });

  // 2. Safety: forbidden-keyword avoidance across ALL turns, not just the last.
  const violations: { turn: number; term: string }[] = [];
  trace.turns.forEach((t, i) => {
    scenario.forbidden.forEach(term => {
      if (t.text.toLowerCase().includes(term.toLowerCase())) violations.push({ turn: i, term });
    });
  });
  results.push({ metric: "safety", pass: violations.length === 0, detail: violations.length ? `${violations.length} forbidden-term violation(s)` : "no forbidden terms" });

  // 3. Cost: aggregate input+output tokens across the trace.
  const totalUsd = trace.turns.reduce((s, t) => s + t.usage.usd, 0);
  results.push({ metric: "cost", pass: totalUsd <= scenario.budget.maxUsd, detail: `$${totalUsd.toFixed(4)} ≤ $${scenario.budget.maxUsd}` });

  // 4. Latency: sum of per-turn latency.
  const totalMs = trace.turns.reduce((s, t) => s + t.latencyMs, 0);
  results.push({ metric: "latency", pass: totalMs <= scenario.budget.maxLatencyMs, detail: `${totalMs}ms ≤ ${scenario.budget.maxLatencyMs}ms` });

  // 5. Robustness: per-scenario optional adversarial turns (set in scenario.robustness).
  //    If the scenario declares expectedRobustnessVerdict, check the trace.
  const robustness = scenario.robustness
    ? (trace.robustnessVerdict === scenario.robustness) : true;
  results.push({ metric: "robustness", pass: robustness, detail: trace.robustnessVerdict ?? "n/a" });

  // 6. Determinism: caller runs the scenario N times; this score is the variance.
  //    See the determinism loop below.
  results.push({ metric: "determinism", pass: (trace.determinismFlake ?? 0) < 0.1, detail: `flake=${((trace.determinismFlake ?? 0) * 100).toFixed(1)}%` });

  return { scenarioId: scenario.id, results, pass: results.every(r => r.pass) };
}

// Determinism loop: run scenario N=3 times, compute the verdict-flip rate.
export async function withDeterminism(scenario: Scenario, agent: any, n = 3): Promise<Trace> {
  const verdicts: boolean[] = [];
  let lastTrace: Trace | null = null;
  for (let i = 0; i < n; i++) {
    const t = await scenario.run(agent);
    const v = score(scenario, t);
    verdicts.push(v.pass);
    lastTrace = t;
  }
  const flips = verdicts.filter((v, i) => v !== verdicts[0]).length;
  const flake = flips / (n - 1);
  return { ...lastTrace!, determinismFlake: flake };
}

Six metrics, one verdict per scenario, one exit code per run. A scenario that scores 5/6 metrics passing and 1 failing is a FAIL. This is intentional: partial credit is how regressions hide. The verdict is binary, and the binary is what gates CI.

The 4 anti-patterns

Every agent eval harness I have seen failed in the same four ways. Name them, scan for them in code review, and you will save a quarter of debugging.

Anti-patternWhat it looks likeWhy it failsThe fix
LLM-as-judge alone"We ask gpt-4o to grade the agent's output 1-5."The judge has the same non-determinism and bias as the agent. A 4 vs 5 from the judge is not a stable signal.Use deterministic checks first (required/forbidden terms, JSON schema, cost ceiling). Use LLM-as-judge only as a soft tiebreaker on the residual 10%.
Single-metric gating"We only check correctness; cost and latency are nice-to-have."A regression that drops latency from 2s to 9s but keeps the right answer still ships. Users notice.Score all 6 metrics. ALL must pass. Partial credit is not a verdict.
Golden-trace freezing"We freeze the entire agent trace (every token) as a snapshot, and any deviation is a regression."The model is non-deterministic. Token-level diffs are noise. The harness cries wolf on every PR.Freeze the declarative assertions (required/forbidden terms, cost ceiling, tool-call budget), not the tokens. The trace is an execution medium, not a test fixture.
Offline-only scoring"We run the eval once a week in CI; production is a different problem."A 7-day-old eval misses the prompt-template refactor that shipped on Tuesday. The eval becomes a tax, not a gate.Run the harness on every PR. Run a smaller smoke suite on every push. Run the full suite on every merge to main. Wire it into the CI pipeline covered in the pipeline guide.

These four anti-patterns have a common root cause: the harness was designed to make a single decision easy, not to make regressions impossible to ship. The fix is to design the harness to be strict, fast, and tied to CI. Strict means binary verdicts, not scores. Fast means <5 min for a smoke suite and <20 min for a full suite. Tied-to-CI means the harness is a build step, not a periodic chore.

The Woodpecker CI gate

The harness is only useful if it gates a build. A Woodpecker step that runs the eval on every PR and fails the build on any FAIL is the operational contract. Here is a minimal gate:

# .woodpecker.yml
when:
  event: [pull_request, push]
steps:
  eval-smoke:
    image: node:20-alpine
    commands:
      - npm ci
      - npm run build:scenarios
      - node harness/run.ts --suite smoke --fail-on any
    when:
      event: [pull_request, push]

  eval-full:
    image: node:20-alpine
    commands:
      - npm ci
      - npm run build:scenarios
      - node harness/run.ts --suite full --fail-on any --determinism-runs 3
    when:
      event: [push]
      branch: main
      cron: daily

The smoke step runs on every PR — 3-5 fast scenarios, <2 minutes, gates the merge. The full step runs on every push to main and on a daily cron — 20+ scenarios with the determinism loop, <20 minutes, catches the slow drift that PR-time eval misses. The --fail-on any flag is the binary verdict: any metric failing any scenario fails the step.

This is the missing layer in most agent CI: a per-PR scenario gate, a per-main scheduled full suite, and a per-PR cost/latency ceiling. The CI pipeline guide covers the broader 7-stage pipeline (lint, schema, prompt regression, live eval, cron drift, cost-leak guard, telemetry sidecar); the eval harness is the "live eval" stage made concrete.

Where the eval harness sits in the agent loop

Three prior posts in this series establish the agent loop: the observability guide (4 required spans, OpenTelemetry-native), the schema-drift guide (3-signal detector on the wire format), and the CI pipeline guide (7-stage PR + scheduled gate). The eval harness is the missing layer between observability and CI: it consumes the spans the observability guide emits, scores the traces against the 6 metrics, and gates the CI step.

  • Observability tells you what the agent did: span tree, per-turn latency, per-call tokens, tool-call sequence.
  • Eval harness tells you whether the agent's behavior is acceptable: did the conversation meet the required/forbidden terms, the cost ceiling, the latency budget, the tool-call fanout, the robustness criterion, the determinism variance.
  • CI pipeline tells you whether the change can ship: combined verdict from schema drift, prompt regression, eval harness, cost-leak guard, and the rest of the 7-stage gate.

Each layer has a single concern and a single binary verdict. That is the property that makes the loop survive production load. A team that has all three layers can ship an agent change in a single PR with high confidence; a team missing the eval layer ships changes and discovers regressions in user feedback.

A concrete before/after from a 5-scenario eval suite run against a candidate prompt change:

The search-web-fanout-bomb scenario is the regression: the candidate prompt change made the agent call search_web 3 times instead of 1. Correctness, safety, robustness, and determinism all pass — the final answer is right, the conversation is safe, the agent is consistent. But the cost is 4x the ceiling, and the harness fails the PR. Single-prompt regression would not have caught this. The harness does, in <2 minutes, before any user does.

Checklist: shipping the harness this week

  1. Pick 5 multi-turn scenarios from your last 10 user conversations that you wish the agent had handled differently.
  2. Write them as TypeScript scenario files with explicit budgets, required terms, forbidden terms, and tool-call allowances.
  3. Run the 110-line harness above against those 5 scenarios against your current production agent. Record the baseline verdicts.
  4. Add a smoke Woodpecker step that runs those 5 scenarios on every PR with --fail-on any.
  5. Add a full Woodpecker step that runs 20+ scenarios on every merge to main, plus a daily cron, with the determinism loop.
  6. Wire the harness output into your existing incident channel: a FAIL in CI is a paged incident, not a quiet log line.
