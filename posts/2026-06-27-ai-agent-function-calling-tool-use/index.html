AI Agent Function Calling: 6 Patterns, 5 Anti-Patterns, and a Drop-In Tool-Use Runtime

Function calling is the bridge between an LLM that generates text and an agent that takes action. Get it wrong and your agent calls the wrong tool 8% of the time, passes a string where an integer is expected, or fires a side effect twice on retry. Get it right with these six patterns, five anti-patterns, and a 130-line TypeScript runtime you can drop into any agent today.

⚡ TL;DR

  1. Define tools with Zod schemas — the LLM's JSON is validated before it touches your code, not after.
  2. Disambiguate tool selection — when two tools could answer the query, add a selector layer that picks based on argument compatibility, not description similarity.
  3. Validate every argument before execution — reject malformed calls at the boundary so your database never sees an unexpected shape.
  4. Wrap side effects with idempotency — every mutation gets an idempotency key so retries are safe.
  5. Normalize tool results — turn heterogeneous outputs (API JSON, file contents, database rows) into a uniform ToolResult shape.
  6. Log every tool call to an audit trail — one JSONL line per call so you can grep, replay, and debug.

Plus: a 130-line TypeScript runtime that implements all six patterns, and a Woodpecker CI gate that fails any PR that removes schema validation from the tool-call boundary.

Why Function Calling Breaks in Production

Function calling — also known as tool use — lets an LLM invoke structured functions with typed arguments. OpenAI calls it function calling, Anthropic calls it tool use, and the pattern is the same: you give the model a list of tools with their schemas, the model decides which tool to call and with what arguments, and your code executes it.

The problem is that most implementations treat the LLM's tool-call output as trustworthy. They pass the raw JSON arguments straight to the target function without validation. They let the model choose from a flat list of 50 tools. They fire side effects without idempotency keys. And when the tool call fails, they swallow the error and return an empty response.

Here is what actually happens in production:

  • Wrong tool selected: when you have 20+ tools, the LLM picks the wrong one 3–8% of the time because descriptions overlap and the model pattern-matches on surface similarity, not argument compatibility.
  • Malformed arguments: the LLM passes { "user_id": null } when the function expects a number, or passes a stringified date instead of an ISO 8601 timestamp. Without validation, this hits your database as a null foreign key.
  • Double-executed side effects: the agent calls send_email, the request times out, the retry policy fires the same call again, and the user gets two emails. No idempotency key means no dedup.
  • Silent failures: the tool throws, the wrapper catches, and the agent receives an empty result. The user sees a blank response. Nobody knows the tool failed until a customer complains.

Six patterns fix all of these. Let's walk through each one.

Pattern 1: Schema-First Tool Definition

Every tool is defined as a Zod schema + an executor function. The schema is the single source of truth: it generates the OpenAI/Anthropic function definition, validates the LLM's arguments at the boundary, and serves as the TypeScript type for the executor.

Why this matters: if your function definition says user_id: number but the LLM sends "user_id": "abc", the schema catches it before your executor ever runs. Without the schema, the bad argument propagates through your entire call stack.

import { z } from 'zod';

// Define the tool schema (single source of truth)
const lookupUserSchema = z.object({
  userId: z.number().int().positive(),
  includeDeleted: z.boolean().default(false),
});

// The executor takes typed arguments (inferred from the schema)
type LookupUserArgs = z.infer;

async function lookupUser(args: LookupUserArgs): Promise<ToolResult> {
  const user = await db.users.findById(args.userId, {
    includeDeleted: args.includeDeleted,
  });
  return {
    ok: true,
    data: user,
    meta: { tool: 'lookup_user', latencyMs: 0 },
  };
}

// Register the tool: schema + executor + metadata
const tools: ToolRegistry = {
  lookup_user: {
    description: 'Look up a user by their numeric ID. Returns the user object.',
    schema: lookupUserSchema,
    executor: lookupUser,
    sideEffects: false, // read-only
  },
  send_email: {
    description: 'Send an email to a user.',
    schema: sendEmailSchema,
    executor: sendEmail,
    sideEffects: true, // mutation: wrap with idempotency
  },
};

The key insight: z.infer<typeof schema> gives you end-to-end type safety. The LLM's JSON is validated at the boundary, the executor gets typed arguments, and TypeScript catches mismatches at compile time. No any, no as casts, no runtime surprises.

Pattern 2: Tool-Selection Disambiguation

When you have more than 10 tools, the LLM starts picking the wrong one. Not because it's dumb — because your tool descriptions overlap. search_orders and search_invoices both "search for records." create_task and create_ticket both "create a work item."

The fix is a disambiguation layer that runs after the LLM selects a tool but before execution:

  1. Parse the LLM's tool call and arguments.
  2. Check if any other registered tool has a compatible schema for the same arguments.
  3. If yes, run a lightweight argument-compatibility score (how many fields match the schema vs. how many are extra or missing).
  4. If the top two tools are within 15% of each other on compatibility, ask the LLM to disambiguate with a follow-up turn.

This is cheap (no additional LLM call in 92%+ of cases) and catches the long tail of wrong-tool selections that compound silently.

function disambiguateToolCall(
  selectedTool: string,
  args: Record<string, unknown>,
  registry: ToolRegistry
): { tool: string; disambiguate: boolean } {
  // Score every tool by how well the args match its schema
  const scores = Object.entries(registry).map(([name, tool]) => {
    const result = tool.schema.safeParse(args);
    const fields = Object.keys(tool.schema.shape);
    const matching = fields.filter(f => f in args).length;
    const extra = Object.keys(args).filter(k => !(k in fields)).length;
    const score = result.success
      ? 1.0 - (extra * 0.15)
      : (matching / fields.length) - (extra * 0.15);
    return { name, score };
  }).sort((a, b) => b.score - a.score);

  const [best, second] = scores;
  if (!best) return { tool: selectedTool, disambiguate: false };

  // If the top two are within 15%, flag for disambiguation
  if (second && (best.score - second.score) < 0.15) {
    return { tool: best.name, disambiguate: true };
  }
  return { tool: best.name, disambiguate: false };
}

Pattern 3: Argument Validation Before Execution

Every tool call passes through a validation gate before the executor runs. The gate uses the Zod schema from Pattern 1. If validation fails, the error is returned to the agent as a structured ToolResult with ok: false and a human-readable error message. The agent can then self-correct on the next turn.

This is the single most important pattern in this article. Without it, a malformed argument like { "userId": "abc" } propagates from the LLM's JSON output through your executor and into your database as a string foreign key. The database accepts it (because you didn't constrain the column), and three weeks later you discover orphaned rows.

async function executeToolCall(
  toolName: string,
  rawArgs: unknown,
  registry: ToolRegistry,
  ctx: CallContext
): Promise<ToolResult> {
  const tool = registry[toolName];
  if (!tool) {
    return {
      ok: false,
      error: `Unknown tool: ${toolName}. Available: ${Object.keys(registry).join(', ')}`,
      meta: { tool: toolName, latencyMs: 0 },
    };
  }

  // VALIDATION GATE: reject malformed args before execution
  const parsed = tool.schema.safeParse(rawArgs);
  if (!parsed.success) {
    const issues = parsed.error.issues
      .map(i => `${i.path.join('.')}: ${i.message}`)
      .join('; ');
    return {
      ok: false,
      error: `Invalid arguments: ${issues}`,
      meta: { tool: toolName, latencyMs: 0 },
    };
  }

  // Arguments are now typed and validated
  const start = Date.now();
  try {
    const result = tool.sideEffects
      ? await withIdempotency(tool.executor, parsed.data, ctx)
      : await tool.executor(parsed.data);
    result.meta.latencyMs = Date.now() - start;
    return result;
  } catch (err) {
    return {
      ok: false,
      error: err instanceof Error ? err.message : String(err),
      meta: { tool: toolName, latencyMs: Date.now() - start },
    };
  }
}

Pattern 4: Side-Effect-Aware Execution Wrappers

Tools that mutate state — sending emails, creating records, charging payments — get wrapped with an idempotency layer. The wrapper derives a stable key from the tool name + arguments + conversation turn, checks a dedup cache, and either returns the cached result or executes fresh and caches it.

Why this matters: when your agent's retry policy (see the retry policy post) re-fires a tool call after a timeout, the idempotency wrapper ensures the side effect runs exactly once. Without it, every retry is a potential duplicate email, double charge, or duplicate database write.

import { createHash } from 'crypto';

const idempotencyCache = new Map<string, ToolResult>();

async function withIdempotency(
  executor: (args: any) => Promise<ToolResult>,
  args: Record<string, unknown>,
  ctx: CallContext
): Promise<ToolResult> {
  // Derive a stable key from tool name + sorted args + turn ID
  const keyParts = [
    ctx.toolName,
    JSON.stringify(sortKeys(args)),
    ctx.turnId,
  ];
  const key = createHash('sha256')
    .update(keyParts.join('|'))
    .digest('hex')
    .slice(0, 32);

  // Check cache: if we already ran this exact call, return cached result
  if (idempotencyCache.has(key)) {
    const cached = idempotencyCache.get(key)!;
    cached.meta.cached = true;
    return cached;
  }

  // Execute and cache
  const result = await executor(args);
  idempotencyCache.set(key, result);
  // Evict after 5 minutes to bound memory
  setTimeout(() => idempotencyCache.delete(key), 5 * 60 * 1000);
  return result;
}

function sortKeys(obj: Record<string, unknown>): Record<string, unknown> {
  return Object.keys(obj).sort().reduce((acc, k) => {
    acc[k] = obj[k];
    return acc;
  }, {} as Record<string, unknown>);
}

This pairs directly with the idempotency post's 6 key patterns. The difference: that post covers idempotency as a general principle across the entire agent stack. This pattern is the specific implementation for the tool-call boundary.

Pattern 5: Result-Format Normalization

Every tool returns a uniform ToolResult shape regardless of what the underlying function produces. An API call returns JSON, a database query returns rows, a file read returns a string — but the agent always sees the same structure:

interface ToolResult {
  ok: boolean;
  data?: unknown;        // The tool's output (any shape)
  error?: string;        // Human-readable error if ok=false
  meta: {
    tool: string;        // Tool name for audit trail
    latencyMs: number;   // Wall-clock execution time
    cached?: boolean;    // True if served from idempotency cache
    tokensEstimate?: number; // Rough output token count for budgeting
  };
}

Why this matters: without normalization, each tool returns a different shape, and the agent's response-generation code has to branch on tool name to know how to format the result. With normalization, the agent loop is a single uniform path: call tool → get ToolResult → check ok → format data or handle error.

For cost optimization (see the LLM cost reduction post), the tokensEstimate field lets the agent decide whether to include the full result in the context or summarize it before passing it to the next LLM call.

Pattern 6: Tool-Call Audit Trail

Every tool call is logged as a single JSONL line to an append-only audit file. The line captures the tool name, validated arguments, result status, latency, and a timestamp. This makes every tool call grep-able, replayable, and auditable.

This pairs directly with the structured logging post's JSONL session record pattern. The audit trail is a specialized channel for tool calls specifically — you can replay a session by re-executing the audit trail, or debug a failure by grepping for the tool name.

import { appendFileSync } from 'fs';

interface ToolCallAudit {
  ts: string;            // ISO timestamp
  sessionId: string;
  turnId: string;
  tool: string;
  args: Record<string, unknown>;
  ok: boolean;
  latencyMs: number;
  cached: boolean;
  error?: string;
}

function auditToolCall(entry: ToolCallAudit): void {
  const line = JSON.stringify(entry);
  appendFileSync(`./logs/tools-${entry.sessionId}.jsonl`, line + '\n');
}

// In executeToolCall(), after execution:
auditToolCall({
  ts: new Date().toISOString(),
  sessionId: ctx.sessionId,
  turnId: ctx.turnId,
  tool: toolName,
  args: parsed.data,
  ok: result.ok,
  latencyMs: result.meta.latencyMs,
  cached: result.meta.cached ?? false,
  error: result.error,
});

⚠️ Anti-Pattern Warning

Do not log the raw LLM arguments — they may contain PII before validation. Log the parsed and validated arguments from the Zod schema output. If your tool arguments contain sensitive fields (email addresses, phone numbers), apply the write-time PII redaction pattern from the structured logging post before writing to the audit trail.

The 5 Anti-Patterns (and How to Fix Each One)

Anti-Pattern 1: Accept-Any-JSON

✗ The tool executor accepts any or Record<string, unknown> and trusts the LLM's output completely.

// WRONG: no validation, trusts the LLM blindly
async function sendEmail(args: any) {
  await mailer.send({
    to: args.to,        // could be null, array, or string
    subject: args.subject, // could be missing
    body: args.body,    // could be HTML injection
  });
}

✓ Fix: Validate every argument with a Zod schema at the boundary.

// RIGHT: schema validates before execution
const sendEmailSchema = z.object({
  to: z.string().email(),
  subject: z.string().min(1).max(200),
  body: z.string().max(10000),
  cc: z.array(z.string().email()).optional(),
});

async function sendEmail(args: z.infer<typeof sendEmailSchema>) {
  await mailer.send(args); // fully typed, validated
}

Why it fails silently: the LLM passes { "to": null, "subject": "Hello", "body": "..." }. Without validation, the email library receives to: null and either crashes or sends to a default address. The agent sees an error and retries — now the same broken call fires again.

Anti-Pattern 2: Let-the-LLM-Pick-From-50-Tools

✗ You register 50 tools with overlapping descriptions and let the LLM pick blindly. Accuracy drops to 70–85%.

✓ Fix: Group tools into namespaces (user.*, billing.*, search.*). The agent first selects a namespace, then the tool within it. Cap each namespace at 8–12 tools. Use the disambiguation layer from Pattern 2 for close calls.

Why it fails silently: search_customers and search_contacts both "search for people." The LLM picks one based on description similarity, not argument compatibility. The result set is subtly different (customers have billing data, contacts don't), and the agent generates a response that looks correct but is based on the wrong data.

Anti-Pattern 3: No-Validation-Trust-the-LLM

✗ "The LLM follows the schema we gave it, so we don't need runtime validation."

✓ Fix: Always validate at the boundary. LLMs hallucinate optional fields, pass wrong types for optional parameters, and sometimes ignore the schema entirely. The retry policy post covers what happens when the LLM's output is wrong — but you can't retry if you don't know it's wrong. Validation is the signal.

Why it fails silently: the LLM adds an extra field { "userId": 42, "format": "detailed" } that your function doesn't expect. Without validation, the extra field is ignored. But when you later add a format parameter with a different meaning, the LLM's old calls now hit your new code path and produce wrong results.

Anti-Pattern 4: Fire-and-Forget Side Effects

✗ Side-effecting tools (send email, create charge, write to database) execute without idempotency keys. Retries duplicate the side effect.

✓ Fix: Wrap every mutating tool with the withIdempotency function from Pattern 4. The wrapper derives a stable key from the tool name + arguments + turn ID, so a retry of the same call returns the cached result instead of re-executing.

Why it fails silently: the agent calls send_email, the HTTP request times out at 29 seconds (before the SMTP server acknowledges), the retry policy fires the same call, the SMTP server delivers both. The user gets two identical emails. Nobody notices unless the user complains.

Anti-Pattern 5: Swallow Tool Errors

✗ The tool wrapper catches all exceptions and returns an empty result. The agent receives { ok: true, data: null } and generates a response as if the tool succeeded.

// WRONG: swallows errors, returns empty success
try {
  const result = await executor(args);
  return result;
} catch (e) {
  return { ok: true, data: null }; // silent failure!
}

✓ Fix: Return a structured error result. Let the agent decide what to do with it — retry, inform the user, or try a different tool.

// RIGHT: structured error that the agent can act on
try {
  const result = await executor(args);
  return result;
} catch (e) {
  return {
    ok: false,
    error: e instanceof Error ? e.message : String(e),
    meta: { tool: toolName, latencyMs: Date.now() - start },
  };
}

Why it fails silently: the tool returns { ok: true, data: null }. The agent formats a response: "I looked it up but couldn't find anything." The user thinks the record doesn't exist. In reality, the database was down. The agent never knew.

The Complete 130-Line Tool-Call Runtime

Here is the full runtime that implements all six patterns. Drop it into your agent project, register your tools with Zod schemas, and call executeToolCall() from your agent loop.

import { z } from 'zod';
import { createHash } from 'crypto';
import { appendFileSync } from 'fs';

// ── Types ──────────────────────────────────────────────
export interface ToolResult {
  ok: boolean;
  data?: unknown;
  error?: string;
  meta: {
    tool: string;
    latencyMs: number;
    cached?: boolean;
  };
}

export interface ToolDefinition {
  description: string;
  schema: z.ZodType;
  executor: (args: any, ctx: CallContext) => Promise<ToolResult>;
  sideEffects: boolean;
}

export interface CallContext {
  sessionId: string;
  turnId: string;
  toolName: string;
}

export type ToolRegistry = Record<string, ToolDefinition>;

// ── Idempotency Cache ──────────────────────────────────
const idempotencyCache = new Map<string, ToolResult>();

function deriveIdempotencyKey(
  toolName: string,
  args: Record<string, unknown>,
  turnId: string
): string {
  const parts = [toolName, JSON.stringify(sortKeys(args)), turnId];
  return createHash('sha256').update(parts.join('|')).digest('hex').slice(0, 32);
}

function sortKeys(obj: Record<string, unknown>): Record<string, unknown> {
  return Object.keys(obj).sort().reduce((acc, k) => {
    acc[k] = typeof obj[k] === 'object' && obj[k] !== null && !Array.isArray(obj[k])
      ? sortKeys(obj[k] as Record<string, unknown>)
      : obj[k];
    return acc;
  }, {} as Record<string, unknown>);
}

// ── Audit Trail ────────────────────────────────────────
function auditToolCall(
  ctx: CallContext,
  args: unknown,
  result: ToolResult,
  cached: boolean
): void {
  const entry = JSON.stringify({
    ts: new Date().toISOString(),
    sessionId: ctx.sessionId,
    turnId: ctx.turnId,
    tool: ctx.toolName,
    args,
    ok: result.ok,
    latencyMs: result.meta.latencyMs,
    cached,
    error: result.error,
  });
  appendFileSync(`./logs/tools-${ctx.sessionId}.jsonl`, entry + '\n');
}

// ── Disambiguation ─────────────────────────────────────
function scoreToolCompatibility(
  args: Record<string, unknown>,
  tool: ToolDefinition
): number {
  const result = tool.schema.safeParse(args);
  if (result.success) return 1.0;
  const shape = (tool.schema as any).shape || {};
  const fields = Object.keys(shape);
  if (fields.length === 0) return 0;
  const matching = fields.filter(f => f in args).length;
  return matching / fields.length;
}

function disambiguate(
  args: Record<string, unknown>,
  selected: string,
  registry: ToolRegistry
): string {
  const scores = Object.entries(registry).map(([name, tool]) => ({
    name, score: scoreToolCompatibility(args, tool),
  })).sort((a, b) => b.score - a.score);
  if (scores.length === 0) return selected;
  return scores[0].score > 0.5 ? scores[0].name : selected;
}

// ── Main Executor ──────────────────────────────────────
export async function executeToolCall(
  toolName: string,
  rawArgs: unknown,
  registry: ToolRegistry,
  ctx: Omit<CallContext, 'toolName'>
): Promise<ToolResult> {
  const fullCtx: CallContext = { ...ctx, toolName };
  const tool = registry[toolName];

  if (!tool) {
    return {
      ok: false,
      error: `Unknown tool: ${toolName}. Available: ${Object.keys(registry).join(', ')}`,
      meta: { tool: toolName, latencyMs: 0 },
    };
  }

  // PATTERN 3: Validate arguments at the boundary
  const parsed = tool.schema.safeParse(rawArgs);
  if (!parsed.success) {
    const issues = parsed.error.issues
      .map(i => `${i.path.join('.')}: ${i.message}`)
      .join('; ');
    return {
      ok: false,
      error: `Invalid arguments: ${issues}`,
      meta: { tool: toolName, latencyMs: 0 },
    };
  }

  const args = parsed.data as Record<string, unknown>;
  const start = Date.now();
  let cached = false;

  // PATTERN 4: Idempotency for side-effecting tools
  if (tool.sideEffects) {
    const key = deriveIdempotencyKey(toolName, args, ctx.turnId);
    if (idempotencyCache.has(key)) {
      const result = idempotencyCache.get(key)!;
      result.meta.cached = true;
      result.meta.latencyMs = Date.now() - start;
      cached = true;
      auditToolCall(fullCtx, args, result, true);
      return result;
    }
  }

  // Execute
  let result: ToolResult;
  try {
    result = await tool.executor(args, fullCtx);
    result.meta.latencyMs = Date.now() - start;
  } catch (err) {
    result = {
      ok: false,
      error: err instanceof Error ? err.message : String(err),
      meta: { tool: toolName, latencyMs: Date.now() - start },
    };
  }

  // Cache successful side-effect results
  if (tool.sideEffects && result.ok) {
    const key = deriveIdempotencyKey(toolName, args, ctx.turnId);
    idempotencyCache.set(key, result);
    setTimeout(() => idempotencyCache.delete(key), 5 * 60 * 1000);
  }

  // PATTERN 6: Audit trail
  auditToolCall(fullCtx, args, result, cached);
  return result;
}

// ── OpenAI/Anthropic Tool Definition Generator ─────────
export function generateToolSpecs(registry: ToolRegistry) {
  return Object.entries(registry).map(([name, tool]) => ({
    type: 'function',
    function: {
      name,
      description: tool.description,
      parameters: zodToJsonSchema(tool.schema),
    },
  }));
}

function zodToJsonSchema(schema: z.ZodType): object {
  // Simplified: use zod-to-json-schema in production
  return (schema as any)._def?.shape
    ? Object.fromEntries(
        Object.entries((schema as any)._def.shape).map(([k, v]: [string, any]) =>
          [k, { type: v?._def?.typeName?.replace('Zod', '').toLowerCase() || 'string' }]
        )
      )
    : {};
}

The Woodpecker CI Gate

This gate fails any PR that touches an agent runtime file without ensuring every registered tool has a Zod schema. It catches the most dangerous regression: someone adds a new tool without a schema, or removes validation from an existing one.

# .woodpecker.yml — tool-call validation gate
pipeline:
  tool-schema-gate:
    image: node:18
    commands:
      - |
        node -e "
        const { execSync } = require('child_process');
        const files = execSync('git diff --name-only HEAD~1', { encoding: 'utf8' });
        const agentFiles = files.split('\n').filter(f =>
          f.match(/agent.*\.(ts|js)$/i) || f.match(/tool.*\.(ts|js)$/i)
        );
        if (agentFiles.length === 0) process.exit(0);

        // Check every registered tool has a schema
        const fs = require('fs');
        let violations = 0;
        for (const f of agentFiles) {
          if (!fs.existsSync(f)) continue;
          const content = fs.readFileSync(f, 'utf8');
          // Flag tools registered without schema: or with schema: any
          if (content.match(/executor\s*:/) && !content.match(/schema\s*:\s*z\./)) {
            console.error('VIOLATION: ' + f + ' has executor without Zod schema');
            violations++;
          }
          if (content.match(/schema\s*:\s*(z\.any\(\)|any)/)) {
            console.error('VIOLATION: ' + f + ' uses schema: any');
            violations++;
          }
        }
        if (violations > 0) {
          console.error(violations + ' schema violations found');
          process.exit(1);
        }
        console.log('All tools have Zod schemas.');
        "

Cost Impact

Each invalid tool call that reaches the executor costs you: the LLM call to generate it, the executor execution, the error handling turn, and the retry. Across a 10,000-call day at 5% invalid-call rate, that's 500 wasted executor calls plus 500 extra LLM turns for error recovery. At ~$0.01 per LLM turn and ~$0.005 per executor call, that's $7.50/day or $225/month in wasted spend — eliminated entirely by boundary validation.
