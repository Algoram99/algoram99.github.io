AI Agent Audit Trail for Tool Calls: Tamper-Evident Logs, Replay, and CI Verification

Published 2026-07-02 · 43rd live post · AI agents, audit trails, tool calls, security, observability

If an AI agent can call tools, the question after an incident is never just "what did the model say?" The real question is: which actor proposed which tool call, under which policy, with which arguments, what was redacted, who approved it, what executed, what changed, and can we prove the log was not edited afterward?

Short answer for search and SGE: a production AI-agent audit trail is an append-only, schema-validated event log for every tool-call decision and result. Each event should include actor identity, task intent, tool name, normalized arguments, policy verdict, approval state, execution result, redaction hashes, trace IDs, idempotency keys, and a hash-chain pointer to the previous event. The log should be queryable for debugging, replayable for incident response, tamper-evident for compliance, and enforced by CI so new tools cannot ship without audit coverage.

This guide is intentionally narrower than a general observability post. Observability tells you whether the system is healthy. Structured logging gives every event a consistent shape. Distributed tracing explains latency and causality across services. An audit trail answers the accountability question: what was allowed, denied, approved, executed, and provably preserved?

Why normal logs are not enough for agent tool calls

Traditional application logs are usually optimized for debugging. They are sampled, rotated, redacted inconsistently, and often written by whatever code path happened to be closest to the failure. That is not enough for AI agents, because agents make delegated decisions in natural language, call tools through a runtime, and often operate across trust boundaries: local files, SaaS APIs, email, payment processors, deployment systems, browsers, databases, and subagents.

A normal log says tool_call succeeded. An audit trail says:

  • the trusted ingress intent that made this class of action in scope,
  • the actor identity that proposed the action,
  • the exact tool registry version and schema used to validate arguments,
  • the normalized arguments after path, URL, amount, account, and tenant normalization,
  • the policy rule that returned ALLOW, DENY, or APPROVAL_REQUIRED,
  • the human or scheduler approval token if the call crossed a public, financial, destructive, privacy, or wallet boundary,
  • the executor result and side-effect receipt,
  • the redacted prompt, result, and secret-detection fingerprints,
  • the previous event hash and current event hash, so edits are detectable.

That difference matters when a customer asks why an action happened, when a regulator asks who approved a decision, when an internal incident review needs exact replay, or when a prompt-injection attempt tries to make a fetched document look like a trusted instruction.

The 8 fields every tool-call audit event needs

FieldPurposeCommon failure if missing
event_id, prev_hash, hashMake each record unique and tamper-evident.Someone can edit or delete a bad decision without detection.
task_intentBind the action to the trusted request, ticket, cron definition, or operator-approved plan.Tool output can smuggle new instructions and appear in-scope.
actorIdentify the agent, subagent, workflow, service account, or human reviewer.Every worker inherits the same ambient authority and nobody owns the action.
tool and schema_versionFreeze which typed tool definition was used.Replay later validates against a newer schema and reaches the wrong conclusion.
args_normalizedRecord deterministic path/URL/account/amount normalization before execution.Reviewers see friendly strings, not the real target that executed.
policy_verdictRecord the exact rule, risk class, and decision before execution.All denied calls disappear, and allowed calls cannot be justified.
approvalPreserve human/scheduler approval for high-risk boundaries.The team cannot distinguish autonomous action from approved action.
result_receiptCapture side-effect receipts, idempotency keys, status, and external references.Retries, rollbacks, and incident reconstruction depend on guesswork.

The canonical event sequence

A tool-call audit trail should not only log successful executions. It should log every decision point. Use this sequence:

  1. tool.proposed — model or worker proposes a tool, arguments, and reason.
  2. tool.normalized — runtime canonicalizes paths, URLs, amounts, accounts, tenant IDs, and idempotency key.
  3. policy.evaluated — deterministic policy returns allow, deny, blur, approval-required, or block.
  4. approval.requested — optional, only for public, financial, destructive, privacy, credential, or wallet-adjacent actions.
  5. approval.resolved — approved, rejected, expired, modified, auto-approved, or escalated.
  6. tool.executed — executor starts with schema version, trace ID, timeout, budget, and idempotency key.
  7. tool.result — success, failure, retryable failure, denied-by-downstream, or partial result with receipt hash.
  8. compensation.started / compensation.result — optional rollback or retraction path for side effects.

This event taxonomy plugs directly into the AI agent permission model: the audit trail is Layer 7, but it should also record evidence from Layers 1-6. It also complements the human-in-the-loop layer: approvals are useless if you cannot replay the context packet that reviewers saw.

Reference TypeScript: append-only hash-chained audit log

The following implementation is deliberately small. It uses Node's standard library, writes one JSON line per event, redacts common secret shapes before persistence, and computes a SHA-256 hash over a canonical JSON payload that includes the previous hash. In production you would store the same record in object storage, Postgres, or an append-only ledger, but the invariants are the same.

import { createHash, randomUUID } from "node:crypto";
import { appendFileSync, existsSync, readFileSync } from "node:fs";

type PolicyVerdict = "ALLOW" | "DENY" | "APPROVAL_REQUIRED" | "BLOCK";
type AuditKind =
  | "tool.proposed" | "tool.normalized" | "policy.evaluated"
  | "approval.requested" | "approval.resolved"
  | "tool.executed" | "tool.result"
  | "compensation.started" | "compensation.result";

type AuditEvent = {
  event_id: string;
  ts: string;
  kind: AuditKind;
  trace_id: string;
  actor: { id: string; role: string; parent?: string };
  task_intent: { id: string; source: "user" | "ticket" | "cron" | "operator_plan"; hash: string };
  tool?: { name: string; schema_version: string; side_effect: string };
  args_normalized?: Record<string, unknown>;
  policy_verdict?: { verdict: PolicyVerdict; rule_id: string; reason: string; risk: string };
  approval?: { required: boolean; reviewer?: string; decision?: string; token_hash?: string };
  result_receipt?: { status: string; idempotency_key?: string; external_ref?: string; result_hash?: string };
  redaction?: { prompt_hash?: string; args_hash?: string; result_hash?: string; redacted_fields: string[] };
  prev_hash: string;
  hash: string;
};

const ZERO = "0".repeat(64);

function sha256(value: string): string {
  return createHash("sha256").update(value).digest("hex");
}

function canonical(value: unknown): string {
  if (value === null || typeof value !== "object") return JSON.stringify(value);
  if (Array.isArray(value)) return "[" + value.map(canonical).join(",") + "]";
  return "{" + Object.keys(value as Record<string, unknown>).sort()
    .map(k => JSON.stringify(k) + ":" + canonical((value as Record<string, unknown>)[k]))
    .join(",") + "}";
}

function redact(value: unknown, redacted: string[] = [], path = "$ "): unknown {
  if (typeof value === "string") {
    const patterns = [
      [/sk-[A-Za-z0-9_-]{20,}/g, "openai_key"],
      [/ghp_[A-Za-z0-9_]{20,}/g, "github_pat"],
      [/xox[baprs]-[A-Za-z0-9-]{20,}/g, "slack_token"],
      [/AKIA[0-9A-Z]{16}/g, "aws_access_key"],
      [/0x[a-fA-F0-9]{64}/g, "wallet_private_key"]
    ] as const;
    let out = value;
    for (const [regex, label] of patterns) {
      if (regex.test(out)) {
        redacted.push(`${path}:${label}`);
        out = out.replace(regex, `[REDACTED:${label}]`);
      }
    }
    return out;
  }
  if (Array.isArray(value)) return value.map((v, i) => redact(v, redacted, `${path}[${i}]`));
  if (value && typeof value === "object") {
    const out: Record<string, unknown> = {};
    for (const [k, v] of Object.entries(value)) out[k] = redact(v, redacted, `${path}.${k}`);
    return out;
  }
  return value;
}

function lastHash(path: string): string {
  if (!existsSync(path)) return ZERO;
  const lines = readFileSync(path, "utf8").trim().split("
").filter(Boolean);
  if (lines.length === 0) return ZERO;
  return JSON.parse(lines[lines.length - 1]).hash;
}

export function appendAudit(path: string, event: Omit<AuditEvent, "event_id" | "ts" | "prev_hash" | "hash">): AuditEvent {
  const redactedFields: string[] = [];
  const safeEvent = redact(event, redactedFields) as typeof event;
  const prev_hash = lastHash(path);
  const unsigned = {
    ...safeEvent,
    event_id: randomUUID(),
    ts: new Date().toISOString(),
    prev_hash,
    redaction: { ...(safeEvent.redaction ?? {}), redacted_fields: redactedFields }
  };
  const hash = sha256(canonical(unsigned));
  const signed = { ...unsigned, hash } as AuditEvent;
  appendFileSync(path, JSON.stringify(signed) + "
", { mode: 0o600 });
  return signed;
}

export function verifyAudit(path: string): { ok: boolean; line?: number; reason?: string } {
  let prev = ZERO;
  const lines = readFileSync(path, "utf8").trim().split("
").filter(Boolean);
  for (let i = 0; i < lines.length; i++) {
    const row = JSON.parse(lines[i]);
    if (row.prev_hash !== prev) return { ok: false, line: i + 1, reason: "prev_hash mismatch" };
    const { hash, ...unsigned } = row;
    const expected = sha256(canonical(unsigned));
    if (hash !== expected) return { ok: false, line: i + 1, reason: "hash mismatch" };
    prev = hash;
  }
  return { ok: true };
}
Do not log raw secrets, private wallet material, browser session cookies, or full private transcripts. The audit trail should preserve accountability without becoming a new exfiltration target. Store hashes and redacted excerpts by default. Store raw private payloads only in a separately encrypted evidence vault with strict retention and break-glass access.

How to connect audit trails to permission gates

The audit trail should sit before and after the executor. The policy gate writes the proposed call and verdict. The executor writes the actual start/result receipt. This prevents the common failure where rejected or blocked calls disappear from logs.

async function auditedToolCall(call: ToolCall, policy: Policy, exec: Executor) {
  const trace_id = call.trace_id ?? crypto.randomUUID();
  appendAudit("agent.audit.jsonl", {
    kind: "tool.proposed",
    trace_id,
    actor: call.actor,
    task_intent: call.task_intent,
    tool: { name: call.tool, schema_version: call.schema_version, side_effect: call.side_effect },
    args_normalized: normalizeArgs(call.args)
  });

  const verdict = evaluatePolicy(call, policy);
  appendAudit("agent.audit.jsonl", {
    kind: "policy.evaluated",
    trace_id,
    actor: call.actor,
    task_intent: call.task_intent,
    tool: { name: call.tool, schema_version: call.schema_version, side_effect: call.side_effect },
    policy_verdict: verdict
  });

  if (verdict.verdict === "DENY" || verdict.verdict === "BLOCK") {
    return { ok: false, blocked: true, reason: verdict.reason };
  }

  if (verdict.verdict === "APPROVAL_REQUIRED") {
    const approval = await requestApproval(call, verdict);
    appendAudit("agent.audit.jsonl", {
      kind: "approval.resolved",
      trace_id,
      actor: call.actor,
      task_intent: call.task_intent,
      approval: {
        required: true,
        reviewer: approval.reviewer_id,
        decision: approval.decision,
        token_hash: sha256(approval.token)
      }
    });
    if (approval.decision !== "approved") return { ok: false, blocked: true, reason: "approval rejected" };
  }

  const idempotency_key = deriveIdempotencyKey(call);
  appendAudit("agent.audit.jsonl", {
    kind: "tool.executed",
    trace_id,
    actor: call.actor,
    task_intent: call.task_intent,
    tool: { name: call.tool, schema_version: call.schema_version, side_effect: call.side_effect },
    result_receipt: { status: "started", idempotency_key }
  });

  const result = await exec(call, { idempotency_key, trace_id });
  appendAudit("agent.audit.jsonl", {
    kind: "tool.result",
    trace_id,
    actor: call.actor,
    task_intent: call.task_intent,
    result_receipt: {
      status: result.ok ? "success" : "failure",
      idempotency_key,
      external_ref: result.external_ref,
      result_hash: sha256(JSON.stringify(result.public_receipt ?? result))
    }
  });
  return result;
}

Replay packets: the incident-response superpower

An audit trail is only useful if the team can reconstruct the decision without asking the model to remember what happened. For every high-risk action, build a replay packet from the audit rows with the same trace_id:

  • trusted user/job intent and anti-actions,
  • agent identity and parent delegation chain,
  • tool registry version, schema, and side-effect classification,
  • normalized arguments and redaction fingerprints,
  • policy verdict and rule ID,
  • approval packet and reviewer decision if applicable,
  • executor receipt, idempotency key, downstream status, and external reference,
  • hash-chain verification result for the event window.

Replay does not mean blindly re-executing the tool. Replay means reconstructing the decision with enough fidelity to answer: would the current policy allow the same call, what changed since then, and which compensating action is available? That is the bridge to idempotency, retry policy, and rollback after approval mistakes.

Retention and privacy: keep proof, not toxic waste

The audit trail should preserve proofs longer than it preserves sensitive payloads. A practical retention policy:

DataDefault retentionWhy
Event envelope, hashes, verdicts, timestamps, actor IDs1-7 years depending on compliance needsLow sensitivity, high accountability value.
Redacted arguments and redacted result snippets90-365 daysUseful for debugging and incident review.
Raw prompts or raw tool results0 days by default; encrypted evidence vault only on explicit incident holdHigh privacy and secret-leak risk.
Approval context packets365 days for public/financial/destructive actionsNeeded to prove reviewers saw enough context.
Hash-chain anchorsPermanent or periodically notarizedLets you prove historical logs were not silently rewritten.

Anchor the hash chain periodically. For many teams, a daily signed summary file is enough: write the last hash of the day, sign it with a KMS key, and store it in immutable object storage. Higher-assurance teams can anchor to transparency logs, append-only databases, or external notaries. The point is not blockchain theater; the point is making retroactive edits detectable.

CI gate: do not let new tools bypass the audit trail

The most common audit-trail regression is not a dramatic breach. It is a new tool added during a sprint that calls a side-effectful API but never emits tool.proposed, policy.evaluated, and tool.result. Prevent that in CI.

# .woodpecker.yml snippet
when:
  event: [push, pull_request, manual]
steps:
  audit_contract:
    image: node:22-alpine
    commands:
      - node scripts/audit-tool-contract.mjs
      - node scripts/audit-log-selftest.mjs
      - node scripts/audit-redaction-selftest.mjs

The contract script should fail if:

  • a tool appears in the registry without a side-effect classification,
  • a side-effectful tool lacks an audit wrapper,
  • a policy decision can return allow/deny without writing an audit event,
  • a result path can throw before writing a failure receipt,
  • redaction self-tests fail for known secret shapes,
  • hash-chain verification fails for fixture logs.

For this site, Woodpecker is the canonical CI layer. The same principle applies in any CI system: audit coverage is a release gate, not a dashboard improvement.

Five anti-patterns that break agent audit trails

1. Logging only successful executions

Failure: denied calls, policy conflicts, prompt-injection attempts, and approval rejections vanish. The incident review sees only what executed, not what the agent tried to do.

Fix: write tool.proposed and policy.evaluated before execution. Blocked and denied decisions are first-class audit events.

2. Pretty-printing raw prompts into logs

Failure: logs become a privacy and secret vault. Teams stop giving engineers access, so nobody can debug the system.

Fix: store prompt hashes, redacted excerpts, source IDs, and retrieval document IDs. Use an encrypted evidence vault only for incident-hold raw payloads.

3. Trusting timestamps without hash chaining

Failure: a bad row can be edited after the incident and still look plausible. The log is chronological but not tamper-evident.

Fix: include prev_hash and hash on every row, then anchor the latest hash periodically outside the mutable log store.

4. Mixing observability spans with audit facts

Failure: sampling drops the one event the auditor needs. Traces explain latency, but audit rows must be complete.

Fix: connect traces and audit rows with trace_id, but never sample audit events for side-effectful decisions.

5. No replay contract

Failure: the team has logs but cannot reconstruct which policy version, schema version, approval packet, or idempotency key applied.

Fix: every high-risk action must produce a replay packet from audit rows alone. If replay needs tribal knowledge, the audit trail is incomplete.

Migration plan for an existing agent runtime

  1. Inventory tools. List every tool and classify side effects: read-only, local-write, network-write, public, destructive, financial, privacy, credential, wallet-adjacent.
  2. Define the canonical event schema. Start with the 8 fields above. Add domain-specific receipts, but do not remove actor, intent, verdict, result, or hashes.
  3. Wrap the dispatcher, not each tool manually. The runtime boundary is where every call already passes. Put audit before policy, after policy, before execution, and after execution.
  4. Backfill fixture logs. Create clean, denied, approval-required, failure, retry, and rollback fixtures. Verify hash chains and replay packets.
  5. Add CI gates. Fail when a new side-effectful tool lacks audit coverage or redaction tests.
  6. Add incident runbooks. Document how to query by trace ID, verify a hash window, build a replay packet, and select a compensating action.
  7. Anchor daily. Persist the daily terminal hash somewhere the application cannot silently rewrite.

How this fits the rest of the production-agent stack

Permission model

The permission model decides whether a call is allowed. The audit trail proves the decision happened.

Human-in-the-loop

The HITL layer routes high-risk actions. The audit trail preserves the approval packet and decision.

Function calling

The tool-use runtime validates arguments. The audit trail records the normalized arguments and schema version.

Structured logging

The structured log is the base event format. The audit trail adds completeness, replay, and tamper evidence.

Definition of done

A production AI-agent audit trail is done when a verifier can pick any high-risk tool call and answer these questions from records alone:

  • What trusted intent made this action in scope?
  • Which actor proposed it, and what parent delegated to that actor?
  • Which tool schema and policy version evaluated it?
  • Were the arguments normalized and within scope?
  • Was approval required, and who approved or rejected it?
  • What executed, with which idempotency key and trace ID?
  • What side-effect receipt or downstream reference proves the result?
  • Were private values redacted before persistence?
  • Does the hash chain verify for the whole event window?
  • Can the team construct a replay packet and decide whether a compensating action is needed?

If the answer to any of those is "we would have to ask the model," the audit trail is not an audit trail yet. It is just a log.
