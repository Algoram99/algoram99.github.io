How to Build a CI Pipeline for AI Agents (Tests, Evals, Drift Gates)

CI AI Agents Prompt Regression Woodpecker Cron Drift 17 min 2026-06-09

TL;DR. Agent CI is not a stretch goal, it is a missing layer. Traditional CI catches code regressions; it does not catch prompt regressions, tool-call regressions, cost regressions, or schedule drift. This post walks through the 4-stage gate (lint, schema, prompt regression, live eval) plus a 5th cron-drift stage, a 6th cost-leak guard, and a 7th telemetry sidecar that closes the loop between shipped code and production behavior. The pipeline is 90 lines of Woodpecker YAML; the gate scripts are zero-dependency Node CLIs. By the end you will have a CI that rejects a PR whose system-prompt change made the model leak a competitor name, that rejects a PR whose prompt change doubled the token cost, and that pages on-call when a scheduled job silently decayed from every 5 minutes to every 47 minutes. Cross-links to three Algoram99 products that ship the same gate as a CLI: CronPulse, Prompt Regression CLI, and Agent Inflight Telemetry CLI.

Why traditional CI is not enough for AI agents

Most teams who build an AI agent in 2026 ship a CI that runs npm test on every PR. The tests pass. The code is correct. The agent is broken. Three weeks later, somebody notices the agent has been hallucinating a competitor's name in every response for 9 days, and the only way to find the regression is to diff the system prompt against a backup from a month ago.

The reason is that traditional CI tests code paths. AI agents have four parallel paths that the code paths do not cover:

  • Prompt paths — the same code can produce very different outputs when the system prompt changes by one sentence. Traditional CI does not run the model, so it cannot see the output drift.
  • Tool-call paths — the agent may call the right tool with the wrong arguments, or call the wrong tool, and still have its npm test green because the wrapper function returns successfully.
  • Cost paths — a 10x token increase is not a test failure, it is an invoice. Traditional CI has no notion of cost.
  • Schedule paths — the cron job that scrapes the user's mailbox every 5 minutes may silently start firing every 47 minutes after a dependency upgrade. The code still works; the schedule broke.

Building a CI pipeline for AI agents means adding four layers that catch these four paths, plus the observability layer that tells you which one regressed in production. The rest of this post is the 9-step build protocol.

Step 1-2: Lint and schema (the cheap layers)

Stages 1 and 2 are the cheap layers. They run in under 15 seconds combined, cost nothing, and catch the dumb mistakes. A .woodpecker.yml for these two stages looks like this: 

steps:
  lint:
    image: node:22-slim
    commands:
      - npm ci
      - npx agentlint run ./agents --rules model-id,tool-schema,env-decl
    when:
      event: [push, pull_request]

  schema:
    image: node:22-slim
    commands:
      - npm ci
      - npx mcp-server-tester check --server ./servers/*.json --checks schema,error-envelope,idempotency
    when:
      event: [push, pull_request]

The agentlint run command is the analogue of eslint for agent source files. It checks that every agent definition has a declared model field, that every tool description has a JSON Schema, and that every env var referenced in the prompt is declared in a .env.example file. The mcp-server-tester check command validates the MCP server's tool input/output schemas and error envelope shape against the official MCP conformance fixtures. Both are exit-1 on failure.

Why this catches more than you'd think. Most prompt regressions start as a missing field: somebody refactors a tool's input schema and forgets to update the agent's call site. The agent's wrapper function still returns successfully, so npm test passes, but the LLM now hallucinates the missing argument. Stage 2 catches the schema mismatch before the agent ever runs.

Step 3: Prompt regression (the most important stage)

Stage 3 is where most teams stop building, and where most teams lose the most money. It is the only stage that catches the "I changed one word in the system prompt and the model now hallucinates a competitor name" failure mode.

The pattern: commit a frozen baseline output for every important prompt, score the candidate output against the baseline, gate the PR on the score. 

// baseline.json (committed to the repo)
{
  "version": 3,
  "fixtures": [
    {
      "id": "summarize_email_v1",
      "system": "You summarize emails in 2 sentences.",
      "user": "Hi Alice, the Q3 report is attached. The numbers are slightly below forecast but the pipeline is strong. Let's discuss Thursday.",
      "baseline": "Alice received the Q3 report, which is slightly below forecast. The pipeline remains strong and a Thursday meeting is planned."
    },
    {
      "id": "extract_action_items",
      "system": "Extract action items from emails as a JSON list.",
      "user": "Reminder: file the expense report by Friday and book the conference room for the review.",
      "baseline": "[{\"action\":\"file expense report\",\"deadline\":\"Friday\"},{\"action\":\"book conference room\",\"deadline\":\"for the review\"}]"
    }
  ]
}

The candidate step runs the model on each fixture, captures the output, and runs the scorer. The scorer is pure offline math — no LLM call — on five metrics:

  • Content Jaccard (topic drift): does the candidate cover the same concepts as the baseline?
  • Shingle Jaccard (phrase rewording): how much of the phrasing is preserved?
  • Length ratio (verbose/terse): is the candidate within 0.5x-2.0x of the baseline length?
  • Keyword coverage: are all required terms (e.g. "Q3", "Friday") present?
  • Forbidden avoidance: did the candidate leak any forbidden terms (e.g. a competitor name)?
# In .woodpecker.yml
  prompt-regression:
    image: node:22-slim
    commands:
      - npm ci
      - npx prompt-regression-cli run --baseline ./tests/prompts/baseline.json --model claude-sonnet-4.5 --strict
    when:
      event: [push, pull_request]
Anti-pattern 1: running the model on the baseline as part of the CI step. If your CI step calls the model twice (once for the baseline, once for the candidate), you have introduced non-determinism. The baseline is a frozen artifact, not a live call. Commit the baseline output and compare against the bytes.
Anti-pattern 2: scoring with an LLM judge. An LLM judge is non-deterministic, expensive, and silently biased toward the model that wrote the judge. Use a deterministic offline scorer. Five cheap metrics beat one expensive judge.
Anti-pattern 3: updating the baseline in the same PR as the prompt change. The whole point of the baseline is to detect drift. If the PR that changes the prompt also changes the baseline, you have proven nothing. Require a separate PR for baseline updates, with a manual review checkpoint.

Step 4: Live eval (the expensive layer, run sparingly)

Stage 4 is end-to-end. Real tool calls, real LLM, real cost. Hold out a small test set (10-30 fixtures) and run the agent against it. The output is a pass/fail plus per-fixture diagnostics. 

# In .woodpecker.yml
  live-eval:
    image: node:22-slim
    secrets: [openai_api_key, anthropic_api_key]
    commands:
      - npm ci
      - npx agent-eval run --suite ./tests/eval/held-out.json --parallel 4 --timeout 120s
    when:
      event: [push]
      branch: main
Anti-pattern 4: running live eval on every PR. 30 fixtures at $0.02 each is $0.60 per PR. Per developer, per day, that is real money. Run live eval on merge to main plus a nightly scheduled run. Use the prompt-regression stage (cheap, deterministic) as the PR-time gate.
Anti-pattern 5: not holding out the test set from training data. If your held-out fixtures were ever used as few-shot examples in your prompt, you are measuring memorization, not capability. Maintain a strict separation between training fixtures and eval fixtures. Treat any leak as a test integrity bug.

Step 5: Cron drift (the silent killer)

Stages 1-4 run on PRs. Stage 5 runs on a schedule. It catches the failure mode that brings down 80% of agent fleets in production: a scheduled job that used to fire every 5 minutes is now firing every 47 minutes, and the only way you find out is when a user reports a stale dashboard.

The drift detector reads your cron manifest, checks each job's last-success timestamp against expected cadence, and exits 1 on any of the 5 drift modes:

  • Last-success drift — the job's last successful run was longer ago than expected.
  • Schedule skew — the job is firing at the wrong cadence (e.g. every 47 minutes instead of every 5).
  • Command drift — the job's command changed without a corresponding manifest update.
  • Missing record — the job is supposed to write a record somewhere (a database row, a log line) and the record is missing.
  • Silent disable — the job was disabled, paused, or its manifest entry was removed without a corresponding disable-record.
# In .woodpecker.yml
  cron-drift:
    image: node:22-slim
    commands:
      - npm ci
      - npx cronpulse check --manifest ./cron/jobs.json --slack-webhook $SLACK_DRIFT_WEBHOOK
    when:
      event: cron
      cron: drift-check

The corresponding Woodpecker cron block in the same file: 

events:
  - cron

steps:
  cron-drift:
    image: node:22-slim
    commands:
      - npm ci
      - npx cronpulse check --manifest ./cron/jobs.json --slack-webhook $SLACK_DRIFT_WEBHOOK
Why this is its own gate. PR-time tests cannot catch a job that worked correctly at merge time and started drifting 90 days later. The drift mode is in the schedule, not the code. A separate scheduled Woodpecker job is the only layer that catches it. Treat the drift webhook the same as a PagerDuty alert: every page is a real incident until proven otherwise.

Step 6: Cost-leak guard (the gate that pays for itself)

Stages 1-4 catch regressions in quality. Stage 6 catches regressions in cost. A PR that changes the system prompt from 200 tokens to 2,000 tokens will pass stages 1-4 — it is a correct, well-tested change — and double your monthly LLM bill. 

# In .woodpecker.yml, in the same stage as prompt-regression:
  cost-guard:
    image: node:22-slim
    commands:
      - npm ci
      - npx llm-context-budget check --prompt ./agents/summarizer/prompt.txt --model claude-sonnet-4.5 --max-tokens 800 --max-cost-usd 0.05
    when:
      event: [push, pull_request]

The cost guard reads the prompt, computes the per-request token count and USD cost, and exits 1 if either exceeds the budget. The budget lives in the repo as a YAML file, so the PR that wants to raise the budget has to justify it in code review.

Anti-pattern 6: setting the budget so high it never fires. A budget that never fires is not a budget. Set the initial budget at 1.5x your current median cost. Raise it only with a PR that explains the new use case.

Step 7: Telemetry (the always-on sidecar)

The seven layers above prevent regressions from shipping and catch drift after they ship. The eighth layer tells you what is happening right now, in production, across every LLM call your agent makes.

The Agent Inflight Telemetry CLI runs as a sidecar process. It captures per-call latency, token counts, cache hits, fallback chains, and error types, then aggregates into p50/p95/p99 percentiles, error rates, and retry-storm alerts. The records are append-only JSONL, self-redacting for sk-, ghp_, and api_key patterns, and optionally gzip-compressed. 

// In your agent runtime
import { telemetry } from 'agent-inflight-telemetry';

telemetry.init({
  output: '/var/log/agent/telemetry.jsonl',
  redact: true,
  gzipAfter: '1d',
  alertOn: {
    p99LatencyMs: 8000,
    errorRatePct: 5,
    retryStormCount: 10
  }
});

const result = await llm.call({ model: 'claude-sonnet-4.5', prompt });
telemetry.record(result); // automatic, async, non-blocking

The telemetry data is what makes the next round of CI fixes tractable. When a regression does ship, the diff between yesterday's p99 and today's p99 is the signal that points at the PR. When the cron-drift gate pages on-call, the telemetry data shows whether the drift caused user-visible damage (high error rate, low success rate) or was silent.

This is the entire reference pipeline. Six steps, three secrets, two event types, one scheduled cron. Every step exits 1 on failure. The pipeline does not pass a PR unless all four PR-time gates are green. The cron-drift gate runs hourly regardless of PR activity.

What this looks like in week one

Week one is exactly one day of work. Stand up the Woodpecker pipeline, copy the baseline.json template, write 5 fixtures, ship the prompt-regression CLI. The cron-drift and cost-guard stages can wait until week two. The telemetry sidecar is its own week-three project.

The first PR the gate blocks will probably be yours. You will refactor a system prompt, push the PR, watch the prompt-regression stage go red on a forbidden term you did not realize was forbidden, and quietly thank yourself for building the gate. That is the moment the pipeline has paid for itself. Everything after that is a 90-line Woodpecker file catching regressions while you sleep.
